# Decisions

Every decision that shapes Magick Agency, by ID, in one place. Read it when you need to know
whether something is settled, why the code is built the way it is, or what is still waiting on
someone. Source comments cite entries here by ID ("decision B8", "Q6 (Manas, 2026-10-09)"), so
IDs are never renumbered or reused. As of 2026-11-04.

Status words: **settled** (a founding product decision, not reopened here); **default, pending
Manas** (built with the recommended option, not yet ratified); **open** (no default yet; a launch
concern); **decided — keep** (Manas ruled the current behaviour stays); **decided — changed**
(Manas ruled a change, and it is implemented).

## 1. Settled product decisions (approved by Manas, 2026-10-08)

| # | Decision |
|---|---|
| S1 | Magick Agency is a self-contained application: its own server, database, Redis, storage and carrier account. It depends on vendors only, never on another service at runtime |
| S2 | It owns its voice engine (the WebRTC bridge and the VoiceLink adapter) and its own VoiceLink capacity: account, numbers and concurrency limits |
| S3 | It owns post-call analysis and transcripts, and its identity data: users, tenants, accounts, memberships, roles, invites |
| S4 | Sign-in uses Firebase Authentication, in a Firebase project that may be shared with other products; agency verifies ID tokens against Google's public keys and its own `FIREBASE_PROJECT_ID`, with no service account (Manas, 2026-10-10; see §4). A separate identity layer may come later |
| S5 | Super-admins create tenants and add users, with their own login and their own console |
| S6 | No credits, billing or credit enforcement in v1. Metering is an open item |
| S7 | AI calling is out of scope |
| S8 | Stack: Node 22, Fastify, TypeScript, raw `pg`, node-pg-migrate, Vitest; Vite + React UIs; pnpm workspaces |

## 3. Build decisions

In one line each:

- **B1** one `tsconfig` per package, tests included, so lint catches a broken test.
- **B2** workspace packages are consumed as TypeScript source; no build step between packages.
- **B3** one Postgres (5436, two databases) and one Redis (6383, db 0 dev / db 1 test) for dev and test.
- **B4** one file per module area for config, routes and background work.
- **B5** the server keeps CommonJS runtime semantics (esbuild `format: cjs`).
- **B6** agency's alert rules and dashboard are a Terraform module in `grafana/`, with its own state; routing comes from the Grafana stack's shared policy.
- **B7** two audit tables (`audit_logs` and `platform_audit_log`), written by one process.
- **B8** DNC is one table: an indexed, fail-closed dial-time read and one transactional mark.
- **B9** the campaign-management layer sits on top of the dialer domain and calls its repository in-process.
- **B10** infrastructure used by more than one module area lives in one shared place.
- **B11** cross-module seams are fixed files in `apps/server/src/seams/`.
- **B12** the agency repository (`agency.repository.ts`, a barrel over `src/db/repositories/agency/`) lives in `apps/server/src/db/`, not `packages/db`, to avoid a package cycle.
- **B13** the guard host counts live bridged calls, so self-heal stays armed during calls.
- **B14** one S3 module, one bucket, one client, one config key.
- **B15** roster replace and clear refuse until a supersede primitive exists.
- **B16** the public API layer serves the console's paths and reaches the internal handler instance in-process through `callCore`.
- **B17** Magick Agency is a standalone brand; nothing user-visible links to or names another product. Amended 2026-10-11: the UIs show the logo artwork.
- **B23** UI pieces both SPAs share live in one workspace package, `packages/web-ui`, consumed as TypeScript source.
- **B24** every workspace package has its own semantic version and changelog, released by release-please from Conventional Commit PR titles.
- **B26** signed-in console URLs name their tenant and account, `/t/:tenantId/a/:accountId/…`, as the router's basename.

## 4. Rulings on open questions (Manas, 2026-10-09)

Each ruling carries a `Q<n> (Manas, 2026-10-09)` code comment and a mutation-checked test. Q3 was
not ruled on; it is in §5.

| # | Question | Ruling | Status |
|---|---|---|---|
| Q1 | Verify the production Postgres TLS certificate? | Yes. When TLS is on (production) the certificate is verified (`rejectUnauthorized: true`). `DB_SSL_CA` takes the PEM **text** of a private CA (literal `\n` allowed; a path or other non-PEM value is a boot error); `DB_SSL_REJECT_UNAUTHORIZED=false` is the only opt-out (strict `true`/`false`). TLS parameters in `DATABASE_URL` (`ssl`, `sslmode`, `sslrootcert`, `sslcert`, `sslkey`, `sslnegotiation`, any case) are refused at config parse, because pg lets them replace these settings | **Decided — changed** |
| Q2 | How many action error codes? | 18. The union in `packages/contracts/src/errors.ts` has 18 members; an older count of 16 was stale. **2026-11-01:** 19, with `not_staffed` (the join's staffing check, `POST /proxy/agency/sessions`) | **Decided — keep** |
| Q4 | Platform audit `actor_type` has no `api_key` | When audit rows are imported from the previous platform at launch, rows with `actor_type = 'api_key'` become `system`, keeping the key name in `details`. Record only; nothing built now | **Decided — keep (launch)** |
| Q5 | Cache invalidation when Redis is down | Revocations retry the Redis DEL (3 attempts) and log at ERROR on final failure. A revocation route that is idempotent on retry answers 503 `cache_invalidation_failed` (the role-change routes, tenant and super-admin); one that is not keeps its 2xx and relies on the error log (both membership-removal routes: a retry 404s before the delete). Non-revocation invalidations keep swallowing. TTLs: membership 30 min, user 20 min, tenant/account records 5 min, local layer 5 s (off by default). No metric fits; none added. There is no tenant/account soft-delete route | **Decided — changed** |
| Q6 | Should bridge-leg and webhook tokens fail open? | Middle option: a missing token when Redis ANSWERED is refused; Redis absent or erroring still accepts (never hard-fail a live call); a wrong token is refused. Kept working explicitly: VoiceLink's late terminal posts (the recording URL) after teardown — the webhook token lives 2 h past the call end instead of being deleted; and a token whose `SET` failed at mint — remembered in-process and still accepted. No other leg relies on the fallback (provider and webhook tokens are stored before the dial; nothing verifies a browser token). The "SET failed at mint" memo is **process-local**, so it is sound only on a single replica: with more than one replica, a token minted (and failed) on one replica and verified on another is refused, so scaling out needs the memo shared or the excuse dropped. **Deployment invariant:** Redis must keep these keys for their TTL (persistence on; `noeviction`, or `volatile-*` with nothing else competing); a key evicted or lost to a non-persistent restart is a refusal that cuts the live call's carrier leg and status webhooks, and each such refusal logs a warning (`WebRTC WS token missing while Redis answered`) | **Decided — changed** |
| Q7 | `trustProxy` for IP-keyed rate limits | See Q9 | **Decided — changed** |
| Q8 | Can an agent act on another agent's session? | No; sealed. The public API layer sends the authenticated actor on every session route; `requireOwnedSession` requires `session.agent_user_id === request.user.id`, else the same 404 as a missing session (no existence leak, checked before the `left_at` 409). A supervisor (`agency.supervise` → `on_behalf`) may act on another agent's session ONLY on `force-available`, the one supervisory session flow; station-token, available, break, break/cancel and leave are the agent's own presence. `requireOwnedAttempt` needed nothing: every attempt route already runs `checkActor`. A station token for session X can only be minted by X's agent, so only X's agent can open X's station socket (the upgrade itself is token-only) | **Decided — changed** |
| Q9 | Client IP behind a load balancer | `TRUST_PROXY_HOPS` (`server.trustProxyHops`, `.int().min(1).default(1)`), never `true`. Passed to Fastify as a hop-count trust function (proxy-addr's `i < hops`), because Fastify 5.12 fails a bare numeric `trustProxy` closed. The same trust makes `request.host` / `request.protocol` proxy-asserted (`x-forwarded-host` / `x-forwarded-proto`); nothing reads them today. **Deployment invariant:** the server must be reachable ONLY through exactly `TRUST_PROXY_HOPS` proxies; bind it to loopback or a private interface, or firewall the port. If it is reachable directly, a client's own `X-Forwarded-For` entry becomes `request.ip` and the IP rate limits can be evaded; if the real chain has a different number of proxies, set the count to match. **Amended 2026-11-01:** per-user bucket. Carrier-grade NAT (Jio, Airtel) puts many agents behind one IP, so the IP is no longer what binds authenticated traffic. `sessionMiddleware` charges a bucket keyed on the VERIFIED user id (`u:<id>`, `RATE_LIMIT_USER_MAX`, default 300/min, platform config block), never on a header. The app-scope limiter, which runs before auth, gives a request carrying `Authorization: Bearer` its own coarse per-IP bucket (`ipa:<ip>`, `RATE_LIMIT_IP_AUTH_MAX`, default 3000/min); a request without one keeps `RATE_LIMIT_MAX` (200) under the plain `<ip>` key. Only the bearer's presence is read there, so a forged one buys the larger coarse bucket and is refused 401 by auth. Webhook, carrier-media and internal buckets and the probe exemptions are unchanged; super-admin routes (own JWT) stay on the IP buckets. Pending Manas's ratification | **Decided — changed** |

Several running campaigns per account, 2026-11-05 (ClickUp "Allow multiple running campaigns per
account within the account's concurrency limit"). An account could run one campaign at a time
(`uq_agency_campaign_running`, Start answered 409 `another_campaign_running`). Dropping the index
alone left the account's `max_concurrent_calls` to whichever campaign's tick drew on the round's
headroom budget first (`PacingRound.takeHeadroom`, first come first served), and let two campaigns
ring one customer at once. MC1–MC7 replace it:

| # | Topic | Default used | Status |
|---|---|---|---|
| MC1 | Allocation rule | Each free slot goes to the running campaign with the **fewest live calls** that still has an agent ready and a contact due (max-min fair share, equal weights). A campaign that cannot use its slots leaves them to the others in the same round; one that ran above an equal share while the other was idle keeps its calls (no hang-ups) and gets no new slot until it is back at or under the others as calls end. Ties go round-robin across rounds. With one running campaign on the account the rule is exactly `MAX(0, MIN(limit − live, idle))`, as before. A campaign whose dials are slow to place gets a slightly smaller share: while its tick is still dialling it is not in the split, so lines freed meanwhile go to its sibling (modelled at about 4.5 against 5.3 of 10 lines, at 1.5 s against 50 ms per dial; never above the limit). Weights and a per-campaign cap set by the supervisor were weighed and left for later: equal share needs no new setting, and a cap can be added as a nullable column without changing the rule | **default, pending Manas** |
| MC2 | Where the split is decided | In the pacing round (`pacing/round.ts`), which already reads each account's limit and live calls once per round. **Members:** every campaign a scheduled round starts joins its account's split before any tick runs (a skipped, quiescent campaign is not a member). It joins NOT contending when it is drain-only (`stopping`) or its last full tick found it not running; before its first full tick it contends. The account is contended when two or more members contend (a member that reports demand counts as contending). Each tick states its demand (available agents with work, bounded under contention by the contacts actually due and by MC5's cap) and its own live calls, or drops out (a tick that fails or returns early withdraws in `finally`). **The split:** once every member has reported or withdrawn, the account's headroom is split by MC1 among those that reported. If some have not reported 1 s (`PACING_SHARE_WAIT_MS`) after the account's FIRST report, the split runs among those that have, and stays OPEN for the rest. **One open split per account:** a split opens when the account's first member joins in a round and closes when every member has reported or withdrawn, or at its deadline, `max(PACING_SPLIT_DEADLINE_MS` (5 s), the wait): a split open that long is closed at the start of the next round with the warning log "Pacing split open past its deadline — closing it". While an account has an open split, a round starts no tick for its campaigns; the first round after the close starts them. So a fast campaign's next ticks wait until its slow sibling reports. **Late reporters:** a member reporting after the split ran but while it is still open gets `min(demand, leftover)` at once, first come first served (not by fewest live calls), and puts it in the ledger, so a consistently slow sibling is served from the leftover rather than starved. A report after the split CLOSED gets 0: the tick is held back by the share (not quiescent, idle `no_slots`, counted in `agency_pacing_share_withheld_total` when `min(demand, headroom) > 0`) and takes part in the next split. **Pending dials:** a tick's dials can outlive its 250 ms round (each attempt is inserted, then the carrier is awaited before the next), so the engine keeps, per account, a hold per tick on the dials its split granted that are not yet attempt rows (the pending-dial ledger, `PacingEngine.pendingDials`, a set of holds per account): the grant goes in right after the report, each inserted attempt row takes one out, and the rest is released as soon as the tick knows it will insert fewer (checked per pair) and at the latest when the tick ends. Each round's account live read is `countLiveForAccount` plus the ledger, the ledger snapshotted before the query, so a row inserted in between is counted twice (a one-round under-dial, never an over-dial); the ticks' recorded `occupied` includes it. A hold with no progress (no grant or insert) for `PACING_DIAL_HOLD_MAX_MS` (60 s, about twice the worst healthy gap between inserts: VoiceLink login 10 s plus `add_lead` 15 s, each with its own timeout) stops counting against the account, with one warning per hold ("A pacing tick has held granted dials with no progress past the bound — no longer counting them against the account"); the hung tick's own `finally` still releases it. The cost: should that tick recover, the account can briefly exceed its limit by what it still inserts, and the account concurrency guard refuses the excess. **Why nothing is granted twice:** no two splits of an account are open at once; every grant (the split's, and each leftover grant while open) is handed out synchronously and goes into the ledger in the microtasks right after, before any later round can read, and a closed split grants nothing more, so every later read includes every grant already made. A campaign alone on its account is unaffected: its own holds are gone before its next tick, and its grant is `MAX(0, MIN(limit − live, idle))`. **Exempt:** a forced `tickOnce` (its own round, no production caller) neither waits for nor holds back a scheduled split; racing one it could grant the same headroom twice, and the account concurrency guard refuses the excess. No Redis state: on this single-replica deployment one engine leads every campaign of an account (MC3 for two processes) | **default, pending Manas** |
| MC3 | Two processes leading one account | Leadership stays per campaign (Redis lease, 15 s). While two processes lead campaigns of one account (a leader failover, or a deploy overlap; an old leader learns it lost a lease only at its next renewal), each splits only among its own campaigns, and each splits the headroom it reads from the database, so the account's live attempt ROWS can exceed `max_concurrent_calls`. Calls are still bounded: the account concurrency guard refuses the excess at bridge admission. This is the same exposure one campaign already has in split-brain (two processes leading it). The one open split per account and the pending-dial ledger (MC2) and the per-account claim lock (MC4) are per process too. An account-level lease or a Redis reservation of the account's slots would close it; neither is built, and whether to is open with Manas (§5). It ends when only one process leads the account's campaigns | **default, pending Manas** |
| MC4 | One live call per number, across campaigns | The claim's busy probe (`numberLiveSql`) is widened from the campaign to the account: a number `in_flight` or `connected` on any campaign of the account is not claimed (a retry child and its parent, or two rosters sharing a number, never ring one customer twice). Claims for campaigns of one account run one at a time in the engine (a per-account claim lock), so the read probe is enough against this process's other pacing ticks, as it was within one campaign. The agent's own dial of one of their contacts (`my-contact-call.ts`, `claimForAgentDial`) uses the same account-wide probe in its claim. The soft phone's tagged dial checks the account too: the number `in_flight` on any campaign of the account refuses `contact_in_flight`, naming that campaign's contact, as an untagged dial already did; `in_flight` only, so a number `connected` elsewhere is not refused (`softphone.md` §4.1). Backed by a partial index on the account's live contacts by number. What remains is §5's: the soft phone's checks and the agent's own dial run outside the engine's claim lock, so each can race a pacing claim of another row of the number by milliseconds | **default, pending Manas** |
| MC5 | Quiescence and claim shortfall | A tick held back by MC1 while the account had headroom is not quiescent: it ticks every round until it is served, so a campaign capped by the share cannot sleep through slots another campaign leaves idle. So is a tick that reports after its account's split closed (MC2). **Claim shortfall** (`demandCap`): after a contended tick claims `c` contacts of a grant `g` with `c < g`, that campaign's demand in later contended rounds is capped at `max(1, c)`, so slots it was granted and could not fill go to the others. The cap lifts once it claims its whole grant, on an uncontended tick, on a tick that finds it not dialling (paused, stopping), and when this process gives up its leadership; a tick that reserved no agents leaves it as it was. The floor of 1 keeps it probing, so it recovers once its contacts become claimable, at a cost of at most one slot a round: while an owner-mode campaign's due contacts stay busy on a sibling campaign, that is one line idled every round, which on a 2-line account is half its lines. It covers what demand cannot see: an owner-mode campaign's demand counts its agents with work due, not numbers busy on the account's other campaigns, and a `pool` campaign's count of due contacts is read before its claim, which can then find fewer (a number live elsewhere on the account, a contact taken in between) | **default, pending Manas** |
| MC6 | Schema and API | Migration `0015` drops `uq_agency_campaign_running`; Start and Resume no longer answer 409 `another_campaign_running` (the code is retired from `packages/contracts`). Agent exclusivity is unchanged: an agent is live on one campaign at a time (the session-join conflict check, `uq_agency_agent_live_tenant`). Contact claims are per campaign (a tick claims only its own roster), but the number busy check behind them spans the account (MC4); DNC, retries and contact ownership stay per campaign | **default, pending Manas** |
| MC7 | Visibility | Campaign stats carry `concurrency`: the campaign's live calls, its equal share of the account limit while other campaigns run (what each would get if every running campaign were busy: neither a cap nor a guarantee, and left out of the console's line when it rounds down to 0), the account limit and live calls, and how many campaigns are running; the console shows it on the campaign cards and the detail page. Metrics: `agency_campaign_slots_in_use` and `agency_campaign_slots_allocated` (gauges, per campaign), set only after a contended report to the split and cleared on every other outcome: no agent available, nothing due, a contended demand of 0 (`no_contacts`), a tick that did not plan, any uncontended tick, and when this process gives up its leadership; and `agency_pacing_share_withheld_total`, `min(demand, headroom) − grant` for every campaign whose demand exceeded what it got while the account had headroom, a report after the split closed (granted 0) counting its whole `min(demand, headroom)`. The starvation signal is withheld while its slots in use read 0 (`agy-pacing-share-starved`). On the agency dashboard | **default, pending Manas** |
