# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Voice AI Orchestrator — a Node.js microservice that orchestrates outbound AI-powered debt collection calls. TypeScript on Fastify 5, backed by PostgreSQL 16 and Redis 7. Full spec lives in `voice_ai_orchestrator_spec.md`.

**Versioning is automated.** Every PR is squash-merged, and the PR title (a conventional-commit message) drives an automatic semantic-version bump on `main` via [semantic-release](https://github.com/semantic-release/semantic-release) — `fix:`→patch, `feat:`→minor, `feat!:`/`BREAKING CHANGE:`→major; `chore:`/`docs:`/`ci:`/etc. cut no release. Each release bumps `package.json`, updates `CHANGELOG.md`, tags `vX.Y.Z`, and creates a GitHub Release. Config in `.releaserc.json`, workflow in `.github/workflows/release.yml`, full details in `RELEASING.md`. **Keep PR titles in conventional-commit form.**

## Architecture

### Request flow

HTTP/WebSocket request → Fastify middleware (request-id → auth → rate-limit) → route handler → core services → database/Redis/external APIs

Auth middleware validates two required headers: `x-mgkvc-tenant` (tenant ID) and `x-mgkvc-account` (account ID). Helper functions `getTenantId(request)` and `getAccountId(request)` extract them in route handlers. All resources are scoped by both tenant_id and account_id.

An optional `x-mgkvc-originator` header identifies where a request/call was originated from. It's seeded into the ambient log context by `tenantAccountChildLoggerFactory` (`src/api/middleware/log-context.ts`) right alongside `tenantId`/`accountId`, so the `originator` value is **embedded as a structured field on every log line** for the request — including Fastify's own request/response logs and unauthenticated webhooks that carry no tenant/account — rather than emitted as a separate log line. Absent/blank headers contribute nothing. `getOriginator(request)` reads the raw header in handlers. The optional `x-mgkvc-tenant-name` / `x-mgkvc-account-name` headers (human-readable names, owned by magick-master) are seeded the same way — stamped as `tenantName`/`accountName` on every log line when present — so Grafana's opaque tenant/account IDs get readable companion fields; these same headers also label the PostHog analytics groups (see *Product Analytics*).

### Configuration (`src/config/`)

All config loaded from env vars, validated with Zod schemas, frozen at startup. Fail-fast on invalid config. Auth supports discriminated union: JWT mode or API key mode. Telephony provider fields conditionally required based on `TELEPHONY_PROVIDER` and `TELEPHONY_ENABLED_PROVIDERS`. Optional `s3` config for audio file storage (bucket, region, credentials). Optional `sqs` config for per-account call queue (`SQS_CALL_QUEUE_URL`, reuses AWS credentials from `s3`). Optional `INTERNAL_S2S_TOKEN` for internal API authentication.

### S3 Storage (`src/storage/s3.ts`)

AWS SDK v3 wrapper for audio file uploads. `initS3Client()` called at startup if `s3` config is present. Functions: `uploadFile()`, `deleteFile()`, `getPresignedUrl()`. Key pattern: `{tenant_id}/{file_id}/{slug}.{extension}`. Bucket provisioned via `serverless.yml`.

## Invariants — read before editing

Facts that bite from outside their own subsystem: violating one usually produces **silence, not
an error**. Each links to the full rationale.

**Silent-write hazards (an explicit column list is the failure point)**

- A column missing from `PROMPT_TOOL_COPIED_COLUMNS` is silently NULLed on *every* prompt edit — nothing throws. Adding a `prompt_tools` column means placing it in that list or in `PROMPT_TOOL_UNCOPIED_COLUMNS`. ([prompts.md](docs/architecture/prompts.md))
- `prompt_templates.update()` deliberately leaves the **old** version's `prompt_tools` rows active (pinned campaigns need them). Any query over `prompt_tools` must choose live-vs-history explicitly — the unqualified form counts history. ([prompts.md](docs/architecture/prompts.md))
- `buildUpdateSet` filters against a repository's allow-list, and a column missing from it makes the call **THROW** `Disallowed update column` (`src/utils/sql-update.ts:30`) — it does *not* silently drop the column, which this list claimed until Phase 3 checked. Louder is usually better, but it relocates the hazard rather than removing it, and **the credit release is NOT what is at risk** — an earlier revision of this bullet claimed it was, which was wrong in a way worth recording, because the real damage is quieter. `calls.retrieval_summary` is written on two teardown paths and each loses something different. In **`handleCallEnd`** the `callRepository.update` sits inside a `try` whose `catch` only logs `Failed to update call record on end`, and `dispatchSettlement` is **outside** it reading `session.*` — so credit is released, but the row loses `status`, `ended_at`, `duration_seconds`, `talk_time_seconds`, `conversation_log`, `extracted_data` and `call_activity`; `analysis_status` is never set so post-call analysis never runs; `endedCallRecord` stays null so settlement ships without `callee`/`variables`/`ivr_session_id`; and the status webhook is skipped. In **`performTransfer`** the throw is caught by `escalateToHuman`'s recovery, which marks the transfer `failed` and `forceEndCall`s — i.e. **a live caller who should have been bridged to a human is hung up on**. Register every new column (`CALL_UPDATABLE_COLUMNS` / `CALL_JSON_COLUMNS`, `KNOWLEDGE_BASE_UPDATABLE_COLUMNS`) and pin it with a source audit. Note it also unconditionally `JSON.stringify`s a JSON column, so routing a generic `update()` through it would write the jsonb literal `'null'` where callers mean SQL NULL. ([telephony-byoc.md](docs/architecture/telephony-byoc.md))
- Same hazard, pinned against `information_schema`: `GREENAPI_INSERT_COLUMNS`. ([messaging.md](docs/architecture/messaging.md))

**Module graph & tests**

- **Do not add exports to `src/telephony/factory.ts`** — 67 unit-test files mock it with explicit factories, and Vitest fails the moment production code reads an export a factory doesn't list. That's why `credential-seam.ts` exists. ([telephony-byoc.md](docs/architecture/telephony-byoc.md))
- `src/config/index.js`'s module body can `process.exit(1)`. A test that transitively imports it unmocked passes locally (`.env` present) and dies in CI (**CircleCI** is the real runner — `.circleci/continue-config.yml`'s `unit-tests` job runs `npm test` on `cimg/node:22.13` with no `environment:` block; note `.github/workflows/test.yml` is `on: workflow_dispatch` and disabled, so do not cite it as evidence). Pure validators stay import-free on purpose: `usage-status-values.ts`, `greenapi-chat-id.ts`, `credential-seam.ts`. **An existing `import { config }` is NOT evidence the hazard is already armed, and that is the trap**: esbuild elides an *unused* named import, so the module body never runs. `call-queue-coordinator.ts` imported `config` for a long time while reading nothing from it — adding the **first actual read** (`config.sqs?.dequeuePollMs`) is what made `config/index.js` execute under Vitest for the first time, failing its whole suite with an opaque "process.exit unexpectedly called with 1". Check whether a file currently *reads* config, not whether it imports it; and verify the fix by running the suite with `.env` moved aside, since a local `.env` hides the failure completely.
- **The Gemini Live setup config is derived from the model FAMILY, never the API surface, and a model id the resolver cannot parse yields the MINIMAL LEGAL SETUP.** Guessing optimistically does not fail quietly: a setup field the model rejects comes back as a **1008 close**, `classifyBackendFailure` matches the reason against `MODEL_UNAVAILABLE_MARKERS` and calls it `region_model_unavailable`, and that kind is **sticky** — it trips on the **first** failure, takes the 15m→2h cooldown ladder and **pages critical**, so one unrecognised id parks a healthy backend and wakes someone with the wrong runbook. `src/ai/gemini-live/model-family.ts` (`liveModelTraits()`) is the single resolver — it replaces `isModel25()`, a bare `/2[\.\-]5/` substring test that matched `2.5`/`2-5` *anywhere* in an id (`gemini-2-5-experimental` read as 2.5) and gated two unrelated setup fields off one boolean — and it is deliberately **import-free** for the reason in the bullet above: it must never pull in `src/config/index.js`, whose module body can `process.exit(1)`. Two surface checks survive the move and are **not** redundant: `thinkingConfig` keeps its Vertex surface guard, and `supportsFullSessionClientContent` is false for 2.5. Neither is a capability claim — both keep the Developer-API-on-2.5 **rollback path byte-identical** while `gemini-3.8-live` (the Developer API default; Vertex deliberately stays on 2.5 GA) rolls out. ([ai-pipelines.md](docs/architecture/ai-pipelines.md))
- **A socket's authority is a per-socket token taken at the SWAP, never a counter bumped at connect start — and a terminal event arriving mid-reconnect is HELD, not dropped.** This is the one that was got wrong, and the failure was silent in the worst direction. A monotonic `sessionGeneration` bumped when a resumption connect *began* silenced the socket that was still installed and still carrying the caller's audio; a close arriving in that window (which is exactly what `goAway` announces) failed the fence and returned, and **restoring the counter in the catch cannot bring it back — a callback that has already returned cannot be replayed.** The call was then left on a dead socket with no `errorCallback`, no `gemini_live_abnormal_closes_total` and no breaker evidence: permanent dead air on a live caller, strictly worse than the behaviour the feature promised never to regress, and invisible to every alert. Generalise it: **a fence that revokes authority before a replacement exists must park what it suppresses, not discard it.** ([ai-pipelines.md](docs/architecture/ai-pipelines.md))
- **The Gemini Live resumption path is unreachable at the shipped defaults, and arming it is coupled to the stale-call sweep.** `CALL_TIMEOUT_SECONDS` (300s) is armed at dial (from answer instead, behind a `QUEUED_DIAL_PICKUP_TIMEOUT_SECONDS` pickup window, on a carrier that `queuesOutboundDials` — VoiceLink) **and** handed to the carrier as `maxDuration`, so a call dies at 5 minutes and the Live API's ~10-minute connection cap — the thing `goAway` and session resumption exist for — is never reached. Raising it past ~600s is what arms the feature, and the sweep must follow: `sweepStaleActiveCalls`'s AI-voice cutoff takes a `Math.max` floor from the same value, the way IVR and WebRTC already do (plus the pickup window and one ring grace, for rows on a `queuesOutboundDials` provider only). Without that floor a call outliving the 30-minute window is failed by a replica that does not own it (`excludeIds` holds only the sweeping process's sessions), settled at `talk_time=0` with the session still running, then settled **again** for real at hangup — one call, two contradictory settlements. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **The silence-nudge ladder is the only thing that can SPEAK into dead air, and it is opt-in per prompt with no seeded template enabling it.** `resolve()` returns null without `silence_nudge_config.enabled` + a directive, `armSilenceNudgeTimer` then no-ops, and the `else` branch wires accounting only (`countUnhandledEmptyTurn`). That was a fine default while `proactiveAudio` was off; from `gemini-3.8-live` proactive audio is **permanently on upstream and `GEMINI_LIVE_PROACTIVE_AUDIO=false` is inert**, so a model answering a completed caller turn with nothing is *expected* behaviour rather than a rare defect. `ai_empty_model_turns_total{action="unconfigured"}` is that exposure and is deliberately a panel, not a threshold-0 alert — with proactivity forced on it is a level, and a rule that pages on normal operation trains people to ignore it. `AI_SILENCE_NUDGE_DEFAULT_ENABLED` + `_PROMPT` arm it fleet-wide; an explicit per-prompt `enabled:false` still wins. ([ai-pipelines.md](docs/architecture/ai-pipelines.md), [gemini-live-model-cutover.md](docs/playbook/gemini-live-model-cutover.md))
- Hot-path metrics reach `src/utils/metrics.ts` through **registration seams wired in `src/index.ts`** (`setTelephonyReleaseObserver`, `setSettlementFanoutObserver`, …), so the **232** test files that stub metrics stay valid — count them with `grep -rlE "vi\.mock\('[^']*utils/metrics\.js'" test/ | wc -l` rather than trusting this number (a plain `grep -rl utils/metrics.js` counts real importers too and reads ~273). The AI layer likewise stays PostHog-free and alerting-free — `src/index.ts` is the only bridge. One deliberate exception, recorded at the import: `src/webhooks/settlement-dispatcher.ts` reads `trackSettlementDispatch` directly, because no suite both mocks metrics with a factory and reaches that module unmocked. It is a bet on the current test tree, not a change of rule; if it ever trips, add a seam rather than deleting the factory that exposed it. ([analytics.md](docs/architecture/analytics.md), [voice-alerting.md](docs/architecture/voice-alerting.md))
- `vi.hoisted()` is required for `vi.mock()` factories, and all source imports in tests use `.js` extensions (Node16 ESM).
- **The conversation-quality timeline rides the media path, so it inherits the media path's rules.** `CallSession.conversationTimeline` is fed per inbound frame, per outbound frame, and at every barge-in, nudge, empty turn and teardown; every method is O(1), capped and swallows its own errors, and every call site uses `?.` because several suites hand `CallManager` plain-object sessions. The modules the call path imports from `src/quality/` import nothing but each other (same `process.exit(1)` reason as above — hence `frame-level.ts` re-derives G.711 rather than importing `src/utils/audio.ts`), and storage is reached ONLY through `setCallQualityTimelineSink`, wired in `src/index.ts`. `AIPipelineSession.onCallerAudioDropped` must fire **synchronously inside `handleAudioIn`** for the frame being dropped — the orchestrator charges the discard against the level of the frame it just handed over, and a report after the first `await` lands on the wrong frame (a drop that is necessarily late — a held run released by a later frame — passes the frame's own `dbfs` instead). It is wired at pipeline ATTACH, not after `initialize()`, because frames reach `handleAudioIn` from the moment `session.aiPipeline` is set. Tenant and prompt version are deliberately NOT labels on the `call_quality_*` metrics; they live in `call_quality_scores` and the per-call `Call quality scored` Loki line. ([conversation-quality.md](docs/architecture/conversation-quality.md))
- **Caller speech on the live adapters is the quality scorer's rule, not a fixed level — and its floor learns from EVERY inbound frame.** `gemini_live` (nudge deferral, `Caller speech` segments, `lastCallerSpeechAt`, and whether the per-turn grace may arm) and `gold_ii` (nudge deferral only — it has no segments or `lastCallerSpeechAt`) judge caller speech with `NoiseFloorTracker` (`src/quality/speech-segmenter.ts`, import-free, the same object `SpeechSegmenter` uses): the -40 dBFS gate AND the tracked floor + 5 dB. A fixed -40 alone read a stationary bed as the caller talking forever (QD-1, [conversation-quality.md](docs/architecture/conversation-quality.md) §3). Not everything moved: the manual-activity driver, the `energy_gate` threshold and `SUSPECTED_FALSE_BARGE_IN_DBFS` are still fixed levels. The floor is fed from every decoded inbound frame BEFORE any gate (opening grace, `not_ready`, per-turn grace, activity lock) — fed only past them, it seeded on the first frame after the greeting and a caller talking then set it at their own voice — while what counts as the caller TALKING (nudge deferral, `lastCallerSpeechAt`, segments, the QD-3 anchor) is still decided on forwarded frames only. The adapters pass `dropoutBridgeMs` (500) so a short zero-filled dropout cannot drag an ESTABLISHED floor to -90 (the scorer keeps the plain rule). The trap is in tests: a suite whose very first caller frame is a constant LOUD fill makes that the floor, and nothing after it at that level is speech — open the line with one quiet frame first. Relatedly, the per-turn grace is **not** armed when the caller resumed talking after the model's endpoint (QD-3): a sustained 3-frame run of floor-relative speech (reset by a >250 ms gap in frame arrival) more recent than the session's VAD `silenceDurationMs` — **with no margin**: the server endpoints only after that much silence, so on an ordinary answer, however fast, the caller's last word is always older than that; a margin on top is what made a prompt answer skip its echo protection (PR #416 review) — and outside the adapter's estimate of its own AUDIBLE play-out + 900 ms (digital silence cannot echo; the window is collapsed by a flushed barge-in only under the T1 opt-in, since `carrierFlushed` means the clear was sent, not obeyed). Kill switch `TURN_BARGE_IN_GRACE_ARM_OVER_CALLER_SPEECH`; and the silence-nudge exhaustion/closing hold runs its guard from play-out END (`max(carrierPlayoutUntilAt, lastCarrierAudioAt) + guard`) — QD-2. Energy is still energy: a bed that fluctuates by more than ~4 dB per frame (babble) defeats the floor the way it defeats any energy VAD — see §3's limitations.

**Billing & call lifecycle**

- **A per-call AI-voice knob must be set in ALL FOUR telephony session builders, and read from the ROW in three of them** (the browser test client, `createBrowserCallSession`, takes none) — `initiateCall` (from the input), `startBulkCall`, `registerDequeuedAiSession` (SQS dequeue *and* the per-broadcast refiller) and the inbound start (all from the row). Missing one is silent: that path just runs the env default. `escalation_number`, the AMD flags and `barge_in_grace_period_ms` each shipped missing one; `turn_barge_in_grace_period_ms` / `_mode` (migration 136) are resolved for the pipeline in `turnTakingInitParams`, the one helper pre-warm and cold start share. ([ai-pipelines.md](docs/architecture/ai-pipelines.md))
- `talk_time_seconds` is anchored on `answeredAt` (pickup), never `startedAt` — dial/ring is never billed, and an unanswered call bills 0. `markAnswered()` is idempotent and must be called at every connected entry point. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- Concurrency-slot release is driven by **session state** (`CallManager.releaseSlots`), never a DB read after `session.destroy()`. All teardown routes through `releaseTelephonyLease`, which never throws. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- The BYOC dial path keys on the **caller ID**, never the tenant (`resolveCredentialIdForCallerId`); everything after the dial reads the **pinned** `telephony_credential_id`. A credential failure is fatal — the platform account is never a fallback. ([telephony-byoc.md](docs/architecture/telephony-byoc.md))
- **SQS refill is level-driven, and admission is the only limiter.** `triggerDequeue()` runs a `drain()` until admission refuses; one dial per slot release merely *conserves* occupancy at its current level (it holds 5 of 40 as faithfully as 40), which is why a 40-slot VoiceLink account sat at 5. Do not reintroduce a single `processNext()` on a slot release, and do not add a second limiter — the drain's correctness rests on admission remaining the sole gate. `processNext`'s boolean deliberately cannot distinguish "queue empty" from "admission refused"; refill logic must use `drain`/`attemptNext`, never a loop over that boolean. **An `account_full` refusal DEFERS (hiding its FIFO group, `ACCOUNT_FULL_DEFER_VISIBILITY_SECONDS`) and the skip scan moves on to another group — the handler never requeues it.** `defer()`'s retention refresh does replace a message (resetting its clock) and leaves the group visible, so after a refresh the group's NEXT head is hidden with `allowRefresh: false` for one window (refresh-then-hide) — otherwise a cohort that crosses half retention together is walked one refresh per receive with its group never hidden. An exhausted skip scan is charged to the drain's refusal budget only once the pass re-sees a group it already hid, so a drain reaches an account behind any number of full ones: the queue is shared, a requeued head leaves its group visible, and FIFO keeps serving it — so one full account's backlog spent every drain's refusal budget and starved every other account's free slots (2026-10-07, a 20-slot account at zero live calls for ~16 min). Only `global_full` requeues, because then no account can start. The hide window is paid by the FULL account (a freed slot waits out the window plus the next drain), so keep it short, and keep the refusal path free of awaited slow work: the backstop reconcile runs on ONE deduplicated background worker per replica (never awaited, never more than one in flight — a burst of Redis SCANs during saturation is the failure to avoid). ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **Retention expiry on the call queue is silent, and `queued` rows are only bounded by the orphaned-queued sweep.** `CallQueue` (`serverless.yml`) is FIFO with a finite `MessageRetentionPeriod`: an un-dequeued message either reaches the front of its group or SQS deletes it at the wall with no log, no metric and no error. **A DLQ would not change that** — redrive keys on *receive count*, so a message that expires unreceived is deleted outright, never redriven; do not read this as an argument for adding a `RedrivePolicy`. `sweepStaleActiveCalls` deliberately excludes `queued` (backlog is not an owned in-flight call), so `CallManager.sweepOrphanedQueuedCalls` is the *only* upper bound on a `queued` row — without it a campaign draining slower than retention strands its tail forever, its batches never satisfy `isBatchComplete`, and master's job stalls at `dispatched` (it does **not** falsely report complete). That is the 2026-08-16 incident: 1,005 of 4,951 contacts never dialled. Three consequences: (1) the sweep's cutoff is read from the **live** queue attribute (`getMessageRetentionSeconds`), so changing `MessageRetentionPeriod` needs no code change — never reintroduce a hand-written retention constant; (2) row age is an **upper bound** on message age — a message is sent no earlier than its row is created, and `requeue()` resets the message's clock while the row's timestamp stays put, so a row can pass the cutoff while its message is still live — and what makes the sweep safe anyway is `claimQueuedToInitiating` refusing a row that is no longer `queued` — worst case is a call failed early, a double dial is unreachable; (3) a recovery path must **never** call `enqueue()` with the bare `callId`, because that is the `MessageDeduplicationId` and FIFO's 5-minute dedup window would swallow it — this is why `requeue()` mints `${callId}:${Date.now()}` and why the sweep settles rows in the DB rather than round-tripping through SQS. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **`defer()` resets a message's visibility, never its retention.** Only a genuinely new `SendMessage` (`requeue`) restarts the retention clock, so a message parked against a saturated scope is on a countdown to silent deletion however many times it is deferred. `defer()` therefore replaces the message once it passes half the queue's retention. Two observability facts that made the original stranding undiagnosable and must not be undone: the defer path had **no log line at all**, and `provider_concurrency_admission_total` was **prom-client only** — Grafana Cloud is fed by OTLP, so its absence there was evidence of nothing (same trap as `gemini_backend_breaker_open`). Both now emit, and `admission_result` must stay OTel-exported: it says WHICH scope a message is parked against. Since 2026-10-07 `account_full` defers too (it used to requeue, which reset its retention clock as a side effect), so both `provider_full` and `account_full` heads age toward the wall and rely on the half-retention refresh.
- **`sqs_queue_depth` cannot distinguish "empty" from "all hidden".** It is fed by `ApproximateNumberOfMessages`, which counts **visible** messages only — deferred messages read as zero, and so do deleted ones. Never treat a zero there as proof the backlog is clear; the diagnostic signal is its **divergence** from `calls_queued_current`, which is the 2026-08-16 fingerprint (1,005 rows queued against a depth of 0).
- **A per-broadcast concurrency group parks its backlog in POSTGRES, not SQS, and only the `GroupRefiller` starts it.** A row with `concurrency_group_id` (migration 130; `concurrency_group` on the three bulk endpoints, flag `broadcast_concurrency`) is admitted gate-first by the funnel (`admitThroughGroupGate`: Redis ZSET, member = row id), and when it cannot start it stays `queued` with no SQS message — never failed. Three consequences: (1) grouped rows are excluded from every `failStaleQueued` and from `calls_queued_*` (they have no retention wall; their backlog is `group_concurrency_parked_current`), so **a new sweep or backlog query over `queued` must decide about grouped rows explicitly**; (2) a new park point must call `CallManager.wakeGroupRefill`, and a new path that admits grouped rows must go through the funnel **with the group** — the gate's `owned` answer means another admitter holds that row's slot, so it backs off rather than share a lease; (3) the refiller (`src/core/group-refiller.ts`) exists with or without SQS, reconciles the gate against Postgres before admitting (rebuilds a ZSET Redis lost, removes members of terminal rows), stops claiming the moment `gracefulShutdown` begins, and runs a boot pass after `drainQueue`. (4) the gate refuses every admission (`unsynced`) until the refiller has synced the group from Postgres (`group_synced` marker), so only the refiller seeds a group — after a Redis loss and for every brand-new broadcast, whose first rows therefore start from the refiller's first pass. (5) Bulk rows persist the request's `enable_recording` / `analyze` (`calls.enable_recording` / `analyze_call`, migration 131) and `registerDequeuedAiSession` applies them (AND with the account ceiling) — a deliberate fix for SQS-dequeued rows too. (6) **The flag gates CREATING a group, not continuing one**: with `broadcast_concurrency` OFF, a request whose group already has its `bulk_concurrency_groups` row (a later wave of a broadcast accepted while the flag was on — master feeds capped broadcasts batch by batch) is accepted and stays capped; only an unseen group id is refused 403 `Feature Not Enabled` (`preflightBroadcastConcurrency`, which reads the row only when the flag is off). So flag off = no NEW capped broadcasts; running ones finish under their cap — to stop one, stop it. (7) An IVR session that `ai_handoff`s is `completed` while its carrier leg runs on under the AI call; its gate member is HELD while that AI call (`calls.ivr_session_id`) is live — the reconcile and the rebuild both know. (8) A group whose row is missing (`unconfigured`) for 10 min has its parked rows failed and settled `CONCURRENCY_GROUP_MISSING`. (9) A crashed replica's capped calls still read live until the stale-active sweep fails them, so their slots come back by member expiry or that sweep, whichever is first — up to one slot lifetime of UNDER-admission, never over. (10) `group_concurrency_parked_current` is fleet-wide (every replica exports the same count): aggregate with `max()`, never `sum()`. (11) **A group release applies only to the admission it read** — a GET, then a compare-and-delete on the exact record (each admission writes a random `token`); a read answered after `GROUP_RELEASE_READ_DEADLINE_MS` (= the 1 s hook timeout) is `abandoned`. So a release the hook timed out on cannot land late and free a NEWER call admitted under a reused lease key — never "simplify" it back to one keyed-only script. (12) Boot/poll/discovery read the parked groups a page (1000) at a time through a keyset cursor on `(tenant_id, account_id, group_id)` that rotates — not oldest-first, which pinned the first page forever once 1000 groups sat at cap. (13) `bulk_concurrency_groups` is purged by retention (migration 135 `last_batch_at`, stamped by every batch's `ensure`; deleted only past the cutoff and with no parked/live row) and remapped by `/internal/migrate-account-ids`. Migration 135 (`bulk_concurrency_groups.last_batch_at` + its index) touches only that small table and needs no out-of-band step. **⚠️ Migrations 132–134 (one per table, `calls` last) build six partial indexes under `SET LOCAL lock_timeout = '5s'`; on large production tables pre-create them `CONCURRENTLY` out of band BEFORE deploy (same names/definitions) — `IF NOT EXISTS` then makes each file a no-op. A lock timeout fails the migration and the container exits before the app starts (see `service-down-after-deploy`); the next start retries.** ([call-orchestration.md](docs/architecture/call-orchestration.md))

- `PREFLIGHT_PRECEDENCE` decides which status code a multi-fault request gets. Reordering it is a public API change, not a refactor. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **`carrierPlayoutUntilAt` is now a MIRROR of `CallSession.playoutClock`, and that mirroring is what makes the rollout safe — do not write to it directly.** `PlayoutClock` (`src/core/playout-clock.ts`, import-free) owns the accumulator; `sendAudioToTelephony` mirrors either the uncorrected write cursor or, under `AI_PLAYOUT_CLOCK_CORRECTION` (default off), the carrier-lead-corrected one. With the flag off the arithmetic is identical to the line it replaced, so the flag gates **only whether a measured lead may be non-zero**, never a second code path — the property every one of the five existing readers depends on. A carrier acknowledgement calibrates **one constant** (the buffering lead) and cannot correct a cursor mid-utterance: acks are per-utterance and one sitting behind audio a `clearAudio` discarded is flushed with it and never arrives. `playout_lag_seconds` is NOT that constant — it times from checkpoint *issue*, so a `turn_drain` sample is dominated by the utterance it followed; the residual is `playout_cursor_error_seconds`, which ships **before** anything keys off the cursor. `heardOfUtteranceMs` is summed over contiguous **runs**, never integrated from the utterance start, because over-reporting makes the model skip content nobody heard on resume — **and the run SPLIT is only half of that; the amount BANKED when a run closes has to be lead-aware too.** A run drains from the write cursor but the ear is `leadMs` behind it, so banking `runWrittenMs` outright at the boundary re-committed the same over-report one step along, at every boundary. Banking now freezes the same expression the live run uses, which is the invariant to preserve: the two cannot be allowed to disagree. Two more the class depends on — `collapse()` does **not** end the utterance (all three collapse sites are followed by the utterance-closing path, and doing it twice zeroed the run accounting one line before the barge-in path asks for it, reporting 0 for the turn that most needs a real `audio_end_ms`), and `now` is guarded exactly as `frameMs` is, because `Math.max(x, NaN)` is `NaN` and one non-finite timestamp poisons the cursor for the rest of the call. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **The play-out cushion is the only thing that makes the cursor honest on the five carriers that never acknowledge playback** (twilio, telnyx, voicelink, z99, generic SIP — twilio and telnyx *can* be issued a `mark` and so can ack, but only under `AI_PLAYOUT_CHECKPOINT_TWILIO_TELNYX`, default off, leaving five until it is flipped). **That flag is a kill switch, not a feature flag**: issuing a checkpoint is pure measurement, but it is the one thing in this work that puts a frame on a live media socket, and an unrecognised control frame can have a carrier close the stream — dead air on every call it carries. It is a boolean and deliberately not a carrier allow-list, because an absent array read through a partially-mocked config throws **on the audio path** while an absent boolean degrades to the historical behaviour. The Telnyx outbound `stream_id` spelling is modelled from the INBOUND ack and has never been observed; spike both carriers before enabling. Relatedly, whether a checkpoint is recorded against the cursor must come from what the SENDER reports, never from the provider name: every sender bails silently on a closed socket or a missing stream id, and an entry recorded for a frame that never went out ages into `lost`, corrupting the one signal that separates "this carrier stopped acking" from "this carrier never did". `PacedFrameQueue` releases immediately until the carrier is `leadMs` ahead, then at cadence. Two hazards: wired to a clock the sink path never advances, `remainingMs` returns 0 forever and it degrades **silently** to today's blast with no error, no fallback and no underrun — the most likely way C1 ships looking fine and doing nothing; and `AI_BARGE_IN_CONFIRM_MS` must stay below `AI_OUTPUT_PACING_LEAD_MS` or a rejected barge-in becomes audible dead air (fail-fast in `src/config/index.ts`, deliberately NOT a `superRefine` — that wraps `aiSchema` in a `ZodEffects` and `.shape` disappears, breaking the two suites that introspect it). Queue **depth** is never a wedge signal: a ten-second utterance pushed in 100 ms legitimately makes its oldest frame wait ten seconds.
- **The silence-nudge timer's five arming sites have five different guard predicates, and they disagree in ways that bite.** `onTranscript` alone omits `!callEndTriggered`/`!endHandled`, so a transcript after a claimed hangup re-arms the timer on a dying call — and a phantom 'user' transcript is very often an echo of our own spoken nudge, which makes it reachable. Only `onTurnEnd` checks `silenceNudgeEndPending`. `TurnController` (`src/core/turn-controller.ts`, import-free) exists to collapse them; `AI_TURN_CONTROLLER_MODE` defaults `off`, `observe` records disagreements without deciding — and `observe` is the **only** other value. A `nudge` member existed, and the schema described it as "the one place the timer is armed", but nothing applied the controller's actions, so it behaved exactly like `observe`; a mode that lies about taking authority is worse than one that does not exist. It returns when the arming sites delegate. For the comparison to mean anything the controller must read the play-out cursor through the **same** flag the legacy readers do: acks are folded into the clock regardless of `AI_PLAYOUT_CLOCK_CORRECTION` (that flag only chooses which cursor is mirrored), so a controller on the corrected cursor against legacy sites on the uncorrected one makes every reported disagreement partly a function of the carrier lead rather than of the arming logic. **`CallSession.callEndTriggered` is an accessor, not a field** — claiming the hangup notifies the controller, because nine sites set it and a tenth would otherwise forget. Two rules the state machine encodes: an UNKNOWN `isGenerating()` must never resolve to `idle` (only one of six pipelines implements it, and `idle` is the one state that arms the timer), and arming happens on **entry** to idle only — `armSilenceNudgeTimer` clears and reschedules, so a benign repeating event would postpone the nudge indefinitely. **`draining` is resolved against the clock, not by an event**: its declared exit `playout_drained` has no producer anywhere in the orchestrator, so an agent turn that ended with audio in flight parked the machine there and never returned to `idle` — the state that arms — meaning a caller who went quiet after an agent turn would never be nudged at all. The settle is computed before the event is applied but the **actions are computed from the pre-settle state**, because a settle into `idle` is a genuine entry and must arm; folding it into the action's `from` reads as a self-loop, emits nothing, and reproduces the same never-armed defect one step along. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **Gemini manual activity mode: `activityEnd` is the ONLY thing that closes a caller turn.** With `automaticActivityDetection.disabled` server VAD is off, so the adapter's own local speech gate (`driveManualActivity` in `handleAudioIn`: -40 dBFS onset run, pre-roll replayed after `activityStart`, hangover timer + 15 s ceiling for `activityEnd`) is what keeps it from being permanent dead air — a timer, not a frame, closes the turn, because a carrier may stop sending frames in silence. It can be enabled per tenant/account (`gemini_live_manual_activity`, ORed with the env flag) and is still a never-spiked path. `GEMINI_LIVE_MANUAL_ACTIVITY` defaults false and the emitted setup is byte-identical to today when off; the `supportsManualActivity` trait is false for any unparseable id. A 1008 naming an activity field while manual mode was armed classifies as `client_config_rejected`, which is deliberately **not** a `BackendFailureKind` (tsc is what keeps it off the sticky `region_model_unavailable` breaker that pages critical on the first failure) and its branch must run **before** the region check, since `"...automaticActivityDetection is not supported"` contains `is not supported`. The safety net matches Google's error TEXT, which has never been observed — capture it in a spike before enabling. **Its markers are the field names we actually send, and nothing looser**: a bare `activity` entry was a substring of `inactivity`, so `1008 "…is not found in this region due to inactivity"` — a genuine `region_model_unavailable` — classified as a client fault and came off the breaker entirely, which is the "genuinely dead backend stays in rotation" outcome the list's own comment warns about. `activityStart`/`activityEnd` declare "never throws" and must honour it with a try/catch around the send: `sendRealtimeInput` throws synchronously on a closed socket, the `!this.session` check does not discharge the contract (the resumption swap closes the old socket after it passes), and these are designed to be driven per caller utterance from the media path. ([gemini-live-audio-pauses.md](docs/playbook/gemini-live-audio-pauses.md))
- A static call's terminal transition is **one atomic claim** (`staticCallRepository.claimTerminal`, `status NOT IN (<terminal>)` in SQL). Winning it is the precondition for the `static_calls_total` increment, the settlement dispatch, the lease release and batch closure — nine of the twelve increment sites sit behind it, one behind `claimInitiationFailure`, and the other two count the rows RETURNED by the set-shaped terminal statements (`cancelBatches`, `failStaleActive`, `failStaleQueued`), each an exactly-once claim of its own — for the counter and the settlement, but NOT the lease: the sweeps never release it, so a swept call reads terminal while its slot is held until the lease TTL. A new path that moves a static row to terminal must count it behind whichever claim it won, or the counter no longer reconciles with calls dispatched. A `findById` + `STATIC_TERMINAL_STATUSES.includes()` check is **not** a substitute: carriers retry status callbacks and deliveries land on arbitrary replicas, so the race is concurrent across processes. The claim only holds while terminal is a one-way door, so every write that could move a row back to `in_progress` goes through `staticCallRepository.updateIfLive` — a resurrected row re-arms a second claim. Adding the `provider` label to `static_calls_total` deliberately terminated that series. ([announcements-static-calls.md](docs/architecture/announcements-static-calls.md))
- **Every multi-row settlement / batch-completion dispatch goes through `src/webhooks/settlement-fanout.ts`. Never reintroduce a bare `for (const row of rows) dispatchSettlement(...).catch(...)`.** Four properties are load-bearing and each loss is silent. **Bounded** — `WEBHOOK_FANOUT_CONCURRENCY` (default 10), sized against **master's** `DB_POOL_MAX` of 20, not core's pool of 50, and applied **process-wide**: one shared worker pool, because `sweepStaleActiveCalls` starts six fan-outs in one `Promise.all` and a per-invocation cap peaked at a measured 30 concurrent settlements against a documented 10. **Detached** — the entry points return `void`; `await`ing one holds the operator's stop open for `ceil(rows/cap) × master RTT` and times out through master's proxy, reading as a failed stop that is in fact succeeding. **Isolated per item** — and the dangerous case is *widespread* failure, not one bad row: with every dispatch rejecting, a `Promise.all`-based pool attempts only the first cap's worth. **Drained at shutdown**, after `callManager.gracefulShutdown` and before `closePool()` — and the drain **re-arms** rather than trusting the idle notification it was woken by, because a continuation already queued behind that notification can enqueue a fresh burst before the `await` resumes. **Split into two queues under the one cap** — a settlement always retires (5s `AbortSignal`), a batch-completion check runs two reads against core's pool with no `statement_timeout`, so completions are capped at half the pool and a waiting settlement is served first; under one FIFO, hung completion checks head-of-line-block every remaining credit release. It bounds the burst; it does **not** make delivery durable — an ungraceful exit still loses queued dispatches, abandonment is the *expected* outcome for a 5,660-row cancellation (30s clears ~1,500), and a lost release is recovered per tenant by master's `POST /super-admin/tenants/:id/credits/reconcile`, **never** by re-running the stop (the rows are already terminal and no longer match the cancellation predicate). The persisted outbox is the open half of `86d41v0n0`. The loop was found in **five** places, one at a time, and the fifth (`sweepStaleWebrtcCalls`) hid from a file-level source assertion because its file already contained the bounded calls — so boundedness is pinned behaviourally, per site, with an above-cap fixture. `WEBHOOK_FANOUT_CONCURRENCY` is **not** an incident lever: config is frozen at load, so changing it needs a restart, and a restart abandons the backlog. **Security boundaries**

- `webhookBaseUrl` always comes from env, **never** a credential row (SSRF / call-hijack). ([telephony-byoc.md](docs/architecture/telephony-byoc.md))
- `recording_url` is persisted verbatim from an unauthenticated carrier webhook. Host checks use parsed-hostname matching (`recordingHostMatches`), never `includes()`. ([telephony-byoc.md](docs/architecture/telephony-byoc.md))
- Caller-ID validation caches **positive verdicts only** — errors are never cached, so master being down stays a fail-closed 503. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **Auth is registered per route plugin, never globally, so a new `/api/v1` plugin without its own `addHook('preHandler', authMiddleware)` is wide open** — Fastify encapsulation means a sibling inherits nothing, and `getTenantId`/`getAccountId` just read `x-mgkvc-tenant`/`x-mgkvc-account`, i.e. attacker-supplied headers become the identity. It fails silently in the worst way: the routes answer 200, tenant scoping still looks right, and a route test that mocks `authMiddleware` passes either way. It has shipped twice — the roster-ingest route (6978183) and `/api/v1/inbound-phone-numbers`, unauthenticated from creation until v1.102.x, where it exposed live DID routing and `escalation_number` to anyone who could reach `/api/`. `test/unit/api/routes/api-v1-auth-coverage.test.ts` now audits every `/api/v1` plugin registered in `src/index.ts`, with an argued allow-list for the public surfaces (carrier webhooks, media/WS legs, signed-token playback, static catalogs). ([inbound-calls.md](docs/architecture/inbound-calls.md))
- Media/URL inputs must be `https://`; Zod's `.url()` accepts `javascript:` and `file:`. ([messaging.md](docs/architecture/messaging.md))
- **IVR `webhook` steps fetch a tenant-authored URL from inside our network, so they are an SSRF sink** and go through `src/utils/outbound-url-guard.ts` (import-free) at three points: `checkOutboundUrl` on the *interpolated* URL; a dispatcher connector that refuses a blocked IP literal itself (`isBlockedHost` — net/tls never call `lookup` for one, so a reused dispatcher without the pre-check would otherwise dial it); and `connect.lookup` = `guardedLookup`, which refuses any private/internal/reserved address at connect time — a resolve-then-fetch pre-check is a DNS-rebinding hole. Redirects are never followed. `success_variable` stores the **HTTP status, never the body**: session variables ship verbatim as `variables`/`callee.metadata` on the completion webhook and as `step_responses` on the sessions API and the settlement, so a stored body is a read primitive for whatever the URL returns. Never add an IPv6 rule whose range contains `::ffff:0:0/96` (that rule, `::/80`, `::/8`, …) — Node's `BlockList` matches every plain IPv4 address against it and the guard silently blocks all of IPv4. The AI tool path (`src/tools/url-validator.ts`, regex-only, follows redirects) and tenant callback URLs (`dispatchWebhook`) are **not** behind this guard yet. ([ivr.md](docs/architecture/ivr.md))
- **Who an `escalate_to_human` transfer rings is decided in exactly one place — `resolveEscalationTargets` (`src/escalation/helpers.ts`) — and a configured destination wins.** Three sources compose and the precedence is not obvious: a destination with **≥1 active member** is rung **in full**; the per-call `escalation_number` supplies the dial list **only when the destination names nobody** (the policy-only destination — a row carrying whisper text / caller ID / timeouts, which `preflightEscalationTransfer` deliberately permits with an empty roster); and the model's `escalate_to` **changes nobody** unless the destination opted into `allow_dynamic_target`. Every violation rings the **wrong human with no error**: the transfer succeeds, the row settles, and the operator finds out from a customer. This precedence was **inverted before 2026-09-12** — the preset "became the roster" and an `escalate_to` naming a member rang that member alone (`source='member'`) — which is how BKP Homes call `5c0949c6` rang a dead placeholder instead of the store executive its operator had configured. `source='member'` is now **read-only history**: the DB CHECK still permits it, nothing writes it. Two consequences that bite from outside: `escalation_targets` (JSONB) is persisted **before** the carrier is told to transfer and is what the `escalate-answer` webhook dials, so the resolver stays the single decision point; and `escalation_target_source='rejected'` is now a **level, not an alarm** — every model request lands there, so anything alerting on it (PostHog properties, the Grafana panel, cusui's call-detail banner) is reading a benign majority. `dynamic` is the value worth watching. ([escalate-to-human-transfer-design.md](docs/escalate-to-human-transfer-design.md) §4b/§4c)
- **CAPABILITY and ENABLEMENT are two different sets, and conflating them is what makes merging an adapter flip a feature on for every existing account.** `TRANSFER_CAPABLE_PROVIDERS` (`vobiz`, `plivo`, `twilio`) is what the webhook routes are DERIVED from, so a carrier can never be enabled without its hops existing. `transferEnabledProviders()` is capable ∩ **master's governance flag** `telephony_providers.live_transfer_enabled` (seeded on for `vobiz` + `plivo` + `twilio`, off for every other carrier; a super-admin toggles it) — it is what `GET /metadata` publishes, what preflight reads (an implemented-but-disabled carrier — or enablement never loaded — DEGRADES dispatch like `ai_call_transfer` off, counted `escalation_suppressed_total{stage="dispatch",reason}`; only an unimplemented carrier is a 400 — design doc §5c.7), what **call-time resolution** checks, and what `resolveTransferProvider` picks from. The split follows the one-directional asymmetry: routes without the gate are harmless (they only ever load a row that could not have been transferred), while the gate without the routes redirects a **live A-leg at a URL that 404s**. There is **no env var** any more (`ESCALATION_TWILIO_TRANSFER_ENABLED` is gone). `escalation/helpers.ts` stays import-free (a config read there arms `config/index.js`'s `process.exit(1)` across a large part of the suite), so it holds a synchronous SNAPSHOT that `escalation/live-transfer-enablement.ts` fills from `GET {MASTER_SERVICE_URL}/internal/telephony-providers/live-transfer` — 60s in-process TTL, 30s background refresh, Redis last-known-good — and every async read point calls `ensureLiveTransferEnablementFresh(stage)` first — which never waits while any snapshot is held (a stale one triggers a background refresh); only a cold process awaits, capped at 2s. **Never loaded ⇒ empty ⇒ fail CLOSED** (master unconfigured, or down since boot with nothing in Redis): counted at every read as `escalation_live_transfer_fail_closed_total{stage}` and warned at most once a minute per stage (the `handoff_prefetch` prediction is neither), and escalations degrade to ending the call. Call-time resolution read the CAPABLE set until this landed, which let inbound, IVR handoff, the intent callback and SQS-dequeued calls (none of which preflight) transfer over a carrier that was gated off.
- **Twilio reaches the same four transfer behaviours by three different mechanisms**, each of which fails silently rather than loudly: its live redirect is `POST /Calls/{sid}.json` with `Url` (the same resource `endCall` posts `Status` to — a stray `Status` hangs up on the customer instead of moving them); the whisper URL and per-leg `statusCallback` are `<Number>` attributes rather than `<Dial>` attributes, and Twilio **silently ignores** an unknown `<Dial>` attribute, so getting that wrong yields a transfer that works and is never screened; and there is **no `confirmKey` attribute at all**, so screened mode is a `<Gather numDigits="1" finishOnKey="">` the adapter renders, whose trailing `<Hangup/>` is the only thing refusing an agent's voicemail. `finishOnKey=""` is load-bearing — the default terminator is `#`, `#` is a legal `confirm_key`, and with the default an agent pressing accept posts EMPTY digits and is refused.
- **A transferred call is still the call that was dialled, and three things about it bite silently.** (1) **Carrier time limits cap the WHOLE call** (Twilio `TimeLimit`, VoBiz/Plivo `time_limit`), and outbound calls are dialled at `callTimeoutSeconds` — so a bridged human conversation was cut ~5 min after the AI call started. Twilio raises `TimeLimit` on the same Call update as the redirect (`TransferCallRequest.timeLimitSeconds`, `transferExtendsTimeLimit`); VoBiz/Plivo cannot change it live, so a call that can escalate is DIALLED with the headroom (`carrierMaxDurationSeconds`) while the AI-side timeout timer still ends non-escalated calls on time. (2) **On Twilio, never close the media socket after the redirect**: Twilio "executes the remaining TwiML" when the server closes a `<Connect><Stream>` socket, so our close beating the async redirect ended the call. The detached session leaves it for Twilio (`CARRIER_ENDS_STREAM_ON_TRANSFER`, 15s backstop), and every Twilio answer document carries `<Connect action=.../escalate-connect-end/:callId>` — `<Hangup/>` for every ordinary call end, the transfer `<Dial>` only for a `transferring` row nobody has dialled (atomic claim `calls.escalation_dial_claimed_by`, migration 126, shared with escalate-answer — which TAKES OVER a connect-end claim, because it is only fetched once our redirect replaced that dial; `performTransfer` re-reads the claim and skips the redirect when connect-end already dialled). That route is registered for Twilio unconditionally, not from `TRANSFER_CAPABLE_PROVIDERS`: its lifetime is the answer document's. (3) **A destination's caller ID is on ONE carrier account** (`escalation_destinations.provider` + `telephony_credential_id`, migration 127, NULL = legacy): writes validate across every enabled carrier and persist the match, `/caller-ids` is the union, the Test dials over it (credential re-resolved from the caller ID at Test and dial time — the stored id is only a hint), and `escalate-answer` presents the CALL's own caller ID when the call's carrier/credential differs (`escalation_caller_id_substituted_total`) instead of failing the B-leg. ([escalate-to-human-transfer-design.md](docs/escalate-to-human-transfer-design.md) §5c.3)
- **Screened mode on Twilio above one member runs as a per-call QUEUE, not a `<Dial>` (2026-09-23; it used to be refused).** Twilio's `<Number>` reference says the first leg to pick up is connected and the rest are hung up, and the whisper `url` is fetched *because* a leg answered — so inside a multi-noun `<Dial>` an agent's voicemail answering first cancels the roster and is then dropped by our own gate. VoBiz/Plivo's carrier-side `confirmKey` screens each leg independently; Twilio parity (`usesScreenedQueue`, design doc §5c.4, migration 128) parks the customer in `<Enqueue>esc-{callId}` (ringback from `escalate-queue-wait`, settlement from the `escalate-queue-result` action), rings each member as its OWN REST leg (`TwilioAdapter.placeTransferLeg` — not `initiateCall`, which records and hard-codes `Timeout=60`) running the existing gate, and the first to press wins a guarded claim (`calls.escalation_winner_member`) and gets `<Dial><Queue>`; every other leg is hung up. Leg SIDs/status live in `escalation_member_legs` (a table, forward-only status — JSONB would clobber concurrent callbacks), inserted BEFORE the `<Enqueue>` is returned so "every leg terminal" is never vacuously true. A create whose answer was lost is `unknown` (NOT terminal). Migration 129: per-leg `answered_at` (an answered member is waited for from their own answer, not the queue clock) and `calls.escalation_queue_left_at` (leave and win are mutually exclusive — a late accept is refused, never bridged into an empty queue). Unsigned hop bodies never pick what is cancelled or deleted (stored SIDs only). §5c.5. Blind mode and single-member screened keep the `<Dial>`. The hops are Twilio-only (derived from `SCREENED_QUEUE_PROVIDERS`). Escalation hops render with the PLATFORM adapter, BYOC calls included (`transferRenderAdapter` — rendering is credential-independent and the platform adapter is always constructible for a transfer carrier; the old pinned-credential fallback was unreachable and was removed in review round 2, §5c.7); REST side effects always use the call's own account.
- **`DialCallStatus` alone cannot say a human took the call, and `resolveTransferStatus` is the rule that decides.** Twilio's `completed` means "the called party answered" — which a voicemail our gate hung up also satisfies — so settling on it alone wrote `escalation_transfer_status=connected` with `outcome=escalate_human` for a call nobody took, AND the fallback branch's `!== 'connected'` guard then skipped the operator's apology, so the customer got a silent hangup. Two pieces of counter-evidence override it: `DialBridged` (Twilio's own field on the same callback) and `escalation_screen_verdict` (migration 125, written by the confirm hop, which is the only place in the system that learns whether a human accepted). **Both are asymmetric — absence is never counter-evidence**: VoBiz and Plivo post no `DialBridged` and run no gate we can see, so reading either absence as "not connected" would settle every successful transfer on two of three carriers as unanswered. Only an explicit `false` / `'refused'` downgrades, and the downgrade target is `no_answer`, never `failed`.
- **The screening policy is SNAPSHOT at transfer start (`escalation_policy_snapshot`, migration 125), because a transfer spans four webhook hops over the seconds a roster rings and `escalation_destinations` is editable throughout.** A `PUT` flipping `screened` to `blind` mid-ring made the whisper hop take its blind branch and return the empty ACCEPT document — screening switched off by an edit that never mentioned the call — and a changed `confirm_key` refused the digit the agent had just been told to press. Only `mode`, `whisper_message` and `confirm_key` are frozen: those are what an already-emitted carrier document has committed to. The row is still LOADED, so a deleted or deactivated destination still resolves to "no context".
- **Both screening hops fail CLOSED, and their degrades are a bare `<Hangup/>` rather than an empty `<Response>`.** An empty document is how Twilio ACCEPTS a screened leg, so returning one from a failure arm switches screening off at exactly the moment we have established we cannot screen — and it is reachable without a programming error, since these routes are registered on every replica independently of `TELEPHONY_ENABLED_PROVIDERS` and `TelephonyProviderRegistry.get` throws for a carrier a replica has not configured. The confirm hop is wrapped whole and coerces `Digits` with `String()` (a duplicate form key arrives as an ARRAY, and `.trim()` on it threw a 500 — which on a `<Gather action>` is not TwiML, so the carrier makes the bridge decision itself). Three sibling facts, each a latent bug for the other carriers until Twilio forced them: `escalationHangupXml` renders through the **adapter** and its degrade is wordless (a literal `<Speak>` is VoBiz's dialect on a provider we just failed to identify, and TwiML has no such element); `mapDialStatus` needs `canceled` (one L, Twilio's spelling); and `escalate-result` must read `DialCallStatus`, the only name Twilio sends. ([escalate-to-human-transfer-design.md](docs/escalate-to-human-transfer-design.md) §5c)

**Migrations & metrics**

- Migration prefixes must be unique (`scripts/lint-migrations.mjs`). Count them with `ls src/db/migrations | wc -l` rather than trusting a written number.
- `.sql` migrations run under `node-pg-migrate` with `singleTransaction` and cannot opt out, so the `NOT VALID` + `VALIDATE` idiom buys **no** lock safety here. ([database.md](docs/architecture/database.md))
- **A query parameter used in more than one context must be typed at every use.** node-postgres declares no parameter type OIDs, so Postgres infers each `$n` during parse analysis from the first context that *constrains* it — and a bare `$n IS NULL` / `$n IS NOT NULL` constrains nothing, while two contexts that deduce different types collide. Either way the statement fails to PARSE (`42P08`) on **every** call, before any row is touched, regardless of the value bound. This has shipped twice: `agencyRepository.transitionStatus` (AD-P4-C-02 — `$3` assigned to a `VARCHAR(20)` column *and* compared to text literals; fixed by casting the **assignment**, because casting the comparisons just moves the conflict) and `staticCallRepository.claimTerminal` (v1.102.0 — a bare `$6 IS NOT NULL` alongside `settlement_claim_token = $6`, which took down every static-call settlement on the dedicated fleet and pinned the tenant at its concurrency ceiling). **A mocked pool never parses SQL**, so a unit test asserting the query text passes against SQL Postgres refuses — it did, for both. Any hand-built predicate needs a real-Postgres integration test.
- Adding a label to an existing Prometheus metric terminates the series: any `rate()`/`increase()` window spanning the deploy under-reports, and pinned recording rules go empty.
- **An incremented counter is not an ingested one, and "the series is absent" is evidence about the metric store at least as often as about the code.** Grafana Cloud enforces a **per-instance active-series cap** (15 000 on this stack, measured 2026-09-22 with ~104 samples/s discarded as `reason="per_user_active_series_limit"`, readable from the `grafanacloud-usage` datasource). An instance at the cap rejects **NEW** series while existing ones keep flowing — so the symptom is a metric that looks dead for one label combination and healthy for every other. That is the 2026-09-21 incident, and the ticket's diagnosis of it was wrong in the instructive direction: `calls_total{status="failed"}` **was** incremented for all 199 dial failures (`call_duration_seconds_count{outcome="none"}`, recorded two statements later in the same `try`, took all 199 and is still in Mimir) — the combination was simply new on that replica and was refused. Before concluding a path does not emit, check a metric emitted **beside** it and check `grafanacloud_instance_samples_discarded`. What filled the cap was `calls.outcome`, which is **free text the model writes** (`CallOutcome = string`, via the `end_call` tool) and was used verbatim as a label: 794 series on `call_duration_seconds_bucket` and 113 on `calls_total`, one new permanent series per phrase the model invents. `metricCallOutcome` (`src/core/call-outcome-label.ts`) now bounds it at the emission site — one `other` bucket, not a slug, because a slug of free text is still unbounded — while the row, the audit event, the settlement payload and PostHog's `call_completed` keep the verbatim value. `api_request_duration_seconds` no longer labels a 404 with the raw URL (`routeMetricLabel` → `/__unmatched__`, `src/utils/metric-path.ts`). The histogram was still large (~7 600 bucket series on 2026-09-22, ~9 800 series in all) because method × route template × status was 9 series per combination, so on 2026-09-29 it was split: **`api_requests_total{method,path,status}`** carries every count/rate/error query (1 series per combination, ~1 085), and **`api_request_duration_seconds` is labelled by `method` only** (latency is only ever read `by (le)`; per-route latency is a trace query). Both are emitted by `trackApiRequest`, the single emission point that owns the split — never put `path`/`status` back on the histogram. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **A dial that never reached the carrier is counted by `call_dial_failures_total{provider,reason}`, NOT by a second `calls_total` increment.** The two are complementary: a dial failure settles the call, so it already increments `calls_total{status="failed"}` exactly once from `handleCallEnd` — all three `.catch()` sites (immediate, bulk, SQS-dequeued) emit `call.failed`, whose listener settles it. Adding an increment there would double-count. What `calls_total` cannot do is separate "the carrier is unreachable" from "the AI pipeline died" from "this number was refused", which is why no alert could be written on it. Emit the counter **before** the `call.failed` emit (the listener is async, `emit` is synchronous, and this signal must survive the process dying during the outage that caused it), and never add `tenant_id` to it. The never-answered-timeout path (`endTimedOutCall` → `forceEndCall(..., 'failed')`) was audited and needed no change: it does reach the `calls_total` increment, and deliberately does **not** increment this counter, because the carrier accepted that dial and then went silent. **Only AI-voice dials are instrumented** — static, dequeued-static, IVR and WebRTC/agency each have their own uninstrumented dial `.catch()`, and VoiceLink is the WS-static carrier, so the same TLS failure on a static batch is still invisible. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **`classifyDialFailure` is bounded by source only because the thing that DECIDES the label is source — a value drawn from a closed set is not enough.** Two mistakes, each of which made the page misinformation rather than merely absent, and both are the general lesson. (1) **No telephony adapter attaches an HTTP status to the error it throws** — every one throws a plain `Error` with our template `` `<Provider> <op> error ${status}: ${body}` `` (`plivo.adapter.ts:284`, `twilio.adapter.ts:230`, `voicelink.adapter.ts:207`, …). Reading `err.status` therefore matched nothing and classification fell through to substring-matching the carrier's **response body**, so a real `401` classified `unknown` and paged nobody while a Plivo `400` whose body read `ring_timeout must be an integer` classified `timeout`, entered the infra set and **paged critical with a carrier-unreachable runbook**. Parse the status out of the prefix *we* wrote and RETURN on it; nothing after the colon may decide a label. (2) **The dial `.catch()` is wider than the dial**: `startTelephonyCall` resolves the BYOC credential, writes the row to `initiating` and resolves the SIP trunk first, so a Postgres outage throws `ECONNREFUSED` from `pg` — indistinguishable from the carrier being down by shape alone — and paged on-call to check the carrier during a *database* incident. Only the carrier request is marked (`dialCarrier`/`markCarrierDialFailure`, a `WeakSet` so nothing extra reaches Loki); everything else resolves against our own error **class names** and falls back to `platform`. Names not messages, because `ByocDisabledForTenantError` says "bring-your-own-**credentials**" (read as a rejected carrier key → paged) while `ByocProviderMismatchError` and `ByocNumberForeignTenantError` say nothing matchable (→ `unknown` → no page): one family, opposite verdicts, both wrong. Same trap as the `activity`/`inactivity` marker. (3) **A 4xx is not automatically "this one number".** Collapsing the whole range into `carrier_rejected` — which neither alert covers, deliberately, because bad numbers are ordinary bulk traffic — meant **402** (account out of credit) and **429** (carrier throttling us) could fail every dial on an account indefinitely and page nobody, which is this ticket's own defect reproduced inside its own fix. The systemic statuses are named separately and DO page: 401/403 `credential`, 402 `carrier_balance`, 408 `timeout`, 429 `carrier_throttled`. A systemic **400** is the one case status alone cannot separate from the per-call one and stays unpaged by design — it shows on the panel as a `carrier_rejected` line at the height of the dial rate. Relatedly, **`DialFailureReason` is a closed union and both alert rules match a closed `reason=~` alternation, so a reason added to neither pages nobody forever.** The union is DERIVED from the exported runtime tuple `DIAL_FAILURE_REASONS` (`typeof …[number]`), never declared beside it, because `dial-failure-grafana-contract.test.ts` has to enumerate it — and a hand-written `DialFailureReason[]` literal in the test is assignable however the union grows, so the test stayed green while a new value sat in neither rule. Enumerating the tuple makes that check complete by construction. `carrier_rejected` (one bad number), `caller_id_rejected` and `sip_connection` (one tenant's configuration) are deliberately not paged, and the excuse list is itself checked against the tuple so a rename cannot leave a stale excuse behind. ([call-orchestration.md](docs/architecture/call-orchestration.md))
- **A test whose fixture cannot occur in production reads as coverage and is worse than no test.** The dial-failure suite's HTTP cases were built as `Object.assign(new Error(...), { status: 400 })` — a shape no adapter produces — so they passed green while the live behaviour was the *opposite* of what they asserted (see the bullet above). Same class, one file over: the `METRIC_CALL_OUTCOMES` test iterated the list and asserted `metricCallOutcome(x) === x`, which is tautological and structurally cannot catch the only defect that list can have (a structural outcome MISSING from it, silently collapsing into `other`) — and it duly missed `remote_hangup`. Both are now anchored: adapter fixtures are verbatim strings from `src/`, and the outcome list is a comment-stripped **source audit** that parses the literal `outcome` arguments out of every `handleCallEnd`/`forceEndCall` call site, with a canary assertion so a rename cannot make the whole audit pass vacuously.
- **A counter incremented only in the shutdown path can be alerted on with NEITHER `rate()` NOR `increase()`, and it only reaches the OTLP view at all if the app owns the SDK flush.** Three separate traps, all of which `vao-settlement-fanout-abandoned` hit in turn. (1) The threshold-0 / `for` > window discipline the rate-limit rules document assumes the series keeps being scraped; a shutdown counter increments once and the process then exits, so `rate(m[10m])` stays positive for at most 10m — strictly shorter than a 15m pending period. (2) `increase(m[15m]) > 0`, the obvious correction, is blind for a different reason: Prometheus needs at least **two** samples of a series inside the range before rate/increase produce anything, and this series only ever gets one. Use `max_over_time(m[window]) > 0` — an aggregation, not a rate — which one sample satisfies and which self-clears when that sample ages out. (3) The sample has to exist: `src/instrumentation.ts` must register **no signal handler of its own** (it is the first import in `src/index.ts`, so its listener runs first and its fire-and-forget `sdk.shutdown()` took the meter provider down ~90s before the counter was written), and `src/index.ts` awaits `shutdownOtelSdk()` after the drain and before `process.exit`, with `metricsApp.close()` after the drain too. `test/unit/webhooks/settlement-fanout-wiring.test.ts` pins all of that as a comment-stripped source audit, because none of it is observable behaviourally. Relatedly, an OTel counter exports no series for a label set until its first `add` — and an `add(0)` DOES create it at 0 — so "absence is the healthy state" holds only because `trackWebhookFanoutAbandoned` returns early on a non-positive count; the `:9090` scrape renders the same instrument, so absence is honest on both views. (Under prom-client an unlabelled counter was registered at 0 from construction, which made the two views disagree.)
- **A histogram that deliberately suppresses zero samples describes only its non-zero population, and "tidying" that away silently moves every quantile to the floor.** `end_call_drain_seconds` emits nothing when the `end_call` drain had nothing to wait for, because a flood of 0s would bury the `truncated` tail the metric exists to expose — the case where a caller heard the bot cut itself off. The suppressed population is not simply dropped: it is recorded under `outcome="nothing_queued"` at 0s, so it stays visible without polluting the quantiles of the others. Same trap in the other direction as the unlabelled-counter note above: what a series does NOT contain is part of its definition. (`src/core/call-manager.ts`, `drainCarrierAudio`.)
- **A `max(updated_at)` is only a change detector once it has SETTLED.** `updated_at` is set from `NOW()` — the writing transaction's start — so a write in flight during a read commits with a value at or below the max that read saw, and a consumer comparing stamps calls a changed batch unchanged forever. The status-summary freshness key (`last_updated_by_batch`) therefore reports `null` until a batch's max is `BATCH_FRESHNESS_SETTLE_SECONDS` behind `clock_timestamp()`, and serializes in SQL at microsecond precision. Any new watermark over `updated_at` needs the same two properties, and a table it reads needs the `update_updated_at()` trigger — `telegram_messages` had the column without one until migration 137. ([api-routes.md](docs/architecture/api-routes.md))
- Metric label values are bounded by **source code, never by input** (`alert_key`, `preflightReasonSlug`) — never widen one to carry a message, phone number or tenant id.
- **Retrieval telemetry has exactly one seam.** `search_catalog`, `search_documents` **and both preview routes** record through `recordRetrieval` (`src/knowledge/retrieval-telemetry.ts`); `catalog-search.ts` and `document-search.ts` emit **no** metrics themselves. That split is the whole reason Phase 3 existed — the two tools had drifted into one PostHog event, one tunable confidence floor and one unlabelled counter between them — so re-adding an emission in either module re-creates the defect. The preview routes were the gap this nearly shipped with: pre-Phase-3 both search modules emitted on EVERY invocation, preview included, and moving emission to the tool layer dropped preview traffic silently — leaving the content-gap list blind to exactly the queries a customer generates while TESTING a KB, and leaving the catalog preview emitting nothing at all while the document preview still had `trackKbDocumentPreviewed`. They pass `session: null` (no call → no `retrieval_summary`, no citations) and `cached: false` with **no** `cacheLookup`, since a preview never consults the hot-query cache and a `miss` there would make the hit rate a function of preview usage. Relatedly, `kb_queries_total{kb_type,result}` splits `empty` (ran, matched nothing → a content gap) from `low` (matched below the floor → a threshold), but the **tool result still reports `confidence: 'low'` for zero matches**, because that is what routes the agent to `escalate_to_human`. ([knowledge-bases.md](docs/architecture/knowledge-bases.md))
- **Catalog retrieval is deliberately NOT billed.** `session.kbSearchCount` increments for `search_documents` only (`src/tools/platform-tools.ts`). The epic metered catalogs by stored rows, so extending the per-invocation charge to `search_catalog` would silently start billing customers for something they were never quoted — a pricing decision, not a refactor. The asymmetry is commented at the handler so it does not read as an oversight. ([knowledge-bases.md](docs/architecture/knowledge-bases.md))
- **A rollup/stats write must never block or fail a call.** `recordRetrieval` is fire-and-forget and swallows a DB failure to a `warn`; a rejection must never surface to the caller or become an unhandled rejection. Analytics reads come from `kb_query_stats`/`kb_daily_stats` and **never** scan `calls.retrieval_summary` — that column is per-call detail only, and is omitted from (not nulled into) list responses, since `formatCallResponse` serves both and a `?? null` would tell every list client "no retrieval recorded" for every call in the fleet. ([knowledge-bases.md](docs/architecture/knowledge-bases.md))
- **The hot-query cache key must carry a content generation, and the filters.** Catalogs use `active_version` (an atomic ingest swap rotates it for free); document folders use `kbDocumentRepository.liveGeneration()` (`COUNT : SUM(active_version) : MAX(updated_at)` over live docs) rather than explicit invalidation at approve/reject/delete, because those sites span several files and forgetting one means a **stale answer spoken to a caller** for a full TTL, silently. `category`/`price_min`/`price_max` are part of the key — a cache ignoring them returns confidently wrong answers. **Do not quote ≤60 s as the cross-replica staleness bound for a catalog price.** That 60 s is the ROUTING cache's TTL and covers TUNING; a `PATCH /:id/items` price sync does not move `active_version`, so on a replica that misses the pub/sub the routing entry refreshes to the SAME version, `buildKey` rebuilds the SAME key, and the stale entry serves until `KB_HOT_QUERY_CACHE_TTL_MS` (default 5 min) lapses — 5× the documented figure, and the "confident wrong price" case the module exists to prevent. Exposure is zero today (the cache is opt-in per KB and off by default); closing it properly needs `catalog_items.updated_at` + an index folded into the catalog generation, the way document folders already work. Relatedly, an **ingest version swap does not call `invalidateKbSettings`** and does not need to (the swap rotates `active_version`, which is in the key) — two comments claimed it did. ([knowledge-bases.md](docs/architecture/knowledge-bases.md))
- **`date` (OID 1082) does NOT come back from pg as a string, and `CURRENT_DATE` is not UTC.** No `setTypeParser` is registered, so pg builds a JS `Date` at **local** midnight: measured, `'2026-09-10'::date` → `Date(2026-09-09T18:30:00.000Z)` under `TZ=Asia/Kolkata`, so on a POSITIVE offset — this platform's primary market — the obvious `toISOString().slice(0,10)` reports the PREVIOUS day. Every query behind a `stat_date: string` projects `stat_date::text`. The write side is the mirror image: `stat_date` is written `(now() AT TIME ZONE 'UTC')::date`, never `CURRENT_DATE`, which is the *session* TimeZone's date and would split one UTC day across two rollup rows on a non-UTC connection (measured: `CURRENT_DATE` = 2026-09-11 vs UTC 2026-09-10 under Asia/Kolkata). Both directions are pinned in `test/integration/repositories/kb-stats.repository.test.ts`. ([database.md](docs/architecture/database.md))
- **`kb_query_stats.query_text` is bounded by the retention purge, NOT by the FK cascade.** The column stores normalized caller utterances behind the `capture_query_text` opt-in, and migration 120 justified that on the text being "retention-bounded". The obvious mechanism is not the one that works: `knowledge_bases` cascades on delete, but `DELETE /:id` is a **soft** delete that deliberately keeps these rows, so the cascade never fires. Both rollups are therefore `PURGE_TARGETS` in `src/maintenance/retention-purge.ts`, keyed on `stat_date`. Two consequences to preserve: the cutoff must be reduced with an explicit `($1::timestamptz AT TIME ZONE 'UTC')::date` — a bare `$1::timestamptz::date` uses the SESSION TimeZone and on a positive offset resolves to the NEXT day, purging a day early (measured: a 20:00Z cutoff → 2026-09-11 vs UTC 2026-09-10) — and turning the opt-in OFF deliberately does **not** erase what was already collected (`recordQuery`'s `COALESCE`), while the analytics read masks it; retention is what makes that survival bounded rather than permanent. ([audit-retention.md](docs/architecture/audit-retention.md))
- **`GET /:id/analytics` returns `daily` DENSE** — exactly one bucket per day in `[from, to]`, zero-filled, via `generate_series` LEFT JOIN in `listDaily`. It is a cross-repo contract, not a cosmetic choice: the SPA's trend chart is index-banded (`bandWidth = PLOT_W / points.length`), so a sparse series draws scattered days ADJACENT rather than leaving gaps, silently relabelling three days of a month as three consecutive days. The scope predicates therefore live in the JOIN's **ON** clause — moved to a `WHERE` they filter the null-extended rows back out and restore the sparse behaviour while every test about ordering and endpoints still passes. ([database.md](docs/architecture/database.md))
- **A de-dup key must reproduce its statement's ON CONFLICT key exactly.** `dedupeByExternalId`'s default `keyOf` is `external_id` alone, which is safe only because both callers scope one statement to a single KB and a single version; the real conflict key is `(knowledge_base_id, version, external_id)`, so `insertBatch` passes the full triple. A key **narrower** than the conflict key does not fail loudly — it silently DROPS rows that would never have collided. ([knowledge-bases.md](docs/architecture/knowledge-bases.md))

**Scoping & conventions**

- A prompt slug is a lineage key only because `create()` now **refuses a slug that already has an active row** — `prompt_templates_active_slug_version_uniq` is partial (`WHERE is_active`) and only rejects a second row at version 1, so it goes blind once the incumbent is edited to v2+. `update()` allocates `MAX(version)+1` across the slug under a `FOR UPDATE` lock (`existing.version + 1` collides with a second lineage and 409s that script's save permanently), and that allocation is exactly what makes a shared slug dangerous rather than merely untidy: the newer lineage out-versions the older one, so `findActiveSuccessor`/`findBySlug` start answering with the wrong script. Hence `findActiveSuccessor` returns null when a slug has more than one active row. ([prompts.md](docs/architecture/prompts.md))
- **Every paginated list's `ORDER BY` must end in a unique key (`id`), or `LIMIT/OFFSET` pages overlap and skip while the fetched count still equals `total`.** `created_at` is not unique: `callRepository.createBatch` is one multi-row INSERT and `NOW()` is transaction-start time, so a whole dispatch chunk ties — and any order among tied rows is legal and can differ per query. It does differ, **with no writes at all**: a sort under `LIMIT n OFFSET k` is a top-N heapsort bounded at `n + k`, so the bound, and the order it leaves the ties in, changes every page; UPDATEs moving tuples and plan changes are further causes. The omissions and duplicates are deterministic, so a re-pull does not recover them. An 8,232-call export lost ~194 calls this way, and master's Retry pages `failed` calls over the same ordering (skipped numbers, or numbers dialled twice). `buildOrderByClause` guarantees it on every branch — the **default** included, which is the one Utils, Retry and the UI actually take — and takes a structured `DefaultSort` (`NEWEST_FIRST`/`OLDEST_FIRST`) rather than a string so a default cannot omit the tiebreak or forget the join prefix (`sc.id`, not a 42702-ambiguous `id`). Never hand-write `ORDER BY created_at … LIMIT … OFFSET`; use the helper or `stableOrderBy`. Pinned by a source audit (`test/unit/db/paginated-order-total.test.ts`) and against real Postgres (`test/integration/repositories/paginated-order-total.test.ts`, which also shows the old ordering failing). ([database.md](docs/architecture/database.md))
- Every resource table carries `tenant_id` **and** `account_id`; both headers are required on `/api/v1/*`. The deliberate exceptions are `alert_channels` / `alert_definitions` (operator infrastructure).
- PR titles must be conventional-commit form — they drive the automatic semantic-release version bump.

**Audio clip cache**

- `readTtsPcm` hardcodes a 44-byte header and is **not** a WAV parser; anything produced by an external tool must go through `parseWavPcm16`. Every producer writing the shared cache goes through `toTelephonyClip`, and clip deletion is reference-counted (clips are content-addressed and shared across batches). ([announcements-static-calls.md](docs/architecture/announcements-static-calls.md))

## Key patterns

- **Zod everywhere**: config validation, API request/response schemas (`src/api/validators/`)
- **Reusable caching primitives**: `src/utils/single-flight.ts` (`SingleFlight` — coalesces concurrent identical async work by key; results never memoized, failures never sticky) and `src/utils/ttl-cache.ts` (`TtlCache` — in-process read-through cache with lazy TTL expiry, LRU `maxEntries` bound, `getOrLoad` single-flight, negative caching; errors never cached; **invalidation-race safe** — a load that started before a concurrent `set`/`invalidate`/`clear` for its key is not written back on completion, via a per-load token, so a stale in-flight read can't resurrect a revoked/updated value). These generalize the ad-hoc `Map`+TTL registries the codebase grew organically. Consumers: the auth-lookup cache (`api-key-cache.ts`); the `account_settings` row cache (`account-settings.repository.ts` — one cached read per `(tenant, account)` backing the per-call `allow_recording`/`analyze_calls`/`default_ai_pipeline` reads, write-through on `upsert`; **`getMaxConcurrentCalls` deliberately bypasses it** and reads the DB directly, because the concurrency guard fronts the limit with its own cross-replica Redis cache and a stale in-process row would re-poison that Redis cache after `invalidateLimit`); and TTS synthesis single-flight (`tts-generator.ts` — a shared-text bulk batch synthesizes each distinct clip once instead of once per concurrent worker). In-process, so a value is stale by ≤ one TTL across replicas — pair a short TTL with explicit invalidation on the writing replica (same trade-off as the existing 60s registries). `allow_recording` (a recording-consent gate) therefore has ≤ one-TTL cross-replica propagation lag on non-writing replicas; the writing replica is immediate via write-through.
- **Rate limiting** (`src/api/middleware/rate-limit.middleware.ts`): `@fastify/rate-limit` **Redis-backed** when a client is available, so the budget is enforced **cluster-wide** (not per-replica — N replicas previously meant an effective `max×N`). `max`/`timeWindow` are env-tunable (`RATE_LIMIT_MAX` default 200, `RATE_LIMIT_WINDOW` default `1 minute`) precisely because the shared store lowers the effective ceiling; size `RATE_LIMIT_MAX` to real aggregate peak, not one replica's. Key is `${tenant}:${sha256(apiKey)}` (or client IP) — never the raw secret in Redis. **Unauthenticated provider webhooks (`/api/v1/webhooks/*`) get their own bucket (`wh:<ip>`) and their own higher ceiling** (`RATE_LIMIT_WEBHOOK_MAX`, default 1000), because they carry no tenant/API-key headers and a carrier delivers every callback for every call from the same handful of IPs — so one dial batch's lifecycle traffic used to land in a single tenant-API-sized bucket. On 2026-09-03 a ~3k-call VoiceLink static batch sustained ~220 webhooks/min against the 200/min ceiling and had **17.5k status callbacks rejected with 429**, and since a carrier retries a rejected delivery the breach fed itself; the knock-on was that retries arriving after the WS-static webhook token's 180s TTL were then refused `invalid_token`. **The token was not what lost the disposition, though** — `WEBHOOK_RECONCILE_TIMEOUT_SECONDS` (30s from playback-complete) shuts around dial+45–75s once the lead has left VoiceLink's outbound queue (minutes later under a backlog), well inside even the old 180s token, so a late callback lands in `persistLateTerminal` regardless of token validity. Recovering the carrier's reason therefore took both halves: a token that outlives the retry schedule (now 1800s; the *media* token is sized from dispatch to cover the carrier pickup window, ring grace and announcement — 900s — see `QUEUED_DIAL_PICKUP_TIMEOUT_SECONDS`) **and** `persistLateTerminal` actually recording `error_message` — it previously wrote `provider_call_id` and nothing else, so a longer TTL alone would only have converted a 403 into a 200 that still persisted no outcome. It deliberately never rewrites `status`/`duration_seconds`, which settlement has already been dispatched against, and it writes the reason through `staticCallRepository.setErrorMessageIfAbsent` rather than the generic `update()`. Three guards, in two places for a reason: `error_message IS NULL` and `status <> 'completed'` are **SQL predicates**, because this path runs on replicas that do *not* own the call (sessions are per-process, so ~(R−1)/R of every terminal webhook lands here) and a read-then-write loses the race against the owning replica's own settle — clobbering a specific media-failure message, or annotating a row the owner just completed. The third guard cannot be SQL and sits in the caller: the **carrier's verdict is classified first** (`classifyVoicelinkOutcome`), so an answered call is never annotated at all. Gating on the row's status alone is not enough there — on a non-owning replica the row is typically still `in_progress` when the callback lands, so a row-status check sees "not completed" and stamps a call the owner settles `completed` a moment later, which `writeTerminalWithRetry` does not clear. The wording would also be actively wrong: VoiceLink reuses Q.850 cause 16 for answered calls, so a perfectly good call would read "16 - Normal Clearing". The **namespacing is what makes a per-request `max` sound** — the plugin keeps one counter per key, so without it whichever request tripped the limit would decide which ceiling applied. Note the ceiling still scales with dial rate: **raising per-account concurrency requires raising `RATE_LIMIT_WEBHOOK_MAX` with it.**

  **The bucket decision is now one predicate, `budgetFor(request)`, and every carrier-facing surface has its own namespace.** `usesWebhookBudget()` covered `/api/v1/webhooks/*` only, which left every *other* unauthenticated route sharing one plain `<ip>` bucket at `RATE_LIMIT_MAX` — the identical failure mode, one door along. `budgetFor` returns the bucket kind and `keyGenerator`, `max` **and** `allowList` all derive from it, so a request's key, its ceiling and its exemption can never disagree; the regression test asserts *webhook ceiling iff `wh:` key* across every auth/path combination, and that invariant is the thing to extend rather than adding a parallel decision path. Order inside it is load-bearing: exempt first (a probe is never limited whatever headers it carries), then the API key (the narrowest key available — a shared IP is the whole problem), then the paths.

  | bucket | key | ceiling | why separate |
  | --- | --- | --- | --- |
  | `webhook` | `wh:<ip>` | `RATE_LIMIT_WEBHOOK_MAX` (1000) | Scales with dial rate; a rejected callback is retried, so a breach amplifies |
  | `carrier_media` | `cm:<ip>` | `RATE_LIMIT_CARRIER_MEDIA_MAX` (600) | Same carrier IPs, but a 429 on a WS upgrade is **dead air on a live call**, not a retryable failure — it must not be exhaustible by a webhook storm |
  | `internal` | `int:<ip>` | `RATE_LIMIT_INTERNAL_MAX` (1000) | magick-master authenticates with `Authorization: Bearer`, not `x-api-key`, so its whole fleet keyed on **one egress IP** at the tenant ceiling — and master retries |
  | `tenant` | `<tenant>:<sha256(key)>` | `RATE_LIMIT_MAX` (200) | Per tenant-key, so one tenant can't exhaust another's |
  | `ip` | `<ip>` | `RATE_LIMIT_MAX` (200) | Everything else unauthenticated |
  | `exempt` | not limited | — | `/health`, `/ready` (**exact** paths — a prefix match would leave `/health/<junk>`, an arbitrary-volume 404 path, as the one uncapped surface) — a 429 there fails the readiness gate, i.e. the limiter causes the outage it exists to prevent |

  `carrier_media` covers `/api/v1/media-stream/*` (the WS-static route nests beneath it), the legacy `/api/v1/static-media-stream/*`, `/api/v1/tts-audio/*`, and — matched on a **suffix** under an otherwise-authenticated parent, which no prefix can express — the two WebRTC bridge legs `/api/v1/webrtc-call/:id/{pstn,browser}-stream` (registered unauthenticated at the plugin root; `pstn-stream` is dialled by VoBiz from the same egress IPs as the webhooks). **What is deliberately still shared** on the plain `ip` bucket, recorded rather than left implicit: `/api/v1/recordings/:id` and `/api/v1/webrtc-recordings/:id` (unauthenticated but signed-token, one fetch per playback), all of `/api/v1/browser-call/*`, and `/api/v1/metadata`. Those are browser-IP traffic rather than one carrier's egress, so a shared per-IP budget is the correct shape for them; revisit if a browser surface ever fans in through a proxy. Those three are **one** bucket because they scale with the same dial rate from the same carrier on the same call, so splitting them further removes no cross-purpose risk — unlike the split from the self-amplifying webhook stream, which does. Two consequences are accepted rather than overlooked: a media upgrade can still be starved by clip fetches on its own batch (~2 requests/call against 600/min ≈ 6.8× headroom at the observed ~44 calls/min), and `/api/v1/tts-audio/:hash` — unauthenticated **and** not token-gated — moves from 200/min to 600/min. `/internal/*` is classified on the **path**, deliberately not on the presence of `Authorization: Bearer`: reading the header would repeat the original mistake one level up, since a request that forgot it would silently land in a bucket other than the one the route serves. `/health` + `/ready` are exempted through the shared predicate rather than per-route `config: { rateLimit: false }`, so the exemption stays visible where every other bucket decision is made. **The exemption also changes readiness semantics, which is worth knowing before the next Redis incident:** `skipOnError` is left at its default `false`, so a store error makes the limiter throw a 500 — and before the exemption that 500 landed on `/ready` and failed the readiness gate. It no longer does, and `/ready` does not itself check Redis, so a Redis outage now has every replica reporting ready while real traffic 500s. That accidental signal was not worth keeping at the price of 429ing a probe, but its replacement (either `skipOnError: true`, so a store failure degrades the limiter to unlimited instead of 500ing the fleet, or a real Redis check on `/ready`) is a deliberate change of its own and is not made here. (`/metrics` needs no entry — it is served by a separate Fastify instance on the metrics port, which never registers the plugin.)

  **`rate_limit_rejected_total{bucket_kind,route_class}` is the 429 counter, and its absence is what made the incident invisible.** There was previously no 429 telemetry at all — no `onExceeded` hook, no counter, no Grafana rule — so 17.5k rejections were found only by log archaeology on `component=error-handler` warn lines, and the new ceiling scaling with dial rate meant the next capacity increase could re-breach it just as silently. It is emitted from `@fastify/rate-limit`'s **`onExceeded`** hook, which fires exactly once per rejected request, immediately before the 429 is thrown, and is idempotent per request via the plugin's `rateLimitRan` latch — so it counts real rejections rather than something inferred from the error handler, which would also pick up 429s raised elsewhere. It is **not** `onExceeding`: that fires on every request that is *not* exceeded, making it an allowed-request hook rather than a rejection signal. The hook body is try/caught on top of `safeEmit`, because the plugin awaits it inside the request path and a throw there would serve a 500 in place of the intended 429. `bucket_kind` comes from the same `budgetFor` call that charged the bucket, so it cannot drift from the ceiling in effect. One OTel counter, written once behind its own `safeEmit` guard (see *Metrics* under Key patterns) — so there is no second, scrape-only copy that could be the one written while the alertable one is not, the trap `gemini_backend_breaker_open` fell into. `route_class` is a **bounded, code-owned slug** (`RATE_LIMIT_ROUTE_CLASSES`, an ordered prefix table mirroring the registration prefixes in `src/index.ts`, first match wins), never a URL: the routes that actually get 429'd carry `:callId`, `:staticCallId` and a `?token=`, so labelling on `request.url` would mint a series per call *and* put a live credential in the metric store. `request.routeOptions.url` — the matched pattern, which `api_requests_total` records through `routeMetricLabel` (unmatched requests collapse to `/__unmatched__`) — was also rejected here: it multiplies ~250 patterns by the bucket kinds. Tenant/account ids are excluded as on the other hot-path counters (a `tenant`-bucket series per customer); identify the client from the request logs instead. The bulk-dispatch surfaces (`static_calls`, `ivr_calls`, `agency`) get their own classes rather than falling into the `api` catch-all, because "a batch dispatch is being refused" and "a CRUD read is being refused" are different operator actions. **Two properties of IP keying bound what any of this can promise, and neither is introduced by the namespaces:** classification happens in `onRequest`, *before* auth, so an unauthenticated caller can reach the `int:`/`cm:` ceilings and one IP's total allowance is the SUM of the ceilings (~2800/min at the defaults) rather than `RATE_LIMIT_MAX` — the loosest surface in that sum being the unauthenticated, un-token-gated `/api/v1/tts-audio/:hash`; and the app sets `trustProxy: true`, so `request.ip` is client-controlled and a hostile client can evade every IP-keyed bucket by rotating `X-Forwarded-For` (which also means `bucket_kind="ip"` can never rise for one). Making `int:` genuinely master-only would mean assigning the bucket in a post-auth hook, and bounding `trustProxy` to the real proxy hop is a separate change; both are follow-ups, not claims this closes. **Alerts as code:** `vao-rate-limit-infra-rejected` (critical, `bucket_kind=~"webhook|carrier_media|internal"`, threshold 0 — those clients cannot back off, so any *ongoing* rejection is data loss, and its runbook line points at `RATE_LIMIT_WEBHOOK_MAX` and its lockstep dependence on per-account concurrency) and `vao-rate-limit-tenant-rejected` (warning, `tenant|ip`, >1/s — an occasional tenant 429 is the limiter working). **A threshold of zero only means "sustained" if the pending period is STRICTLY LONGER than the rate window**, which is the easy thing to get wrong here: `rate(m[10m])` stays positive at every evaluation for a full 10m after one increment, so `for: 5m` would have paged critical on a single stray 429. Hence `for` 15m over `[10m]`, and 30m over `[15m]`; do not "tighten" either towards its window, since `for` == window sits on the boundary that `vao-gemini-all-backends-down` already documents as unreliable in the other direction. Both `no_data_state = "OK"`, deliberately: no 429s means the series is *absent*, which is the healthy state. Both counters plus the token-rejection series are charted on the dashboard's **Rate Limiting & Late Carrier Callbacks** row — an alert names a breach, it is not an exploration surface.

  **Companion signals on the WS-static terminal path.** `ws_static_late_terminal_total{provider,cause}` splits the terminal webhooks landing in `persistLateTerminal` with no live session into the populations that path documents — `non_owning_replica` (sessions are per-process, so ~(R−1)/R of *every* terminal webhook across R replicas; the dominant and entirely benign case), `locally_settled` (the **first** carrier account of a call we settled on our own clock) and `duplicate_delivery` (a **retried** delivery — **a spike here is the signature of a carrier retry storm**, which is what a 429 wave produces) — plus `unknown_call` (token verified, row gone; should be ~0). A counter rather than log counting precisely because the benign case is webhook-volume-bound and buries the other two. **`duplicate_delivery` is keyed on the (call, EVENT) pair and takes priority over the settle-derived labels; both halves were got wrong in turn, and each mistake killed the signal from a different side.** Classifying purely on how the call *settled* left it near-unreachable — VoiceLink reports at dial+45–75s (measured from when the carrier actually dials, not from `add_lead` — see the pickup window in `docs/architecture/announcements-static-calls.md`), i.e. after the 30s reconcile window has shut, so the first terminal webhook normally arrives on this path rather than the reconciling one, and every retry read as another `locally_settled`, inflating N-fold the label documented as "the only account we will ever get". Then keying the fix on the *call* alone over-fired it: **VoiceLink emits two distinct terminal events per call** (`call.ended`, then ~30 s later `call.completed` carrying the final disposition — only the latter has `callStatus`), so the healthy follow-up counted as a duplicate on every call, and a constant baseline hides a real storm as effectively as a silent zero. That follow-up is `carrier_settled` (first sighting of a *different* terminal event on a call the reconciling path already settled) — benign, and deliberately not folded into `duplicate_delivery`. Read `locally_settled` for this carrier as a **level**, not an anomaly. The cause comes from a bounded per-replica ledger (`TERMINAL_LEDGER_MAX` = 20 000, oldest-first eviction) that records every accounted delivery, not just this replica's own settles — so it is sized for the whole terminal-webhook stream (~3 100 keys per replica for a 3 100-call batch across 2 replicas). Overflow, a restart, and the dequeue-path dial failure that settles via `unregister` rather than `finalize` all degrade a label to `non_owning_replica` — the conservative direction, since the ledger can forget a call but can never invent that we handled one. The duplicate count is also a **floor, not a census**: deliveries #1 and #2 of one event can land on different replicas, each seeing a first sighting. Treat the labels as a rate signal, not an audit trail. `ws_static_events_total{event="webhook_token_rejected"}` counts the `403 invalid_token` rejections: 93 of those in the incident were a *downstream symptom* of the 429 storm (a rejected delivery is retried, and the retry outlived the then-180s token), so a rise correlating with `rate_limit_rejected_total{bucket_kind="webhook"}` is the tell that the ceiling is breached and the retries are now arriving too late to record anything either. Caveat when reading it: token verification is fail-closed on an **absent Redis client and on a Redis error** too, not only on a stale token, so a Redis incident spikes it with no 429s anywhere and inverts that correlation.

- **Metrics — one declaration, one write**: every metric in `src/utils/metrics.ts` is ONE OTel instrument, declared through a facade in `src/utils/metric-instruments.ts` (`counter<'a' | 'b'>(meter, name, …)` / `histogram` / `gauge` / `observableGauge`; the type argument is the attribute-key contract) and written once. prom-client is gone. The `:9090` scrape is rendered from the SAME meter provider (`renderPrometheusScrape` in `src/utils/otel-sdk-config.ts`, `@opentelemetry/exporter-prometheus`'s serializer, reached through the import-free seam `src/utils/metrics-scrape.ts`): with OTLP on, it serves the batch the one `PeriodicExportingMetricReader` **last exported** (`LastExportedMetrics`, recorded by the `withFreshGauges` exporter wrapper; `renderLastExportScrape`) and never collects — so it is up to one export interval stale (60s default; counters/histograms exact as of that export) and comment-only before the first export. **A collection is NOT side-effect free**, whatever the temporality: it runs every observable callback, and runtime-node's `eventLoopDelayCollector` resets its histogram on observe while `eventLoopUtilizationCollector` diffs against its last reading, so a scrape-time `collect()` of the OTLP reader stole the interval from the next export (a 2.5s stall, one curl of `:9090`, and Grafana Cloud read max=0). Never reintroduce `renderPrometheusScrape(otlpReader)`, and do **not** add a second `MetricReader`, which doubles every instrument's storage work and, unscraped, accumulates unbounded. With OTLP off, `instrumentation.ts` installs a scrape-only `ScrapeMetricReader` and `renderPrometheusScrape` collects it on demand (nothing else reads it, so there is no export to disturb). Invariants: (1) what Grafana Cloud receives — names, kinds, attribute keys, descriptions, units, buckets — is pinned by `test/unit/utils/metrics-otlp-contract.test.ts` against `test/fixtures/metrics/otlp-instruments.json`; a deliberate change updates the fixture in the same commit and says which series it terminates; (2) gauges are exported with **DELTA** temporality (`freshGaugeTemporality` / `withFreshGauges`) because the SDK's cumulative path re-exports a label set its callback stopped observing, frozen at its last value, forever — expiry and a gauge's `reset()` only work because of this, and the visible consequence in Grafana Cloud is that a removed/expired gauge label set goes ABSENT from the next export instead of repeating a frozen last value (a deliberate behaviour change: a query that relied on a gauge sticking now sees a gap — `grafana/README.md`); (3) the LastValue aggregator keeps the sample with the later `Date.now()` timestamp (`LastValueAccumulation.record` stamps `millisToHrTime(Date.now())` in sdk-metrics 2.6 — not `hrTime()`/the performance clock), so a suite that fakes timers must start its fake clock in the past (`vi.setSystemTime(Date.now() - 10 * 60_000)`) or a real-clock sample from earlier wins; (4) a suite that needs a value read back uses `installMetricReader()` from `test/helpers/otel-metric-reader.ts` inside a `vi.hoisted` block (the meter is taken at `metrics.ts` load and `@opentelemetry/api` 1.9 has no proxy provider, so installing it later binds nothing).

Manual spans via `src/utils/tracing.ts` (`withSpan()`, `startSpan()`). `@Traced` decorator wraps async class methods in OTel spans with static/dynamic attributes — use `Traced.getSpan(this)` inside decorated methods to add runtime attributes. Only active when `OTEL_ENABLED=true` + `OTEL_EXPORTER_OTLP_ENDPOINT` set. Forces `http/protobuf` protocol (Grafana Cloud doesn't support gRPC). Its testable pieces live in `src/utils/otel-sdk-config.ts` (import-free — never `src/config`): the **60s** default export interval (`OTEL_METRICS_EXPORT_INTERVAL_MS`; Grafana Cloud bills DPM above 1/min/series, so 30s was ~2×, and one sample per minute empties a `[$__rate_interval]` panel at the datasource's 15s default scrape interval, so every Prometheus query in the committed dashboard pins a `1m` **Min step** (target `interval`, not the panel's Min interval, which Grafana ignores for that term) — `grafana/README.md`), the metric **drop views** (every auto-instrumentation metric, incl. `gen_ai.*`, which leaked until 2026-09-29) and a ~4-series Node runtime allow-list. **An allow-listed instrument must match NO drop view** — views have one `*` and no negation, and when two views match, the first registered wins and a sync instrument double-records — so the `nodejs.*` family is enumerated, not wildcarded; `otel-sdk-config.test.ts` pins it against the real SDK. **No `service.instance.id` by default**, so all replicas write one series in Grafana Cloud (gauges last-writer-wins, multi-replica counters read as resets); `OTEL_SERVICE_INSTANCE_ID_ENABLED=true` fixes it at ×replicas series — enable only after verifying headroom, and never alongside `OTEL_NODE_RESOURCE_DETECTORS=all|serviceinstance`, whose random per-process UUID merges OVER the hostname-based id and churns every series on each restart (rollout at the end of [call-orchestration.md](docs/architecture/call-orchestration.md)).
- **Audio utilities**: mu-law codec and PCM16 resampling in `src/utils/audio.ts`
- **Graceful shutdown**: `src/index.ts` waits up to 60s for active calls, drains the settlement fan-out, flushes the audit buffer, and only then flushes + shuts down the OTel SDK, closes the metrics server and exits. One shared shutdown promise (a repeat SIGTERM/SIGINT joins it) and a `finally` around the exit, so no step's rejection can leave the process alive with the shutdown latched; each step is individually wrapped so one failure cannot skip the settlement drain

## API routes

All authenticated routes under `/api/v1/` require both `x-mgkvc-tenant` and `x-mgkvc-account`
headers. Internal S2S routes under `/internal/` are protected by `INTERNAL_S2S_TOKEN`.
Unauthenticated: `webhooks` (telephony callbacks + static/IVR webhooks), `media-stream`
(WebSocket audio), `browser-call` (test client), `tts-audio`, `metadata`. Health at `/health`
and `/ready`. Call API responses include `error_code` / `error_message` when a call fails.

**The full route reference — every path, its semantics, status codes and auth mode — is in
[`docs/architecture/api-routes.md`](docs/architecture/api-routes.md).** Read it before adding
or changing a route; several routes have non-obvious contracts (202-vs-200 semantics, tri-state
PATCH fields, deliberately ungated reads).

## Custom Commands & Agents

Reusable slash commands and agents are available on a need basis. Use them when the task matches — don't force them into unrelated work.

### Slash Commands

**`/project:next-migration <name>`** — Creates the next sequentially-numbered SQL migration file with the project's standard template (tenant/account scoping, UUID PKs, timestamps, triggers). Use when adding a new DB table or altering schema. Example: `/project:next-migration user_preferences`.

**`/project:typecheck-all`** — Runs `tsc --noEmit` across all three Sapionic projects (magic-voice-core, magick-master, magick-comms-cusui) in parallel. Use after cross-service changes to catch type errors before committing. Reports pass/fail per project with error summaries.

**`/project:git-status-all`** — Shows git branch, uncommitted changes, and last 3 commits for all three repos in a summary table. Use to get a quick overview of work-in-progress across the platform before starting a session or before committing.

### Planning & Coordination

**`/project:cross-service-feature <feature description>`** — Plans a feature that spans multiple services. Identifies which layers are affected in each repo (DB, model, repository, validator, routes, UI), determines the correct implementation order (core -> master -> cusui), maps integration points (proxy, webhooks, credits, scheduling), and produces an implementation checklist. Use this **before** starting any feature that touches more than one repo.

### Agents (Analysis & Implementation)

**`/project:cross-service-implementer <feature description>`** — Implements a feature end-to-end across core, master, and cusui in dependency order. Follows each project's exact patterns (auth, RBAC, credit billing, CSS conventions). Use when you have a clear feature spec and want autonomous multi-repo implementation with verification at each phase.

**`/project:test-gap-analyzer <module or feature>`** — Analyzes a module and identifies untested code paths. Cross-references source exports against test cases, checks for missing edge cases, and produces a prioritized gap report. Can generate the missing tests. Use after completing a feature to verify coverage, or pass `all` to scan the entire project.

**`/project:migration-reviewer <migration file>`** — Reviews a SQL migration against project conventions: tenant/account scoping, indexes, triggers, naming, safety (no DROP without confirmation, NOT NULL with defaults), and rollback feasibility. Use before running `migrate:up` on any new migration. If no file is specified, reviews all uncommitted migrations.

**`/project:webhook-flow-tracer <flow name>`** — Traces an async webhook/event flow hop-by-hop across all services. Maps dispatch points, handlers, error handling, HMAC signing, and retry behavior. Identifies gaps like missing handlers, unsigned webhooks, or credit leaks. Use when debugging async flows or adding new webhook-driven features. Example: `/project:webhook-flow-tracer call completion`.
