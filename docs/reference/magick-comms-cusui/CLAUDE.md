# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

MagickVoice Customer UI — a React SPA for the MagickVoice voice AI platform. Provides Firebase-authenticated access to voice calls, credit management, team admin, IVR workflow building, and a super-admin panel.

## Prerequisites

- Node.js >= 20 (22 recommended), npm >= 10
- Magick Master Platform Service running at `http://localhost:3010`
- Firebase project with Email/Password + Google auth enabled

### CI Pipeline

GitHub Actions (`.github/workflows/ci.yml`) runs on all PRs and pushes to main:
- **Lint & Test** — `npm run lint` (type check) + `npm test` (Vitest)
- **Build** — production build with placeholder env vars to verify compilation

Both jobs must pass before merging.

### Versioning & Releases

Versioning is **automated** via [semantic-release](https://github.com/semantic-release/semantic-release) (`.github/workflows/release.yml`, config in `.releaserc.json`). On every push to `main` (i.e. each PR merge), it inspects the conventional-commit / PR titles since the last release and:

- Bumps the semver in `package.json` (`feat` → minor, `fix`/`perf`/`refactor`/`ux`/`revert` → patch, `feat!` or `BREAKING CHANGE` → major; `docs`/`chore`/`test`/`ci`/`build`/`style` → no release)
- Regenerates `CHANGELOG.md`
- Commits the bump back to `main` as `chore(release): X.Y.Z [skip ci]`
- Creates a git tag `vX.Y.Z` and a GitHub Release with auto-generated notes

**Because PR titles become the squash-merge commit subject, PR titles must follow [Conventional Commits](https://www.conventionalcommits.org/)** (e.g. `feat(calls): add voice selection`) for the version to advance correctly. The release commit is marked `[skip ci]` so it doesn't trigger another release.

**Always append the originating ticket ID at the end of the PR title when one is provided**, in parentheses — e.g. `fix: add info about 100-number limitation (#8ygjekeb2)`. Omit it only when no ticket is associated with the change.

The current version is surfaced in the UI sidebar footer. It's injected at build time via the `__APP_VERSION__` global (`vite.config.ts` `define`, declared in `src/vite-env.d.ts`) sourced from `package.json`.

## Architecture

### Two Auth Systems

1. **Regular users** — Firebase Auth (email/password + Google). After Firebase sign-in, the UI calls `POST /auth/session` to create a platform session. Auth state lives in `AuthContext`, tenant selection in `TenantContext`, account selection in `TenantContext.accountId`.
2. **Super admins** — Direct email/password login via `POST /super-admin/login` (no Firebase). JWT stored in `sessionStorage`. Auth state in `SuperAdminContext`.

These are completely independent auth flows with separate contexts, API modules, layouts, and route trees.

**System 1 has TWO front doors, which is not a third auth system.** `/login` serves the platform; `/agency/login` serves the Agency Dialer. Same Firebase SDK, same `POST /auth/session`, same session and memberships — agency staff are ordinary users whose RBAC role is what makes them an agent or a supervisor. The agency door differs in having no signup (an `is_new` session there is a *failure*: `POST /auth/session` provisions a tenant for an unrecognised address, so a signup strands an invited agent in an empty tenant of their own), in defaulting to `/agency` so `AgencyHomeRedirect` resolves the persona, and in forwarding an already-signed-in visitor rather than showing a form.

**Which door somebody is sent to is decided by the DESTINATION, not by a role** — at the moment `RequireAuth` or a 401 handler runs there is no session to read a role from. `loginPathFor` in `src/utils/returnPath.ts` owns that rule (`/agency`, `/dialer`, `/station` → the agency door), and four call sites use it: `RequireAuth`, `sessionExpiredLoginUrl`, and the 401 guards in `api/client.ts` and `AuthContext`. **Anything that asks "am I on a login page?" must use `isLoginPath`, never `pathname.startsWith('/login')`** — the latter is `false` for `/agency/login`, which is how both 401 guards silently lost their loop protection when the second door was added.

### Tenant + Account Selection

`TenantSwitcher` and `AccountSwitcher` in the TopBar allow switching active tenant and account. Both persist to localStorage. All data hooks guard on `if (!tenantId || !accountId) return;` — no data fetches until both are set. Switching account reloads all data via `useCallback` dependency arrays.

### API Layer Pattern

All backend calls go through `src/api/client.ts` → `apiFetch()`, which auto-injects `Authorization: Bearer <token>`, `X-Tenant-Id`, and `X-Account-Id` headers. Each domain has its own API module in `src/api/` and a corresponding React hook in `src/hooks/` that fetches on mount and returns `{ data, loading, error, refetch }`. All hooks pass both `tenantId` and `accountId` to API functions.

Super admin API calls (`src/api/super-admin.ts`) bypass `apiFetch()` and use their own fetch wrapper with the super admin JWT from `sessionStorage`.

### Error Handling & Masked Errors

The platform service **masks internal/upstream error detail** before it reaches the client (see magick-master#119). Masked responses use a generic body (`{ error: "Internal Error" | "Request Failed", message, statusCode, requestId }`) and echo the correlation id in the `x-request-id` header on every response. **Validation errors (`details`/`fieldErrors`) and our own business 4xx (insufficient credits, permissions) still arrive in their original shape and render unchanged** — only internal/provider detail is hidden.

Error helpers live in `src/utils/errors.ts` (the single source of truth for the masking contract — `isMaskedErrorBody`, `getErrorMessage`, `getRequestId`, etc.). `ApiError` (and `saFetch`/raw-`fetch` paths via `toFetchError`) capture the `requestId` (header preferred) and, **for masked errors only**, embed it in the error message via `appendRequestId`. Because data hooks reduce errors to a `message` string, this lets the id survive to the display layer with no call-site churn: the shared primitives `ErrorAlert` and `Toast` call `splitRequestId` and render the id as a copyable `RequestId` chip. Prefer `useToast().showErrorToast(err, fallback)` over `showToast(err.message, 'error')` for error toasts. **Never parse raw core/provider error text out of a response body** — it's no longer present.

### Endpoint Config

All API endpoints are centralized in `src/config.ts` under `ENDPOINTS`. This is the single source of truth for URL construction — never hardcode API paths elsewhere. TTS language/voice options are defined as `TTS_LANGUAGES` in the same file (29 VoBiz-supported languages with locale codes and available voices).

### RBAC

Client-side role checks use `src/utils/permissions.ts`. Roles: `viewer(10) < operator(20) < account_admin(30) < tenant_admin(40) < tenant_owner(50)`. The `usePermission` hook and `hasPermission()` utility gate UI elements. The `Permission` type enumerates all checked permissions.

### Product Analytics (PostHog)

PostHog is wrapped in `src/analytics/posthog.ts` — a fail-safe layer that is a complete no-op unless `VITE_POSTHOG_KEY` is set, so analytics can never break the app or dev without a key. Identity mirrors the backend: `distinct_id = user.id` with `tenant` and `account` group profiles (`usePostHogIdentify` wires this up, including group-level org properties and the user's `role` as a person property). The active tenant/account id **and name** are also registered as super properties (`tenant_id`/`tenant_name`/`account_id`/`account_name`), so every event carries readable org context without threading it through call sites.

**Never call `posthog.capture()` directly.** All custom events go through the typed catalog in `src/analytics/events.ts` — one `track*()` emitter per event, each with an explicit, PII-free property shape (IDs / enum labels / counts / booleans only — never bodies, emails, phone numbers, or contact data). Add new events there rather than scattering string literals. Autocapture handles pageviews, rage clicks, and dead clicks automatically.

Feature flags are read via `isFeatureEnabled` / `getFeatureFlag` (or the `useFeatureFlag` hook for components) — all default to off/undefined when analytics is disabled, so gated UI fails closed.

### Context Provider Hierarchy

`ThemeProvider` → `ToastProvider` → `AuthProvider` → `TenantProvider` → `MetadataProvider` → `SuperAdminProvider` → `BrowserRouter` (see `App.tsx`). Route guards: `RequireAuth` for `/app/*` and for the agency surfaces (`/agency/*`, `/dialer`, `/station`), `RequireSuperAdmin` for `/super-admin/*`. `RequireAuth` also chooses WHICH sign-in page to bounce to — see *Two Auth Systems*. The two public sign-in routes (`/login`, `/agency/login`) and `/verify-email` sit outside every guard: there is no tenant to resolve entitlements for before somebody has signed in.

### Phone Number Selection

Call initiation forms (InitiateCallPage, IvrSessionsPage batch modal, StaticCallsPage batch modal) use a **dropdown** of assigned phone numbers via `usePhoneNumbers()` hook instead of free-text caller_id input. The provider is auto-resolved from the selected phone number on the backend. Numbers that live on the tenant's own carrier account carry an "Own carrier" badge — see *BYOC Telephony*.

## Key Features & Data Patterns

### Call Scripts list (server search + pagination)

`/app/prompts` (`PromptsPage`) pages and searches on the server: `usePromptsPage({ q, offset })` → `listPromptsPage()` → `GET /proxy/prompts?limit=&offset=&q=`, answered as `{ prompts, total, limit, offset }`. `q` matches name or slug (case-insensitive substring) or the script id (a full id, or its first 8+ characters). Search and page live in the URL (`?q=&offset=`), the box is debounced 300ms, a new search resets to the first page, and "no matches" is a different empty state from an empty library. The hook keeps the previous page on screen during a refetch and returns `current` — whether that page answers the query now being asked; nothing that states a finding about the query (the match count, either empty state, the library-total badge, the step-back past the last page) may render off a page that is not `current`, and the pager is labelled by the kept page's own offset and disabled until the new one arrives. A kept page is also scoped to the tenant + account it was read for and is dropped during render on a workspace switch (TenantContext clears `accountId` mid-switch, so no new read starts to supersede an old one). `listPromptsPage` pages a bare array itself, so an SPA deployed ahead of core degrades to an unsearched list instead of crashing.

**`listPrompts()` / `usePrompts()` stay the FULL-list read and must keep sending no `limit`/`offset`/`q`.** Core switches `GET /prompts` to the paginated envelope (capped at 100) when any of the three is present, and returns the bare array of every active script only when none is — which is what every picker (Initiate Call, IVR builder, campaigns, inbound config) needs. Adding a param to `listPrompts` silently caps every dropdown at one page. Onboarding asks for `limit: 1` and reads `total`.

### Contact Lists

CSV-based bulk contact management at `/app/contact-lists`. Users upload CSV files with `phone` + arbitrary variable columns. Lists are type-agnostic — reusable across IVR, static calls, messaging, and AI voice calls.

**Shared component:** `PhoneInputToggle` (`src/components/contact-lists/`) — segmented toggle between "Enter Manually" (textarea) and "Use Contact List" (dropdown). Shows column compatibility indicators when `expectedColumns` is provided.

**Data layer:** `src/types/contact-list.ts`, `src/api/contact-lists.ts` (upload uses raw `fetch` + `FormData`, template download uses raw `fetch` for `text/csv`), `src/hooks/useContactLists.ts`, `src/hooks/useContactList.ts`.

### Scheduling & Recurring Schedules

Schedule-ahead capability for all communication types. `ScheduleConfig` (`src/components/common/ScheduleConfig.tsx`) provides the "Send Now" / "Schedule for Later" toggle with name, datetime, timezone, and retry config. When scheduling, submit calls `createSchedule()` instead of the immediate dispatch function.

Recurring schedules (`/app/recurring-schedules`) automate on daily/weekly/monthly cadence. Each recurrence creates a child one-time schedule instance. Data layer: `src/types/recurring-schedule.ts`, `src/api/recurring-schedules.ts`, corresponding hooks.

### Messaging

Multi-platform messaging under `/app/messaging/*`. Supports WhatsApp and Telegram. Legacy `/app/wa-*` routes redirect to `/app/messaging/*`.

**Pages:** Connections (manage business accounts), Templates (approved message templates), Messages (send/batch campaigns with contact list or manual entry), Message detail (delivery status per contact).

**Data layer:** `src/types/messaging.ts`, `src/api/messaging.ts`, hooks: `useMessagingConnections`, `useWhatsAppTemplates`, `useWhatsAppMessages`.

### Announcements & TTS

Static audio playback campaigns at `/app/announcements` and `/app/audio-files`. TTS announcements support `{{variable}}` placeholders — variable extraction uses `extractVariables()` from `src/utils/variables.ts`. VoBiz TTS language/voice selection uses `TTS_LANGUAGES` from `src/config.ts`. Legacy short codes resolved via `resolveTtsLanguageLabel()`.

When a TTS announcement with variables is selected in StaticCallsPage batch modal, the UI dynamically switches to a tabular input with columns for phone + each detected variable.

### Knowledge Bases — Catalogs & Documents

Grounding sources an agent can answer from, sharing the `knowledge_bases` resource (RBAC capability `knowledge_bases`, endpoints under `ENDPOINTS.proxy.knowledgeBases`). Two kinds, discriminated by `kb_type`: **Catalogs** (`/app/catalogs`, `kb_type='catalog'`) are CSV product catalogs with a column-mapping step (`CatalogsPage`/`CatalogDetailPage`, `useCatalogs`/`useCatalog`, `src/api/catalogs.ts`, `src/types/catalog.ts`); **Documents** (`/app/documents`, `kb_type='document'`) are PDF policy/FAQ/returns docs the agent answers from mid-call.

**Documents — folder → multi-file model (Phase 2.1):** a "document" is a **folder** holding multiple source **files** (PDFs), each independently prepared, approved, and browsable at passage level (customer copy: folder = "document", inner PDF = "file"). Three pages:

- `/app/documents` — folder list (`DocumentsPage`): each row a folder with a per-file rollup status (`N files live` / `N to review` / `Getting ready…` / `Needs attention`, via `folderSummary`); "Upload a document" creates a folder + its first file; open / delete folder.
- `/app/documents/:id` — folder detail (`DocumentDetailPage`): the folder's source-files list with per-file status, an "Add a file" upload, per-file re-upload / delete, and a folder-level "ask a question" test (searches every approved file).
- `/app/documents/:id/files/:docId` — per-file detail (`DocumentFileDetailPage`): the extraction/structure outline; an in-context "test before you approve"; **per-file approve / reject**; the **"Inside your file" chunk viewer** (paginated passages the agent can quote — prose + structured tables); a **source-PDF spot-check** (opens the original via a short-lived signed URL, tab opened synchronously to survive popup blockers); per-file re-upload.

**Shared components:** `DocumentTestBox` (the "ask your document a question" retrieval test — three honest states, names the source file per passage) and `PdfUploadModal` (drag-drop PDF picker for add / re-upload), both in `src/pages/documents/`. `document-copy.ts` holds customer-facing status labels + `folderSummary` / `isDocumentLive`.

**Attach-gate:** an agent attaches a *folder* (`tool_config.knowledge_base_id`) through the `search_documents` tool card in `ToolList` (`src/pages/prompts/components/`); only folders with a live file are offered — `isDocumentLive` (`documents_live > 0`, pre-2.1 rows fall back to `status === 'ready'`).

**Data layer:** `src/types/document.ts` (folder rollup fields on `KnowledgeDocument` + `FolderDocument` / `StructurePreview` / `DocumentChunk`), `src/api/documents.ts` (folder wrappers `listFolderDocuments` / `getFolderDocument` / `addDocument` / `reuploadFolderDocument` / `approveFolderDocument` / `rejectFolderDocument` / `deleteFolderDocument` / `getDocumentSourceUrl` / `listChunks`; `previewDocument` threads `document_id`). Hooks: `useDocuments` / `useDocument` (folders), `useFolderDocuments` / `useFolderDocument` (files, poll while preparing), `useChunks` (chunk viewer, stale-response guarded). Endpoint getters on `ENDPOINTS.proxy.knowledgeBases`: `folderDocuments` / `folderDocument` / `folderDocumentFile` / `folderDocumentSourceUrl` / `folderDocumentApprove` / `folderDocumentReject` / `chunks`.

### Dialer Call Summaries (post-call analysis)

Post-call transcript + summary UI for **dialer** (browser→PSTN human) calls, at `/app/call-summaries` plus additions to the dialer pages. Double-gated in the router *and* the sidebar: `RequireCapability capability="calls.dialer.analytics"` wrapping `RequireFlag flag="dialer_call_analysis"` — both default **off**, so the whole surface is invisible until master grants the capability and core enables the flag. Adding the capability also meant extending cusui's two hand-maintained unions (`RequireCapability.tsx` and the analytics `CapabilityGateId`) — a capability string alone won't compile.

**Pages/components:** `AnalysisProfilesPage` (settings-style CRUD for reusable analysis profiles — name, business context, language hint, custom dimensions, default toggle; form logic split into the pure, unit-tested `analysisProfileForm.ts`); `WebRtcDialerPage` (profile picker + consent-aware recording control — VoBiz is an explicit per-call toggle, while VoiceLink carrier recording is locked on with an explanatory message; the picker preselects the account default); `WebRtcCallsListPage` (per-row `analysis_sentiment_label`, projected scalar from the API rather than the full blob); `WebRtcCallDetailPage` (transcript, summary, quality scores, custom dimensions, Retry, and DSAR Delete-transcript).

**No transcript↔playback sync.** The detail page deliberately does **not** highlight the active transcript turn during playback. Per-turn timestamps come from LLM diarization and aren't trusted for positional accuracy — a confidently-wrong highlight is worse than none — so `findActiveTurnIndex`/`onTimeUpdate` were removed, with a NOTE comment and tests pinning it so it isn't reintroduced.

**Sentiment colours are centralized.** `getSentimentColor` in `src/utils/vocabulary.ts` is the single source of truth (it had been privately redeclared in four places). It tolerates a missing label — callers read it off optional analysis payloads, so absent means "no sentiment yet" → neutral grey, not a crash.

**Data layer:** `src/api/call-analysis-profiles.ts`, `src/api/webrtc-call.ts` (`retryWebRtcAnalysis`, `deleteWebRtcTranscript`), `src/hooks/useCallAnalysisProfiles.ts`, `src/types/call-analysis-profile.ts`, analysis fields on `src/types/webrtc-call.ts`. Endpoints live under `ENDPOINTS.proxy.callAnalysisProfiles` and `ENDPOINTS.proxy.webrtcCall.{retryAnalysis,transcript}` — all reached through master's capability-gated proxy, never core directly. Retry is async (core answers 202, so the UI reflects "queued", not a finished summary). **No new `VITE_` env vars.**

### Campaign workspace sections (agency campaign tabs)

One campaign is **seven sections behind one tab bar**, not one long scroll with four sibling screens hanging off its header. `CampaignTabs` (`src/components/agency/`) renders the bar; `src/utils/agencyCampaignTabs.ts` owns the tab list, the permission on each, and `campaignPanelFromPath`.

Three sections are panels of `AgencyCampaignDetailPage` and share its campaign fetch, its stats poll and its header: **Overview** (`…/campaigns/:id` — the contact-state counters, the dialing activity and the account guardrails rail), **Performance** (`…/performance` — `CampaignPerformance`'s derived read-outs) and **Agents** (`…/agents` — `AgentFloor` plus `CampaignAgentAssignments`). Four are the standalone screens that already existed and are unchanged apart from growing the bar: **Contacts**, **Call attempts**, **Activity**, **Settings**.

The bar sits directly below whatever identifies the *page* — the campaign header and any stall diagnosis on the detail panels, the breadcrumb on the four standalone screens (whose own `<h1>` names the section below it). That is not the same pixel offset in both groups, so the bar shifts vertically when you cross between them; pinning it would mean giving those four a campaign-level header of their own.

**Sections are URLs, not component state.** All three panel routes are registered in `App.tsx` and mount the same component, which reads the panel off the path — so a section survives a refresh, can be sent to a colleague and answers the back button. The bar is a `<nav>` of plain `Link`s with `aria-current="page"`, deliberately not `role="tab"` (four of the seven are page navigations) and deliberately not `NavLink` (its prefix match would mark `…/campaigns/:id` current on every section beneath it).

**Two things stay above the bar on every section:** the lifecycle controls in the header — a supervisor must be able to press Stop from wherever they noticed the problem — and `CampaignHealthStrip`'s stall diagnosis, because a blocker only visible on the section you happened to open is a blocker that goes unread. Everything else the header used to carry (Contacts, Call attempts, Activity, Settings) is now a tab, leaving it holding only what *changes* the campaign.

**Each tab carries the permission master actually enforces** (`agency.supervise` for the spine and Settings, `audit.read` for Activity) — a tab that renders and then 403s on arrival is worse than no tab. Mounting the Agents panel only while it is open is also what keeps `GET …/agents` and the tenant member list off every campaign page view. The Agents tab badges the live floor count as a *someone is there* signal: it renders only for a positive count, so a known `0` and an absent `stats.agents` ("not known", not "nobody") both show nothing — the tab is not where either gets diagnosed, and `AgentFloor` itself tells them apart. `campaignPanelFromPath` reads the panel as the segment **following** the campaign id, never as the tail of the path: core owns the id format and a campaign called `agents` must not render the Agents panel on its own overview URL.

### The contact funnel's sixth state (the counters do not sum to the total)

**`AgencyContactState` has six members; `AgencyCampaignStats` carries counters for five.** The one with no counter is `connected` — the contact a supervisor reads as *"On a call"* — so on any campaign with a bridged contact the five counters **cannot** sum to `contacts_total`, and this is a property of the payload rather than a bug in it. Measured on production: 36 contacts, five buckets summing to 33, a bar drawn to 91.7% and a key whose rows added to 91.7%, with nothing on the panel saying where the other three were.

**The bar was already honest and is not what was fixed.** `contactFunnel` divides every width by `contacts_total`, never by the sum of the buckets, precisely so a payload that does not add up draws **short** instead of silently filling to 100% — that rule predates this and stands. What was missing is that a short bar had no *voice*: it looks identical whether a counter failed to arrive or three customers are mid-conversation.

So the funnel now carries a sixth cell, `contacts_on_call`, whose count is `contacts_total` minus the five, and three rules keep it honest:

- **It is marked as derived, because it is.** `ContactFunnelCell.derived` drives a different hint and a dotted underline on the figure. A real `contacts_on_call` from core wins the moment it exists, and `derived` goes false with no second change here.
- **A missing counter makes the remainder `null`, never a number.** A failed read also produces a short bar, and subtracting anyway would turn a delivery problem into a confident claim that three people are on the phone. All five must have arrived or the question is not asked.
- **A negative remainder is withheld, not clamped.** Buckets summing past the total means the payload was assembled from two moments — the incoherence `listWorkedRing` already refuses to draw — and clamping to `0` would report "the buckets reconcile", the one thing known to be false. `reconciles` is a separate question from `unaccounted === 0`.

**Two type-level guards stop this drifting again**, and neither is decorative — the original drift happened *inside one repo*, between two unions keyed differently (`connected` vs `contacts_*`), so nothing could catch it. `CONTACT_STATE_BUCKET` is a `Record<AgencyContactState, ContactStateKey>`, so a seventh contact state fails to compile until somebody says which bucket it belongs in; `COUNTED` is a `Record<CountedKey, true>` reduced to the list of summed keys, because **a `Record` key set is exhaustiveness-checked and an array literal is not** — left as an array, a new bucket would drop out of the sum and its contacts would be attributed to "on a call".

**On a terminal campaign the same count is a fault, not a state**, and `onCallNote` says so: the panel is badged **Final**, the pulse strip reports nobody still on the line, the rail reports no lines in use, and a contact still `connected` contradicts all three. (Those are two separate cards — "Still on the line" is a `PulseCell`, and the concurrency read-out is `CampaignHealthStrip`'s, account-wide rather than campaign-scoped.) Production had three such rows on a campaign stopped at 09:44, each with its attempt already closed, dispositioned and carrying a real talk time — the calls had ended and only the contact rows were never advanced. The note states the contradiction and names who can act; it deliberately does **not** diagnose the cause, because from the browser a leaked lease and a lagging stats read are indistinguishable and picking one would be a guess printed in the product's voice.

**It takes a `CampaignEnding`, and there is no `terminal: boolean` anywhere near this copy.** The first version took the boolean and the sentence then said "on a campaign that has stopped" to a **completed** campaign, badged as such two inches above — the exact conflation `campaignTimeline` and `howItEndedLines` exist to keep apart, reintroduced on a new surface. The funnel panel's own caption had it too ("A *stopped* campaign places no new calls" → "A *finished* campaign…"). Rule for this page: a sentence covering both endings uses **finished**; a sentence that names one takes the `CampaignEnding` and branches.

**And it no longer says "The calls themselves have ended."** That was true of the three production rows it was written for and is not something the function can see — it reads a derived remainder, not `attempts_live`, attempt state or talk time. Stopping a campaign stops *new* dialing and lets live calls finish, so for the first minutes after a stop the sentence was confidently false about an ordinary floor. It may speak only about how the contacts are **marked**. The docstring had already promised not to diagnose a cause; the sentence was the promise being broken one paragraph below it.

**The Suppressed hint no longer says "Skipped".** On a collections campaign the commonest route into `suppressed` is to be dialed, answered, and written up with an outcome whose `suppress` flag is set — the campaign's *successes*, the same rows the pulse strip counts as wins two panels up. "Skipped because of Do Not Call rules or an unusable number" inverted that, and sent supervisors to a Do Not Call page reading "Nothing on the list". The hint now states the one thing true of every suppressed contact and points at the per-contact reason. Note the *reason* itself is core's (`suppressed_reason: 'dnc'` on a disposition-driven suppression); `suppressedReasonLabel` falls back to the raw code, so cusui is reporting faithfully and the fix for the reason is core's.

**No bar at all on an incoherent payload, and the stylesheet is why.** `.funnelSeg` is `flex: 0 1 auto`. The `flex-grow: 0` half is what makes the "divide by `contacts_total`" promise true — segments summing to 91.7% stop at 91.7%, because nothing grows to fill the track. But `flex-shrink: 1` means the converse does **not** hold: segments summing *past* 100% get shrunk by flexbox, proportionally, until they fit — rendering exactly the always-full bar this module refuses to compute, arrived at through CSS instead of arithmetic. So when `reconciles` is false the counts stay (their percentages summing past 100% is the evidence) and the picture is withheld, which is the answer `listWorkedRing` already gives the same payload. `funnelBarWithheldNote` owns all four reasons there is no bar, because the page had two of them as an inline ternary and the new one needs explaining.

**`.funnelBar` has no `gap`, and that is arithmetic rather than taste.** Segment widths are percentages; a `gap` is pixels added on top of them, so a set summing to 100% asked for `100% + 8px` and flexbox shrank every segment to fit — harmless mid-range (a 60% bar never reaches the track) but at the top it drew a 97% bar as exactly full, the one thing the short-bar rule exists to avoid. The separator is now an inset `border-right` in the card's own background: with the global `box-sizing: border-box` it is drawn *inside* the percentage, so six segments cost the track no more than one. `flex-shrink: 1` stays, and now only `min-width: 5px` still needs it — a hairline segment forced up to 5px is the last way a *reconciling* set can overrun, and shrinking a nearly-full bar by a few pixels beats overflowing the card.

**An empty segment set is never "no contact has reached any of these states".** That sentence was the module's own opening rule broken by the sentence reporting it: every contact is in exactly one of the six states by construction, so a positive total with nothing in any state cannot describe a real campaign. Two payloads reach it and both mean *we do not know where they are* — a counter that did not arrive with every counter that did at zero (`contacts_pending` is both the likeliest to be missing and the likeliest to hold the whole roster), and every counter arriving as a real zero against a non-empty total, the uninitialised row `countersInformative` already refuses to subtract from. They share one message because they share the only next step a supervisor has; distinguishing them would name a cause the browser cannot see.

**The key's track count comes from the markup.** `.funnelKey` is explicit tracks and never `auto-fit`, because at ~856px `auto-fit` resolves to four and drops the last state onto a row of its own where it reads as a footnote. A hard `repeat(5, …)` was correct for exactly as long as there were five states — the sixth cell then hit that same failure from the other side, five on row one and Exhausted alone at a fifth of the width, on precisely the campaign this work came from. The page hands `data-count={funnel.cells.length}` down and each count has a rule, scoped inside `@media (min-width: 1181px)` so the attribute selector does not out-specify the plain `.funnelKey` in the narrow blocks below it (5 and 6 both fill a 2-track and a 1-track grid without a short row). happy-dom computes no grid, so a rendering test cannot see a wrapped row: the guard is a test that **reads the stylesheet** and requires a rule per reachable count, derived from `CONTACT_FUNNEL_STATES.length`.

**A remainder needs the five counters to have said something.** Every counted bucket a real `0` against a non-empty list means they have said nothing about where any contact is — and subtracting then attributes the WHOLE list to "on a call". A 500-contact campaign rendered "On a call 500 · 100%", which no concurrency limit in the product can produce. A real campaign in that state has its contacts in `contacts_pending`, so all five at zero with a non-empty total is an uninitialised payload, not a floor mid-conversation. Found by writing the test, not by reading the code.

`--teal` colours the new segment. Not `--ember`, though it is the live hue and the semantics fit: ember and `--warning` are the narrowest pair in the palette and are separated **only by motion**, and `contacts_exhausted` in this same bar is a static `--warning` block. See *Ember — the second brand hue*.

### Campaign time series (the workspace's day-by-day charts)

`AgencyCampaignStats` is a lifetime-to-date aggregate with **no time dimension**, so a campaign whose connect rate fell off this morning reads identically to one that has been steady all week. `GET /proxy/agency/campaigns/:id/stats/series?from=&to=&bucket=` is the answer: day buckets that mirror `AgencyAgentStatsBucket` **field-for-field**, which is master's contract rather than a coincidence — it is what lets `bucketSeries` / `bucketDay` serve both surfaces, and why `bucketDay` is exported from `agencyAgentPerformance.ts` rather than copied. A second `AgencyCampaignStatsBucket` with the same five fields would be a second place for the "never hand `bucket_start` to `new Date()`" rule to be re-learned.

**"There is no chart" must not advise pressing a control that is already pressed — nor claim a range it does not cover.** Both empty-chart notes used to end *"Pick a wider range"* unconditionally, and both pickers **default to the widest option** (`life` on a terminal campaign, the primary case for this whole section), so the commonest reading of either was dead-end advice: a campaign that ran for twenty minutes showed "Whole campaign" selected above "Pick a wider range to see one". Fixing that with a single `atWidest` boolean then bought a quieter bug, because *cannot widen* and *covers the whole campaign* are different facts and the replacement copy asserted both. `campaignSeriesReach` is therefore **three-valued**, not a boolean:

- `'narrower'` — a wider range exists; the advice is worth giving.
- `'widest'` — the widest on offer, but not the campaign. Withhold both the advice and the claim. Two ways to land here: `life` is **withheld** from a campaign with no known start (`campaignSeriesWindows`), so `30d` is the widest and the campaign may well have dialed before it; and `life` itself is **clamped** to `CAMPAIGN_SERIES_MAX_DAYS`, so a longer campaign keeps only its most recent 92 days — which `campaignSeriesRangeNote` states in words a few pixels under the sentence that would otherwise claim to cover all of it.
- `'campaign'` — `life`, unclamped. Only here may copy say "this campaign".

A **missing range resolves to `'widest'`**, not `'campaign'`: that is the stronger reading and this module does not take the stronger reading off an absence. `rateTrend`'s parameter defaults to `'narrower'` for the same reason — a caller that has not been updated publishes no claim about the campaign.

**The window on the wire is half-open `[from, to)` and filters `dialed_at`** — the `/my-stats` convention, deliberately **not** the inclusive `to` the attempt LIST uses. Both are right and neither is to be unified: a stats read must not count a call that was never placed, while a day picker over a list means the whole day. `campaignSeriesRange` derives the exclusive end as the start of the day after the last day shown, never `T23:59:59.999` — that literal is ambiguous wherever the clocks go back at midnight.

**A rate whose denominator is zero is `null`, and a line chart is where breaking that costs most.** A Sunday with no dials plotted at 0% does not read as "we did not dial on Sunday"; it reads as a cliff, and a supervisor acts on a cliff. So `rateTrend` returns `values: (number|null)[]` plus `runs` — index ranges of consecutive measured days — and `CampaignRateChart` draws **one path per run**, never one path across a gap and never an interpolated segment. A run of length one is a dot, because a line needs two points.

**Days below `RATE_MIN_ATTEMPTS` are withheld, per day, against each series' own denominator** (dials for connect rate, connected calls for conversion). The constant is imported from `agencyCampaignPerformance.ts` rather than restated, for the reason `ratesWithheld` is imported into the Overview: one threshold, so two sections of one workspace cannot disagree about whether a figure is publishable. `withheldNote` says on screen that the gap is a day and not a missing reading — a silent gap reads as a failed read.

**One section component draws both charts.** `CampaignSeriesSection` (`chart: 'activity' | 'rates'`) owns the fetch, the range picker, the four states and the notes; `CampaignActivityChart` (Overview, grouped columns — dials vs conversations) and `CampaignRateChart` (Performance, two rate lines) render the plot and nothing else. Two call sites mount it, so `useCampaignSeries` runs twice — never at once: the workspace's sections are URLs and the page renders exactly one panel, so switching tabs unmounts one and mounts the other, and that unmount is the only refresh this needs. **It does not poll**: the counters beside it are a live position, this is a shape over days, and re-requesting 92 buckets every ten seconds would move nothing a supervisor can see.

**The window is derived, never seeded by an effect.** `defaultCampaignSeriesWindow` depends on the campaign, which loads asynchronously — so the obvious shape (state seeded from it, plus an effect that re-seeds on arrival) issues a request for the wrong window and then cannot tell a stale default from a supervisor's choice. The chosen window is `null` until somebody picks one, and the window in force is `chosen ?? default`. A terminal campaign defaults to `life`, a live one to `14d`: "last 7 days" on a campaign that stopped three weeks ago is an empty chart under a heading promising a trend.

**"Has it finished?" is a BOOLEAN the caller derives, never `ended_at` and never a status string inside the series module.** `campaignLifespan()` is the single adapter (status → `finished`), and `CampaignLifespan` carries the boolean for two reasons: the module has no use for `paused` vs `running`, and `useCampaignSeries` memoises on its inputs — depending on the string re-read the whole series on `running → paused`, which is the control a supervisor presses while watching the page. `ended_at` moves the range only when `finished` agrees; an unguarded read truncated a LIVE campaign carrying a stale timestamp to seven empty bars from last month. And a finished campaign whose end we were never told counts FORWARD from its start rather than 92 days back from today — otherwise it charted this month's zeros and captioned them "ran longer than 92 days", a truncation of a run that never happened.

**`offline` is out of the floor's bar and its "on shift" count, on BOTH surfaces.** `ON_SHIFT_STATES` in `agencyAgentFloor.ts` mirrors the Overview rail's `FLOOR_BAR_ORDER`, which mirrors core's own `shift_seconds` (`foldOccupancy`): a signed-out agent is still a ROW in the table — their handled calls are real — but they are not on shift, and counting them put signed-out time in the denominator every other band is a share of. Overview said "3 of 9 free" and the Agents tab reported a different number for the same payload.

**A refetch keeps the drawn chart on screen.** Only the first read shows a skeleton; a later one marks the ready state `stale` (dimmed, `aria-busy`). Dropping to `loading` unmounted a chart for the length of a round-trip on a section whose whole argument is that it avoids churn.

**The tense follows the real status, not "is it terminal?"** `campaignTense` gives `paused` / `stopping` their own arm — "Running for 6 hours" beside a **Paused** badge and a Resume button is the contradiction `PAUSE_IN_FLIGHT_NOTE` prevents one row above.

**One phrase per concept: `human_connects` is "Spoke to a person" everywhere** — legend, table caption, SVG accessible name and the rate chart's denominator. "Reached a person" is one word from "Reached someone", the pulse strip's label for the wider `attempts_connected`, and blurring them is worse than never having drawn the distinction.

**An absent `successes` is an absence.** It is passed through, not `?? 0` — coercing it turned "master did not send this" into a measured 0% conversion that joins the line and draws a cliff.

**"Has it finished?" is decided by STATUS, never by `ended_at`.** `isTerminalCampaignStatus` in `agencyCampaignControls.ts` is the repo's single definition — there were three hand-rolled copies of `status === 'stopped' || status === 'completed'` and the series module had a fourth answer keyed on the timestamp. `ended_at` is optional because a master that predates it does not send it, so a campaign that stopped in July defaulted to the last 14 days (fourteen empty bars under a heading promising a trend) and printed "Today is still in progress" beneath them. `useCampaignSeries` must pass `status` down with the two dates: the pure function was right and tested, and the caller was handing it two thirds of its input.

**`stopped` and `completed` are different events and `CampaignEnding` keeps them apart.** Everything behind the old `terminal` boolean was worded for `stopped`, so a campaign that ran its whole list — the *good* outcome, badged **Completed** two inches above — reported "Stopped by: Automatically", which reads as the dialer having killed it. A completed campaign has no ender to name: it ran out of list, and `last_transition_by: null` there is a fabrication rather than the abandonment auto-pause it means on a stopped one.

**Range boundaries are walked from local NOON.** `addDays` preserves its anchor's wall-clock time, and where the clocks move at midnight (Chile, Paraguay, Cuba, Lebanon) local midnight does not exist, so `startOfDay` resolves to 01:00 and every boundary inherits the hour — measured in Santiago on 2026-09-06 as a window an hour late at both ends, excluding the first hour of the first day shown and including the first hour of the day after the last. This is `bucketDay`'s own rule applied to building the range instead of parsing the answer, and it is pinned in `agencyCampaignSeriesRange.timezone.test.ts` — an ordinary test file would have read UTC and proved nothing.

**Every rate sits with its own numerator.** `connect_rate_pct` is `human_connects / attempts_total`, so the Performance card's denominator line reads `human_connects` — it read `attempts_connected`, a wider population, and rendered "2,104 of 6,742 dials placed" beside "22.4%", a fraction that does not equal its own percentage, directly above a split card counting 1,509 people. The fixture hid it by picking numbers where the two coincide.

**The chart's conversion and the card's conversion have different denominators, and the chart says so.** A bucket's `connected` is `human_connects` (it mirrors `AgencyAgentStatsBucket`); `success_rate_pct` divides by `attempts_connected`. Neither can be re-derived into the other from what the wire carries, so `CONVERSION_DENOMINATOR_NOTE` states the difference rather than leaving two figures a few inches apart to disagree in silence.

**Withheld days are counted as DISTINCT days.** A quiet day is normally withheld on both lines, so summing per-line tallies put "14 days are left out" above a seven-column chart — the one caveat this chart's honesty rests on, falsifiable by counting the bars. And a range holding one 400-dial day and one 4-dial day is SHORT, not quiet: `noTrendReason` checks whether anything was measured before saying no day cleared the threshold.

**Lifecycle timestamps are on the campaign row, not derived from the activity trail.** `started_at` / `ended_at` / `last_transition_by` feed the header's "Started 11 Aug, 09:00 · Running for 6 hours" and the terminal rail's **How it ended**. The trail carries the same transitions, and deriving from it would be wrong three ways: a second request on every page view for three header values; a different permission (`audit.read`, not `agency.supervise`), so a supervisor without it would read a campaign with no start date; and a server-side retention horizon, which loses a start time on exactly the historical campaigns the summary exists to describe. `last_transition_by: null` is **not an absence** — it is core saying nobody did this, which on an abandonment auto-pause is the most useful sentence on the page, so it renders "Automatically". Only an absent field drops the line.

`campaignRunLength` is a second duration format beside `agentDurationLong`, which tops out at hours: a four-day campaign reading `97h` is a number the reader has to divide by 24 before it means anything.

**`attempts_retried` and `agents_peak` are nice-to-have and neither has a fallback.** `attempts_total` silently includes retries, so "6,742 dials" against a 2,100-contact list cannot be reconciled without the first; `agents_live` is always empty on a stopped campaign, so only the second can answer "was anyone ever on this". An absent field drops one sentence, which is what let them ship as the lower-priority half of the contract — and `agencyStatsConsumers.ts` is what stops that becoming a field nobody notices has stopped arriving. `agents_peak: null` is NOT MEASURED and is dropped; a measured `0` renders "Nobody", because that is the finding.

**Both charts are MEASURED, not scaled** (`useChartWidth`). `AgentBucketChart` draws into a fixed `viewBox` and lets the browser scale it, and says why — but that breaks on a surface `max-width: 2400px` wide, because **a scaled viewBox scales its type**: a 720-unit box at 2280px is scaled 3.2×, so `font-size: 12` axis labels landed on screen three times the size of the card heading above them, and the 4px bar radius and the 2px surface gap between a bar pair stopped being the sizes the mark specs give them. Measuring makes one SVG unit one CSS pixel at every width. The fallback width is load-bearing: happy-dom performs no layout, so an unmeasured chart draws at a known width and its geometry stays testable.

`niceCeiling`'s ladder was widened from 1/2/5 to `[1, 2, 3, 4, 5, 6, 8, 10]` at the same time, and the campaign chart is why: a peak of 516 dials a day rounded to a top of **1,000**, so every bar sat in the bottom half of the plot. The result is always **even and never below 2**, because the midpoint gridline is labelled with `Math.round`: a ceiling of 1 printed the axis as `0, 1, 1`, and the new `3` rung put a line drawn at 1.5 under a tick reading 2. This changes `AgentBucketChart` too, in the same direction.

Endpoint: `ENDPOINTS.proxy.agency.campaignStatsSeries` — the only campaign-scoped route in that block, and there is deliberately no `my-` twin, because an agent has no campaign-wide view.

### Agency Campaign Outcomes (the disposition catalog)

The "How agents work" step of the agency campaign builder (`CampaignBehaviourSection`, shared with `AgencyCampaignSettingsPage` via `layout`/`include`) edits the campaign's **outcomes** — what an agent can file at the end of a call. Every rule is pure and tested in `src/utils/agencyCampaignConfigForm.ts`; the component is assembly plus the copy that is itself the feature.

**An outcome is a card, because the five flags are not five independent switches.** They used to render as bare checkbox labels in a wrapping row, where "Ends this contact" (`terminal`) and "Stops calling this contact" (`suppress`) read like the same setting worded twice. Each flag now carries the sentence that says what it does (`DISPOSITION_FLAGS`), on a three-column grid whose wrap point is load-bearing — the second row is the pair that decides the contact's fate. The card closes with `dispositionSummary()`, the combination stated once in English; it is the same argument as `callingWindowEcho`, that the combination is what was configured and no single control shows it. `suppress` + `terminal` together get `SUPPRESS_BEATS_TERMINAL_NOTE` rather than a validation error: the pair is legal and saves, but core's `resolveDispositionDecision` returns on the `suppress` arm, so the second flag is unreachable beside the first.

**Order is the agent's number key**, shown as a keycap and changed with the row's arrows. Built-ins are locked against *deletion* (removing one removes a capability agents need) and never against position.

**Codes are derived, then owned.** `slugifyCode` fills a new outcome's code from its label; the row stops following the moment the code is typed into, and a row **loaded from the server is never eligible** — a code that has been saved once is the operator's, and every historical call record is filed under it. That eligibility is tracked per row index (`autoCodeRows`) rather than inferred from "does the code still equal the label's slug", which cannot tell an auto-fill from a careful operator's own typing. Relatedly, the list is keyed by **position, never by code**: a key containing a value the operator types remounts the card on every keystroke.

**A disposition's own `retry` has a control**, seeded from `DEFAULT_DISPOSITION_RETRY` (core's voicemail rule) — the retry *table* says voicemail retry lives here, and until this existed nothing showed or could change it. It is withdrawn, with the reason in its place, where `suppress` or `terminal` makes it unreachable. Because the rule is now editable, catalog entries are copied with `cloneDisposition` and a builder starts from `emptyCampaignConfig()` rather than sharing the module-level singleton.

**Client-side validation reaches the fields.** Both save paths populate `fieldErrors` from `validateConfig` when `configBlockReason` blocks, since the block copy says "Fix the highlighted fields" and `fieldErrors` had only ever been filled from a server response.

**A step is complete when it is valid AND has been visited — validity alone is not enough.** `hours` and `behaviour` are keyed on `configBlock === null`, and the config the wizard seeds *already* passes, because `emptyCampaignConfig()` is a working default. So on step 1 of 5, before the operator had been anywhere, steps 3 and 4 rendered ticks while step 2 did not. A tick says "there is nothing for you here", and these are the two steps that decide the calling window and the disposition catalog — including which outcomes carry `suppress` and so take a contact off the list for good. `basics` and `contacts` were always honest (`basicsReady` / `contactsImported` cannot be true without the operator acting); the `visited` set gives the other two the same property.

**`ComposerSection.step` is optional, and the settings page is why.** `AgencyCampaignSettingsPage` renders `CampaignBehaviourSection` with the default `sections` layout, which used to hardcode `step={3}` / `step={4}` — the numbers those sections carry in `CampaignComposerPage`, which does have a five-step sequence. The builder passes `layout="plain"`, so that branch served exactly one consumer, and there the numbers belonged to a run of steps that does not exist: the page opened with a card badged "3", another badged "4", and no 1, 2 or 5 anywhere. Omitting `step` drops the badge and keeps the card's title and helper. A `complete` tick still earns a badge without a number, because "satisfied" is a fact about the section itself rather than a position in a sequence.

### The spine views' two claims about a campaign

**A disposition renders as the operator's NAME, never its code.** All four spine surfaces printed the operator's raw disposition code verbatim — `attempt.disposition_code` on three of them, `contact.last_disposition` on the roster — so a supervisor read `ptp` — while the campaign's own `disposition_catalog` holds `label: 'PTP'` beside that code, and every one of those pages already fetches the campaign carrying it. The wrong field, not a missing name. It reads worse here than it would elsewhere, because the copy around it is unusually careful ("Spoke to a person", "Counted as a win"), so a raw code reads as something internal that leaked.

`dispositionLabel` **falls back to the code, never to a dash.** Four ways to miss and the code is what we know in all of them: an older master that sends no catalog, a campaign still loading, a code retired from the catalog since the call was filed, and a code core wrote that the catalog never held. A dash would claim the call was never written up, and a row filed under a retired code is exactly what an audit is about — the same reasoning `activityActionLabel` uses for an unrecognised action.

**Recording is stated once, above the table.** `record_calls` is off by default per campaign, and while it is off no call the campaign places keeps audio — but the Call column and the tip "a recording is only kept for a call that actually connected" both read as a promise of audio, so a supervisor learned otherwise from a drill-down saying "Recording was not enabled for this call", one row at a time. `recordingDisabledNote` claims it **only on a literal `false`**: `undefined` is an older master, and announcing "this campaign does not record calls" off a field that never arrived would be a confident claim about a campaign we know nothing about, on the screen a compliance question is asked from.

**And it describes the SETTING, not the rows.** The first version said "there is no audio behind any of these rows", which reads the current flag as a history. `record_calls` is PATCHable at any point in a campaign's life, and `agencyCampaignRecording.ts` is built around exactly that — master deliberately permits the on→off write even to a tenant that has *lost* `agency.recording`, so a campaign that recorded four hundred calls and was then switched off is a supported state, not a hypothetical. On it, the sentence withdrew audio that exists and is linked from the column beside it. Nothing on the wire dates the change, so the note is scoped forward ("the calls it places now") and says older rows may still carry a recording; the rows themselves are left to `recordingCellCopy` and the drill-down, which can actually see them.

**Suppressed contacts were not "never dialed", and this inversion had three copies.** The funnel hint, the roster page's tips, and `ROSTER_DESCRIPTION` — and the third was missed on the first pass, in the most prominent slot of the three: `PageDescription` renders it as the standing paragraph *above* the tips, so a reader who never expands the guide reads only that one. Suppression is also the terminal state a contact reaches when an agent files a disposition carrying `suppress: true`, so on the production campaign this came from, 23 of 36 suppressed contacts had been dialed, spoken to and closed as wins — described to their supervisor as contacts the campaign failed to reach. All three copies are pinned by tests now, each forbidding the wording rather than merely asserting the new one.

**All four spine surfaces resolve the name, including the deepest.** `AgencyAttemptCallPage`'s disposition card was the last one printing the code, and the worst place for it: the one screen that exists to explain a single call, with the field labelled `Code` and the value `ptp`. The label now follows the value — a resolved name earns **"Written up as"** and `Code` stays when only the code came back, so the heading never promises more than the value delivers. Two nearer words were already taken *on that screen*: **"Outcome"** is what campaign Settings calls the concept, but the Call Information card above spends it on the telephony outcome (Connected, Busy, No answer), and **"Disposition"** is the card's own title. Note the fact's `data-testid` derives from its label, so it changes with the resolved/unresolved branch.

That column's header is **"Call", not "Recording"** on both the attempts view and the contact drill-down — the cell has always linked to the attempt's drill-down whether or not audio exists (`recordingCellCopy` gates on `webrtc_call_id`, so a Busy attempt with a call row still gets a link). Only the header said otherwise.

### Retry campaigns (the agency dialer's second pass)

A supervisor re-runs *part of* a finished campaign — the voicemails, the no-answers, the ones an agent wrote up as "call back next week". The re-run is a **new campaign**, linked to the one it came from, and the agent taking those calls sees what happened last time. Built against the frozen wire contract in the superproject's `docs/agency-campaign-retry-wire-contract.md`; the reasoning (DR-1…DR-10) is in its companion design doc. Three routes, all `/proxy/*`: `GET …/retry/preview`, `POST …/retry`, `GET …/lineage`.

**The selector IS the contacts tab's filter set** (DR-3), which is why the applied filters moved out of `AgencyCampaignRosterPage`'s state and into the URL (`agencyRosterFilters.ts`). "The query string they were already looking at becomes the selector" is a sentence about one representation, not a coincidence of two — and it buys the ordinary URL properties on the way (a narrowed roster survives a refresh, can be sent to a colleague, and answers the back button). Drafts stay in component state; only **applied** filters are written, so there is no history entry per keystroke.

**`phone`, `from` and `to` are not retry dimensions, and are dropped LOUDLY.** A phone filter is a lookup, not a cohort; `from`/`to` filter `created_at`, which is when the row was *ingested* and reads on a retry dialog as "dialled between", which it is not. Core answers `400 <key> is not a retry selector dimension` on the **whole request**, so a leaked key is not a widened cohort — it is a refused retry with a message about a field the supervisor never typed. `selectorFromContactFilters` strips them and returns which ones it stripped; `droppedFilterNotice` names them on screen. Silently narrowing builds a smaller campaign than the screen promised and silently widening builds a bigger one; both are discovered after the calls are placed. The split is pinned in both directions by a `Record`-plus-`Exclude` pair, so a filter added to `AgencyContactFilters` is a compile error until somebody says which side it is on.

**`excluded` on the preview is not decoration.** `dnc` and `invalid` suppressions are removed from the seed unconditionally (DR-4) — a customer's recorded request not to be contacted is not an operator choice, and a bad number does not become good. A supervisor who ticks "everything suppressed" and is shown 40 where they expected 300 reports it as a bug unless the other 260 are accounted for in the same block as the count, which is where the note renders.

**The one-running-campaign rule is stated before the button, not discovered at Start.** `uq_agency_campaign_running (tenant_id, account_id) WHERE status='running'` means a child cannot dial while its parent does. The child is created `draft` (DR-9) so creation never fails for that reason — only Start does, with `409 another_campaign_running`. Telling the supervisor while they are still authoring costs one sentence.

**The lineage strip is in the campaign HEADER, not an eighth tab.** `agencyCampaignTabs.ts`'s own rule: the header holds what *changes* the campaign and each tab answers one question. Lineage answers none — it is navigation, and it is the fact a supervisor needs before reading any number on the page. `CampaignLineageStrip` fetches on **every** campaign, because a parent that has been retried carries `retry_generation: 0` and `parent_campaign_id: null` exactly like a campaign that never was: nothing on its own row can gate the call. Every failure renders nothing — a master that predates the route answers 404, and an error strip at the top of every campaign in the product for the length of a deploy is worse than the line this build showed before.

**The confirm reuses `HoldToConfirmButton` rather than forking it.** The mechanism (500ms fill, `E`,`E` window, phase machine) stays single-definition and the words move into a `HoldToConfirmCopy` prop whose default reproduces the hang-up button byte for byte. Two fields are decisions rather than copy: `shortcutScope: 'self'` (a page-wide key that creates a campaign is a worse failure than any it prevents; Tab-then-`E`,`E` keeps it keyboard-operable) and `confirmation: 'caller'` (the create is an awaited request, so the console's 3s "no `released` arrived" deadline would announce a failure while the request is still in flight — the dialog re-arms the button by changing its subject instead).

**Agent side: lineage and a banner, and nothing else.** `AgencyPriorAttempt` gains `campaign_id` / `campaign_name` / `dialed_at`, and core's read re-orders onto `ended_at DESC NULLS LAST` because **`attempt_number` resets in every retry campaign** (DR-2) and is no longer a global ordering. `groupPriorAttempts` partitions the list — this campaign first, then each ancestor — preserving core's order inside each group rather than re-sorting, and treats a blank `campaign_id` as "this campaign", which is the only thing an older core could have meant and what makes the non-retry case degrade to exactly today's flat list. The list is keyed on campaign + number, never the number alone: two campaigns legitimately both hold an "attempt 1".

**A disposition code the child's catalog lacks renders AS the code.** `disposition_catalog` on the bootstrap is this campaign's and nothing else, so a code the parent had and the child does not is routine — an operator dropping an outcome between passes is the ordinary reason to author a retry. The old fallback printed the literal words "Unknown outcome", which reads as "the write-up was lost" about a write-up that is intact; `priorDispositionLabel` shows the code instead, styled as one (`data-unlabelled`), with the campaign name in the group heading as the explanation. **The parent's catalog is not shipped to the agent to work around this** — `agent` is level 5 with exactly four `agency.*` permissions, and the label is not worth the widening.

**`retry_context` is on the BOOTSTRAP, not the `reserved` frame.** It is campaign-constant, and `reserved` is the one payload whose latency the dialer design guards hardest. That is also what lets the banner sit above the console body without breaking rule 1 (geometry is frozen): it is fixed at join, so it is present for the whole shift or absent for the whole shift and can never appear under a cursor mid-call. `selection_summary` is built core-side from the frozen selector and **rendered verbatim** — re-deriving it here would be a second answer to the same question, and this client does not hold the input.

**One pre-existing defect was fixed on the way.** The agent console's contact-detail column wrapped the prior-attempt history inside its "no extra details" branch, so a contact whose uploaded columns were all claimed by the hero row — a phone number and a name, the commonest roster there is — showed no history at all, under copy claiming it had "only a phone number". Survivable while history came from one campaign; not survivable once the history *is* the reason the agent is being told anything.

**The create is at-most-once, and the browser is the only layer that can make it so.** `POST .../retry` commits a campaign and a seeded roster in one transaction, and **there is no campaign delete route in either service** — so a create whose *response* is lost (a proxy timeout, a pod eviction) leaves the supervisor looking at a failure over a campaign that exists and is fully dialable. What they do next is press the button again, which built a second campaign over the same cohort: every customer in it dialled twice, by two campaigns, with nothing in the product able to undo it. `AgencyRetryDialog` therefore mints an `idempotency_key` **once per opening of the dialog** (`mintRetryIdempotencyKey`, held in a ref), master forwards it verbatim, and core makes it unique per `(tenant, key)`. A key minted per REQUEST — here, in the fetch, in master, anywhere — is a different value on the second press and protects nothing; that is the whole trap.

The key is deliberately **held stable across a refusal** rather than re-minted: core rolls `retry_selection_empty` / `_too_large` back before writing it, so pressing again after widening the selection creates normally — and if that "refusal" was really a lost success, the same key replays it instead of duplicating it. A replay is an ordinary **success**: core answers `200` with `idempotent_replay: true` and the campaign the supervisor already made, so `onCreated` fires and the console navigates to it. `contacts_seeded` and `excluded` are `null` there — this request seeded nothing, and `retryCreatedToast` says "was already created" rather than restating a count it does not have. That toast is a shared helper precisely because it was written twice, identically, at the two call sites that open the dialog; a replay reaching only one of them would have rendered `null.toLocaleString()`.

### Campaign Activity (agency audit trail)

`/agency/campaigns/:id/activity` (`AgencyCampaignActivityPage`) — what happened on one campaign, who did it and when, reached from the **Activity** tab of the campaign workspace's section bar (see *Campaign workspace sections*). It lives in the **agency workspace, not at `/app/audit-log`**: a supervisor should not have to leave the campaign to ask what happened to it, and that page is a different shell, tenant-wide, with no campaign scoping. No extra route guard — `AgencyLayout` already requires the `agency` capability and the `agency_dialer_enabled` flag, and master gates the route on `audit.read`.

**A terminal campaign is the primary case**, so nothing is gated on the campaign being live, there is no polling, and the date-range filter is a first-class control rather than an afterthought.

**Two systems record here and both rows belong.** Master's rows say a supervisor pressed Pause; core's say the campaign transitioned — so a pause legitimately appears twice, and the `Recorded by` column (`Console` / `Dialer`) is what tells them apart. The rows only the dialer has are the automatic pause with its measured abandonment rate; the rows only the console has are dispositions, DNC marks and staffing changes.

**Three things could make the list shorter than the truth, and each says so in words** rather than being left to be inferred from an absence — an audit view that silently omits rows is worse than one that says it is incomplete:
- `partial: true` → an amber banner naming *what* is missing (status changes and any automatic pause), in the same register as the dashboard's "Live updates paused" strip. "Some data is unavailable" would be useless: a supervisor who does not know which part is missing cannot judge whether the screen answers their question.
- The **retention horizon**, sourced from the API. The window is configured server-side (in core's retention Lambda, not even in core's own config), so a copy here would go stale and tell the operator the wrong thing. `unbounded` renders nothing; `unknown` still gets a sentence, because silence reads as "all of it".
- The **CSV export ceiling** → a toast naming the limit and the remedy.

**Export CSV is server-side** (`GET …/activity.csv`), so the file is everything matching the active filters rather than only the pages loaded. A **424 from master is an answer, not a transport failure** — it refuses to write a file missing the dialer's half, because a screen can carry an "incomplete" banner and a file that leaves the building cannot — so its message is surfaced rather than retried.

**The action filter is rendered from the server's own vocabulary** (`available_actions` on the activity response: `{value,label,group}[]`). It used to be a hand-maintained list in `src/types/agency-activity.ts`, and nothing could check it — master and core are separate repositories, neither a dependency of this one, and in CI only cusui is checked out. Master knows both stores' action names, so master serves them. **There is deliberately no fallback list**: against an older master that sends no vocabulary, the action filter is hidden with a sentence saying why, and the date range keeps working. A built-in copy would be the same unverifiable mirror, and each stale entry in it a checkbox that matches nothing, which reads as "this never happened".

An action this build does not recognise still renders, labelled with its raw name and its raw detail (`activityActionLabel` falls back to the raw action, `activityDetailSummary` to the raw key/value list). That is independent of the filter and survives an absent vocabulary — the served list says what is worth OFFERING as a filter, never what the trail can contain, and the unanticipated row is exactly the one an audit needs.

**Who acted is READ off the row, never inferred from `user_id` (86d45t7rm).** Master's API-key branch loads `platform_api_keys.created_by` into the request user, so until master's migration 067 a key-authenticated action was stamped with the id of whoever *minted* the credential — possibly years earlier — and was indistinguishable from that person acting in a browser. Master now leaves `user_id` null for a key and names the credential (`actor.api_key_id`, plus `actor.display` resolved to the key's own name), which makes the obvious client reading actively wrong in two places at once: the workspace Audit Log's `user_id ? id : 'System'` would have labelled a credential **"System"**, and this page's `actor.system` branch would have read the same row as **"Automatic"** — each telling an operator that nothing human was involved in an action somebody's credential performed. Both surfaces now branch on the recorded fact: `activityActorKind` here, `auditEntryActor` on the workspace page.

⚠️ **`actor.type` and `actor.system` are not interchangeable, and collapsing them is the trap master's own contract names.** They agree on every row written since 067. On an older one they deliberately disagree — `type` is `'unknown'` (nothing was recorded) while `system` keeps the inference the trail made before the column existed. **Read `system` to decide what to show and `type` to know whether the distinction was captured**; rewriting a cell as `type === 'system'` flips every historical background row in every campaign trail to an unhandled value, which is a visible rewrite of history from a change whose whole promise was that history renders unchanged. Pinned by a mutation-checked case in `AgencyCampaignActivityPage.test.tsx`.

`'unknown'` is in the row union and in **no served vocabulary**, and that asymmetry is master's: `available_actor_types` is the *audit log's filter*, and "not recorded" is an absence rather than something to select. So this client owns that label — and deliberately renders no badge for it, because marking every row written before the upgrade as unattributed would flag the whole of a tenant's history to make a point about a column. The workspace Audit Log states the same fact where it actually bites: filtering by actor excludes pre-067 rows (master matches on the column, and theirs is null), so the page says so **whenever the filter is in force** rather than only when the list looks short — a full page of results is exactly where the omission is invisible.

**Data layer:** `src/types/agency-activity.ts` (row/page shapes + `activityActionLabels` / `groupActivityActions` / `activityActionLabel`, which resolve the filter and the labels from what the API returned, and `activityActorKind`, which decides which of the four actor renderings a row gets), `src/api/agencyActivity.ts`, `src/utils/agencyActivityCopy.ts` (the copy decisions, pure and unit-tested). The workspace Audit Log's half is `auditEntryActor` / `AuditActorTypeOption` in `src/types/audit.ts`, the `ActorCell` in `src/pages/settings/AuditLogPage.tsx`, and the fourth served vocabulary (`available_actor_types` → `?actor_type=`) threaded through `src/api/audit.ts` and `useAuditLog`. The permission is `audit.read`, whose `account_admin` floor is now pinned by `src/__tests__/utils/agencyPermissionMirror.test.ts` — raised back to `tenant_admin`, master's route would be correct and unreachable by the role it was built for.

### Agent Performance (per-agent numbers)

Two surfaces over one pair of routes. **`/dialer/performance`** (`AgentPerformancePage`) is the agent's own "My performance", reached from a link on `AgentHomePage`; the **"By agent" tab** on `AgencyAnalyticsPage` (`AgentAnalyticsSection`) is the supervisor's view of one named person. Both render the same component, `AgentPerformancePanel`, so an agent's view of their shift and their supervisor's view of it cannot drift in wording, rounding, or what counts as absent — a coaching conversation held over two different screens about one shift is worse than one screen.

**Paired routes, not one parameterised route.** `GET /agency/my-{stats,attempts,campaigns}` are floored at `agency.station.connect` so a bare `agent` (level 5) can call them, and take **no subject** — master scopes them to the caller. `GET /agency/agents/:userId/{stats,attempts}` are the twins, floored at `agency.supervise`. An optional `agent_user_id` on the agent-floored route would be a subject the client controls; keeping them apart means an agent cannot form the request. `useAgentPerformance` takes a discriminated `{kind:'me'} | {kind:'agent',userId}` for the same reason.

**`/dialer/performance` is full-viewport and OUTSIDE both shells**, beside `/dialer` in `App.tsx`, gated identically (`RequireAuth` + `RequireCapability capability="agency"` + `RequireFlag flag="agency_dialer_enabled"`, both default off). No new capability — `agency` was already in `RequireCapability`'s hand-maintained union. A supervisor opening it is **served** (they cover shifts and have their own numbers) but nothing routes them there; it is deliberately absent from `GlobalSearch`, whose only reachable audience is the roles that must not be sent there. It waits for BOTH `tenantId` and `accountId` and treats "resolution settled with no account" as `AccountUnavailable` rather than a spinner — the same guard `AgentHomePage` and `RequireFlag` carry, for the same 403/400 pair.

**Three honesty rules, each a rendered sentence rather than a comment:**
- **Dials and conversations are never one number.** `headlineTrio` always returns `Dials · Connect rate · Conversations`, in that order, so the rate sits between its own denominator and numerator. "Calls" is ambiguous in exactly the way that matters to the person being measured on it.
- **Day buckets are cut in each campaign's own timezone** (core enforces calling windows there). Every attempt lands in exactly one bucket so the totals are exact, but a "day" is not one contiguous 24 hours for somebody working two zones. `BUCKET_TIMEZONE_NOTE` says so beside the chart, in the product's words — pinned by a test that also asserts it contains no implementation vocabulary.
- **A zeroed occupancy breakdown is never drawn.** Core computes occupancy from an event log that shipped after the dialer, so an older session returns **zeros, not nulls**; `occupancyBreakdown` checks the SUM of the states (not `shift_seconds`) and reports `measured: false`, and the component renders `OCCUPANCY_UNMEASURED_NOTE` instead of a bar. This is the `abandonment_rate_24h_pct` null-not-zero rule in a different costume, aimed at a person rather than a campaign. Shares are taken of what was *recorded*, with the gap named separately — and `offline` is in **neither** the sum nor the bar, because core's `shift_seconds` excludes it (`foldOccupancy`: an agent who logged out at 17:00 was not on shift at 18:00). Including it diluted every share by signed-out time and made the gap note unreachable, since the recorded total could then never fall short of a shift that excludes it.

**The chart is inline SVG** (`AgentBucketChart`), not chart.js — `Sparkline`'s precedent: two series, ≤31 pre-aggregated points, no zoom/pan/time scale, on the page whose reader is most likely on the oldest machine in the building. Nothing added to `package.json`. **Grouped columns, never stacked** (every connected call is also a dial, so a stacked height would be a number that does not exist), legend always present, one direct label on the peak, and a "Show the numbers" table. Series colours are `--accent` and `--teal` — deliberately not `--success`, which is a status token and must not stand in for a series identity. Occupancy reuses `AgentFloor`'s own per-state colours so a state is one colour everywhere.

**Conversion rate is `is_success`'s first consumer anywhere.** `attempts_success` and `success_rate_pct` join `AgencyCampaignStats` (with entries in `agencyStatsConsumers.ts`, whose exhaustive record makes a declared-but-unread field a compile error) and render as a fourth `CampaignPerformance` readout labelled **"Conversion of conversations"** — `success_rate_pct` is measured against CONNECTED calls while `connect_rate_pct` is measured against attempts, so neither may appear as a bare percentage beside the other. The count travels as that readout's secondary rather than as an eleventh counter tile, because it is the rate's numerator.

**Staffing history** (`GET /agency/my-campaigns`) is on the agent's page and includes ENDED assignments — `my-assignments` is the entry list, this is the history, and the per-campaign breakdown will name a campaign the agent was taken off. `assignmentEntry` is reused for status→meaning (its allow-list-of-blocks shape treats a status core adds as ordinary, so a second mapping would be the copy that goes stale) and `AgencyCampaignStatusBadge` keeps printing an unrecognised status verbatim. `active` is read from master's own flag, never re-derived from `unassigned_at`.

**`bucket_start` is `YYYY-MM-DD`, not an instant**, and must never be handed to `new Date()`: a date-only string is the one literal JS parses as UTC midnight, and reading it back with `getDate()` / `toLocaleDateString()` in local time dated every bar, tooltip, peak label and table row a day early west of Greenwich. `bucketDay` parses the components onto the reader's own calendar, anchored at **noon** because Cuba and Chile spring forward at 00:00 and Lebanon falls back at 00:00, so a local midnight is a time that either does not exist or exists twice.

**Both surfaces reset their campaign scope by remounting**, never in an effect: `AgentPerformancePage` is keyed by `tenant:account` and `AgentAnalyticsSection`'s inner component by `userId`. An effect runs after the render that has already issued three scoped reads, so the wrong request goes out and its answer is on screen until the corrected one lands. The selector is shown whenever a scope is APPLIED as well as whenever there is a choice to make — the two used to disagree, which left a scope in force with no control to clear it.

**Files:** `src/types/agency-stats.ts`, `src/api/agencyStats.ts` (routes from `ENDPOINTS.proxy.agency`), `src/hooks/useAgentPerformance.ts`, `src/utils/agencyAgentPerformance.ts`, `src/pages/agency/AgentPerformancePage.tsx`, `src/components/agency/{AgentPerformancePanel,AgentBucketChart,AgentAnalyticsSection}.tsx`. `AgencyAnalyticsPage`'s "no `AgentFloor` here" note still stands: the floor is a polling table of live state with an intervention control per row, and the per-agent tab is a settled record with no controls at all.

### Agent dial history ("My calls")

The same pair-of-routes shape one level of detail down: **`/dialer/attempts`** (`AgentAttemptsPage`) is the agent's own cross-campaign dial history, and the per-agent section on `AgencyAnalyticsPage` renders it again beneath that person's figures. One component, `AgentAttemptsPanel`, shared through the same `{kind:'me'} | {kind:'agent',userId}` discriminator `useAgentPerformance` uses — the discriminator picks the route AND the second-vs-third person of the copy, so "you haven't taken any calls" cannot be shown to a supervisor about somebody else. Reads are `GET /agency/my-attempts` and `GET /agency/agents/:userId/attempts`; the `agent` form is gated on `hasPermission(role, 'agency.supervise')`, master's exact floor.

Gated and shelled exactly like `/dialer/performance` — full-viewport, outside both shells, beside `/dialer` in `App.tsx`, same capability and flag, no addition to `RequireCapability`'s union, deliberately absent from `GlobalSearch` for the same reason. Both pages now share `AgentSurfaceShell`, which owns the header, the way back, the sibling cross-link and the **account-resolution guard** (wait for both ids; "resolution settled with no account" is `AccountUnavailable`, never a spinner) — a guard `AgentHomePage`, `RequireFlag` and `AgencyAnalyticsPage` each carry separately and each got wrong first.

**No phone-number search on this surface.** The campaign-scoped view has one and it works. Master's whitelist for the two AGENT routes (`AGENT_ATTEMPT_QUERY_PARAMS`) does not carry `phone`, and `forwardQuery` drops an unlisted key **silently** — so the control that used to be here answered 200 with the person's entire unfiltered history, presented as the calls matching their search. `phone` stays on `AgencyAttemptFilters` because `AgencyCampaignAttemptsPage` sends it; `isAttemptFiltered` and `attemptFilterGroupCount` deliberately do not count it, because a badge for a filter this surface never sent turns an empty list into "your search matched nothing" about a search that never happened.

**`to` is INCLUSIVE here and the range filters `created_at` — the opposite of `/my-stats`.** The performance page has an EXCLUSIVE `to` on `dialed_at`. Both are right: a STATS read must not count a call that was never placed, while a LIST filtered on the nullable `dialed_at` would silently drop the `orphaned` and pre-dial failures the attempt spine exists to surface — and a day picker reading "to 3 August" means the end of the 3rd. Neither convention is to be "unified". `src/utils/agencyAttemptFilters.ts` owns both facts and `ATTEMPT_RANGE_NOTE` states them on screen in words that deliberately avoid the stats page's period vocabulary. The end of the range is **derived** as one millisecond before the next local day starts (date-fns, anchored on noon) rather than written as `T23:59:59.999`: that literal is ambiguous wherever the clocks go back at midnight (Chile, Paraguay, Cuba, Lebanon), resolves to the earlier offset, and dropped the last local hour under copy promising "Both dates are included".

**The campaign column is the point.** `AgencyAttempt.campaign_id` exists because this list is not campaign-scoped, and the row carries an id and no name. Ids resolve through a map the caller already holds — `getMyCampaigns` (staffing history, ENDED assignments included) on the agent's page, the account's campaign list on the supervisor's — never a fetch per row and never a second list. An unmatched id degrades through `campaignLabel` to `Campaign <first 8>` with the full id in a `title`: a blank cell would say the dial belonged to nothing, and a bare UUID dressed as a name is unusable. The campaign *picker* offers only campaigns it can name, because an option is chosen rather than read.

**No CSV export, deliberately.** The campaign spine has `/campaigns/:id/attempts.csv`; master's performance plugin has **no csv route**, so `downloadSpineCsv` here would 404 on every press. Adding one is a core→master change, not a screen change. **No recording link either**, and for a different reason: `/app/calls/dialer/history/:id` is `calls.dialer`-gated inside `AppLayout`, which is the empty-shell trap `/dialer` exists to avoid for a level-5 `agent`. Both absences are recorded in the panel's docstring and pinned by tests.

**Disposition codes are operator-configured free text, per campaign.** Cross-campaign there is no single catalog to offer, so the filter shows the codes on the rows *loaded so far* as chips plus a free-text box for anything else, with a rendered sentence saying the list is not complete. Codes are added one at a time and never split on commas, because that is what the operator typed — but **a code containing a comma is unfilterable, and no client-side spelling changes that**: master's `forwardQuery` joins a repeated param's values with a comma and core's `multiParam` splits on one, so `Not interested, will call back` reaches core as two codes, matches nothing, and returns an empty list. Repeated params are the right form because both services accept them and both spines send them, not because they preserve a comma. Fixing it is a core→master change to the filter encoding.

**Keyset paging, so no page numbers.** `filters` live in `useAgentAttempts`, not in the panel, which is what makes "a filter change resets the cursor" structural rather than remembered: the caller never holds a cursor. Out-of-order responses go through `decideListResponse` in `src/utils/agencyStaleResponse.ts` — the read-side twin of that module's disposition guard, and the reason it lives in the same file. A failed "load more" is kept apart from a failed first page, because the rows already on screen are what the reader came for.

**Both destinations are reachable from inside the station, in a NEW TAB.** `AgentHomePage` carries the links, but most agents never see that page — the single-assignment redirect sends "the overwhelmingly common shift" straight into the station — so their own numbers used to cost them a **Leave**, i.e. their place in the dialable pool. `StationMenu` therefore carries the same two destinations as `target="_blank"` + `rel="noopener noreferrer"` links (`STATION_HISTORY_LINKS` in `agencyStationExit.ts`). That is not a softening of "no links out of the console": a new tab is not a navigation, so the socket stays open and the heartbeat keeps renewing core's 45s lease. A **same-tab** link there would still manufacture the answered-call-with-no-agent that Exit's `available` refusal exists to prevent.

### Call Script AutoPilot

A conversational editor for a call script, as a third tab in `PromptEditorPage`'s inspector (`rightTab: 'preview' | 'test' | 'autopilot'`). Built on **`@assistant-ui/react` headless primitives only** — no styled/shadcn package, no Tailwind. Markdown rendering is `react-markdown` (see *Markdown in the chat* below).

**It never saves the script, and authors no diff of its own.** Applying a proposal writes into `workingDraft` through the editor's own state setter and offers Undo; the existing confirm-before-save gate (`SaveReviewModal`) stays the only thing that creates a version, and the only place a change set is committed.

A proposal card **does** show the values it would set (`plan.preview` → `previewProposal` in `autopilotPatch.ts`, which is literally `diffPromptForms(draft, applyProposal(draft, changes))`). It cannot contradict the review because it is the review's own function over the same two snapshots — shown earlier and rendered more quietly (no chips, no before/after pair, one excerpt with the review's own "Show the text" expander at the shared `VALUE_PREVIEW_CHARS`). Without it, Apply was the only way to read a suggestion, which put the commitment before the review. What is still never shown is a diff the **model** wrote about its own work.

**Connected tools are the one thing AutoPilot writes to the server, and the version race around them is guarded in three places** — none sufficient alone, because a prompt save mints a new `prompt_templates` row in core and copies the old version's tools onto it, so a write against the version being replaced is reported as "Saved" and is then absent from the version `ToolList` reloads (no diff, no undo, unrecoverable):
1. `AutopilotSurface.toolWriteBlocked` — set while `saving`, disables the tool confirm and *says why* (a dead control reads as a bug). Distinct from `toolGate`, which is the standing "nothing to attach tools to yet" condition and replaces the button.
2. `canSave` includes `toolWritesInFlight === 0`, with the header button's `title` and a `handleSave` early return carrying the reason — the same mechanism the concurrent-save guard already used, so all five save entry points are covered.
3. `applyAutopilotToolChanges` takes an `activePromptId` getter and re-reads it **before every write**, abandoning the batch with `staleVersion: true` if the id moved. The editor feeds it from a ref, because the id inside the surface memo is a render-time capture — exactly the value a save invalidates. Guards 1 and 2 make this hard to reach on purpose, so it is covered as wiring plus unit tests rather than as a clickable scenario.

**`dropped[].reason` is model-facing and is never rendered.** It carries function names, uuids and raw Zod text (operators were reading "Call list_knowledge_bases and use the id of a catalog knowledge base"). The optional `note` is the author-facing sentence and is the only one that reaches the screen; when it is absent — normal, and the whole of a Phase-2 server — the friendly field label stands alone, with **no fallback to `reason`**. Labels go through the surface: `describeField` (→ `describeWireField`) for a form field, `describeToolLabel` for a `tool_changes[<name>]` entry, so the "Left out" list never shows a column name.

**The tab is hidden, not disabled, when the feature is absent.** `GET /proxy/prompts/autopilot/capabilities` answers 200 (present, with `model_label` / `max_turns`) or 503 (absent) — there is no 200 that means disabled — and `useAutopilotCapabilities` collapses *any* failure to `unavailable`. This is the deliberate opposite of the neighbouring "Improve writing" button, which ships unconditionally and lets users discover its 503 by pressing it.

**Transport** (`src/api/autopilot.ts`) bypasses `apiFetch` the way `exportCsv.ts` does: `EventSource` is GET-only and cannot set `Authorization` / `X-Tenant-Id` / `X-Account-Id`, so it is `fetch` POST + `response.body.getReader()` + an SSE line parser, with headers from `buildAuthHeaders`. Two properties are load-bearing and are why `readSseFrames` is a separately exported generator (unit-tested against fabricated `ReadableStream`s): bytes are buffered until a blank-line terminator, so **a frame split mid-`data:` survives**; and the caller **settles exactly once** — on the server's `done`, on `aborted` when the user presses Stop (no error event: they meant it), or on a synthetic `error` when the stream dies without `done`. Pre-stream failures arrive as JSON, not SSE, and are mapped (503/429/4xx) before the reader is touched.

**Wire → form translation** lives in `src/pages/prompts/autopilotPatch.ts` and **calls the load path's own helpers** — `dimensionsToFormItems` / `nudgeConfigToFormFields` / `listToFormRows`, extracted from `promptToFormData` in `promptForm.ts` for exactly this reason. A proposal speaks core's field names (`analytics_config.custom_dimensions`, one `silence_nudge_config` object) and the form does not (flat `custom_dimensions` with comma-joined `options`, four string-backed `nudge*` fields); a second hand-written copy would drift silently, since the two paths are exercised by different tests. `applyProposal` touches only keys **present** in `changes` (an absent key must not clear a field) and skips a malformed field rather than failing the proposal. `slug` is deliberately not applicable — it is derived and hidden. A `changes: {}` with a non-empty `dropped` is a valid answer and renders as "nothing I can apply here", with what was dropped and why — never as a success.

**The panel is parameterised by a small surface adapter** (`AutopilotSurface` in `src/components/autopilot/types.ts`: `noun` / `transport` / `entityId` / `hasContent` / `snapshot` / `plan` / `apply`), so a second surface is a new object literal beside `PromptEditorPage`'s, not a fork. That prediction has now been cashed twice — see *Automation & IVR AutoPilot* below. Still deliberately **not** a plugin registry: three consumers, each naming its own surface at its own call site, is not a lookup problem. The draft's type stays out of the panel: `apply` returns an undo thunk, so the panel can never become a second owner of the form state.

A run that ends at the server's turn cap (`done.status === 'max_turns'`) says so in an info strip rather than letting the panel go quiet — a clean stream that simply stops reads as "it finished thinking", not "it ran out of room".

`prompt_id` is sent only when the script exists server-side, so AutoPilot works on an unsaved draft; `script_snapshot` (via `formToSnapshot`) is always sent, so the model reads what the author is looking at rather than the last saved version. The opening question asks **"How do you want to improve this?" only when the script both has content and has been saved** — a template-seeded draft has plenty of content and has not been created yet, so it gets "What are you trying to create?" like a blank one. The panel stays mounted across tab switches so checking the Preview after applying does not cost the conversation.

**AutoPilot is reachable from the create flow's first screen.** `TemplatePicker` carries a third choice — *"Describe it and let AutoPilot build it"* — which starts a scratch draft, selects the AutoPilot tab and opens the inspector (collapsible and persisted, so it must be opened explicitly). It is passed **only** when the capabilities probe reports available, for the same reason the tab is hidden rather than disabled. Before this, the create-mode early return rendered the picker without the inspector, so the feature's primary entry point could not be reached in the one case it was written for.

**The create-mode save review shows content, not just counts.** `CreationSummaryItem` carries `text` (and `long`) beside its count, rendered with the update path's own expander at the same threshold — this is the save that puts an agent on a live phone line, and the case where AutoPilot may have written every word of it.

**Markdown in the chat is rendered, by `react-markdown`** (`src/components/autopilot/markdown.tsx`). v1 shipped assistant prose as literal text, reasoning that a half-supported subset would show stray `**` and `#` and be worse than promising nothing. The premise was false: **nothing tells the model to write plain text.** The "no markdown" lines in master's prompts govern the *spoken* words it writes into a script or an IVR step, not its reply — so it writes markdown by default, and authors were reading raw asterisks and digits. The real choice was markdown or visible syntax.

The module is the *mapping* onto this pane's styles, not a parser. **Do not reintroduce one.** A hand-rolled subset shipped first and was replaced: markdown has a specification and a wide edge-case surface (intraword `_` in snake_case, left-flanking delimiter runs, list-item continuation, unclosed fences mid-stream) and every one of those is a solved, tested problem in remark. The library also renders the constructs a bounded subset had to refuse — tables, task lists, strikethrough, blockquotes — so those are styled here rather than left to the browser's article-column defaults.

Four things about the wiring are load-bearing:

- **No `rehype-raw`, ever.** Without it, raw html in the model's output is inert — react-markdown builds React elements and never parses html into the tree, so `<script>alert(1)</script>` is escaped text and there is no injection surface. Adding `rehype-raw` would create one in a pane whose content is model output shaped by whatever the author pasted into the composer.
- **An image renders as its alt text, never an `<img>`.** `<img>` is the one element CommonMark can produce that makes the browser issue a request on its own, with no click, disclosing the viewer's address, user agent and referrer — so `![x](https://…/pixel.png)` in model output is a working read receipt on the author's pane, and `urlTransform` cannot catch it because the scheme is an ordinary `https`. A `components` mapping rather than `disallowedElements`, since an `img` node has no children and `unwrapDisallowed` would drop the alt text with it. Nothing legitimate is lost: no reply and no tool result has a reason to carry an image. `MarkdownInline` is safe by construction — `img` is simply not in its `allowedElements`.
- **`urlTransform` is a scheme allow-list** (`http`, `https`, `mailto`) — narrower than react-markdown's own default, and it *parses* rather than prefix-matches, so a scheme smuggled through with control characters or padding (`java\nscript:`, `  javascript:`) is normalised first and rejected on the result. A refused url then renders as plain text, because the `a` mapping drops an `href`-less anchor rather than leave something that looks clickable and is not.
- **`remark-breaks`**, so a single newline is a line break. CommonMark collapses it, which is right for a document and wrong here: the model puts a question and its options on consecutive lines.
- **Headings render as styled paragraphs**, never `<h1>`–`<h6>`. A chat transcript is not a document outline; real headings would inject the model's wording into the page's heading order at whatever level it typed, so a screen-reader user browsing by heading would land inside a conversation turn.

The task-list bullet is suppressed by `.mdListItem:has(.mdCheckbox)`, since react-markdown gives the `li` no distinguishing class. It must be a **descendant** selector: a *loose* list wraps each item's content in a `<p>`, so the checkbox is `li > p > input` there and `li > input` in a tight one — a child selector matched only the tight shape and left the bullet on the real case. Both shapes are pinned by test, because a selector over someone else's DOM shape is what breaks quietly on a major upgrade.

A **proposal card's `summary`** uses `MarkdownInline`, whose `allowedElements` is inline-only with `unwrapDisallowed`: the summary is the model's one-line description so it can carry a backticked field name, but a card is no place for a heading or a list, and filtered constructs lose their formatting and never their words.

`vite.config.ts` routes the markdown stack to its own `markdown` chunk beside `assistant-ui`, for the same reasons: it belongs to one lazily-loaded feature and is ~48 kB gzip. Nothing about it is eagerly loaded — `dist/index.html` does not preload it — and the panel's own chunk got *smaller* (9.4 → 8.4 kB gzip) once the hand-rolled parser left it.

**Only assistant prose goes through it.** A user's message stays literal — what someone typed is not a document to interpret, and their `*` is an asterisk. That mapping is one line in `PART_COMPONENTS` and is asserted end-to-end through the real panel, because reversing it leaves every unit test green while the pane either shows raw syntax or mangles what the author wrote.

`src/__tests__/autopilotMarkdown.test.tsx` is deliberately **not** a parser suite — remark owns the parsing. It is a contract over what this pane depends on: the two departures above, the two safety properties, the mid-stream partial forms, and snake_case (CommonMark already gets that right; the test is there because it is the regression an author would notice first and blame on the model).

**Files:** `src/api/autopilot.ts`, `src/hooks/useAutopilotCapabilities.ts`, `src/pages/prompts/{autopilotPatch.ts,autopilotToolChanges.ts}`, `src/components/autopilot/{AutopilotPanel.tsx,AutopilotPanel.module.css,useAutopilotThread.ts,types.ts,index.ts}`. Endpoints under `ENDPOINTS.proxy.prompts.autopilot`. Analytics: `trackAutopilotOpened` / `trackAutopilotTurnCompleted` / `trackAutopilotProposalApplied` / `trackAutopilotProposalUndone` — counts, enums and booleans only, never a message, a summary or a field value. `vite.config.ts`'s `manualChunks` routes `@assistant-ui/*` to its own chunk **before** the React rule, because `@assistant-ui/react`'s path contains `/react/` and would otherwise ship ~270 kB of chat runtime eagerly to every page.

### Automation & IVR AutoPilot

The same feature on two more screens: a conversational editor for a post-call **automation** (`AutomationBuilderPage`) and for an **IVR call flow** (`IvrWorkflowBuilderPage`). Read *Call Script AutoPilot* first — every rule there holds here unchanged (never saves, authors no diff of its own, the tab is hidden rather than disabled, `dropped[].reason` is never rendered, the panel stays mounted across tab switches). What follows is only what differs.

**The panel needed one new field, not a fork.** `AutopilotSurface.transport` names which of master's endpoint pairs the surface talks to and what that pair calls its two request keys. Three constants in `src/api/autopilot.ts` (`CALL_SCRIPT_TRANSPORT` / `AUTOMATION_TRANSPORT` / `IVR_WORKFLOW_TRANSPORT`); a surface names one, never a literal, so a renamed endpoint is a compile error rather than a 404 at the first message. Above the transport everything speaks one neutral shape (`resourceId`, `snapshot`) and `streamAutopilot` renames it on the wire — the call script keeps its historical `prompt_id`/`script_snapshot` because a tab open across a deploy is still sending them, the other two use the generic `resource_id`/`snapshot`. That rename is the one thing only the transport can see, so it is pinned there (`autopilot.sse.test.ts`).

**Neither surface has connected tools.** `planTools` / `applyToolChanges` / `toolGate` are call-script notions (an agent's tools, written immediately, outside the save gate). Master always sends `tool_changes: []` on these two, so both surfaces omit those capabilities and the panel reports any tool change as ignored. Nothing on these screens writes to the server before Save.

**Automation** (`src/pages/automations/autopilotPatch.ts`). Six proposable fields, and the builder's state IS the wire shape field-for-field — so unlike the call script there is no translation, only which fields are applicable, their labels, and how to render one for a card. `describePredicate` turns a condition into a sentence about a call ("call → status is completed and (…)"), parenthesised below the top level because *a and b or c* groups two ways. `draftHasContent` is false for the empty Telegram step the builder seeds on mount, so a brand-new automation is asked what it is for rather than how to improve something that does nothing. `trigger_type` is proposable only before the first save; master drops it afterwards with the reason, because the update endpoint does not accept it.

**IVR** (`src/pages/ivr/autopilotPatch.ts`). Three proposable fields — `name`, `description`, `steps` — and the two that are absent are the interesting part: **`variables` is derived** (the builder rebuilds it from its gather steps' `variable_name`s on every save) and **`max_duration_seconds` is carried through** off the stored row. Either would be a card the author accepts and then does not get, so master does not offer them in its write tool at all and this module reports them as `unsupported`; `formToSnapshot` also does not send them, because this screen does not hold either value. `steps` is ONE field carrying the whole graph, which is what makes the conditional revert load-bearing rather than a nicety: an author who dragged a step after applying has changed `steps`, so Undo correctly leaves it alone.

**An applied call flow goes through `stepsActions.setSteps`, not `replaceAll`.** `replaceAll` exists for a load and deliberately resets the undo stacks; routing an apply through it silently destroyed the author's own history, leaving Ctrl+Z unable to reach anything they did before the proposal. `setSteps` commits through the same history every other edit uses, so the builder's own Undo reaches back past it — and `markDirty()` is called too, or a proposal could be applied and navigated away from with no unsaved-changes warning.

**Clicking a step on the canvas reveals the inspector.** Both `handleSelectStep` and `handleFocusStep` switch the tab back, because that is the exact move an author makes to check what a proposal just did, and while AutoPilot is showing the click would otherwise appear to do nothing. Only the tab switches; the panel stays mounted, so the conversation is still there. `openWorkflowSettings` does the same, since `handleSave` calls it to reveal the blank-description error and flagging a field on a hidden panel is how a save appears to do nothing.

**Applying a proposal carries stored webhook credentials forward, and the browser is the only place that can.** Master never sends a credential to the model and refuses a proposal that would orphan one, so a proposal always arrives with the credential-bearing step still in it — and with the credential itself absent, because the model was never shown it. But `actions`/`steps` are whole-array replacements, so a plain apply overwrote the draft's array (the one holding the values the API *did* send the browser) and Save persisted the deletion. `carryStoredCredentials` matches an automation's webhook actions by **`url`**, consuming each stored match once, because an automation's actions have no ids — the save path is a positional array. `carryStoredHeaders` matches an IVR step by **`id` AND an unchanged `url`**: headers authenticate to an endpoint, so a step that kept its id and re-pointed its url is a bearer token aimed at a new host, and it gets nothing. Either way, only a key the proposal omitted is filled in, and anything that could not be carried is reported by `previewProposal` in the author's own words *before* Apply — the one change on these screens that Undo cannot reach.

**Undo reads LIVE draft state, through a ref.** `revertProposal(live, before, applied, fields)` exists so a field the author edited after applying is left alone, and both builders defeated it: `before` and the `draft` inside the undo closure were captured in the same `useMemo` render, so the comparison always concluded "nothing has changed since" and the revert was unconditional — an author's own edit, discarded by Undo. `PromptEditorPage` gets this right with a functional `setWorkingDraft(prev => …)`; these two hold the draft as several `useState`s behind a `writeDraft` fan-out, so there is no single `prev` and a `draftRef` mirroring the live value is what the closure reads instead. One rule, two mechanisms, both commented at the call site.

**The IVR pane's `WorkspacePanel` label follows the tab.** It is the pane's accessible name, its visible title, its Hide/Show tooltips and its collapsed rail text, so a fixed `"inspector"` told a screen-reader user where they were not and put "Hide inspector" on the button that hides a conversation. The `id` — which persists open/closed state — is deliberately unchanged.

**Only one of the two surfaces reports `savesCompleted`.** The automation builder does — a save keeps the page, so an applied card must stop claiming "not saved yet". The IVR builder does not, because a successful save navigates away and the panel does not outlive it; a counter it could read would never fire, and reporting a save it cannot observe would be worse than the optional field being absent.

**Files:** `src/pages/automations/autopilotPatch.ts`, `src/pages/ivr/autopilotPatch.ts`, `src/pages/ivr/builder/stepsReducer.ts` (`setSteps`), `CHANNEL_LABELS` in `src/types/automations.ts`. Endpoints under `ENDPOINTS.proxy.automations.autopilot` and `ENDPOINTS.proxy.ivrWorkflows.autopilot`. Both panels are `lazy`, so `@assistant-ui`'s ~270 kB chunk stays off each builder's critical path.

### The broadcast workspace (shell + per-type adapters)

`/app/bulk-dispatch-jobs/:id` — one broadcast, whatever its `dispatch_type`. It was a single 1,692-line component in which `dispatch_type === 'ai_voice_call'` appeared eleven times inside one render and four blocks of row translation sat inside a `useEffect`; it is now a **shell** (`BulkDispatchJobDetailPage.tsx`) plus two URL-addressed panels plus five adapters.

**Two panels are URLs, not component state.** `…/:id` (Overview) and `…/:id/log` are both registered in `App.tsx` and both mount the same component, which reads the panel off the path (`broadcastPanel.ts`) — so a panel survives a refresh, can be sent to a colleague and answers the back button, exactly as *Campaign workspace sections* records. `broadcastPanelFromPath` reads the segment **following** the id, never the tail. The bar is a `<nav>` of plain `Link`s with `aria-current="page"`, deliberately not `role="tab"` (these are page navigations) and deliberately not `NavLink` (its prefix match would mark Overview current on the log route). Both links **carry `location.search`**: `broadcastPanelPath` returns a bare path, and a `<Link>` to a bare path discards the query — which silently widened a `?batch=`-narrowed view to the whole broadcast and took the export's scope with it.

**Three things stay above the bar**, because they belong to the broadcast rather than to a panel: its name and status, the buttons that CHANGE it (Stop, Retry — a reader must be able to stop a broadcast from wherever they noticed the problem), and the live dialling strip.

**An adapter supplies details, never layout** (`adapters/types.ts`). It returns metric tiles, distribution rows, log columns, a row link, config groups and `nouns`; where any of it goes is the shell's decision, which is what makes a sixth dispatch type one object literal rather than a fork. `BROADCAST_ADAPTERS` is a `Record<BulkDispatchType, BroadcastAdapter>`, so a new type is a compile error until somebody says what it is called and how it reads — but `broadcastAdapter()` still returns `null` for an unknown one, because `dispatch_type` arrives off the wire from a service this repo is not a dependency of, and returning the missing entry unchecked took the whole page white. `nouns` drive every phrase, so an announcement is never "dialled" and `completed` reads "Played to the end" on it, "Finished the menu" on a phone menu, "Connected" on an AI call. The chip label comes from `TYPE_LABELS`, never a literal: the Broadcasts list draws its type filter, chips and row badges from that map, and a literal here let a reader filter by "Voice message" and open a broadcast labelled "Announcement".

**The metric row is `[outcome, outcome, time, speed]`, and the order is a contract.** It keeps the two shares adjacent so they can be read as a pair, and never leaves a rate between two counts it is not a share of.

**Every figure names the population it describes, and they are different populations.** `OutcomeBreakdown` partitions `total` across four phases — `not_started`, `in_flight`, `finished`, `stopped` — and:

- **Rates divide by `finished`**, never `total`. This was guarded by a `live` flag, which was the wrong question: `isLiveJob` is false for a **cancelled** broadcast, and those are precisely the ones that end with thousands of contacts never dialled (the reason "Stop remaining calls" exists). A broadcast stopped after 250 of 5,205 calls read "Reached a person 200 · 3.8%" with a sub-line asserting "Of 5,205 numbers dialled", for one that connected 80% of the calls it placed.
- **`stopped` is its own phase** so `missed = finished - reached` stops counting calls stopped before dialling as reach failures. It does **not** claim those rows were never dialled: an `initiating` row holds a concurrency slot and whether core had handed it to the carrier is unknowable here (the cancel endpoints return a bare count), so the copy says "we have a result for" rather than naming dials — the weaker claim, because the stronger one would shrink the denominator and OVERSTATE the reach rate.
- **An AI stop is `failed`, and only `status_summary_stopped` can say so.** Core writes a stopped AI call as `failed` + a stop code (there is no `cancelled` on `calls`), so before master served `status_summary_stopped` a broadcast stopped after 10 of 50 calls counted 40 never-dialled rows as failed calls and read a 10% connect rate for one that connected half of what it placed. That field is the per-status SUBSET of `status_summary` core counts as a deliberate stop (the rule Super Admin usage and core's batch analytics exclude). `buildOutcomeBreakdown` moves those parts out of their status into one merged row keyed `STOPPED_ROW_STATUS` (`'stopped'`, labelled like `cancelled`, phase `stopped`) and, with the split known, files a `cancelled` row core did NOT call a stop as `finished` under `CANCELLED_AFTER_DIALLING_LABEL` — a voice-message call that was already dialled when it was cancelled (by the carrier, or by a Stop that landed after the dial recorded a carrier id; core cannot tell which), so a real miss, and the "Didn't reach" tile says "cancelled after dialling" for it. Every one of those cancel branches keys on `isCancelledStatus`, which covers both spellings core has written (`cancelled` and one-L `canceled`), so a one-L row cannot be relabelled in the breakdown and described differently in the tile. `retryable` stays on raw counts, because a retry of `failed` does pick the stopped rows up — but the merged row's own "Can retry" tag is an AND over its parts, never an OR: a row of 3 stopped `cancelled` + 2 stopped `failed` must not claim 5 retryable calls when the retry dialog can select only the 2. Absent/`null` (older master or core, a failed read, messaging) is unknown and gives exactly the old behaviour. **The log's status chips call it with `splitStopped: false`**: they filter the log by raw status, and a "Stopped" chip would match no row (a stopped AI call is `failed` in the log). `friendlyProgress` (the header subtitle and the list row's progress line) applies the same split: the stopped part leaves "didn't connect" and gets its own "· N stopped" clause. `useBulkDispatchJobs` and the detail page's poll carry the field together with the summary it describes, so a poll that loses core's summary keeps the previous pair rather than mixing an old summary with an unknown split. The list row's segmented progress bar still reads raw statuses.
- **Dialling speed divides `dialled` (`finished + inFlight`)**, never `total`. Core writes the per-item rows up front, so a rate over `total` read "2,603 calls / min" two minutes into a broadcast that ran ninety, and FELL as it progressed. In-flight items count because a ringing call consumed a dial.
- **`unmeasured` is honoured by every consumer.** An absent `status_summary` renders a dash and a sentence, not `0` — a zero is a measurement, and it sat directly above the card correctly saying the results were unknown.
- **Retryability is per dispatch type**, from `RETRY_CALL_STATUSES`. A flat five-status set overclaimed three ways: `timeout` is not retryable for an AI call or an announcement, `switched_off` is not for a phone menu, and it offered a WhatsApp broadcast's failures for retry while master had no message retry. Message broadcasts now have entries of their own (`failed` + WhatsApp's `undelivered`, never `sent`, which may have arrived), mirroring master's `RETRY_STATUSES`, and `RetryCampaignModal` gives them a one-step dialog (`MessageRetryContent`): outcomes only, no outbound number, no "Simultaneous calls", and no `caller_ids` on the wire — master refuses that field on a message job and re-sends from the original connection. `isRetryEligible` offers it only while at least one message is in a retryable outcome (call broadcasts keep Retry even when everything connected): a delivered-everything broadcast had no Retry before this and must not grow one whose dialog says there is nothing to retry. Email broadcasts retry through master too, but this UI has no `email_message` broadcast type yet.

**A log column earns its place twice**: the type must have the field (`adapter.logColumns`) and this page of rows must have a value in it (`anyRowHasValue`). On the broadcast this redesign came from, four of nine columns were dashes on all 5,205 rows. Two absences are also deliberate: **no recipient search** where the endpoint would not filter (`listMessages` takes no `phone`, and an unlisted param is dropped *silently*, so a search box there answers 200 with the whole list dressed as search results — declared as `supportsRecipientSearch`), and **no chevron** where `rowHref` is null for every loaded row (a static call has no per-call page).

**A failed log read is an ERROR, never an empty one.** The three empty messages — "haven't started going out yet", "No calls match the filters you've set", "No calls have been recorded" — are all findings *about the broadcast*, and the `catch` used to clear the rows and store nothing, so a transport failure chose one of them. The filtered one is the worst: a 500 on page 2 of a status chip read as "your filter matched nothing", which sends the reader to change a filter that was working. `callsError` renders an `ErrorAlert` *ahead of* the empty branch, and a later good read clears it.

**The live poll advances the ROWS as well as the counters.** The log effect is keyed off the job's stable primitives, which is what stops the 30-second poll flashing the table's spinner — and also meant the rows never refreshed at all, so a `ringing` row stayed `ringing` for the session while the summary inches above it counted the same call completed. `callsPollTick` is the job fetch's own `silent` idea applied to the log: a background read that leaves the rendered table in place, keeps the last good page on failure, and shows neither spinner nor error. Only a foreground read — a filter, a page move, a cancel — reports either, because only those were asked for.

**ONE monotonic token governs every log read, foreground and background alike.** Each effect holding its own `cancelled` flag only ever invalidates the previous read of its *own kind*, so a background read was cancelled by nothing but the next poll tick or an unmount — and a filter change, a page move or a retry-chain link followed while one was in flight left it to resolve afterwards and commit its old scope over the rows the reader had just asked for. `callsTokenRef` is `fetchJobTokenRef`'s pattern eighty lines up in the same component, and the same rule follows from it: whichever read is latest is the only one allowed to commit, and the only one allowed to clear the spinner, because a superseded request no longer can. The "nothing to read" guard takes **no token on a background tick** — bumping it there would invalidate a foreground read legitimately in flight against a scope that branch cannot serve.

**The error branch carries a retry, and it is load-bearing rather than a courtesy.** In that state the table and the pager are both hidden and a *terminal* broadcast does not poll, so a transient failure on the first read had no route back at all. The only control still rendered is the status chip row, and clicking the already-active chip changes no fetch dependency — so it does not re-read either. `callsRefreshKey` already existed for the post-cancel reload and is in the foreground effect's deps, so it is exactly the right lever.

**IDs render in FULL in Technical details, truncated only in the identity strip.** That block's own summary says "internal ids", and an id in a technical disclosure exists to be pasted into a support thread, a log search or an API call, which a `truncateId` prefix cannot be — while `contact_list_id` and `schedule_id` appear nowhere else on the page, so the 8-character prefix was the only form of them available anywhere in the product. The strip keeps truncating, because there the id is a glanceable handle. `.techValue` needs `overflow-wrap: anywhere` and `.techFact` a `min-width: 0`, or a 36-character UUID pushes its own 180px grid track wider and the grid overflows the card.

**Test that refresh through `visibilitychange`, not by advancing the timer.** The poll effect wires one `refresh()` to two triggers — a 30-second `setInterval` and the handler that refreshes when the tab comes back — so the event path exercises the same line with no timers. Reaching it through the interval means `useFakeTimers` plus an async advance racing the render's own promises: it passed locally and failed in CI on the slower scheduling, with the same `expected 1 to be greater than 1` the mutation check produces, which makes a real regression and a flake indistinguishable.

**A tile may only claim what is true of every status inside it.** `outcomeTiles` sums `DONE_STATUSES` (`completed | sent | delivered | read`), and `utils/vocabulary.ts` is explicit that those are not one event: `sent` is "Sent to the network", only `delivered` is "Reached the person's phone". So messaging's reached tile is **"Went out"**, not "Reached the phone", which reported every message the provider merely accepted as delivered to a handset. The label was weakened rather than the figure narrowed, because narrowing is worse both ways: `sent` is not a failure, so moving it out would file it under "Didn't arrive"; and it is not reliably transitional either — a provider that never returns a receipt leaves a row `sent` for good, so treating it as in-flight makes a finished broadcast read as permanently unfinished. The outcome card below breaks the statuses out for anyone who needs the difference.

**`LiveDialingStrip` is voice-only, and a noun could not generalise it.** Both figures are concurrency — `liveDialingCallCount` sums the four statuses that hold an account line, `onCall` is `in_progress` — and a messaging broadcast has neither (its live rows are `sending` / `pending`). So an actively sending WhatsApp campaign read **"0 messages dialling now · 0 of them are talking to somebody"** under a live ember dot: a confident zero about work in progress. The shell gates it on `nouns.scope === 'call'`; swapping `itemPlural` cannot fix a sentence about lines and conversations. The test that covered this had asserted the opposite, on a fixture that planted `in_progress: 1` on a WhatsApp job — a status that type never produces.

**`stopped` is labelled "Stopped", not "Stopped before dialling".** A cancelled row can have come from `initiating`, which was holding a slot, and whether core had already handed it to the carrier is unknowable here — the cancel endpoints return a bare count. `denominatorSentence` refuses that claim two cards above for the same reason, and the heading was making it in the direction that *under*-reports placed calls.

**The phase key groups on the PHASES PRESENT, not on `live`.** `groupByPhase={live}` hid the Stopped heading on a cancelled broadcast — exactly the payload the phase was added for, which has `finished` rows and `stopped` rows both. The reasoning for skipping the grouping ("on a finished one every row is in `finished`") is true only of a broadcast that ran to the end. Relatedly the caption uses `formatShare`, never `Math.round`: 5,204 of 5,205 rounds to "100% of the way through" above a key still showing a waiting row, which is the one thing `formatShare`'s `>99.9%` cap exists to prevent.

**`denominatorSentence` returns `null` for two OPPOSITE reasons and only `reachedSubtitle` may resolve them.** `finished === total` means "let the type's own sentence speak"; `finished === 0` means "say nothing at all". A bare `denominatorSentence(...) ?? copy.reachedSub(ctx)` treated both as the first, and every adapter's `reachedSub` names the whole list — so a just-started broadcast and one cancelled before anything settled both read "Reached so far · 0" over **"Of all 5,205 numbers dialled"**, which is the precise claim this module exists to prevent. The adapter tests covered `finished === total` and mid-run, never `finished === 0` against a non-empty roster.

**An empty `configGroups` drops the CARD, never the `children`.** Messaging has no launch snapshot and must not get a card whose heading promises one, but `children` is the page's technical-details disclosure — batch counters, contact-list id, schedule id, retry-of — and the only place those ids appear. `return null` took it off every WhatsApp and Telegram broadcast, leaving a truncated job id in the identity strip as the page's only id.

**`Column<T>.align` has to win a cascade, and no test in this suite can see it.** `.table th` / `.table td` set `text-align: left` at (0,1,1), so a bare `.alignRight` at (0,1,0) loses outright and the column renders left with the correct class on it — happy-dom applies no stylesheet, so a rendering test can only assert the class landed. It broke by writing an explanatory comment *between* `td` and `.alignRight`: CSS discards a comment at the tokenizer rather than treating it as whitespace, so the declarations moved into a bare rule that could never apply. Alignment must be declared on the `.table th`/`.table td` compound, and `src/__tests__/components/dataTableAlignCss.test.ts` reads the stylesheet to require it — comments stripped first, so the guard can neither be satisfied by a commented-out rule nor match its own prose.

**A test must await the VALUE, not the element that will hold it.** `AgentPerformancePanel` renders `…` for each figure while a read is in flight, *inside* the element the `data-testid` names — so `await findByTestId('today-connect_rate')` resolves on the loading render and every assertion after it is a race, won locally and lost under CI's scheduling (`expected '…Connect rate' to contain 'Not measured yet'`). Wrap the value assertion in `waitFor`.

**A failure reason renders only when it adds to the badge.** `explainCallFailure` returns `restatesStatus`, computed by comparing the resolved text against what the status alone would say — a property of the TEXT, not of the branch. Per-branch it did not work: three error codes resolve to sentences byte-identical to the status branch's, and that is the common path, so the duplication returned on every row core stamped with a code.

**The log's view state is one object tagged with its broadcast**, reset *during render* when the tag stops matching. Both tab routes and every `…/:id` mount the same component and react-router reconciles rather than remounting, so held separately the filter, page size and offset leaked: page 2 of a 5,000-call log survived into a 12-call retry, which fetched at `offset=20` and rendered "No calls match the filters you've set" on a broadcast with twelve calls and none set. The search **draft** lives there too, because the panel unmounts on a tab switch and took anything typed inside the debounce window with it.

**`OutcomeBreakdownCard` inherits the agency contact funnel's arithmetic**: `flex-grow: 0` so a set summing to 91.7% stops at 91.7% rather than growing to fill; **no `gap`**, because percentages plus pixels overflow and flexbox then shrinks a 97% bar to look exactly full (the separator is an inset `border-right`); every width divided by `outcome.total`, never by the sum of the rows drawn; and a total that disagrees with `contacts` stated in words rather than clamped.

**A card's internal layout responds to the CARD, not the viewport.** `OutcomeBreakdownCard` and `DistributionCard` are `container-type: inline-size` with `@container` rules, and `src/__tests__/broadcastCardContainerQueries.test.ts` forbids a `@media` rule for the same decision. `AppLayout` swaps the content column's margin between `--sidebar-width` and `--sidebar-width-collapsed` with a **class driven by a user toggle**, so a card's width at a given viewport differs by 172px according to a preference no viewport query can observe — there is no viewport value correct for both states. The panel's own row may still use `@media`: it governs how many columns the page has, close enough to the viewport that the 172px never crosses a boundary that matters.

**`LiveDialingStrip` is this feature's only ember element** — accent says what a broadcast IS, ember says what the platform is DOING — and it delegates its pulse to `LiveDot` rather than hand-rolling one, so it inherits the reduced-motion static ring. In light theme its ink is mixed toward black: `--ember` measures 4.53:1 on bare `--bg-primary` but only ~3.97:1 on the `--ember-subtle` wash it actually sits on.

**Two conventions the shared primitives grew**, both purely additive: `Pagination` gained `showEdges` / `itemNoun` / `pageSizeOptions` / `layout="split"` / `flush` for a card-footer pager (changing the page size resets to the first page), and `DataTable`'s `Column<T>` gained `width` — **advisory**, since the table deliberately has no `table-layout: fixed` — and `align`, which also brings `tabular-nums`.

The bar now records the intent (`onNavigate` → a ref) and the shell decides, because only the shell can tell a click from Back/Forward from a first paint. That is also what gives `from_panel` a real value; it was hardcoded `null`, so a Back from the log reported as a landing. ### Broadcast lifecycle — Sending → Calling → Done

A broadcast has three live phases and they are measured in different units, which is the whole reason the old single treatment lied. `processing` counts **batches** going out to master/core; `dispatched` means every batch is with the platform and counts **calls** in flight; only then is it terminal. Cross-service contract: `MagickVoice-platform/docs/bulk-campaign-lifecycle-design.md` (cusui is §5).

**`utils/vocabulary.ts` names the phases and everything else follows.** `processing` → "Sending", `dispatched` → "Calling", `completed` → "Done". `dispatched` used to read "Sending…" — the sending word on the phase that had finished sending — which left the calling phase unnamed and put the chip in direct contradiction with the per-call progress line beside it. `STATUS_OPTIONS` on the list page and every badge draw from `statusLabel`, never a literal, so the rename propagates.

**`JobProgressCell` drives the bar AND the line off `jobPhase`**, which is derived from the same `status` the chip is. `sending` forces `SegmentedProgressBar`'s new `basis="batches"`: during `processing` a per-call `status_summary` covers only the batches ALREADY sent, so segments drawn from it fill toward 100% of a population that is still growing and go **backwards** as the next batch lands. `calling` gets per-call segments, the `friendlyProgress` sentence and the dialling figure; terminal gets the outcome breakdown alone. It takes `liveDialingCallCount` — the figure `LiveDialingStrip` is built on — rather than the strip itself, because the strip is a `role="status"` live region with a hint line: right once above one broadcast, twenty announcing over each other in a table. **Live rows render on the rail, not in the history table** (`isLiveJob` splits them), so `LiveJobCard` is where `Sending`/`Calling` is actually read — it gained the status chip it never had, and shares the same cell.

**`BroadcastLifecycleStepper` is the direct answer to the ticket.** Created → Started → **All batches sent** → Finished, each with the timestamp master recorded. "All batches sent" earns its own milestone because collapsing it into completion is exactly the defect: master used to finalize the direct and contact-list dispatch paths the instant core acknowledged the request, so that moment became `completed_at` and the customer got a completion email with zero calls connected. State is on `data-state` as well as in words — happy-dom applies no stylesheet, and colour alone would not carry it anyway.

**`isSettling()` / "Finishing up" is now a LEGACY fallback and is commented as one.** It was the primary mechanism (ticket `86d372ngx`); it is not any more, because a new row sits in `dispatched` and reads "Calling" off its real status. It stays because rows written before the fix cannot be repaired — a `completed` row with `completion_tracking_expected = false` means both "no callback yet" and "callbacks were never configured" and nothing distinguishes them, so there is no backfill (design §6; master keeps `SETTLING_JOB_SQL` for the same rows). `dispatched_at` is `string | null` for the same reason, and the stepper renders a legacy row's dispatch milestone as reached-but-**"Time not recorded"** rather than unreached — drawing it unreached on a finished broadcast would replace the false claim being removed with a new one.

**`useBulkDispatchJobs` asks for `include_status_summary` on EVERY poll.** The 1-in-4 `lightweight` cadence and the `needsImmediateTerminalVerification` latch are gone: both existed only to ration master's per-job core fan-out, and master now issues one grouped request per dispatch type per page (design §4.5). Rationing the summary is also what made the old heuristic unreliable — it needs the summary, had it a quarter of the time, and a first load that missed it never started polling at all, because `isLiveJob` for such a row *requires* it. What survives the cut and must keep surviving: the monotonic **load token** (only the latest response commits), the **visibility** handling (no timer while hidden, one catch-up on return), the `loadRef` that keeps the interval stable across polls, and `needsTerminalVerification` — master's summary block swallows a core failure in a bare `catch` and answers with the rows and no summary, which is indistinguishable on the wire from "no calls yet", so a formerly-live voice row keeps its previous status until a summary can settle it.

**Stopping a broadcast reports what it stopped, and is offered only to a role that can.** Stop is the same job-level control for AI, IVR and voice-message broadcasts (ClickUp `14ygtkj95yp`). `broadcastStopToastMessage` builds the toast from `cancelled_in_core` in the adapter's nouns ("1,204 calls that hadn't started were cancelled; calls already ringing or connected will finish") — "Broadcast stopped." alone read the same whether core cancelled everything or nothing. `core_cancel_complete` / `core_cancel_failed_batches` are optional on the wire: **absent is an older master, i.e. unknown**, and only a literal `false` turns either toast into a warning (the Stop one points at "Stop remaining calls"). That pointer is honest because `isStopRemainingEligible` now waives the 24h age gate for a **`cancelled`** job — the operator already said stop, so there is no "Finishing up" to protect, and the gate hid the only recovery control for the day after a Stop that stranded calls. Every other terminal status keeps the gate. The buttons mirror master's floors (`JOB_STOP_PERMISSION` for the job routes, `BATCH_CANCEL_PERMISSION` per type for "Stop these calls" — IVR is on `proxy.calls.create`, like AI calls); `LiveJobCard` renders no Stop when the caller passes no `onCancel`, so the permission check stays with the page.

**Files:** `src/components/bulk-jobs/{JobProgressCell,BroadcastLifecycleStepper}.tsx`, `jobPhase` / `batchProgressText` in `src/pages/bulk-dispatch/progress.ts`, `dispatched_at` in `src/types/bulk-dispatch-job.ts`.

### Broadcast "Simultaneous calls" (per-broadcast concurrency)

An optional cap on how many of ONE broadcast's calls are live at once (ClickUp `14ygtkj9pgr`; cross-service design `MagickVoice-platform/docs/broadcast-concurrency-design.md`, cusui is §7). Operators see their account limit read-only and may only go LOWER — the documented exception to the agency D10 "concurrency is a commercial lever" posture. The label is always "Simultaneous calls", never "concurrency".

**Gating — a flag-off tenant sees and sends nothing new.** The only gate is `GET /proxy/calls/concurrency-limits` (`getConcurrencyLimits` → `useConcurrencyLimits`), which master answers `enabled: true` only when core's `broadcast_concurrency` flag is on AND master's preconditions hold. The hook's `status` separates two hidden states that must not be confused: **`disabled`** (a clean `enabled: false` — whose other fields are neutral placeholders and ignored — or a 404 from an older master) renders nothing at all; **`failed`** (a 403, 5xx, network, or a body it cannot read — an `enabled: true` body is validated WHOLE: a known `mode`, a finite non-negative `account_total`, and a `providers` object whose every value is a finite non-negative number, so a bad entry fails the read instead of becoming a provider with ceiling 0) keeps the field hidden and renders `SimultaneousCallsLoadError` ("Couldn't load simultaneous-call limits." + Try again) in its place **only when `showLoadError`** — this tenant::account's last CLEAN answer was `enabled: true`, remembered in a small localStorage map (`KNOWN_ENABLED_STORAGE_KEY`; set by an `enabled: true`, removed by a clean off/404, untouched by a failure (a 403 included); every access try/caught, absence = not known enabled). Anywhere else a failure is silent, because during rollout every tenant is flag-off and a notice about a control it has never seen would appear whenever master's flag read hiccups. The payload is the same either way: the composer sends nothing without `enabled`, and the retry dialog treats `failed` as `unknown` (omit ⇒ inherit; master's `details.max_concurrency` 400 still shows inline where the field would be) — a failure is never a clean "off". A 403 is a failure, not an "off", precisely because a clean "off" is the one state in which the retry dialog sends `null` and drops a capped parent's limit. Answers are cached per tenant+account for 60 s, failures for 30 s (`utils/concurrencyLimitsCache.ts`); `refetch` bypasses it, and sign-out (`AuthContext`'s three sign-out paths) clears it — markers included — with a generation bump so a read in flight cannot write the old session's answer (or marker) back.

**Payload contract.** Composer: `DispatchContext.maxConcurrency` — the key is OMITTED when empty (never `null`), top-level `max_concurrency` on the immediate-send endpoints, `call_payload.max_concurrency` on a schedule. Retry (`RetryBulkDispatchJobInput.max_concurrency`) is three-way — absent = inherit the parent's cap, `null` = no cap, number = new cap — and `retryMaxConcurrency` in `RetryCampaignModal.tsx` is the whole rule table (pinned row by row in its test): untouched inherits (master CLAMPS an inherited cap but VALIDATES an explicit one); touched and emptied on a capped parent sends `null` — an explicit clear always wins, a zero ceiling included; a zero ceiling otherwise inherits whatever number was typed (it is not on screen) and says "This retry keeps the original broadcast's limit of N simultaneous calls."; availability unknown inherits; a clean `disabled` on a capped parent sends `null` and says so ("…this retry will run without a limit" — warning-styled, `role="status"`, and referenced by Start's `aria-describedby`), because master refuses an inherited cap it cannot honour rather than letting it silently become uncapped. Master's 400 `details.max_concurrency` is read by `retryCapRejection` in the callers' `catch` (which also fires `max_concurrency_rejected`, once) and goes onto the field — or, when there is no enabled field to carry it, into the field's place — never a toast or banner; the dialog anchors it to the request it was about DURING RENDER (not in an effect, so the first paint that carries it already blocks Start) and retires it when that request changes.

**Ceiling.** `concurrencyCeiling` mirrors master's `ceilingFor` exactly: `legacy_total` → the account total; `provider_breakdown` → the single dialled provider's allocation (0 if it has no row), else the account total; clamped to 1000. A zero ceiling disables the field, warns that calls from those numbers will fail, and makes the review row a warning — but does not block launch (master and core are the authority).

**Details page.** `simultaneousCallsRows` (adapters `shared.tsx`) renders a Delivery row ONLY for a set cap, labelled "(current)" because it reads the job column (a super-admin may change it mid-run) under a card headed "a snapshot taken when the broadcast launched". While live it reads "5 (3 in use now)" from the best-effort `job.concurrency` block, with a hint that fewer than the cap may be active; the figure is dropped (cap alone) unless `in_use` is a non-negative integer and the block's `max_concurrent` agrees with the recorded cap.

**Analytics.** `campaign_launched` carries `max_concurrency` / `max_concurrency_ceiling` (both `null` when not offered); `max_concurrency_rejected` (`surface: 'composer' | 'retry'`) records a 400 on the field.

**Files:** `src/utils/broadcastConcurrency.ts` (every rule and every sentence), `src/utils/{concurrencyLimitsCache,strictInteger}.ts`, `src/hooks/useConcurrencyLimits.ts`, `src/components/campaigns/{SimultaneousCallsField,RetryCampaignModal}.tsx`, `src/pages/campaigns/CampaignComposerPage.tsx` (+ `registry/{ai,static,ivr}.tsx`, `registry/types.ts`), `src/pages/bulk-dispatch/adapters/shared.tsx`, `e2e/broadcast-simultaneous-calls.spec.ts`. Deliberately untouched: the legacy bulk modals and `CreateRecurringSchedulePage` (they send no cap; master still honours a stored `call_payload.max_concurrency`).

### AI reply grace period (per-reply barge-in grace)

Two optional AI-voice settings beside the greeting grace (ClickUp `14ygtkjadr9`): `turn_barge_in_grace_period_ms` (0..30000; `0` turns it off) and `turn_barge_in_grace_mode` (`drop` | `energy_gate`). They hold back caller audio at the start of EVERY AI reply so the AI's own echo is not read as an interruption; the greeting grace covers only the opening after pickup. **Placement is exactly `barge_in_grace_period_ms`'s**: inside `config` on a single call (and on a schedule's `call_payload.config`), TOP-LEVEL on a bulk dispatch. Offered wherever the greeting grace is — `InitiateCallPage` (Advanced), the composer's AI panel, the legacy bulk modal on `CallsListPage` — and not on the inbound DID drawer (inbound has no per-call reply grace). Retry needs nothing: master re-dispatches from its stored snapshot.

**One name on every surface, and it is about the AI starting to speak.** The field is **"AI reply grace period"**, its select **"Caller audio during this time"**, and a Review/confirm/broadcast-detail row **"AI reply grace"**. Bare "Reply grace" was read as the *customer's* reply. The modes are **"Ignore all caller audio"** (`drop`) and **"Let loud speech through"** (`energy_gate`) — `energy_gate` is a LOUDNESS gate (audio at or above roughly −30 dBFS passes after a short onset), not a speech detector, so the label says "loud" and the copy never says "clear speech". Customer copy carries no implementation terms ("dBFS", "energy gate", "pipeline").

**What is offered follows the voice tier**, through one pure helper, `turnGraceSupport(pipeline)` → `'full' | 'period_only' | 'none' | 'unknown'`. It accepts both spellings a form may hold (the tier name the chips carry and core's pipeline name); there is no other tier→pipeline map in this repo.

| Tier (pipeline) | Support | UI |
|---|---|---|
| Platinum (`gemini_live`) | `full` | both fields |
| Silver, Gold, Gold II (`openai_realtime`, `elevenlabs`, `gold_ii`) | `period_only` | the period; in place of the mode, "Only the Platinum tier can let loud speech through…" — these tiers treat every mode as "ignore all caller audio" |
| Bronze, Copper (`sarvam_openai`, `sarvam_gemini`) | `none` | neither field; one line, "This voice tier doesn't use an AI reply grace period." |
| none chosen (with no account default loaded yet) / a tier this build does not know | `unknown` | both fields, plus a line naming which tier supports what |

**The legacy bulk modal's blank pipeline option is a real tier.** It omits `ai_pipeline`, so the server dials the account default — and the option and the confirm row both name it ("Default (Silver)"). So that modal resolves the tier from `batchPipeline || defaultPipeline`, in the payload, the validation and the render alike; reading `batchPipeline` alone offered (and sent) "Let loud speech through" on a Silver default, and a period on a Bronze one. `''` is `unknown` only while metadata has no default. (The single-call page and the composer require a tier chip, so they have no blank tier.)

**A field the tier hides is neither sent nor echoed**, and must not block: `turnGracePayloadFields`, `turnGraceReviewLabel` and `turnGraceSecondsError` all take the support, so switching from Platinum to Silver after choosing "Let loud speech through" drops the mode from the payload and the Review row, and a hidden out-of-range value never refuses a launch. A Review row that records a setting with no effect is exactly what this rule exists to prevent; on `none` the row says "Not used by this voice tier".

**A typed period that does not parse omits BOTH keys** (`turnGracePayloadFields`' backstop, behind the submit-time `turnGraceSecondsError`): sending the mode alone would apply it to the platform-default window. Blank is different — it is a real "default period", and a mode beside it is still sent. The range error names the positive minimum ("0 (off) or … from 0.001 to 30"), so a refused `0.0004` is explained.

**A period of `0` disables the mode select** (with a sentence saying why), the mode is not sent, and the Review row reads "Off" — never "Off · Let loud speech through".

**The window is a fixed duration from the START of every AI reply; it does not end when the AI stops speaking.** So a long value in "ignore" mode swallows a quick "yes" after a short AI line. The copy says "Usually best between 0.5 and 1.5 seconds", and above **3 s** each form shows a non-blocking warning ("Long values mean the AI may miss quick answers like "yes"."). Core's 0..30 s contract is unchanged — the bound lives in the error, not as an invitation in the tooltip. Choosing "Let loud speech through" shows its risk inline (on strong-echo lines the AI may stop itself; a caller's real "yes" will interrupt the AI; switch back if you hear that).

**Every rule lives in `src/utils/turnBargeInGrace.ts`.** Each key is sent only when set and in effect (`0` is sent as `0`; the mode's "Default" option sends nothing), and no default value is written anywhere — the platform default is env-tunable at core (1.5 s / ignore today), so the copy says "Default", never a number. Unlike the greeting grace, an out-of-range period is **refused, not clamped** (the composer's `derive` returns `isReady: false` with the reason; the other two refuse the submit), and so is a positive value that rounds to 0 ms (`0.0004`): the user typed "a little", not "off". `Math.round` stays — `0.7 * 1000` is `700.0000000000001`, which core's integer schema refuses. The legacy bulk modal resets both grace settings (and the greeting grace) whenever it opens and after a successful send, so one campaign's value never leaks into the next.

**The broadcast detail card** shows one "AI reply grace" row only when the launch snapshot carries either key, so older broadcasts read unchanged (absent/`null` = not set; `0` reads "0 sec — no grace", the greeting grace's wording). It reads each key **top-level first, then under `config`**: an immediate bulk send stores them top-level, but a scheduler-sourced job stores the single-call shape the scheduler replays, with the fields under `config` — reading one place showed every scheduled broadcast as default. The greeting-grace row uses the same fallback. A setting the broadcast's tier ignores is labelled "not used by this voice tier" / "not supported by this voice tier" rather than recorded as if it took effect.

### Notification settings (per-user email subscriptions)

`/app/notifications` (`NotificationSettingsPage`) — which emails the signed-in person receives from this workspace, and how often the usage digest arrives. Master-native routes under `ENDPOINTS.notifications`, like `governance` and `dnc` rather than a `/proxy/*` route.

**The catalog is SERVED, never mirrored.** The events, their labels, descriptions, categories, cadences and defaults all arrive on `GET /notifications/preferences`, and nothing about them is written in this repo — no key union, no label table, no "which ones are digests". Same rule as the audit log's `available_actions`, for the same reason: master is not a dependency of this repo, nothing could check a copy, and the copy is what drifts. `CATEGORY_LABELS` is a presentation nicety with a humanising fallback, **not a whitelist** — a category this build has never heard of still renders its events. A master build with a new event lights it up here with no change on this side.

**It is about the signed-in person and nobody else.** No user picker, no role gate: master reads the caller from the session and every route takes **no subject**, so the page cannot show or change a colleague's subscriptions — the same property the agency `my-*` routes get from their query whitelist. That is also why the sidebar entry and the `GlobalSearch` entry floor at `tenant.read` rather than an admin permission: an unsubscribe only admins can follow is not an unsubscribe.

⚠️ **An `agent` has REAL subscriptions here, and this section used to say the opposite.** The claim was that the page "renders an honest *nothing to configure*" for them because every catalog event is addressed to campaign recipients or `account_admin` and above. False: `isEventAddressableToRole` returns true for every `explicit`-audience event for EVERY role, so an agent sees `campaign.dispatched` and `campaign.completed` — those addresses are typed into a campaign form and may well be theirs. Only `agency.campaign.completed` (`agency.supervise`) and `usage.digest` (`account_admin`) floor above them. The empty state is for a genuinely empty catalog, which today is rare. What IS true is that an agent never sees the main sidebar (`AgentLanding` leaves `/app`), so the `tenant.read` floor is not what decides their access; the route is ungated and a direct link works.

**`AgencySidebar` carries its own entry, floored at `agency.supervise`.** Supervisors who live in `/agency` are the audience for `agency.campaign.completed` and the usage digest, and they had no path to their own settings without switching products — the main sidebar's entry is AppLayout-only and so is `GlobalSearch`, so Cmd+K did not help either. It is the one entry in that shell that deliberately leaves it (`/app/notifications`). The higher floor is about whose shell carries the link, not about who may open the page: a viewer or operator reaches it from the main sidebar at `tenant.read`.

**A form with one Save, not a switch per request.** A digest has TWO controls (on, and how often), so saving on each change would write an intermediate state — and a partial save is invisible on a screen where "I thought I turned that off" is the failure to avoid. Only what actually changed is sent (`changed`), because the body is a PATCH: an event omitted keeps its value, so a client built against an older catalog cannot reset one it has never heard of. A frequency is sent **only on a digest**, since master REFUSES one on an immediate event rather than ignoring it — including it would 400 the whole save over a field the person never touched. Picking a cadence also switches the digest **on**, or somebody selects "Every day" on a disabled digest and saves a setting that changes nothing.

**`is_default` is surfaced, not hidden.** Somebody who has never opened this page IS subscribed — the catalog default applies — so rendering that as "unset" would invite them to turn on something already on. The chip says the value is the default, not that it is absent. **It tracks the DRAFT as well as the stored row** (`isAtDefault`): keyed on `is_default` alone it survived an edit, so toggling a default subscription off read "Off · Default" until Save and reload. The chip's claim is about the value on screen, and once the draft diverges that value no longer came from the catalog. Both halves are compared, because changing only a digest's cadence is as much a divergence as switching it off.

**Preview renders, it does not send.** `POST /notifications/digests/preview` builds the caller's own digest for the most recently completed period and returns it. It earns its place three ways: it is how somebody decides whether they want the mail before subscribing; master deliberately never retries a failed send (a claimed delivery row is kept, not deleted), so this is the *recovery* for a digest that never arrived; and it makes the whole feature demonstrable with no mail provider configured, which is the state of every developer machine. `is_empty` is rendered as a sentence rather than as a blank document — the scheduled run SKIPS an empty period, so "there would be nothing to send" is the true and more useful answer.

**Renderings that must agree with the mail, all pinned by tests on both sides.** `change_pct: null` means "grew from nothing" and renders as the word **"new"**, never `0%` and never `Infinity%` — the same word master's template uses. Millicredits arrive as a **string** (`bigint` does not survive `JSON.stringify`) and are divided for display; the figure is invoice-adjacent and must not pass through a float on the wire.

⚠️ **The change figure and its CAPTION are two elements, not one sentence**, exactly as `usage-digest.template.ts` treats them — the cell is a bare `new` and the caption is `first activity here`. Interpolating `formatChange` into a sentence is the failure that produced "2.1 credits used (new on the period before)", and this page had it: `formatChange(null)` is `'new'` and " vs previous period" was appended unconditionally, describing a comparison with no second term. The credits-figure tests already sent `consumed_change_pct: null` on a non-empty preview and never asserted the string, so the suite stayed green.

The modal also renders **talk time** per operation (`formatDuration`, mirroring master's thresholds, and ABSENT rather than "0m" for a row with none — a `kb_search` row legitimately has no duration) and **credits added** when `added_millicredits > 0`, both of which the mail shows and the modal omitted. The promise is "exactly what would be sent", so an omitted row breaks it as surely as a wrong number.

**The in-flight GET is fenced by a monotonic token** (`loadTokenRef`, the shape `BulkDispatchJobDetailPage`'s `fetchJobTokenRef` uses), and that is not defensive tidiness — without it the page could commit ANOTHER TENANT'S preferences and then save them here. `load` is recreated when `tenantId` changes and the effect re-fires, but nothing cancelled the request already out, and TopBar's tenant switcher is on this very page: GET A in flight → switch to B → A resolves last → the form holds A's values under B's session → Save writes A's draft under B's `X-Tenant-Id`. Neither request failed, so nothing surfaces. The token is re-checked after every await, the post-save refetch included. That refetch is also **silent** (`load(true)` sets `loading` only on a first read), since replacing the whole form with a spinner after a successful save makes a slow follow-up GET read as a failed save. Errors go through **`showErrorToast(err, fallback)`**, the repo's convention, which keeps a masked 5xx's request id in a copyable chip at the longer dwell rather than inline in the sentence — and the page's test mock deliberately no longer aliases it to `showToast`, because one mock behind both names made either call satisfy either assertion.

**Files:** `src/pages/settings/NotificationSettingsPage.tsx`, `src/api/notifications.ts`, `src/types/notifications.ts`. The account is deliberately NOT threaded through the API module: master scopes a digest from the caller's own membership rather than from `X-Account-Id`, since that header is unauthenticated and optional and an account-scoped member could otherwise preview a sibling account's spend by omitting it.

### Super Admin Dashboard

Separate layout at `/super-admin/*` with its own sidebar. Pages: Tenants (list + detail with members, credits, phone number assignments, service config), Users, Admins, Audit Log, Providers (telephony provider CRUD), Phone Numbers (pool management with lifecycle actions), Usage (`SAUsagePage` — per-tenant/account usage by offering and date range: summary StatCards incl. actual vs billed minutes, paginated records via `useSuperAdminUsage`, chunked CSV export following `X-Next-Cursor` with abortable cancel; API in `src/api/superAdminUsage.ts`. **All view state lives in the URL** — tenant/account/offering/period/custom dates, the record filters, the sort and the page offset are `useSearchParams`, so the whole view is shareable and restores exactly; partial URL state would restore half a view, which is worse than none. Beyond the offering/period selectors the records narrow by **direction** (ai_calls only — the param is a 400 elsewhere), a **multi-select status** filter (comma-separated; `USAGE_STATUS_OPTIONS` is a hand-copy of core's `USAGE_STATUS_VALUES` per offering, pinned by an exact-equality test since there's no build-time link), and a **spoken-seconds comparison** (`>`/`<`/`=`/`between` is UI-only vocabulary, mapped onto the inclusive `spoken_seconds_min`/`_max` wire pair so no operator enum has to be mirrored across three repos; never sent for `messages`). Every param is validated on read against the current offering, so a stale or hand-edited link degrades to a valid request rather than a 400. The CSV export narrows with the same filters. Two things about the hook are load-bearing: `updateParams` writes through a **ref**, because `setSearchParams` — including its functional `prev =>` form — composes against the params captured at the last render, so two setters in one tick would clobber each other; and read-modify-write setters (`toggleStatus`, `toggleSort`) take `updateParams`' functional form for the same reason. Pagination and sort **push** history entries (Back undoes them); filter edits **replace** (no history spam while typing). The summary StatCards are deliberately filtered too, so a chip row states each filter in force, with per-chip clears — and a spoken-seconds *minimum* above zero is called out as restricting the view to connected calls, since core's contract gives an unconnected row `spoken_seconds = 0`), and Voice Alerts (`SAAlertsPage` — catalog-driven platform alert configuration with channel/definition CRUD, inherited roster labels, dry-run-first testing, explicit real-call confirmation, and write-only platform-key replacement; API in `src/api/superAdminAlerts.ts`).

**The tenant detail page shows the CACHED credit balance beside the ledger one, because they are two different numbers and only one of them is what the customer sees.** Master serves `credit_cache` on `GET /super-admin/tenants/:id`: Postgres' `tenant_credit_balances.balance`, Redis' spendable balance, the ledger-derived hold total, the settled Redis-path usage Postgres never recorded (`redis_consumption`), and the `drift` between what the cache serves and what it should. Until this existed the page rendered only the Postgres figure while the customer's own `CreditBadge` rendered the Redis one, so a tenant could be shown 49.81 credits against a 4,052.83 ledger with nothing on this page saying so — which is exactly what happened, for twelve hours, after a super-admin top-up that never reached Redis. `POST …/credits/reconcile` (`reconcileCredits`) is the repair; the balance key has no TTL, and while the write-time sync does adjust it by deltas, nothing else ever rewrites it to a known-absolute value — so an error already baked in is carried forward forever until someone presses that button.

Three states must stay distinct, and conflating any two is a false statement about money: the field **absent** (an older master — render nothing, there is no route to call), **`null`** (master could not reach Redis — drift UNKNOWN, never "no drift"), and **present** (comparable, though `drift` is itself `null` when no cached key exists, which is not the same as `'0'`). One non-obvious rule: with no cached key the "Tenant sees" tile reads **`expected_balance`**, and it reads it rather than re-deriving it. That is exactly what master's Postgres fallback serves — the same `ledger_balance - redis_consumption - open_holds`, floored at zero, computed from the same snapshot in the same request — so the two cannot disagree, whereas reproducing the arithmetic here is a second copy of master's rule with nothing checking it against the first. That copy had already gone stale once: it subtracted only `redis_consumption`, on the reasoning that a hold cannot be honoured against a missing balance key, which is false — `SETTLE_SCRIPT` keys off the independent *reservation* key, so a hold survives the balance key's eviction and can still settle. It is **not** the raw `ledger_balance` either: that row is never debited by a Redis-path settlement, so it is stale-high by the tenant's lifetime consumption. A fixture that leaves the three terms equal cannot tell which one the tile read, which is exactly the fixture a test reaches for by default.

**The ledger tile is labelled "Ledger balance", not "Available", whenever there is a cache to compare against.** `credits.balance` is the raw Postgres row — gross of both settled Redis usage and live holds — so beside "Tenant sees" the two legitimately differ on a perfectly healthy tenant. Under the footer's "matches what it should be serving", an operator reading **Available 4052.83** next to **Tenant sees 4000.00** takes the gap for the drift the card exists to report: the same class of false statement, moved from customer-vs-console to one tile versus the next. Naming it removes the by-eye subtraction; with no cache present the label stays "Available", because then the ledger row is the best figure the page has. The footer's positive claim is keyed on `drift === '0'` — its own evidence — rather than on `cached_balance !== null`; the two are equivalent under master's current contract, and only one of them is the thing being asserted.

**Money is formatted through `BigInt`, never `parseInt`.** These are Postgres `BIGINT`s on the wire. At realistic balances the two agree (dividing by 1000 and rounding to two decimals hides an error below one millicredit, which is why a test written at a realistic magnitude proves nothing), so the guard is pinned at a deliberately absurd value where the float's step size grows past the rounding boundary.

**A reconcile is fenced on the tenant it started against.** The router keeps ONE instance of this page across `/tenants/t-1` → `/tenants/t-2`, so the continuation of an in-flight reconcile is still closed over t-1 — including `reload`, which is `useCallback`'d on the old id. Clearing the note in an `[id]` effect is not enough: that effect has already run by the time the POST resolves, so the late continuation writes t-1's "Repaired" note onto t-2 and then `setData`s t-1's balances there. Every update the run makes — success, error, the reload, and the `finally` — is gated on a `useRef` holding the tenant it began with. A test that unmounts and remounts cannot see this.

**A silent refetch must not blank the page.** `{ silent: true }` originally skipped only `setLoading`, and the page early-returns a full-page `ErrorAlert` on `error` as well as a spinner on `loading` — so a reconcile that SUCCEEDED whose follow-up GET then 500'd replaced the whole tenant view with "Failed to load tenant", taking the result note with it. The money was fixed and the screen said the repair had failed. `useSuperAdminTenant` now routes a silent failure to a separate `refreshError`, keeps the current `data` on screen, and the page reports it beside the note ("these figures are from before the repair"). A full-page error stays reserved for a real initial load, where there is nothing to keep on screen. The `outcome` union is hand-mirrored from master with no runtime validation, so an unrecognised value reports neutrally rather than as a repair that did not happen; and a `repaired` whose balance did not move is a real outcome (master compares the hold counter too) that must not render as `X → X`.

### BYOC Telephony (tenant's own carrier)

A tenant can dial on **their own carrier account** rather than the platform's. Core owns the credentials and the numbers; master proxies. This repo carries two surfaces.

**Super admin** — the `telephony` tab on `SATenantDetailPage`, mounted only while selected (same convention as Feature Flags: the panel owns its own fetches, one of which is a super-admin read of carrier credentials no other tab has a reason to trigger): `TenantTelephonyCredentials.tsx` (credential CRUD, token rotation, the carrier verify probe, revoke) and `ByocPhoneNumbersPanel.tsx` (bulk paste import, retire, per-account scoping). Data via `useSuperAdminTelephonyCredentials` / `useSuperAdminByocPhoneNumbers`, types in `src/types/telephony-credential.ts`. Pure helpers live in `src/utils/byocTelephony.ts` so they can be unit-tested away from the components:

- `scrubSecret()` — belt-and-braces removal of a just-submitted auth token from any message before it reaches a DOM node. Master must never echo one back, but a server quoting its own input is very ordinary. Uses split/join, never a RegExp, so no part of a secret is treated as pattern syntax.
- `describeLiveCallConflict()` — turns core's 409 revoke body into a sentence naming what is still running ("3 announcement calls, 1 IVR session"). Deliberately duck-typed: the count map is per-call-type and core may add one without this repo knowing, so an unrecognised shape falls back to the server's message rather than throwing inside a render.
- `parsePastedNumbers()` — one number per line with an optional `,label`. Normalises to E.164 **client-side** because core's unique index is on the exact string, so `+91 98765 43210` and `+919876543210` would otherwise be two rows for one DID. Duplicates within a paste are reported, not collapsed: the import is one transaction, and an operator who pasted twice should be told.

**Tenant-facing** — a BYOC number is marked wherever a number is shown or chosen: `PhoneNumberRow.tsx` and `CallerIdPicker.tsx` render an "Own carrier" badge off the `is_byoc` flag master returns, with the constants (`BYOC_BADGE_LABEL`, `BYOC_BADGE_TITLE`, `BYOC_OPTION_SUFFIX`) centralised in `src/config/telephonyProviders.ts`. Nothing here decides which carrier a call runs on — that is core's, keyed on the caller ID — so the badge is disclosure, not control.

No feature-flag gate in this repo: the surfaces are super-admin JWT-gated or reuse `proxy.phone_numbers.read`, and there is no new governance capability or RBAC permission.

## Testing Patterns

Tests use Vitest with happy-dom. Key patterns to follow:

**Module mocks:** Use `vi.hoisted()` for mock state that needs to be available before module loading, then `vi.mock()` for the modules themselves.

```ts
const mockState = vi.hoisted(() => ({ user: null as User | null }));
vi.mock('firebase/auth', () => ({ getAuth: () => mockState }));
```

**Context testing:** Use `renderHook` from `@testing-library/react` with a wrapper component providing the necessary context. Use `waitFor` for async assertions and `act` for state updates.

**Fake timers:** Use `vi.useFakeTimers()` / `vi.useRealTimers()` for time-dependent tests (e.g., date formatting, polling).

**Timezone:** the suite is pinned to `TZ=UTC`, set in `vite.config.ts` **at module scope** (guarded on `VITEST`). It has to be there and not in `test.env` or `setup.ts`: Node applies a `TZ` change only when it is assigned on a process's MAIN thread, and this suite runs on `pool: 'threads'`, so a `TZ` set from inside a worker updates the variable and changes nothing about `new Date()`. Vitest loads the config on the main thread before any worker exists.

A test that needs a **non-UTC** zone must live in a `*.timezone.test.ts(x)` file. Those form a second vitest project on `pool: 'forks'` — the main thread of their own child process — which is the only place `process.env.TZ = …` actually moves the clock. The same assertions in an ordinary test file read UTC and pass whatever the code does, which is worse than no test. Both projects declare their own `include`; there is deliberately **no** `include` at the root `test` level, because `extends: true` would inherit it and each project would collect the whole suite. Existing examples: `src/__tests__/agencyBucketDates.timezone.test.tsx` (day-bucket labels west and east of Greenwich, plus a midnight DST transition each way) and `src/__tests__/utils/agencyAttemptRange.timezone.test.ts` (the attempt list's inclusive `to` across a fall-back at midnight).

**Test file naming:** `src/__tests__/<name>.test.ts` or `.test.tsx` for React components.

## Styling

Custom dark theme with CSS Modules. No component library. Design tokens are CSS custom properties in `src/global.css`. Accent color: `#7c5cfc`.

### Ember — the second brand hue

`--ember` (orange) is a **fixed, brand-independent** hue beside the whitelabel `--accent`. It exists because `--accent` is injected per brand at build time (`brands/<name>/brand.config.json` → `__BRAND__` → derived in `src/brand/index.ts`), so it cannot be turned orange without turning Samarthya orange too. The rule is one sentence:

> **Ember colours what the platform is DOING, never what the platform is CALLED.**

Seven tokens per theme (`--ember`, `-hover`, `-deep`, `-subtle`, `-faint`, `-glow`, `--gradient-ember`), plus `--button-ember-bg`. Ember gets only what is **literally in motion**: live indicators, progress fills, ONE primary action per page, the primary chart series. The mark, wordmark, nav, avatars, links, labels and tabs stay on `--accent`; every status, validation and error surface stays on `--danger` / `--warning`. This has been over-applied twice; **bias low.**

**`--orange: #f97316` is NOT ember.** That one is a chart-series colour used positionally beside `--pink` / `--teal`. Rendered as swatches the two are **nearly indistinguishable in dark theme**, so they must never appear adjacent. That is why the whole **announcements identity moved off `--orange` to `--pink`** when `calls` became the ember chart primary — the channel card, its gradient (`--gradient-pink`, added to both theme blocks), the chart series and the `ActivityFeed` row icon, all four, because one concept wearing two colours across surfaces a reader compares is worse than either choice alone. `themeTokenParity.test.ts` asserts the two tokens never collapse to one value.

**One `--orange`/ember adjacency is knowingly tolerated:** `statusColors.ts`'s `busy` renders as a `MiniStatusBar` segment about ten pixels below the ember live badge on the same channel card. `busy` keeps `--orange` because `no_answer` and `timeout` are both already `--warning`, so moving it there would collapse two distinct outcomes into one colour in the one place the segments must be told apart. What separates them instead is the rule itself — the badge moves and pulses, the segment never does, they are different shapes, and the badge carries the word "live" in text. Under reduced motion the badge loses its motion but the segment was never moving, so the *pair* stays distinguishable by shape and by the word "live" — what is lost is the encoding that made them tellable apart at a glance, not the one that made them tellable apart at all.

A related trap that guard cannot see: it parses only `:root` and `[data-theme='light']` **in `global.css`**, so a themed value defined inside a CSS Module is invisible to it. Put any two-theme token in `global.css`, or nothing is checking its second half.

**Ember and `--warning` are 25° apart — the narrowest pair in the palette** — so hue alone cannot separate them at badge size. What does: **ember always moves, warning never does.** Widening the gap by pushing warning toward yellow was tried and rejected: it drops light-theme warning to 3.37:1, under AA.

**That separator is removed by `prefers-reduced-motion`, and an ember indicator therefore owes a STATIC signal too.** The reduced-motion block at the foot of `global.css` is a global `*` kill-switch, so for that reader nothing moves and a live dot becomes an orange warning dot. `LiveDot` (`src/components/common/`) is the shared answer: under reduced motion its halo does not vanish with the motion, it is **held as a static ring**, because a dot-inside-a-ring is a different *shape* from any status dot in the app — an axis that survives when travel cannot. It needs `animation: none !important` to do it, since the global rule's `animation-duration: 0.01ms !important` would otherwise run the halo to its faded end and leave nothing. Anything hand-rolling an ember indicator instead of using `LiveDot` inherits that obligation.

**`prefers-reduced-motion` does not stop an animation — it collapses it, so an animated element's base styles must BE its resting state.** The global block sets `animation-duration: 0.01ms !important` and `animation-iteration-count: 1 !important`, so the animation still *runs*, instantly, and the element lands wherever its fill-mode plus base styles put it. A shimmer written with no fill-mode and no base transform therefore reverted to `translateX(0)` and parked a permanent white band across the middle of a progress bar. Give a sweep a base `transform: translateX(-100%)` (its own `from` frame) and let `overflow: hidden` clip it. The corollary is that a *deliberate* static fallback — like `LiveDot`'s ring — must come from inside a `@media (prefers-reduced-motion: reduce)` block with `animation: none !important`, never from a base style, or it becomes permanently visible for everybody.

**`LiveDot`'s `live` prop is required and deliberately not defaulted.** It replaced eleven hand-rolled pulse keyframes, several of which animated unconditionally — a dot still pulsing on a finished job. A pulse on something that is not progressing is a lie told every two seconds, and making each call site answer the question is the only way to stop writing it. Two escape hatches are legitimate: `WebRtcDialerPage`'s pill dot takes `currentColor` (four pill states, one of them live), and `AgentConsolePage`'s three dots are genuinely semantic (`--danger` recording, `--warning` muted, `--success` healthy).

**A pulsing status chip is not a live indicator.** The "Getting ready…" dots on Catalogs and Documents keep their status colour: a catalog stuck in `processing` for an hour pulses identically to one three seconds from done, so the motion tracks a *poll*, not work. `WrapupTimer` stays `--warning` for the same class of reason — amber there is the feature-wide "this agent is not taking calls" semantic, and ember would collide with it on the one surface where the distinction matters most.

**Never use `--ember` or `--gradient-ember` as a ground for white text.** `--ember` is tuned to be legible *as text* on a dark background (7.32:1 on `--bg-secondary`), which is exactly what makes it a poor background — white on `#fa8231` is **2.53:1**. `.btn-ember` / `--button-ember-bg` run across the dark half of the ramp instead (`#9c3f00 → #c65100` dark, `#a33f04 → #bd4f05` light), where all four stops clear AA. It is a separate class rather than a retheme of `--button-primary-bg`, which is brand-derived and has 157 raw call sites — pointing that token at ember would turn every modal confirm orange at once.

**Light ember is a different colour, not a tint.** A bright orange fails AA on white, so light is a burnt `#bd4f05` (4.90:1 on white, 4.53:1 on `--bg-primary`), and `--ember-deep` goes *lighter* than the base there rather than darker so gradients still run in the same direction. `src/__tests__/themeTokenParity.test.ts` pins every colour token in both blocks: one added to `:root` and forgotten in light resolves to its initial value and fails **silently in one theme only**, which no type check and no unit test in this suite can see, because no stylesheet is ever applied here.

**`hidden` loses to any class that sets `display`.** The attribute's effect is a *user-agent* `display: none`, and origin is compared before specificity ever is — so an author-origin `display` beats it outright, whatever the selector. Put a `display: flex` class on the same element as `hidden` and the attribute silently does nothing: no type error, no warning, and under test it still reports as set, because no stylesheet is ever applied — there is no cascade for the attribute to lose to. The only signal is the pixels. It has cost us this twice (`WorkspacePanel`, then both AutoPilot builders at once, where the pane stayed on screen on every tab and its `flex: 1` held open a tall blank gap). Any such class needs its own guard:

```css
.myPanel[hidden] { display: none; }
```

`src/__tests__/hiddenPanelCss.test.ts` scans for the pattern and fails with the file and rule to add, so a new call site is caught rather than discovered in a screenshot. It ignores `aria-hidden`, which is unrelated to `display`.

**A `position: sticky` grid item is NOT bounded by its grid area.** Sticky is constrained by the element's *containing block*, and CSS Grid §6.6 says a grid item's containing block IS its grid area — so on a spec reading this trap cannot exist. It does: Chromium leaves the item pinned straight out of its own row and onto whatever is placed below it (measured, not inferred; we could only test Chromium here, and the fix is a no-op on an engine that does clamp). Trust the pixels over the spec on this one. This is invisible while the grid has one row, which is how the page lays out on a desktop viewport: Call Scripts' section navigator only started overlapping the inspector at ≤1200px, where the inspector leaves the third column and stacks full-width in a second row, and only when the open editor section was shorter than the navigator. Give any sticky column a plain wrapper element with `align-self: stretch` and stick inside that — the wrapper is a real containing block and is exactly as tall as its row. Both halves matter: no wrapper and the item escapes; no `stretch` and the wrapper collapses to the item's own height, so it can never stick at all. `src/__tests__/PromptEditorNavSticky.test.tsx` pins the pair, since happy-dom has no layout and nothing behavioural can see two boxes overlap. Four other sticky sidebars (CampaignComposerPage, TenantSettingsPage, DashboardPage, AgencyCampaignDetailPage) instead go `position: static` when their grid collapses — the simpler answer, and the right one wherever nothing stacks into a second row beneath a column that stays sticky. Call Scripts is the only grid in the repo pairing a sticky item with a `grid-column: 1 / -1` sibling, which is why it is the only one that needs the wrapper.

**Checkboxes and radios are styled once, globally, and should not be re-styled per module.** The base `input` rule in `global.css` is a text-field rule (`width: 100%`, padding, border) and explicitly excludes `[type='checkbox']` / `[type='radio']` — it used to catch them, which stretched every checkbox to its container with the tick drawn in the middle of the resulting slab. The replacement block is wrapped in `:where()` so it carries **zero specificity**: any module that genuinely needs a different control (the custom pills, the visually-hidden inputs behind switches) still wins without doing anything. Two consequences worth knowing:

- **Never write `width: auto` on a checkbox.** It was only ever a workaround for the old rule; on an `appearance: none` control `auto` resolves to ~2px. A `min-width`/`min-height` floor in the global block catches a stray one, but the declaration is dead and should be deleted rather than relied on.
- **`accent-color` no longer paints anything** — the control is drawn, not native. It is harmless where it restates the accent, but a checkbox that needs a *different* colour must say so with `:checked { background-color; border-color }` (see `WebRtcDialerPage`'s red recording-consent box).
