# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Magick Master Platform Service — a customer-facing Node.js microservice that sits between a React SPA and the Voice AI Orchestrator core service (magic-voice-core). TypeScript on Fastify 5, backed by PostgreSQL 16 and Redis 7. Adds Firebase Auth, multi-tenant RBAC, credit-based billing, and a proxy layer to core.

## Commands

```bash
npm run build          # tsc → dist/
npm run dev            # tsx watch (hot reload)
npm start              # production: node with 4GB heap
npm run lint           # tsc --noEmit (type checking only)
npm test               # vitest run
npm run test:watch     # vitest in watch mode
npm run migrate:up     # apply pending SQL migrations
npm run migrate:down   # rollback last migration
```

Run a single test file: `npx vitest run test/unit/credits/credit-service.test.ts`
Run tests matching a name: `npx vitest run -t "CreditService"`

Local infrastructure (Postgres + Redis): `docker compose -f docker/dev-docker-compose.yml up -d`
Note: Uses port 5433 (Postgres) and 6380 (Redis) to avoid conflicts with core service.

## Architecture

### Request flow

HTTP request → Fastify middleware (request-id → session auth → tenant context → RBAC → [credit check]) → route handler → proxy to core / database → [error-mask `onSend` hook]

### Route registration (`src/index.ts`)

Routes are Fastify plugins registered with prefixes. Each route module exports an async function, adds `preHandler` hooks for auth/RBAC, and defines endpoints. Services (e.g. `creditService`, `settlementService`) are passed via plugin options. Super-admin routes are conditionally registered only when `SUPER_ADMIN_JWT_SECRET` is configured.

### Authentication (`src/auth/`)

Three auth modes:
1. **Firebase Auth** (primary): Bearer token → `verifyIdToken()` → load user from DB
2. **Platform API Key** (fallback): `X-Platform-Key` header → SHA-256 hash → DB lookup
3. **Super Admin JWT** (`src/auth/super-admin.middleware.ts`): Separate JWT auth for platform-wide admin endpoints under `/super-admin`

**A platform API key carries the authority of its CREATOR, bounded by its scopes — and never more than either.** `sessionMiddleware`'s key branch loads `platform_api_keys.created_by` into `request.user`, so a key minted by a person authenticates carrying that person's `UserRecord`, and `tenantContextMiddleware` then resolves that user's membership for RBAC. Three consequences are load-bearing, each of which was a live hole:

1. **No membership, no access.** `requirePermission` used to open with `if (request.apiKeyTenantId && !request.user) return;` — so a key whose `created_by` did not resolve skipped **every** floor in `PERMISSION_MATRIX`, on every route. The reachable set included `POST /credits/allocate`, `PUT /users/:id/role` (which can grant `tenant_owner`), `PUT /tenants/:id`, `DELETE /accounts/:id`, `POST /proxy/sip/connections` — and `POST /api-keys` itself, which made it self-propagating (`created_by: request.user?.id` is `undefined` for that caller, so an unrestricted key minted more unrestricted keys). It read as a decision rather than an oversight because it was *tested*: `platform-api-key-auth.test.ts` asserted "grants full access when the key has no created_by user". Migration 003's `created_by … ON DELETE SET NULL` was the mechanism that produced the state routinely — deleting a user did not disable the keys they had minted, it **promoted** them from that person's role to unrestricted tenant access, silently. Migration 065 makes that FK `RESTRICT`; the middleware is the half that actually closes it, so the two ship together. A NULL-`created_by` key is now **inert** on every permissioned route; the remedy for a genuinely system-provisioned key is a service user with an explicit membership, never a re-opened bypass.
2. **`scopes` is enforced, as an INTERSECTION with the role** (`src/auth/api-key-scopes.ts`). The field was accepted by `POST /api-keys`, stored as JSONB defaulting to `["*"]`, echoed back in the 201 body and the list response, and read in exactly three places — the INSERT, the create response, the list SELECT — and in **no authorization path anywhere**, so a key minted with `scopes: ["calls.read"]` could send WhatsApp messages and delete knowledge bases. The vocabulary is `Permission` itself rather than a parallel one (a second vocabulary needs its own route mapping and drifts the first time a route changes permission); a scope entry is `'*'`, a curated bundle name (`KEY_SCOPE_BUNDLES` — what the UI should offer), or a raw permission. Scopes can only ever **narrow** a key below its creator, never widen it — the reverse reading would make this field privilege escalation by string. Backward compatible by construction: the column default is `'["*"]'` and the wildcard means "defer to the role", so every key already issued behaves exactly as before. Note the deliberate asymmetry — **strict at creation, lenient-but-not-fail-open at request time**: an unknown entry is a 400 naming it (a typo must not become a permanently mis-scoped key), while at request time an unknown entry *alongside recognised ones* is ignored, since the recognised entries are clear intent.

   **What must NOT happen is the wildcard fallback, and the first version of this did exactly that.** Before enforcement, `scopes` was validated as `z.array(z.string())` and nothing more, so a key could have been minted with any vocabulary — `["calls:read"]`, a colon instead of a dot. Resolving an all-unrecognised array to the wildcard handed such a key every permission its creator's role clears, including the ones that spend credits: the keys somebody had **deliberately narrowed** were exactly the keys that came out unrestricted. So an array in which *nothing* resolves **denies**, and so does a value that is not an array at all (JSONB can hold `{}`, a bare string, a double-encoded array — none of which any code path here writes). Only a genuinely **empty** array falls back to the wildcard, because that is absent intent rather than unreadable intent, and the column default is `'["*"]'`. `requirePermission` logs the unresolved entries (`unknownScopes`) so a denial of this kind is diagnosable rather than mysterious. Find affected keys before a deploy with a **structural** predicate — `AND (jsonb_typeof(scopes) IS DISTINCT FROM 'array' OR (jsonb_array_length(scopes) > 0 AND NOT (scopes @> '["*"]'::jsonb)))`. The tempting text form (`scopes::text NOT LIKE '%"*"%'`) is wrong in both directions: a malformed JSONB *scalar* `"*"` renders with those bytes so the text form EXCLUDES the row while the resolver denies it, and `[]` is flagged though it is allowed.
3. **Some routes refuse a key outright, whatever the creator's role** (`denyPlatformApiKey`, `src/auth/api-key-caller.ts`). A role check is not the right question for them: `created_by` is *provenance* — who minted the string, once — not the identity of whoever holds it now, so a key clearing `credit.allocate` is not evidence that a human authorised this particular transfer. (`platform_audit_log` can now at least *say* a key acted rather than a person — `actor_type`/`api_key_id`, migration 067 — but a record written afterwards is not authorisation given beforehand, and these surfaces need no integration at all.) Blocked: key management (`/api-keys`, whole plugin — a credential that mints credentials makes revocation meaningless, and the LIST route would enumerate sibling prefixes), identity/RBAC administration (`/users/*`, whole plugin), credit allocation **and deallocation**, tenant settings (`PUT /tenants/:id` — mirrors into core's `account_settings.default_ai_pipeline`, so it changes **inbound** call behaviour that never passes through master), account create/update/delete, SIP writes **including the test-call trigger**, escalation-destination writes and its test-call trigger, **caller-ID and inbound-routing administration** (`/phone-numbers/:assignmentId/{tags,account-default,inbound}` — `PUT …/inbound` decides which AI answers a tenant DID and which human number a call escalates to, the same inbound-behaviour argument as `PUT /tenants/:id`), `GET /auth/me`, and **`GET /accounts/mine`** (no "mine" for a machine credential; it has no `requirePermission` at all, so neither the role gate nor the scope gate was looking at it). The guard runs **before** `requirePermission`, so the 403 cannot turn into a 200 when the creator is promoted. Reads stay open on every one of these surfaces — an integration legitimately needs to see which trunks and numbers exist to pick a valid `caller_id` — and escalation `DELETE` stays open for the same reason its capability gate does: removing a misbehaving destination is exactly the incident operation.

   Two layers, and one deliberate asymmetry between them. `UNSCOPEABLE_PERMISSIONS` refuses these permissions at key *creation* so a customer cannot build a key they will reasonably expect to work, and the route guards are what hold if one of those permissions is ever reused by a new route. The asymmetry: `proxy.escalation_destinations.write` is unscopeable, yet the escalation `DELETE` above deliberately accepts a key — so only a **wildcard** key can perform that incident operation, never a narrowed one. Splitting the delete onto its own permission is the fix if that ever matters; it is recorded at the list rather than papered over. Note also that `/auth/me` answers **403 `api_key_not_permitted`** while the agency `my-*` routes answer **400 `missing_actor`** — both refuse, but a client branching on status sees two contracts.

**`GET /tenants` and `GET /auth/me` register `sessionMiddleware` ONLY** — no `tenantContextMiddleware`, therefore no `X-Tenant-Id` and no `apiKeyTenantId !== tenantId` check — and both answered from `request.user`, i.e. the key's creator. `tenantRepository.listByUserId` returned every tenant that person is an active member of (names, slugs, settings, statuses) from a credential scoped to one; `/auth/me` added `findAllByUserId` memberships across all of them. For a key minted by a support engineer who belongs to many tenants, that enumerated them. `GET /tenants` now answers a key from `apiKeyTenantId` (the authenticated fact) and keeps the list shape so no client branches on credential type; `/auth/me` **refuses** a key, because there is no "me" for a machine credential — same posture as the agency `my-*` routes.

**The creator's `status` is checked on the key branch.** Its absence was an asymmetry, not a decision: the Firebase branch has always refused `user.status !== 'active'`, so a deactivated person's keys kept working for as long as any membership of theirs survived. Refused rather than downgraded to "no user", which before (1) meant unrestricted access. **Two limits worth knowing:** the user record is Redis-cached for 20 minutes and `invalidateUserCache` has only two callers, both on the signup path — nothing in this service writes `users.status`, so deactivation is a manual `UPDATE` that invalidates nothing and the check is up to 20 minutes stale per instance. **Revoking the key is the only immediate lever** (`DELETE /api-keys/:id` busts `cache:apikey:` directly, and that family is deliberately outside `LOCAL_CACHE_FAMILIES`). And "a NULL-`created_by` key is inert" means inert on every *permissioned* route — it still gets 200s from the few routes with no `requirePermission` at all, which is now just `GET /tenants` (scoped to its own tenant) and `GET /governance/effective`.

Still open, and why the customer-facing docs must say so: there is **no per-key rate limit** (only the global IP bucket — see Rate Limiting) and **no per-key audit COVERAGE** — `auditLogger.log` is called from five route files and three files under `src/scheduling/` only, so calls, messages, uploads and credit moves write no platform audit row at all. The ATTRIBUTION half is closed: the rows master *does* write now carry `actor_type` + `api_key_id` (migration 067, see *Audit*), so a key action names the credential rather than the person who minted it. Keys also have no default expiry. `docs/platform-api-key-exposure-review.md` is the route-by-route classification and the remaining gap list.

The two guards that keep this from regressing are `test/unit/auth/api-key-route-blocks.test.ts` (a **comment-stripped** source audit — this repo documents holes by quoting the old code, so a raw-text `not.toMatch` would fail on the explanation and the tempting "fix" is to delete the explanation) and the inverted assertions in `test/unit/rbac/rbac-middleware.test.ts`. Mutation-checked: reintroducing the one-line bypass fails **11 unit tests** — 3 in those two files plus the 8 agency `my-*`/actor tests, which assert 403 for the system-key shape and so double as bypass detectors. The source audit strips comments through a **string-and-comment-aware state machine**, not two regex passes: stripping block comments from the raw file first meant a `/*` inside a `//` comment (`// see src/api/routes/*.ts` — a shape this repo writes constantly) opened a phantom comment that swallowed the lines after it, and a bypass hidden that way passed the entire audit. Every assertion in that file runs over stripped source for the same reason — when only one did, a guard that was merely commented out passed too.

### Multi-tenant RBAC (`src/rbac/`)

Role hierarchy: `viewer(10) → operator(20) → account_admin(30) → tenant_admin(40) → tenant_owner(50)`

Permission matrix maps each permission to a minimum role. `requirePermission()` preHandler factory checks membership role against required permission. Tenant-level members (account_id=NULL) can access all accounts.

**`requirePermission` proves the caller's ROLE and never looks at the target row — so every tenant-facing query needs its own `tenant_id` predicate, and two separate reviews found places that did not have one.** Three rules follow, each of which was a live cross-tenant defect:

1. **A repository method reachable from a tenant route takes `tenantId` and puts it in the same statement as the write.** `accountRepository.update`/`softDelete` took an id alone, so an `account_admin` of tenant A could `PUT /accounts/<uuid in tenant B>` — renaming B's account and receiving B's whole row back (`tenant_id`, `name`, `settings`, `status`), or soft-deleting it with no body at all. A fetch-then-check in the route is *not* equivalent: it is a read and a write that can disagree. `findById` stays deliberately unscoped for the super-admin tree and the name resolver (which checks ownership itself); the tenant-facing lookup is `findByIdInTenant`.
2. **`X-Account-Id` is validated against `X-Tenant-Id` in `tenantContextMiddleware`, once, for every route.** The header used to be assigned to `request.accountId` verbatim; the tenant-wide membership fallback (`m.account_id === null`) grants access to every account *in that tenant* and has no account to compare against, so naming a foreign account satisfied it. Downstream that meant writes storing the foreign id (the agency ingest job stamps it onto core's roster rows), a read leak (the resolved display name went to core as `x-mgkvc-account-name`), and PostHog filing one tenant's events under another's account group. Checked on the platform-API-key branch too — a key proves which *tenant* is calling and says nothing about which *account* it may name. A malformed id (Postgres `22P02`) is refused, not 500'd; a genuine DB fault propagates rather than being disguised as a 403.
3. **A miss answers 404, not 403.** A cross-tenant id and a nonexistent one must be indistinguishable, or the response is an account-id oracle.

**`requirePermission` also never looks at which ACCOUNT the caller's own membership is scoped to — a second, orthogonal axis from the `tenant_id` rules above. An initial security review found three routes with the gap; re-deriving the fix and grepping the same file neighborhood found four more.** Nothing in the schema stops a `tenant_admin`/`account_admin`/`viewer` membership from ALSO being account-scoped (`memberships.role` and `memberships.account_id` are independent columns), so a route that checks only the caller's ROLE lets an account-scoped member act on ANY sibling account **in the same tenant** — a narrower blast radius than the cross-tenant bugs above, but the identical shape of bug. Each fix is a small local helper (`accountScopeMismatch`/`accountScopeAllows`/`callerAccountScope` — the name varies per file because this codebase's convention is a module-local helper, not a shared one, matching `auditAccountScope` in `audit.routes.ts`) that compares `request.membership.account_id` — never `request.accountId`/`X-Account-Id`, which is an unauthenticated header — against the request-named account, and refuses (or forces the filter to the caller's own account) on a mismatch. A tenant-wide membership (`account_id === null`, or absent — the shape an unrestricted platform key resolves to) is unrestricted by every one of these checks, by design.

- `PUT`/`DELETE /accounts/:id` (`account.routes.ts`) — 404 on mismatch, matching the cross-tenant 404 above (a sibling account and a nonexistent one must be indistinguishable).
- `POST`/`GET`/`DELETE /dnc` (`dnc.routes.ts`, `dnc.service.ts`, `dnc.repository.ts`) — `POST` refuses (403) an account-scoped caller who omits `account_id` (⇒ would write a TENANT-WIDE suppression blocking dialing for every account), names the tenant, or names a sibling account; `GET` forces the filter to the caller's own account when omitted and 403s an explicit foreign/tenant ask; `DELETE /dnc/:id` threads the caller's account through `dncService.remove(id, tenantId, accountScope?)` → `dncRepository.deleteById`, whose scoped branch adds `AND account_id = $3` — an **equality**, not `IS NULL OR =`, so a tenant-wide entry (`account_id IS NULL`) is correctly unreachable to a scoped `DELETE` (`NULL = $3` is never true in SQL).
- `GET /credits/transactions` and `POST /credits/{allocate,deallocate}` (`credit.routes.ts`) — the read forces/validates `account_id` against the membership (403 on mismatch); the two writes add the same check plus a second, independent one: `account_credit_allocations.account_id` is `REFERENCES accounts(id)` with **no composite FK back to `tenant_id`** (migration 002) and `creditAllocationRepository.allocate`'s `ON CONFLICT (tenant_id, account_id)` does not require the account to be in that tenant — the identical shape `POST /users/invite` already documents and fixes for `memberships.account_id` — so both routes now also call `accountRepository.findByIdInTenant` before touching the ledger.
- `POST /users/invite`, `PUT /users/:id/role`, `DELETE /users/:id/membership` (`user.routes.ts`) — invite refuses an account-scoped caller who omits `account_id` or names a sibling account (omission is the dangerous one: `canManageRole` only compares roles, so it cannot catch a membership handed out wider than the inviter's own reach). Role-update and remove FILTER `memberships` to the caller's own account **before** calling `primaryMembership` — not after — and that ordering is load-bearing, not stylistic: invite's own duplicate check means a target holds at most one membership per account, so a user who is `operator` on account A and `account_admin` on sibling account B has two rows here, and `primaryMembership` picks by ROLE STRENGTH across ALL of them. Picking first and scope-checking second (the first version of this fix) meant A's own `tenant_admin` got the B row picked — it outranks A's — and was then 404'd as out-of-scope, unable to manage a user who plainly had a manageable row in A. Filtering first makes "the row in my account" the actual subject; a tenant-wide caller (`account_id === null`) is unrestricted, so every row stays a candidate. A miss after filtering is 404 (same reasoning as `accounts.routes.ts`), indistinguishable from "no membership at all".
- `POST /:assignmentId/tags`, `DELETE /:assignmentId/tags/:accountId`, `PUT /:assignmentId/account-default` (`phone-number.routes.ts`) — same account-scope check, plus the same `findByIdInTenant` tenant-membership check as credits allocate (`phone_account_tags.account_id` has the identical no-composite-FK shape; `tagToAccount`'s and `setAccountDefault`'s upserts do not check it either), since a `POST`/`PUT` here can create a tag row rather than merely fail to find one the way `DELETE`'s existing-row lookup safely does.

**A third pass — an external review of the fix above, not a grep — found the identical gap surviving in READS the first two passes had already touched, plus one more write.** Two lessons this round adds: a *write*-focused review misses reads that leak the same rows, and "the check exists in this file" is not the same claim as "every route in this file has it".

- `GET /accounts` (`account.routes.ts`) — `findByTenantId` had no account predicate, so `account.read` (floor `viewer`) handed an account-scoped caller every sibling account's full row — `name`, `slug`, `settings` (including `default_pipeline`), `status` — the exact enumeration the original `PUT /accounts/:id` finding used, reachable by a plain read instead of a write. Confined to `findByIdInTenant(callerAccountId, tenantId)` when the caller is account-scoped; `GET /accounts/mine` already did this for a caller with no `account.read` at all, this mirrors it for one who does.
- `GET /phone-numbers` (`phone-number.routes.ts`) — branched on `request.accountId`, the `X-Account-Id` **header**, which `tenantContextMiddleware` treats as optional: an account-scoped caller who simply omits it (legal — the middleware falls through to their own membership) fell through to `findByTenantId` plus a per-tag `findTagsForAssignment` join on `accounts.name`, for every account in the tenant. Fixed to `request.membership?.account_id ?? request.accountId` — membership first, header as the fallback for a tenant-wide caller who names one. Never a widening: whenever both are present, `tenantContextMiddleware` has already refused a caller whose header disagreed with their own membership before the handler runs, so preferring membership can only narrow what the header would have allowed, never override a validated header with something looser.
- `POST /dnc` (`dnc.routes.ts`) — the account-scope check (round 2) narrowed *who* a caller could name, but nothing checked that a named `account_id` belonged to this tenant at all. `dnc_entries.account_id` is `REFERENCES accounts(id)` with no composite FK back to `tenant_id` (migration 050) — the identical shape invite/credits-allocate/phone-tags already close — so this gets the same `findByIdInTenant` guard. Lower stakes than the write-side gaps above (dial-time suppression lookups are tenant-scoped, so a foreign account id here cannot suppress the OTHER tenant's numbers), but the same write-hygiene class this PR treats as load-bearing everywhere else.

**A fourth pass — an automated PR review — found three more instances, all of the "the guard checks the wrong thing" shape rather than "the guard is missing".** Each fix has the same lesson as the third pass restated once more: a scope check that guards WHICH ROW gets acted on is not the same claim as a scope check that guards EVERY EFFECT of acting on it.

- `PUT /users/:id/role`, `DELETE /users/:id/membership` (`user.routes.ts`) — the filter-then-pick fix (round 3) correctly scopes WHICH membership an account-scoped caller may change, but the offboarding side effect — `closeAgencyStaffing()` → `agencyCampaignAgentRepository.closeAllForUser(tenantId, userId)` — closed that user's agency staffing across **every account in the tenant**, unconditionally. An `account_admin` scoped to account A, demoting or removing a user from A, still closed that user's staffing on every campaign in sibling accounts B and C — a cross-account mutation the membership guard exists specifically to prevent, reached through its own tidy-up rather than through the guarded write itself. `closeAllForUser` gained an optional third `accountId` parameter (`AND account_id = $3`, equality — a tenant-level assignment, `account_id IS NULL`, is correctly unreachable to a scoped close, same reasoning as `dncRepository.deleteById`'s scoped branch), and `closeAgencyStaffing` threads `request.membership?.account_id ?? null` through to it. A tenant-wide caller closes tenant-wide, exactly as before.
- `POST /credits/deallocate` (`credit.routes.ts`) — round 2's `findByIdInTenant` guard closed the cross-tenant gap correctly for both allocate and deallocate, but its `status != 'deleted'` filter is wrong for exactly one of the two: a soft-deleted account can still hold an unrefunded balance in `account_credit_allocations` (nothing on the deletion path returns it to the pool), and the active-only lookup made that balance permanently unreachable — the 404 that correctly blocks a NEW allocation into a deleted account also blocked the one operation that could recover what a deleted account is still holding. `accountRepository.findByIdInTenantIncludingDeleted` (same tenant predicate, no status filter) replaces the active-only lookup on deallocate alone; allocate keeps `findByIdInTenant`, because crediting a deleted account is a real product bug, not a recovery path.
- `GET /phone-numbers` (`phone-number.routes.ts`) — round 3 fixed which ASSIGNMENTS an account-scoped caller sees (`findAvailableForAccount` via `request.membership?.account_id`), but `findTagsForAssignment(assignmentId)` answers for the assignment, not for one account — a shared/untagged number can be tagged to several accounts at once — so the tag list riding along on each row was never narrowed the same way. A caller whose own account legitimately has access to a number still received every sibling account's `account_id`/`account_name` in that row's `account_tags`. Filtered to `tags.filter((tag) => tag.account_id === accountId)` when the caller is account-scoped; a tenant-wide caller sees every tag, unfiltered, exactly as before — there is no "own account" to narrow to.

**A fifth instance, from a scheduled app-sec review (ClickUp `14ygtkj8rvu`): `GET /tenants/:id/members` (`tenant.routes.ts`).** `tenant.read` floors at `viewer`, and the route checked only `params.id === request.tenantId` before `membershipRepository.findByTenantIdWithUser(tenantId)` — no account predicate — so an account-scoped viewer of A received every active member of the tenant: sibling accounts' emails, display names, roles, `account_id`s and `invite_state`. The same enumeration `GET /accounts` was confined against in the third pass, reached through the Team page instead. `findByTenantIdWithUser` gained an optional `accountId` (`AND m.account_id = $2`, **equality** — tenant-wide members, `account_id IS NULL`, are deliberately NOT served to an account-scoped caller, the same call `dncRepository.deleteById` and `closeAllForUser` make, and consistent with an account-scoped admin being unable to manage a tenant-level row in `user.routes.ts`), threaded from `request.membership?.account_id` — never `X-Account-Id`. A tenant-wide caller sees the whole roster, unchanged; a cross-tenant `:id` is still 404. Pinned against a real Postgres in `test/integration/repositories/membership.repository.test.ts` (repository) and `test/integration/api/tenant.routes.test.ts` (route). **Accepted consequence, deliberately not "fixed":** a user holding BOTH a tenant-wide membership and an account-scoped one on A resolves to the A row whenever `X-Account-Id: A` is sent (`tenantContextMiddleware` prefers the named account's row), so their Team page shows only A's members — the same selection that already decides their role and scopes `GET /accounts` / `GET /phone-numbers`. Changing it belongs in the middleware's selection order for every route, not in a one-off widening here.

**A sixth instance, from the same scheduled app-sec review (ClickUp `14ygtkj8rvv`): the agency ingest-job routes (`proxy-agency-campaigns.routes.ts`).** Jobs are stamped with an `account_id` at create, but `agencyIngestJobRepository.findById`/`requestCancel` filtered on `id + tenant_id` only, so an account-scoped caller who knew a sibling account's job id could poll it (`GET /ingest/jobs/:id`, `viewer`), stream its rejected-row CSV from S3 (`…/rejected.csv` — roster PII), and stop the import (`POST …/cancel`, `account_admin`). Both methods gained an optional `accountId` (`AND account_id = $3`, **equality** — a job a tenant-wide caller created, `account_id IS NULL`, is unreachable to an account-scoped one, same call as `dncRepository.deleteById`), threaded from `request.membership?.account_id` on **all three** routes via one module-local `ingestJobAccountScope`. Cancel's predicate lives in the UPDATE itself — that is the fix; the unscoped UPDATE cancelled a sibling's live import and answered 202. On a miss the route re-reads under the same scope, so a sibling or nonexistent id answers **404** and 409 "already finished" is reserved for a job the caller can see (it used to answer 409 for every miss, which was misleading rather than an oracle). Create now stamps `membership.account_id ?? X-Account-Id` (the `GET /phone-numbers` rule) — an account-scoped caller who omitted the header used to stamp NULL, which the scoped lookup would then hide from its own creator. Two consequences of that stamping worth knowing: such a job now also applies that account's account-scoped DNC entries at ingest (`findSuppressed` is `account_id IS NULL OR = $3`), which it previously skipped — more suppression, the compliance-correct direction — and a job stamped NULL that way BEFORE this fix is invisible to its account-scoped creator, including its rejected-rows download; nothing was backfilled. Unused `findLatestForCampaign` (unscoped) was deleted rather than left for a future caller to reintroduce the leak. Pinned against a real Postgres in `test/integration/repositories/agency-ingest-job-account-scope.test.ts`.

**A fresh-context review of that fix found two more doors on the same surface, and the first one bypassed it outright.** (1) **The rejected-rows export was readable as an `s3_key`.** It is written to `agency-ingest/{tenant}/{jobId}/rejected-rows.csv` — the same prefix as an upload, keyed by nothing but the job id — and `isTenantOwnedKey` was a bare tenant-prefix test, so naming it on `POST /ingest/analyze` returned a sibling's headers and sample values, and a dry-run `POST /ingest/jobs` re-ingested it into a job the caller owned, whose own rejected-rows download then served the sibling's PII. `src/agency/agency-ingest-keys.ts` now owns both key shapes (`uploadKey`, `rejectedExportKey`) and the one check (`isTenantUploadKey`: exactly four segments, tenant match, never the export basename); the upload route renames a file literally called `rejected-rows.csv` so the refusal can never catch a genuine upload. An UPLOAD key stays tenant-bound rather than account-bound on purpose: its id is a `randomUUID()` returned only in the uploader's own 201 and served back by no route, so holding one already proves having uploaded it — if a route ever serves upload keys back, that stops being true (the module header says so). It is import-free and its own module because the route suites mock both the route's neighbours and the ingest service wholesale, and the writer and the checker must read one definition. (2) **Master never proved ownership of a body-supplied `campaign_id` before writing its roster.** The chunk writes (`sendRosterChunk`) and the replace/clear supersede go over `coreInternalRequest` to `/internal/agency-campaigns/:id/…`, past core's `authMiddleware` and `requireOwned` — and core's internal contacts handler (`agency.routes.ts`, `POST /agency-campaigns/:id/contacts`) resolves the campaign by id ALONE and writes under the campaign's own tenant/account, ignoring the `tenant_id`/`account_id` master sends. So an `account_admin` who knew any campaign id — a sibling account's or **another tenant's** — could load contacts into it, and they get dialled. `proveCampaignOwnedForWrite` now probes `GET /agency-campaigns/:id` through `proxyToCore` (core's `requireOwned` 404s unless tenant AND account match) with the same account the job is stamped with, before any `POST /ingest/jobs` that names a campaign and before `POST /campaigns/:id/roster/clear` (which also switched from the header to membership-first). The live exposure was the contacts write; core has no `roster/supersede` route yet, so the clear probe guards the hop master will make once it lands. Unlike the activity trail's probe it **fails closed** — a write cannot be taken back — and a caller with no resolvable account gets `400 account_scope_required`, since `requireOwned` has nothing to compare against. **A dry run naming a campaign is probed too**: it sends nothing to core, but `dropSuppressed` applies that campaign's campaign-scoped DNC entries, so an unprobed one was a suppression oracle over a sibling's campaign (and stored the unverified id on the job). Only a dry run with no campaign skips the probe, and so stays reachable with core down. Consequence: a tenant-wide caller previewing against a campaign must now send `X-Account-Id`. **Core should still compare the body's `tenant_id`/`account_id` to the campaign in its internal handlers** — this closes master's door, not the S2S contract's. **Three pre-existing edge cases on the same path were closed with it.** (a) **Membership selection is deterministic.** `findByUserAndTenant` had no `ORDER BY` and `tenantContextMiddleware` fell back to `memberships[0]`, so a user holding two account-scoped memberships and no tenant-wide one, sending no `X-Account-Id`, resolved to whichever row heap order returned — the account, the role and every account-scoped filter downstream could flip between requests or across a membership-cache refresh (an import created under A would 404 for its own creator once they resolved to B). The query now orders `created_at ASC, id ASC`, and the one `selectMembership` both middleware branches call re-applies that order in code, because arrays already in the membership cache predate the clause and come back through JSON with string dates. "Oldest" is a deterministic choice, not a semantic one: a client that means a specific account sends the header. The usage-digest preview reads the same query, and review found it choosing its scope from ALL of the caller's memberships while its gate only proved that SOME membership clears `usage.digest`'s floor — so an `agent` row on A (now reliably the oldest) set the scope of an `account_admin`-on-B preview, serving A's spend. It now filters to floor-clearing memberships first (tenant-wide wins among those, else the oldest), the rule `resolveRoleFloorAudience` applies to the real digest — and "the oldest" only agrees between the two because `findNotifiableMembers` now orders `u.email, m.created_at, m.id`: it used `ORDER BY u.email` alone, so `collapseByInbox` (which keeps the first account-scoped row per inbox and never re-sorts) mailed a person with two eligible accounts whichever row the executor returned, and the preview could show one account's spend while the mail carried the other's. (b) **A malformed job id is a 404, not a masked 500.** A non-UUID `:id` on poll, cancel or `rejected.csv` reached Postgres as `22P02`; the handlers now refuse it first with the same `Import not found.` body as an unknown id. It is checked in the handler rather than with `requireUuidPathParams` because the route suite's RBAC source audit requires each route's `preHandler` to be exactly its `requirePermission(...)` guard (or an array of nothing but those), so a `requireUuidPathParams()` beside it fails the audit. (c) **A platform key's creator is no longer recorded as the person who ran an import.** `created_by` is `NULL` for a key caller — `request.user` is the key's creator there, i.e. provenance of the credential, the correction `requestAuditActor` already makes — and the column has no key-id twin.

**Left open, deliberately, pending a product decision rather than a mechanical fix:** `GET /credits` returns the TENANT's shared pool balance to every caller regardless of account scope, including an account-scoped `viewer`. Unlike the reads above, there is no per-account "balance" to confine it to — `tenant_credit_balances` is a tenant-level concept by design (see *Credits System*), and every account draws from the same pool for dispatch, so an account-scoped member arguably needs to know the shared number to make sense of a `402`. Narrowing this would mean inventing a new account-level figure (from `account_credit_allocations`'s `allocated`/`consumed`/`reserved`) rather than filtering an existing one, which changes the response's meaning, not just its scope — a decision for whoever owns the credits product surface, not a drive-by fix.

### Credits System (`src/credits/`)

Per-minute billing in millicredits (1 credit = 1000 millicredits). Default rates: voice_call=500mc/min, ivr_session=200mc/min, static_call=100mc/min, webrtc_call=250mc/min (post-paid, no reservation), whatsapp_message=50mc/message, telegram_message=30mc/message, kb_search=50mc/search (per-invocation, unit=`search` = 0.05 credit; post-paid, no reservation). These hardcoded `DEFAULT_RATES` (`rate-card.service.ts`) are the fallback when no DB rate card exists; each must match its seeded migration so a settlement arriving before the migration is applied (deploy/rollback window) isn't mispriced — e.g. `kb_search: 50n` mirrors migration 042, avoiding a 10× fall-through to the 500mc voice default.

**Bulk dispatch reserves as a batch, not per recipient.** `creditService.reserveCreditsBatch(tenant, operation, minutes, count, account)` is the entry point for every multi-recipient path (chunked contact-list dispatch, the three direct-dispatch routes, the lane/SQS batch executor, both scheduler dispatch methods). It reads the rate card **once**, takes all N holds in a single `creditReserveMany` Lua call, and writes the rows with one `creditReservationRepository.bulkCreate` INSERT — 3 awaited round trips for a 100-recipient batch instead of 300 (measured ~25× faster on loopback; far more against managed Redis/Postgres), plus one background `creditTransactionRepository.bulkCreate` for the ledger. `creditReserveMany` is itself chunked at 500 holds per Lua call, because Redis runs a script to completion on its single thread and the direct-dispatch routes apply no length cap when SQS is unconfigured. The ledger rows carry a **stepped `balance_after`** anchored so the last row holds the true post-batch balance — a flat run of N identical rows breaks any reconciliation that walks `credit_transactions` expecting `balance_after[k] == balance_after[k-1] - amount` — and `metadata.estimated_minutes`, matching the single-reservation path. That write is one statement per chunk rather than a per-row loop specifically so it cannot half-succeed: `releaseCredits`' DB fallback recovers a hold's amount from exactly this row, so a partial write would leave holds that cannot be released. It is **all-or-nothing**: a tenant that cannot afford the whole batch gets no holds and an `InsufficientCreditsError`, which removes the old reserve-until-exhausted-then-unwind window where a crash mid-unwind stranded holds until TTL. Single-reservation paths (one call, one browser call, one message batch, one workflow action) keep using `reserveCredits`. **Invariant:** every reservation key in `creditReserveMany` travels in KEYS, never ARGV — ioredis applies the client `keyPrefix` only to KEYS, and `release`/`settle` look holds up through KEYS, so an ARGV-carried key would be written one prefix short and silently orphaned at settlement.

Flow: **Reserve** (before call) → **Settle** (webhook from core with actual **answer-anchored talk time** — `talk_time_seconds`, billed as `ceil(seconds)·rate/60`; measured from call pickup, so dial/ring time is excluded and never-answered calls bill 0 → released) → **Release** (if call failed).

Redis atomic operations via Lua scripts for hot path. DB as source of truth. Idempotent settlements via unique index on `(reference_type, reference_id, type)`.

**Postgres and Redis hold two DIFFERENT numbers, and exactly two primitives may reconcile them — `redisCache.adjustBalanceIfPresent` on every write path (the `creditAdjustIfPresent` Lua script — an `EXISTS`-guarded `INCRBY`), and `redisCache.rehydrate` on the super-admin repair path alone (see *Cache reconciliation* below).** Redis holds the **spendable** balance, already net of every in-flight hold; `tenant_credit_balances.balance` is the ledger balance. Both obvious ways to sync them are wrong, and neither errors — each just produces a plausible number. **`SET`ting the key to the post-write ledger balance re-inflates spendable credits by the whole reserved amount**, so a campaign spends holds Redis no longer knows about; that is what `deductCredits` and `chargeTalkTime` did. **A bare `INCRBY` creates a missing key from 0**, leaving a tenant whose cache merely expired with a Redis balance of exactly the delta — and on a *debit* a NEGATIVE one, which `getBalance` then serves as the whole balance, refusing every reservation for a well-funded tenant. A miss must stay a miss and fall through to Postgres. **`RELEASE_SCRIPT` and `SETTLE_SCRIPT` both had that bare form until `86d41v0n0`** and are the reason the rule is stated for the scripts and not only for the sync paths: releasing a hold on a tenant whose balance key had been evicted (it carries no TTL, unlike reservation keys, so it is the prime eviction candidate) left a cached balance of exactly the released amount, and `RESERVE_SCRIPT` then answered `-1` `insufficient` — an AUTHORITATIVE refusal that deliberately does not fall back — so the act of releasing a hold locked a funded tenant out of dispatch. Measured against a real Redis: an evicted key plus one 2,500mc hold produced a cached balance of 2,500. Settle had it on its COMMON path, since most calls settle for less than they reserved. Both now retire the hold and leave the balance key absent, reporting `cache_absent`; the credits come back through Postgres' three-term spendable figure, and the release ledger row is what records them. `syncCacheAfterDebit(tenantId, debited)` is the post-paid form and covers **every** Postgres-only debit: `chargeTalkTime`, the KB-search charge on `settleCall`, `settleAgencyConnectedCall`, `settleDialerAnalysis`, `settleAgencyAttemptBatch`. Two deliberate exceptions remain, both Redis-unavailable fallbacks with nothing live to keep in step: `reserveBatchWithLedger` and `restoreReservationWithLedger` on `releaseCredits`' DB fallback (`creditBalanceRepository.release`, which that one replaced, is gone — see *Release idempotency* below). `initializeBalance` is the one surviving `setBalance` — a brand-new tenant has no holds to wipe.

**What the sync is given must be the amount DEBITED, never the amount charged.** `recordPostpaidConsumption` and `agencyAttemptSettlementRepository.settleBatch` floor the balance row at zero to honour `CHECK (balance >= 0)` while the consumption row still records the true cost, so on an out-of-credit tenant the two differ; both return `debited` (`min(amount, current)`) for exactly this reason. Subtracting the charge instead drives the cache below the ledger and eventually negative. The distinction is invisible in any test whose fixture makes them equal — substituting the cost for `debited` at all four `settlement.service.ts` call sites once passed the entire unit **and** integration suite, so each path now has a case where `debited < cost`.

**The sync NEVER throws, and that is load-bearing.** Every caller has already committed its Postgres write by the time it runs. A Redis blip propagating out of a settlement becomes a masked 5xx; core redelivers; `recordPostpaidConsumption` hits `ON CONFLICT`, reports `charged: false`, and the sync branch is skipped — so a transient error would permanently reintroduce the exact staleness the mechanism removes, and on the agency connected-call path the redelivery folds the leg as free. `syncCachedBalance` therefore logs and swallows, which is only safe because the swallow is **visible**: `credit_cache_sync_total{result="adjusted"|"absent"|"error"}` is the sole signal that a tenant's cached balance is now over-stated, and nothing retries. Alert on `result="error"`. Watch `absent` for a different reason — **nothing repopulates an absent balance key automatically**: `getBalance` falls through to Postgres without writing Redis, and `topupCredits`' old unconditional `INCRBY` was the only accidental re-warm, so an evicted tenant stays on the slower DB reservation path until someone runs the super-admin reconcile below, which is the one deliberate re-warm. Correct and conservative, but a hot-path change, not only a consistency one.

**Super-admin top-up/deduct is the bug that produced all of the above.** `POST /super-admin/tenants/:id/credits{,/deduct}` wrote Postgres with raw SQL inside the route and never involved `CreditService`, so the Redis key kept its pre-top-up value: ops loaded a tenant's account and the tenant went on being told it had insufficient credits. Both routes now go through the service — hence `superAdminRoutes` taking a `creditService` option — and `allocateToAccount`/`deallocateFromAccount`, which never touched Redis at all, sync too. **Note the behavioural consequence of that last one**: an allocation now drops the tenant's spendable Redis balance where it used to lag, and nothing spends an allocation back, so allocating the whole balance 402s every dispatch until it is deallocated. Two further details are load-bearing rather than stylistic. `created_by` is left **unset**, deliberately: `credit_transactions.created_by` is `UUID REFERENCES users(id)` (migration 002) and a super admin is not a user — they live in `super_admins` with their own id space — so passing the admin id raises Postgres `23503`, which `errorMaskHook` serves as a generic 500, i.e. **every** super-admin top-up fails. Attribution lives in `metadata.admin_id` and the `super_admin_audit_log` row; the raw SQL never wrote the column for the same reason. And the balance move and its ledger row commit **together**, via `creditTransactionRepository.applyBalanceChangeWithLedger` — the raw SQL held its own `BEGIN`/`COMMIT` around the pair, and issuing them separately let a failed ledger INSERT leave the balance moved with nothing in `credit_transactions`, the one table an auditor reconciles against and the one the retention purge never touches. Same window, same fix, as `reserveBatchWithLedger` on the reservation path.

**Cache reconciliation is a SEPARATE, admin-triggered repair, because the write-time sync cannot fix its own history.** `syncCachedBalance` applies a *delta* at the moment of a mutation, so a key that was already wrong stays wrong by exactly the old error forever — and "forever" is literal: only *reservation* keys carry a TTL, the balance key is a bare `SET`, `getBalance` reads Redis first, and `setBalance`'s only caller is `initializeBalance` at signup. Nothing ages it out, nothing repopulates it, and there is no sweep. Every tenant topped up before the sync shipped therefore kept a pre-top-up balance indefinitely; the production case read 49.81 credits against a 4,052.83 ledger for twelve hours across two 2,000-credit top-ups, and would have read it forever. `POST /super-admin/tenants/:id/credits/reconcile` → `creditService.reconcileCachedBalance` is the repair, and `inspectCachedBalance` is its read-only half, surfaced as `credit_cache` on `GET /super-admin/tenants/:id` so the console can *show* drift before anyone acts on it — until then that page rendered the Postgres number while the customer's own badge rendered the Redis one, which is precisely why nobody could see the disagreement.

**`tenant_credit_balances.balance` is NOT the tenant's spendable balance, and treating it as one refunds real money.** On the Redis reserve/settle path Postgres is **never debited**: `reserveCredits` decrements only the Redis key, and `settleCredits` → `writeSettlementTx` → `createConsumptionIdempotent` writes a ledger row and touches nothing else. The row is therefore stale-**high** by every credit the tenant has ever consumed that way, for the life of the tenant — `credit_transactions` is the one table the retention purge never touches. Measured: reserve 500, settle it, and the row still reads the pre-call balance while Redis correctly reads 500 less. The spendable figure needs **all three** terms, `balance − redis_consumed − openHolds`. `redis_consumed` is a **column** on `tenant_credit_balances` (migration 066), advanced by `creditTransactionRepository.recordRedisConsumption` in the same transaction as the consumption row and **only when that `ON CONFLICT DO NOTHING` insert actually inserted** — core redelivers settlements routinely, and advancing it outside that guard would charge the tenant again on every redelivery while the ledger still showed one row. It is materialised rather than aggregated because the ledger form measured **104–550ms on a 300k-row tenant** and has to serve `getBalance`'s fallback too; as a column that read is **0.68ms** and needs no extra query at all. Drop the middle one and a reconcile hands back the tenant's whole consumption history; drop the last and it hands back every credit a live campaign has reserved, to be spent twice. The counter covers exactly the Redis settle path (both `settleCredits` and `settleMessageCredits` reach it through `writeSettlementTx`) and deliberately **excludes** the post-paid consumptions (`webrtc_call`, `kb_search`, agency) — `recordPostpaidConsumption` *does* debit `balance`, so counting them would subtract the same spend twice. 066's backfill applies the same rule to history **with one deliberate exception**: `metadata.source` only exists from 2026-08-09 (fd2a66f), before which `writeReservationTx` wrote no metadata at all, so it treats an untagged reservation older than 2026-08-11 as Redis-sourced. Matching the tag alone would exclude the platform's entire pre-August history — and excluding it is not neutral, it *refunds* that consumption, on every reconcile and every `getBalance` fallback, forever. Pre-tag Redis and DB-fallback reservations are genuinely indistinguishable in the ledger, so this assumes Redis, which is right for all but reservations taken during a past Redis outage (the DB fallback writes a row only when Redis was unreachable — on insufficient funds it throws and writes nothing). Those few are double-subtracted, i.e. under-credited: chosen deliberately, because an under-credit is visible and an operator can top up, while the refund is silent and permanent. The runtime hold query needs no such clause and deliberately has none — it is bounded to the last `RESERVATION_LEDGER_LOOKBACK_SECONDS`, which can never reach back that far. `openHolds` is reconstructed from the ledger rather than Redis' own `reserved` counter: that counter is a high-water mark only an explicit release/settle decrements, so every *expired* hold inflates it permanently and reconciling against it would re-strand the tenant. A hold is live only if tagged `source: 'redis'` (a DB-fallback hold already moved the balance row and would subtract twice), taken within `RESERVATION_LEDGER_LOOKBACK_SECONDS`, and not since settled or released; one older than that is deliberately not counted, because its key is gone (lookback ≥ hold TTL) and the tenant never consumed it. **The anti-join carries NO time bound**, and the obvious `s.created_at >= r.created_at` is wrong rather than merely unnecessary: `NOW()` is transaction-start time and the reservation's ledger row is written fire-and-forget, so a settlement can be stamped *earlier* than the hold it settles — the bound then misses it, a settled hold counts as live, and the tenant is under-credited (it also made the suite flaky at ~1 in 5). A slack bound fixes that but buys nothing once 066's `idx_credit_transactions_tenant_reference` exists (4.4ms vs 4.2ms measured), so the unbounded form is taken for being strictly safer. That index is needed because `idx_credit_transactions_reference` cannot serve this: it leads on `reference_type`, which the anti-join does not constrain, and is partial on `reference_type IS NOT NULL`, which release rows fell outside of until `86d41v0n0` gave them a `reference_type` (`RELEASE_REFERENCE_TYPE`); rows written before that still have none. It is created **before** 066's own backfill, which is that index's first and heaviest user — created after, the correlated `EXISTS` falls back to a sequential scan per probe and holds the migration transaction open while its `CREATE INDEX` blocks every settlement INSERT. `CONCURRENTLY` is unavailable (node-pg-migrate wraps the file in one transaction and the backfill has to be inside it), so the lock wait is bounded with `lock_timeout` exactly as migration 065 does: a blocked deploy fails fast and rolls back rather than queueing the credit hot path behind it. These constants live in `src/credits/reservation-contract.ts` — `RESERVATION_LEDGER_LOOKBACK_SECONDS` read by the query as its cutoff and `MAX_CREDIT_HOLD_TTL_SECONDS` capping the TTL the cache writes with (so the cutoff always covers every hold `reserve` actually wrote; see the hold-TTL paragraph below), `RESERVATION_SOURCE_REDIS` written by the service and filtered on by the query — because the query measures what `reserve` actually did and a second copy of either value would silently stop matching. The pair is written by one Lua script (`creditRehydrate`) so the two keys cannot be observed disagreeing, floored at zero (a negative cached balance makes `getBalance` refuse every reservation for a funded tenant), and — unlike the write-time sync — it deliberately **creates an absent key**, re-warming a tenant that had fallen onto the slow Postgres reservation path. That exemption turns on one fact: `adjustBalanceIfPresent` knows only a delta, while this knows the absolute value.

**The same staleness made `getBalance`'s Postgres fallback refund settled usage, and that is fixed here too.** With no cached key it fell through to `tenant_credit_balances` and served the row verbatim — so any tenant whose key was evicted, flushed, or `DEL`eted by hand (until this route existed, the only remedy for a drifted cache) was handed their entire consumption history back, on the read behind `GET /credits`, the S2S balance core gates dispatch on, and the reservation fallback itself. It now serves the same three-term figure the reconciliation writes, `balance − redis_consumed − openHolds`. An earlier revision left the holds in, on the reasoning that an absent balance key makes `RESERVE_SCRIPT` refuse everything and so renders them inert; that is wrong, because `SETTLE_SCRIPT` keys off the *reservation* key, which is independent, and selective eviction or a hand-run `DEL` removes the balance key alone — a hold that can still settle must not be reported as spendable. Under-serving a merely-evicted tenant by a live hold is the safe direction and self-corrects when the hold settles or expires. Both terms come from **one statement**, `creditTransactionRepository.findSpendableSnapshot`, and that is a correctness requirement rather than a round-trip saving: read separately, a `recordRedisConsumption` committing in between is seen by exactly one of them — the old counter beside a hold its charge already settled, or the new counter beside a hold still counted open — and either tears the figure by a whole charge, which `reconcileCachedBalance` then writes to Redis as authoritative. `inspectCachedBalance` uses the same snapshot for the same reason.

**Redis has TWO different refusals on the reserve path, and collapsing them into one was an overspend.** `RESERVE_SCRIPT` and `RESERVE_MANY_SCRIPT` used to read an absent balance key as `0` and answer `-1` for both "no key here" and "the tenant cannot afford this", so `reserveCredits` saw a single `null` and fell through to Postgres either way — and the Postgres gate was a bare `balance >= cost` against the row that is stale-high by `redis_consumed`. The result was that **every hold Redis declined was granted by the ledger instead**, against credits already spent: a tenant at balance 100000 / `redis_consumed` 80000 can genuinely spend 20000 and would be handed a 50000 hold. It is not only the post-`DEL` shape either — a perfectly healthy cache that has simply been spent down also answers "insufficient", so Redis' limit was unenforceable in the ordinary case. The scripts now return `-2` for *no usable balance key* (absent, or a non-numeric value) and `-1` for *judged and refused*, surfaced as `RedisReserveRefusal = 'cache_absent' | 'insufficient'`. Only `'cache_absent'` may fall back; `'insufficient'` raises `InsufficientCreditsError` directly. **The trade is deliberate and worth stating**: a cache that has drifted *low* now refuses a reservation the ledger would have allowed, rather than quietly succeeding — a loud failure with a one-click repair, in place of a silent, unbounded, unauditable overspend. Both Postgres gates are corrected to match, `reserveBatchWithLedger` and `applyBalanceChangeWithLedger`'s debit branch (super-admin deduct, allocate), which now read `balance - redis_consumed >= $2`.

**`SETTLE_SCRIPT` moves the cached balance by `reserved - actual` WITH ITS SIGN, and `if surplus > 0` was a systematic overspend.** Redis holds the spendable balance and `RESERVE_SCRIPT` debited it by the ESTIMATE, so settling has to move it by the difference in whichever direction that falls. Skipping the write when a call cost *more* than its estimate looks conservative and is not: every voice call reserves a flat five minutes (`reserveCredits(tenantId, 'voice_call', 5, ...)` at all four call sites), so an overrun is the ordinary case for any call over five minutes. The cache was therefore never debited for the excess while `redis_consumed` advanced by the full actual cost — the two stores disagreed by the overrun, and the Redis one, which is what gates dispatch, was the generous one. Measured: a 12-minute call (6,000mc) against a 2,500mc hold left the cached balance 3,500mc high, per call, unbounded in aggregate. Correcting it means a tenant who genuinely overspent can now be driven negative and refused — loudly, with a one-click reconcile — which is exactly the trade `RedisReserveRefusal` already documents. Related, and fixed with it: `tonumber(GET(...) or '0')` made one corrupt reservation value fail the whole release with `ERR attempt to compare nil with number` (an unreleasable hold is worse than an unrestored one), and the scripts' numeric reply collided with a legitimately negative cached balance — `-1` was also the "no reservation" sentinel, so a release that HAD happened was reported as a miss and took the DB fallback, writing no release row. Both scripts now reply `[status, heldAmount, newBalance]`. The same absent-key rule applies one counter over: the `DECRBY reserved_key` in both scripts is **EXISTS-guarded** too, because `DECRBY` creates a missing key at MINUS the amount and `reserved` carries no TTL either. That counter is not the reconcile authority (`sumOpenRedisReservations` rebuilds open holds from the ledger and never reads it) but it IS reported — `inspectCachedBalance` serves it as `cachedReserved` on `GET /super-admin/tenants/:id` — so a fabricated negative renders on the very console page this work exists to make trustworthy, indistinguishable from real corruption. Measured against a real Redis: an absent `reserved` key plus one 2,500mc hold came out at **-2,500**, from release and from settle alike. **All of this is pinned by `test/integration/credits/release-settle-lua.test.ts` against a real Redis**, for the same reason the SQL claims are: the unit tests mock `defineCommand` and never execute a line of Lua, which is how three money bugs lived in twenty lines.

**A settlement that misses its Redis key is still a REDIS settlement, and must be booked as one.** `SETTLE_SCRIPT` answers `-1` whenever the reservation key is gone, and that key lives only `CREDIT_HOLD_TTL_SECONDS` (600s by default, 1500s once raised — see the next paragraph) — so any call outliving it, and any settlement webhook delayed past expiry, lands on the DB fallback holding a hold that *Redis* took. Booking it the Postgres way wrote the consumption row, left `redis_consumed` untouched, and decremented a `reserved` column that was never incremented for it; the hold was by then too old for `sumOpenRedisReservations` to count, so nothing recorded the spend at all and the next reconcile handed it straight back. Both fallbacks (`settleCredits`, `settleMessageCredits`) now classify the hold through `creditTransactionRepository.isRedisSourcedReservation` and route Redis-sourced ones to `recordRedisConsumption`, which does not touch `reserved` at all; a DB-sourced hold goes to `settleReservationWithLedger` (see *Settle atomicity* below). `creditBalanceRepository.consume` is **removed**, like `release` before it. **A reservation with no ledger row counts as Redis-sourced** — an inference, not a default: the DB path writes its debit and its row in one transaction, so a hold with no row cannot have come from it, while the Redis path writes the row fire-and-forget and a lost write leaves exactly that shape. Unlike 066's backfill this consults the tag alone, with no date fallback, because nothing settling today was reserved before the tag existed.

**The Redis hold TTL and the ledger lookback are two numbers, and the only rule between them is lookback ≥ TTL.** `RESERVATION_LEDGER_LOOKBACK_SECONDS` (1500, in `src/credits/reservation-contract.ts`) is the cutoff `sqlOpenRedisHolds` is bound to everywhere — `findSpendableSnapshot` / `sumOpenRedisReservations` (reconcile, `getBalance`'s Postgres fallback) and every Postgres write gate. The hold TTL is `CREDIT_HOLD_TTL_SECONDS` (`config.credits.holdTtlSeconds`, passed to `RedisCreditCache`), default 600, allowed 600..1500; the schema and `RedisCreditCache` (`assertCreditHoldTtl`) both refuse a TTL above the lookback. Lookback **<** TTL is a double-spend: a hold still live in Redis drops out of `openHolds`, so the fallback reports it spendable, the gates reserve or deduct against it, and a reconcile writes it back into the cache. Lookback **>** TTL is merely conservative — an expired-unsettled hold is still subtracted until the lookback passes, which is the same subtraction the cache is already making (expiry never re-credits it); its eventual release (`redis_hold_gone_no_restore`) or settlement (`recordRedisConsumption`) is keyed on ledger rows, not the window, so nothing is released or charged twice. They were one constant until `14ygtkj9b7j`, whose single-step 600→1500 raise was unsafe in a rolling deploy for exactly the first reason. **The raise is therefore staged:** (1) deploy — lookback 1500 everywhere new, TTL still 600, so old and new pods agree; (2) once *every* pod runs it, set `CREDIT_HOLD_TTL_SECONDS=1500` (every pod is already at lookback 1500; the boot log line `Credit hold TTL configured` confirms each pod); (3) only then deploy core `magic-voice-core#395` — before step 2, a VoiceLink call settling >600s after master dispatch outlives its hold. Unlike the single-step raise, a super-admin reconcile is safe throughout this sequence (every pod satisfies lookback ≥ TTL at every step). The one cost of lookback > TTL: a reconcile that lands while an expired, never-closed hold is still inside the lookback leaves that hold's credits stranded exactly as they already were (the cache was debited and expiry never re-credited it), and the next reconcile after it ages out — or after its release row closes it — recovers them. To roll the code back after step 2, unset the variable first and wait 1500s. Deliberately **not** sized for: calls queued behind slots/SQS before the dial, IVR's 3600s cap, and calls whose owning core process died — core's stale sweep settles those after `max(floor, STALE_CALL_SWEEP_MINUTES)`, 30 min by default, past 1500s, so they still land `redis_hold_gone_no_restore` (pre-existing, not made worse). Sizing and the cross-repo drift check live in `test/unit/credits/reservation-contract.test.ts`, which reads the sibling core checkout and skips when it is absent (so on CircleCI). **One class of hold lives longer on purpose: a capped broadcast's, renewed while its batch is outstanding at core.** The invariant is then really "every live Redis hold is visible to `sqlOpenRedisHolds`" — inside the lookback, or covered by a live `credit_hold_leases` row (migration 078) that is always written before, and always outlasts, the Redis TTL it covers (`CREDIT_HOLD_LEASE_MARGIN_SECONDS`). See *Per-broadcast "Simultaneous calls" cap* → *Credit holds*.

**`releaseCredits` returns a `CreditReleaseOutcome`, and exactly TWO of its nine values give credits back** (`redis`, `db_restored`). The other seven restore nothing, and until `86d41v0n0` every one of them was an indistinguishable `Promise<void>` — which is why cancelling 5,660 stranded calls could not be diagnosed from master at all. Three things about it are worth knowing before reading the counter.

**The DB fallback reads the RESERVATION row first and the balance row second**, and that ordering is a pool saving on the one path that matters. The Redis-sourced arm returns without touching the balance row, and it is the *common* case here: reaching the fallback at all means the reservation key is gone, which for a bulk cancellation of long-queued calls means every row TTL-expired. Reading the balance row first spent a connection checkout per settlement **to decide nothing**, against the same 20-connection pool the settlement burst was already exhausting. Writes are unchanged — the `balance` guard still gates the only write there is.

**`redis_hold_gone_no_restore` is a LEVEL, not an anomaly, and must not be alerted on at threshold 0.** It is what a bulk cancellation produces for every row, but it does *not* by itself mean credits are stranded: a hold that TTL-expired unsettled (genuinely short until `POST /super-admin/tenants/:id/credits/reconcile` runs) and a hold that was already released land on the same label. It is now **narrower** than it was — every release writes a ledger row, so an already-released hold normally reports `already_released` instead, leaving this label holding the expired case plus the residue with no marker (a release from before the row existed, or one whose fire-and-forget write was lost). Still a level, not a clean signal; watch for a step change correlated with a cancellation. **`cache_unavailable` is the same shape from a process with no Redis at all (degraded mode), and it is the one release arm that writes NO ledger row.** The split is not cosmetic: `redis_hold_gone_no_restore` means Redis was asked and answered `no_hold`, so the hold is provably gone and the release row is safe; `cache_unavailable` means nothing was asked, so the hold may be LIVE in the cache another replica is serving and settleable at any moment (`SETTLE_SCRIPT` keys off the reservation key alone). A release row is the marker that CLOSES a hold for `sqlOpenRedisHolds`, so writing one from a process that cannot see the cache drops `openHolds` by the hold's amount for every reader of the three-term spendable figure — `getBalance`'s fallback and the `reserveBatchWithLedger` / `applyBalanceChangeWithLedger` / `deduct` gates then treat still-held credits as spendable, and `reconcileCachedBalance` writes `balance − redis_consumed − 0` into Redis as authoritative, re-inflating the cached balance by a hold that then settles. Spent twice. So this arm restores nothing, records nothing, and leaves the hold to settle, be released by an instance that can see the cache, or expire — all of which a later reconcile accounts for correctly. `no_reservation_row` is **not** benign: nothing ever deletes reservation rows (the retention purge excludes `credit_transactions`), so a second release always finds the row — it means a lost fire-and-forget `writeReservationTx`, i.e. a missing billing record. Of the three labels added with the idempotency, `already_released` is benign and expected on every redelivery; **`already_settled` is not** — it means a release arrived for a hold that was consumed, i.e. two producers disagreeing about one call; and `cleared_no_cached_balance` is the one label naming an actionable *cache* state (the hold was retired but there was no cached balance key to credit, so the tenant is on the DB reservation path until a reconcile). And note what reconcile can and cannot do: **replaying settlements never recovers a TTL-expired hold** (`SETTLE_SCRIPT` keys off a reservation key that is gone), so the per-tenant reconcile is the only remedy — the credits come back because an expired hold is correctly excluded from `openHolds`.

**Release idempotency is a DB-level claim, and the release branch had none until `86d41v0n0`.** The guard above it, `findByReference(<operation>, <call_id>)` in `settlement.service.ts`, looks for a ledger row keyed on the CALL id while every row for a hold — reservation, consumption, release — is keyed on the RESERVATION id, so **it has never matched anything on either branch**. The settle branch survived that on `recordRedisConsumption`/`createConsumptionIdempotent`'s own `ON CONFLICT` alone; the release branch restored the balance on every delivery, and core redelivers as a matter of routine. `CHECK (reserved >= 0)` decided which way a duplicate broke, and both were measured against the real schema: with no other live hold the decrement went negative and the UPDATE raised `23514`, which escapes `releaseCredits` into all three of `settlement.service.ts`'s release branches — they `await` it uncaught, so a non-billable call 500s its webhook and core redelivers forever; with another live DB-sourced hold to absorb it (a campaign mid-flight on this very path) the check was satisfied and the restore simply repeated, taking a 5,000mc balance to 11,000mc over six deliveries while quietly releasing 5,000mc of the other campaign's `reserved`. The fix is the `recordPostpaidConsumption` shape: `creditTransactionRepository.restoreReservationWithLedger` moves the balance and inserts the release row in ONE transaction under `SELECT ... FOR UPDATE`, gated on that insert actually inserting (migration 070's partial unique index), and `recordReleaseIdempotent` is the insert-only form for the two arms that restore nothing. Three consequences worth knowing: `creditBalanceRepository.release` is **removed**, not merely unused, because it was the unguarded mover itself; a release for a hold with a `consumption` row is refused as `already_settled` rather than credited (on a DB-sourced hold that refusal *is* the money); and the release row now carries a real `amount` and a non-NULL `reference_type` (`RELEASE_REFERENCE_TYPE = 'reservation_release'`, a FIXED value — the Redis arm releases without reading the reservation row, so it does not know the operation, and an idempotency key the two arms spell differently is not one), which is also what finally closes a released hold for `sumOpenRedisReservations`' anti-join. **These properties are pinned by integration tests, not unit tests, and that is not laziness**: the idempotency is a partial unique index plus an `ON CONFLICT` plus a row lock, and a mocked pool never parses SQL or enforces a constraint. Writing them against a real Postgres is also what caught a `42P18` parse failure in `RELEASE_CLAIM_CTE` — an unreferenced, untyped `$n`, the trap the *Migrations & metrics* rule in core's CLAUDE.md documents twice.

**Settle atomicity is what makes that `already_settled` guard TRUE, and without it the guard was decorative.** `RELEASE_CLAIM_CTE`'s `settled` test is a snapshot READ — `idx_credit_transactions_release_idempotent` is partial on `type = 'release'`, and a consumption row differs in BOTH `type` and `reference_type`, so `ON CONFLICT` can never see a settle. Its soundness therefore rests entirely on the settle side holding the balance row's lock while its consumption row is missing, and the DB settle path was TWO autocommits (`creditBalanceRepository.consume()` then `createConsumptionIdempotent()`) which released that lock in between. Measured against a real Postgres, with one bystander hold to satisfy `CHECK (reserved >= 0)`: a release landing in that gap read "not settled", inserted its release row and took the balance 99,000 → **100,000** — the whole 1,000mc reservation handed back for a call that billed 500, with a `consumption` row and a `release` row for the same hold. The reverse order lost money too: with the release committed first the reserve's debit is already undone, so the settle wrote a consumption row that debited nothing (a FREE call) and its unconditional `consume()` ate 500mc of the *bystander* campaign's `reserved`; with no bystander it raised `23514`, which escapes the webhook as a 500 and core redelivers forever. `creditTransactionRepository.settleReservationWithLedger` is the fix, the `recordPostpaidConsumption` shape once more: one transaction, `SELECT ... FOR UPDATE` on the same balance row the release path locks, the consumption insert gated on `NOT released`, and the `reserved` decrement gated on that insert having actually inserted — which also closes a quieter defect, since `consume()` ran on EVERY redelivery while the insert no-op'd. A settle arriving after a release is refused as `already_released`: loud (an `error` log naming both rows) rather than silent, and strictly better than either old branch. **What it does NOT do is recover the money** — the credits are genuinely back and there is no hold left to charge, so that call is unbilled and needs a manual adjustment. Pinned by `test/integration/flows/credit-settle-release-interleave.test.ts`, which holds a third connection's lock on the balance row and queues the two transactions behind it in a known order (Postgres grants row locks FIFO; `pg_stat_activity` is polled rather than slept on). **A SEQUENTIAL test passes on the broken code** — by then the consumption row exists and the guard reads it — so interleaving is the whole point of that file.

**Two things about that pair are still open, and both are narrower than what it closed.** (1) The **Redis-sourced** arm of the settle fallback (`recordRedisConsumption`) carries no `NOT released` predicate, so a Redis hold that was released and then settled late still advances `redis_consumed`. It is deliberately left: unlike the DB case, the release there restored the *Redis* balance rather than undoing a Postgres debit, so "charge anyway" is defensible and picking a side is an accounting decision rather than a bug fix — and the dangerous direction (handing credits back) is the one now closed. (2) `cache_unavailable` no longer distinguishes `already_settled` / `already_released`, because classifying would cost the connection checkout that arm exists to avoid and the answer is unactionable in degraded mode; the label itself is the signal, and a sustained rate means instances are running without Redis.

**The release row carries the ACCOUNT on both arms.** The healthy Redis arm passed none while the DB-fallback arm copied it off the reservation row, so one hold produced two row shapes — and `GET /credits/transactions?account_id=` filters on equality, so every Redis-arm release vanished from the account-scoped ledger page an `account_admin` is allowed to read while `db_restored` rows for the same campaign appeared on it. `releaseCredits` takes an optional third `accountId` and the settlement webhooks plus the three proxy dispatch routes thread the one they have already resolved; it is taken from the caller rather than looked up because reading the reservation row on that arm would spend exactly the checkout it is documented as saving. The DB arm still prefers the reservation row's own account, falling back to the caller's.

`credit_release_outcome_total{tenant_id,outcome}` is **the** release counter — total releases are `sum by (tenant_id)` over it. It was introduced beside `credit_releases_total{tenant_id}` rather than as an `outcome` label on it (adding a label to a live metric terminates the series), and `recordRelease` then incremented the two on adjacent lines on every returning path of `releaseCredits` (a path that throws increments neither), so the old counter was exactly its sum and was deleted as a duplicate series. It is reached through the `setCreditReleaseObserver` seam wired in `src/index.ts` — which avoids adding an **8th** export to the metrics-mock surface that ~80 test files stub with explicit factories, not "keeping this service out of it" (it already imports 7). Unwired (unit tests), releases count nothing. Its alerts are `mst-credit-release-anomalous-outcome` and `mst-credit-release-cache-unavailable` in the superproject's `MagickVoice-platform/grafana/terraform/alert-rules-master.tf` — the **only** writer of alert rules on the Grafana Cloud stack. This repo's `grafana/provisioning/alerting/magick-master-alerts.yaml` (`mm-*` uids) is Grafana *file* provisioning, which never reaches Grafana Cloud: it is a reference copy, so a rule changed there must be ported to the superproject module or it does nothing. It is charted on `grafana/dashboards/magick-master-overview.json`; the core-side half of the same incident (`settlement_dispatch_total{result="failed"}`, `webhook_fanout_abandoned_total`) is core's to alert on.

⚠️ **`DB_POOL_MAX` (default 20) is a cross-repo paired value.** Core's `WEBHOOK_FANOUT_CONCURRENCY` (default 10) is sized against it — a settlement takes ~5 sequential checkouts here, and up to 2 *concurrently* since the healthy release path launches a detached ledger write that overlaps its own caller, so budget ~2N for N concurrent settlements rather than N. Lowering this without lowering core's cap re-opens `86d41v0n0`.

**A corrupt cached value reads as absent rather than throwing.** `getBalance`/`getReserved` used a bare `BigInt(val)`, so a non-integer key 500'd `GET /credits` **and** made the corruption unrepairable — `reconcileCachedBalance` inspects before it overwrites, so the throw escaped before `rehydrate` could clear the bad value, and the one tool that could fix the key was the one thing that could not run against it.

**Two limits worth stating rather than discovering.** The Postgres read and the Redis write are not one atomic unit and cannot be — a reservation landing in between is lost from the cache — so this is a manual, audited, per-tenant action, not a sweep, and a tenant mid-campaign is worth reconciling *after* the campaign. And both reservation paths write their ledger rows fire-and-forget, so a hold taken microseconds earlier is under-counted; the window is one INSERT wide, and the alternative (trusting the inflated counter) is wrong all the time rather than occasionally. `credit_cache_reconcile_total{result="hydrated"|"repaired"|"in_sync"|"skipped_no_cache"}` counts outcomes — a steady trickle of `repaired` means drift is still being produced somewhere the write-time sync does not cover. Audited as `reconcile_credit_cache` carrying **every term of the arithmetic** — `ledger_balance`, `redis_consumption`, `open_holds`, and the resulting `new_balance`, plus the `previous_*` pair. The two subtrahends are not decoration: with only the ends recorded, an auditor cannot distinguish a correct `balance − redis_consumed − holds` write from an arbitrary overwrite that happens to be smaller than the ledger, which is the one question the record exists to answer.

**WebRTC human calls are the exception to the reserve/settle/release flow**: they are **POST-PAID with NO reservation**. Core posts `POST /webhooks/core/webrtc-completed` (or the unified `/completed` with `call_type=webrtc`) on completion; the handler charges credits directly by talk time via `creditService.chargeTalkTime`, which calls `creditTransactionRepository.recordPostpaidConsumption` — an atomic, idempotent, race-safe (`FOR UPDATE`) debit that is **floored at zero** to honor `CHECK(balance>=0)` while the consumption row always records the true cost, so a finished call is never billed for free (and an out-of-credit tenant never 500s/retries). Idempotent on (`reference_type=webrtc_call`, `reference_id=call_id`). Non-billable statuses / zero talk time are a pure zero-charge (no transaction). The unified `/completed` endpoint now supports `voice_call`, `ivr`, `static`, and `webrtc`.

WebRTC is gated in core by two flags — `webrtc_calls_enabled` (bool, default off, client-exposed) and `webrtc_max_duration_seconds` (number, default 1800, bounds 60..14400) — surfaced through the existing transparent super-admin feature-flag passthrough. No platform-side code is needed for these; the toggle UI lives in the frontend SPA.

**Dialer call analysis is post-paid, per analysis-minute, and swept — not fired.** Core transcribes + analyses a recorded dialer (WebRTC human) call after the fact and posts `POST /webhooks/core/dialer-analysis-completed` (HMAC-SHA256, same secret as the other core webhooks). `settleDialerAnalysis` charges `reference_type='dialer_analysis'` at **100 mc/min** (`dialer_analysis`/`minute`, seeded by migration 045; `DEFAULT_RATES.dialer_analysis = 100n` mirrors it so a settlement arriving in the deploy window before 045 applies isn't priced at the 500mc voice default — a 5× overcharge, the same trap kb_search/042 documents). Billed units are `ceil(analysis_audio_seconds / 60)` — a **charge for the analysis run, entirely separate from the `webrtc_call` talk-time charge** for the same call, so one call can produce two independent consumption rows.

**Idempotency here is load-bearing, not a nicety.** Core does not fire-and-forget this settlement: it sweeps `settlement_status='pending'` jobs and **redelivers until master returns 2xx** (up to ~50 attempts, 120s backoff), so master will see duplicates as a matter of routine, not as an edge case. The charge must therefore be idempotent **at the DB level** — `recordPostpaidConsumption`'s `ON CONFLICT` against the partial unique index on `(reference_type, reference_id, type)` — and **not** a `findByReference` read-then-write, which races under concurrent redelivery. Return 2xx **only** on a durable write or a provable conflict; a charge that throws must surface as 5xx so core retries rather than silently dropping revenue. The inverse also matters: ancillary work after the charge (automation dispatch and similar) is best-effort and must never turn a durable charge into a 5xx, or core will redeliver a charge that already landed. Non-billable/zero-second payloads are a pure zero-charge with no transaction.

**Governance + proxy.** The `calls.dialer.analytics` capability (parent `calls.dialer`, **default false**, enforcement `['nav','behavioral']`) gates the feature for cusui; because it's a child of `calls.dialer`, turning the parent off takes analytics with it. Master proxies three surfaces, each requiring that capability plus the usual RBAC: `/proxy/call-analysis-profiles` (CRUD for the reusable dimension sets), `POST /proxy/webrtc-call/:id/retry-analysis`, and `DELETE /proxy/webrtc-call/:id/transcript` (DSAR erasure). The two WebRTC passthroughs are easy to overlook — the original brief specced only the profiles proxy and the dispatch validator, and without them cusui's Retry and Delete-transcript buttons 404. Core owns all validation; master forwards verbatim. **No new master env vars** — the feature reuses `CORE_WEBHOOK_SECRET`, the existing core proxy plumbing, and the rate card.

**Deploy order is core → master → cusui.** Master's handler mirrors a contract core defines, and cusui gates on a capability master defines. Everything is additive-nullable and the feature ships flag-off at core, so core and master can be deployed ahead of enablement safely.

**Knowledge-base search is billed per-invocation, riding on the voice-call settlement.** Core's `voice_call` settlement webhook carries two optional fields — `kb_search_count` (billable `search_documents` tool invocations during the call) and `kb_search_credits` (core's *advisory* credit figure). **Master is the pricing authority**: `settleCall` charges `kb_search_count × kb_search` rate off master's own rate card (`rateCardService.calculateActualCostPerMessage('kb_search', count, tenant_id)`); core's `kb_search_credits` is recorded in the transaction metadata for reconciliation only, **never debited directly**. The charge is an **independent, idempotent, post-paid** consumption (`recordPostpaidConsumption`, `reference_type=kb_search`, `reference_id=call_id`, floored at zero) that runs **first in `settleCall`, before the voice-call idempotency early-return and the release branch** — a search on a call that ultimately didn't connect still consumed a query, so it bills whether or not the voice call itself is billable/settled/released. It's wrapped in its own try/catch (logs, never rethrows) so a transient DB error on the KB charge can never abort the voice-call settlement; the balance-missing path warns. Fields are threaded into `settleCall` from both `POST /webhooks/core/call-completed` and the unified `POST /webhooks/core/completed` (voice_call). Rate card seeded by migration 042 (50mc/search); `search`-unit so it uses per-invocation `calculateActualCostPerMessage` (rate × count), not the per-minute `/60` math.

**Agency Dialer legs are billed per connected call, NOT by talk time — and the discriminator is `campaign_id`, not `call_type`.** An agency leg is physically the same browser→PSTN bridge as a dialer call and arrives on the same settlement webhooks, so without a branch it would be charged `webrtc_call` at 250mc/min (a ~10× overcharge on a one-minute call, unbounded above that). Design D7 prices it as `agency_connected_call` — a flat **25 millicredits, duration-independent** — and `webrtc_calls.campaign_id` is what selects it, which is precisely why that column exists. There is deliberately **no new `call_type`**: the unified endpoint 400s on an unknown one, and that rejection is the deploy-order safety net (core must not ship agency settlements before master's branch is live). Branched in **both** `POST /webhooks/core/completed` and `POST /webhooks/core/webrtc-completed`, because core picks which it posts to — in practice always `/webrtc-completed`, since `resolveSettlementUrl` derives the endpoint by swapping the last path segment and no core path reaches `/completed` for any call type. The `/completed` branch accepts **both** `webrtc` and `webrtc_call`: core sends the latter, master's own callers use the former, and a branch keyed on only one silently falls through to the 400. `settleAgencyConnectedCall` prices through the per-**unit** path (`calculateActualCostPerMessage(op, 1, tenant)`; the per-minute path's `/60` and 1mc floor would bill 1 millicredit for anything under 2½ minutes), is post-paid with no reservation, and is idempotent on (`agency_connected_call`, call_id) via `recordPostpaidConsumption`'s `ON CONFLICT`. Two non-obvious rules: an **abandoned** attempt is zero-charge despite having talk time and a status outside `NON_BILLABLE_STATUSES` (the customer answered but no agent connected — `AGENCY_NON_CONNECTED_OUTCOMES`, keyed on the settlement payload's `outcome`, additive so an unrecognised outcome still bills). **Outcome, not status, and the distinction is load-bearing:** core's `webrtc_calls.status` CHECK (migration 047) permits only `initiating|ringing|in_progress|completed|failed|no_answer|busy|canceled`, so `'abandoned'` can never arrive as a status — an abandoned leg ends `status='completed'` carrying the apology clip's talk time. A status-named set steers the next reader into testing `status === 'abandoned'`, which is unreachable, and the leg bills as an ordinary connected call (MAG-119), and a **cross-rate guard** refuses to add an agency charge to a leg already settled as `webrtc_call`, since `ON CONFLICT` cannot see a charge filed under a different `reference_type`. The thread fold takes the synchronously-computed amount because an agency leg has no `webrtc_call` ledger row to re-read and would otherwise fold as free.

**Dial attempts are billed in batches with a remainder carry, because 0.2 millicredits is not a representable rate.** `rate_millicredits` is `BIGINT`, so migration 052 stores the `agency_dial_attempt` rate at its true granularity — **2 millicredits per 10 attempts, unit `10_attempts`** — and it must only ever be consumed through `rateCardService.calculateAttemptBatchCost`, which computes `attempts × 2 / 10` and returns the sub-millicredit remainder. The two obvious shortcuts are both wrong in the expensive direction: `rate × count` is **10×**, and rounding 0.2 up to 1 is **5×**. Core counts attempts per campaign and posts a batch hourly and at campaign end to **its own endpoint, `POST /webhooks/core/agency-attempts-completed`** — not a `/completed` branch, because every `/completed` branch requires a `call_id` and a batch is not a call (the `dialer-analysis-completed` precedent, reached by the same last-segment settlement-URL swap, so no new transport or secret). The payload carries `campaign_id`, `attempts` and a `batch_reference` (`h:<ISO hour>`, **hour-keyed only** — **opaque to master, never parsed**; the only properties master depends on are stability across redeliveries and uniqueness per campaign). There is deliberately **no `final` reference**: campaign end flushes the open hour under the same `h:<ISO hour>` the hourly sweep will later repost, and `uq_agency_attempt_settlement_batch` no-ops the duplicate. A distinct `final` key for those same attempts would double-bill the partial hour — see `AGENCY_BATCH_REFERENCE_MAX_LENGTH` in `src/agency/agency-billing-contract.ts`, which is the contract of record. `settleAgencyAttemptBatch` writes the carry row, the credit-ledger consumption and the balance debit in **one transaction** (`src/agency/agency-attempt-settlement.repository.ts`): they are one fact, and splitting them either charges without advancing the carry or advances it without charging. Idempotency is `uq_agency_attempt_settlement_batch (campaign_id, batch_reference)` and **not** the credit ledger's index — the ledger would dedupe the charge while still letting the carry advance twice, which is why 052 keeps a row per batch instead of a mutable counter. The carry read cannot join that transaction (the rate may be Redis-cached), so it is optimistic: the write asserts the remainder it priced against is still the tail of the chain, reports `stale` otherwise, and the service re-prices (bounded at 3 tries, then throws so core redelivers). **Be precise about what "core redelivers" means here, because it is not the dialer-analysis mechanism:** `dispatchAgencyAttemptBatchSettlement` says in as many words that "no separate retry sweep exists" — it takes `dispatchWebhook`'s bounded `withRetry({ maxRetries: 3 })` (which loops `attempt <= maxRetries`, so **4 attempts**, not 3) and then throws, and what stands in for redelivery is the ordinary hourly batcher tick re-deriving counts from `agency_call_attempts`. That is bounded by `ATTEMPT_BATCH_LOOKBACK_MS` (**48h**) and memoised in an in-process `Set` any restart clears. Only `dialer-analysis-completed` has the durable `settlement_status='pending'` sweep (~50 attempts / 120s backoff); a 5xx window longer than 48h loses attempt batches for good. Route validation **rejects** a malformed batch rather than coercing a missing `attempts` to 0, which would burn the `batch_reference` and leave those attempts permanently unbillable; a zero-attempt batch (which core states it never sends) is acknowledged 2xx *without* writing a row, since a 400 would put core into an unbounded retry loop and settling it would consume the reference. **A missing tenant balance row THROWS here**, unlike every other operation's warn-and-2xx: the remainder is not lost but the attempts are, because an attempt count is derived state core never presents again once master says 2xx — a call at least leaves a row to reconcile against. The wire `call_type` and the rate-card operation are both `agency_dial_attempt` — the freeze made them byte-identical so the mapping is the identity function — and both live in `src/agency/agency-billing-contract.ts` with a test pinning it, because a future divergence would price the wire value at the 500mc voice fallback (250×). That module also holds `normalizeSettlementAccountId`: core types its campaign `account_id` `VARCHAR(100)` with a literal `'default'` fallback while the ledger column is `UUID`, so a non-UUID is treated as "no account" rather than raising `22P02` inside the settlement transaction and redelivering forever.

### Proxy Layer (`src/proxy/`)

All `/proxy/*` routes: session auth → tenant context → RBAC → resolve encrypted core API key → forward to core's `/api/v1/*`. Core API keys stored AES-256-GCM encrypted in DB, decrypted on demand with 5min LRU cache. Includes WebSocket proxy for media streams (`/proxy/media-stream`) and browser calls (`/proxy/browser-call`).

`proxyToCore()` wraps each call in an OTel CLIENT span and injects W3C `traceparent` for cross-service tracing. Forwards both `x-mgkvc-tenant` and `x-mgkvc-account` (IDs) headers to core, plus `x-mgkvc-tenant-name` / `x-mgkvc-account-name` — the human-readable display names so core can attribute its metrics by name. The names are resolved (and cached ~1h) by `src/services/tenant-name-resolver.ts`, attached to the request by the tenant-context middleware (and to the log context on background dispatch paths — scheduler, recurring schedules, bulk-dispatch consumer), and read back from the log context by `proxyToCore()`. Values are URL-encoded via `src/utils/header-encode.ts` for header safety (no injection, never breaks the request on unicode); **core decodes with `decodeURIComponent`**. Name resolution is best-effort: a miss/error simply omits the name header.

**Metric `path` labels are route templates, never interpolated paths** (`src/utils/metric-path.ts`). Call sites hand `proxyToCore()`/`coreInternalRequest()` an already-interpolated path (`/calls/<uuid>`, `/knowledge-bases/<uuid>/documents/<uuid>`); writing that into the `path` label of `proxy_requests_total` / `proxy_request_duration_seconds` made the metrics SDK retain one permanent series per resource id, forever, multiplied by the histogram's bucket count — a slow memory leak that also bloated every scrape. `metricPathLabel()` normalises identifier-shaped segments to `:id` (UUIDs, all-digit ids, hex digests ≥16, E.164 phone numbers raw or `%2B`-encoded, anything outside lowercase-kebab, over-long or long digit-bearing tokens) and strips any query string built into the path, while leaving static routes intact so `/calls/export` and `/calls/batch-analytics` stay distinct. Because the segment after a collection is partly client-controlled, shape rules alone are a heuristic, so a **hard cap of 250 distinct templates per process** backs them: anything first seen after the cap collapses to `/__other__`. Pass `metricPath` on the request for the rare call site where inference is wrong — it must be a *fixed* string. Spans keep the full path (`proxy.path`); spans are per-request, not aggregated series. The same invariant applies to the HTTP-side `onResponse` hook in `src/index.ts`, which uses `request.routeOptions.url` and buckets unmatched (404) requests under `__unmatched__` rather than their raw URL.

**`/proxy/calls/export`, `/proxy/static-calls/export` and `/proxy/ivr-calls/export` forward core's row-ceiling headers, and only those** (`src/api/routes/helpers/export-headers.ts`). Core caps each of those CSV exports at 10,000 rows and flags a cut file with `X-Export-Truncated: true` / `X-Export-Truncated-Reason: row_limit` / `X-Export-Row-Limit`, plus `X-Export-Rows` on every export, and on every export `X-Export-Sort-By` / `X-Export-Sort-Order` naming the order the ceiling was applied in — which is what says WHICH end a capped file kept, and it differs by surface: `/calls/export` keeps the **oldest** 10,000 (`created_at`/`asc`), `/static-calls/export` and `/ivr-calls/export` keep the **newest** (`desc`). The export handler builds its response from core's body alone, so before this the flag stopped at master and a capped file reached the browser looking complete. `forwardCoreExportHeaders` copies exactly those six names (`FORWARDED_EXPORT_HEADERS`) — never core's headers wholesale, which would forward `content-length`/`transfer-encoding` describing core's response rather than ours — and all six are in `exposedHeaders` (`proxy-calls.routes.test.ts` asserts every entry of that list is), so cusui can read them cross-origin. An older core sends no sort pair, and nothing is invented in its place.

### Outbound HTTP (`src/utils/http-agent.ts`)

`initHttpAgent(config)` runs first in `main()` and installs a tuned undici `Agent` as the process-wide dispatcher, so **every** existing `fetch` call site (proxy layer, `coreInternalRequest`, Mailjet, PostHog) is re-pointed with no call-site change. Node's stock agent closes idle sockets after **4s** and caps sockets per origin at nothing — this service proxies to core in bursts spaced further apart than that, so nearly every batch was paying a fresh TCP+TLS handshake. Defaults: 60s keep-alive (300s ceiling), 128 connections/origin, and **300s headers / 300s body — undici's own defaults**. The timeouts are deliberately left alone: this is a pooling change, and because the dispatcher is process-wide any lower value silently cuts the timeout for the ~95 proxy routes that set none of their own (interactive chunk dispatch, `POST /calls/bulk`, KB PDF upload, `/super-admin/usage/export` streaming), turning a slow-but-successful core call into `UND_ERR_HEADERS_TIMEOUT` → masked 500 → released credits and a failed campaign row. Tighten per route class once core's p99 is known, not globally by guess. Tunable via `HTTP_AGENT_*` (read once at startup — changes need a restart); `HTTP_AGENT_ENABLED=false` restores Node's default dispatcher as an incident escape hatch. Per-request `timeoutMs` (`AbortSignal.timeout`) still applies on top and remains the tighter bound where a caller sets it.

### In-process cache (`src/cache/local-cache.ts`)

A short-TTL LRU inside `redisCache`, in front of the Redis reads the middleware chain makes **serially** on every authenticated request — user record (session), membership (tenant context), tenant + account records (name resolution), governance overrides (capability-gated routes). Measured at 0.5ms/request against loopback Redis; because it removes five *serial* round trips the saving scales with RTT, so on a managed Redis at ~1ms it is ~5ms/request.

**The layer is only safe because invalidation is broadcast.** `redisCache.del`/`delByPattern` publish on `<keyPrefix>cache:invalidate` and every instance drops the matching local entries. This is not a nicety: `PUT /users/:id/role` and the membership-delete route `del` the membership key *specifically* so a permission change takes effect at once. A purely TTL'd local copy would keep serving the **old role** from every other instance until it expired — turning revocation into an eventually-consistent operation. `test/integration/cache/local-cache-invalidation.test.ts` runs two independently-initialised caches over one real Redis to prove it; dropping the broadcast fails it.

Three things are load-bearing in *how* that broadcast is done, each of which was a real hole before it was closed:

- **Publish AFTER Redis is authoritative, never before.** Publishing first tells peers to drop their copies while the value is still readable from Redis, so ordinary traffic re-reads and re-caches the thing being invalidated. For `delByPattern` the window is the entire SCAN+DEL sweep: measured at 412 of 5,000 memberships still served after a tenant-wide revocation *completed*. Pinned by `test/unit/cache/redis-cache-invalidation-order.test.ts`, which asserts the call order rather than racing two caches.
- **An in-flight read must not repopulate an invalidated key.** `get` snapshots `LocalCache.epochFor(key)` before issuing the Redis read and populates through `setIfEpoch`; any `delete`/`deleteByPattern`/`clear` bumps the epoch and the populate is dropped. Without it, cache-aside's classic race resurrects the old role *after* the revocation — on the very instance that performed it — for a full TTL.
- **Publishing is NOT gated on this instance having the layer enabled.** `LOCAL_CACHE_ENABLED=false` is the incident lever and is rolled out instance by instance; an instance that stopped broadcasting when disabled would strand its still-enabled peers on the stale role, making the lever least safe exactly when it is reached for.

Values are stored **serialized** and `JSON.parse`d per read, so a local hit reproduces the Redis path exactly: each caller gets its own object (no aliasing between concurrent requests) and `Date` columns come back as ISO strings rather than depending on which layer served the call. The subscriber gets its own unbounded `retryStrategy` instead of inheriting the main client's give-up-after-5-attempts — the main client dying is survivable, the subscriber dying silently removes the guarantee while the cache keeps serving — and clears the local map on `ready`, since pub/sub has no replay for messages missed while disconnected.

Three deliberate constraints: **opt-in by key prefix** (`LOCAL_CACHE_FAMILIES`) rather than blanket — notably `cache:bulk-status-summary:` is excluded because those keys are written through the generation-fenced helpers, and a local copy would sit outside the fence it exists to provide; **`set` does not broadcast** (a `set` is overwhelmingly a refill of the same value on every cache miss, so publishing there would put pub/sub on the hot path for no freshness gain — genuine changes go through `del`); and **`get` populates from the Redis read**, not only from our own writes, since the common shape is one instance filling Redis and every instance reading it. The subscriber needs its own connection (ioredis puts a subscribed client into subscriber mode where ordinary commands are rejected), and the channel is prefixed by hand because ioredis applies `keyPrefix` to KEYS, not channel names — without that, two stages sharing a Redis clear each other's caches. Tunable via `LOCAL_CACHE_*`. **Defaults OFF**, and that is a rollout requirement, not timidity: instances on the previous release do not publish invalidations at all, so enabling it by default means a role change served by an old instance never reaches a new one during a rolling deploy. Ship once with it off, enable it when the whole fleet can publish; `LOCAL_CACHE_ENABLED=false` is the incident lever thereafter. `local_cache_operations_total{family,result}` is how you judge whether it earns its keep.

### Rate Limiting (`src/api/middleware/rate-limit.middleware.ts`)

Global IP limit (`RATE_LIMIT_MAX`, default 200/min) backed by the **shared ioredis client**, so counters span instances and survive deploys (`skipOnError: true` — a Redis outage allows traffic rather than 429ing the platform; without a client the plugin falls back to a per-process store, which is a limit only in dev/test). The hook runs `onRequest`, i.e. **before** the `preHandler` chain authenticates — so `keyGenerator` keys on `request.ip` only. It must never key on a caller-supplied header: the previous `apiKeyTenantId ?? x-tenant-id ?? ip` chain had a dead first term (never populated that early) and an unauthenticated second one, so rotating `x-tenant-id` minted a fresh bucket per value and bypassed the limit entirely.

**`request.ip` is only trustworthy because `trustProxy` is a hop count.** `trustProxy: true` trusts the whole `X-Forwarded-For` chain and resolves `request.ip` to its **leftmost** entry — and `nginx.conf` uses `$proxy_add_x_forwarded_for`, which *appends*, so the leftmost entry is whatever the client sent. Keying on `request.ip` under `trustProxy: true` is therefore still keying on an unauthenticated header: measured at 50 requests against a max of 5, **zero were blocked**. `config.server.trustProxyHops` (env `TRUST_PROXY_HOPS`, default 1, matching the committed nginx) makes proxy-addr walk in from the socket and trust exactly that many hops, so `request.ip` is the address nginx observed. Raise it by one per additional trusted proxy; never set it back to `true`. Two different guards are needed and it is worth knowing why: `test/integration/api/rate-limit.test.ts` ("keying" → the x-forwarded-for spoofing cases) proves a hop count *behaves* correctly, but it builds its own Fastify instance with a literal `trustProxy: 1`, so it **re-declares the value it is protecting** and cannot see `src/index.ts` reverting to `true` — mutation testing confirmed that one-word revert passed the entire unit and integration suite. `test/unit/api/trust-proxy-wiring.test.ts` closes that by asserting the wiring at the source level; `src/index.ts` builds its app inside `main()` against live config and a real listen, so there is no factory to instantiate and a text assertion is what actually catches it.

Note the limit is now **global rather than per-instance** (Redis-backed), so effective capacity went from `200 × instances` to `200`. That number has **not** been calibrated against production traffic, which is why it is an env var (`RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW_MS`, plus `RATE_LIMIT_ENABLED=false` as an incident lever) rather than a constant — raise it, watch the 429 rate, then tighten. Real per-tenant quotas need a separate post-auth limiter — dropping the `x-tenant-id` term removed the only per-tenant fairness the platform had, spoofable though it was. `/webhooks/core/*` stays exempt (HMAC-authenticated, single source IP, ~1000/type/tick recovery sweeps). The exact S2S paths in `S2S_RATE_LIMIT_EXEMPT_PATHS` (currently only `GET /internal/telephony-providers/live-transfer`) are exempt **only when the bearer token verifies** (`hasValidS2sToken`, the reply-less half of `verifyS2sToken`) — a missing or wrong token is still counted, so the exemption is no brute-force or flood path. Every other `/internal/*` call from core (caller-ID checks, agency, notifications) still shares core's egress-IP bucket; add a path there only when a 429 on it is worse than an uncounted authenticated caller.

### Error Masking (`src/api/middleware/error-mask.middleware.ts`)

A single global Fastify `onSend` hook (`errorMaskHook`, registered in `src/index.ts` right after `setErrorHandler`) is the one choke point that stops internal/upstream error detail (core stack traces, Google AI / telephony provider failures) from leaking to the client — covering both errors we raise and the ~95 routes that forward core's response body verbatim. **Policy:** always mask `5xx`; always pass through `429` (authored rate/concurrency/cooldown pacing signals — masking them into a support-ticket message is misleading); mask other `4xx` that was *forwarded from core* unless it carries field-level validation feedback (`{ details }` / fieldErrors — our Zod issues or core's); pass through our own `4xx` (Zod validation, RBAC, credit, business) unchanged. Everything else from core is masked — bare `{ message }` / `{ error }` **and** per-recipient `{ calls: [{ error_message }] }` (free text that can embed provider strings). The masked body is `{ error, message (contact support@magickvoice.com + quote the request id), statusCode, requestId }` and the hook sets `x-request-id`; the full original error is logged (error for 5xx, warn for 4xx, truncated) so it stays queryable in Grafana. Ops probes (`/health`, `/ready`, `/metrics`) are exempt so their diagnostics survive.

Telling a core-forwarded error apart from one we generated ourselves uses a per-request seam in the AsyncLocalStorage log context (`src/utils/log-context.ts`): `proxyToCore()` / `coreInternalRequest()` call `recordCoreErrorStatus(status)` on any `>= 400` core response, and the hook reads `sawCoreErrorStatus(status)`. Detection keys off the status *code*, which relies on the invariant that a route's own client errors are returned **before** any core call that records its status. Beyond the alert routes, the super-admin feature-flag relay marks core's `Invalid Scope` / `Invalid Value` / `Not Found` 4xx reviewed per response (see *Super Admin* routes). Best-effort core lookups whose failures are swallowed (not forwarded) must pass `recordCoreErrors: false` to `proxyToCore()` to preserve that invariant; routes that forward core via raw `fetch()` (audio upload, inbound-intents) call `recordCoreErrorStatus()` themselves.

### Phone Number Management (`src/proxy/phone-number-resolver.ts`)

Centralized phone number pool managed by super admins. Each phone number is intrinsically linked to a telephony provider — selecting a number auto-determines the provider.

**Phone number resolver** (`resolveCallerPhoneNumber()`): called by proxy-calls, proxy-ivr, and proxy-announcements routes before forwarding to core. Validates `caller_id` against the tenant's assigned phone numbers, checks account-level accessibility (tagged vs untagged/tenant-wide), and returns the resolved provider name. The proxy injects the resolved `telephony_provider` into the request body. Returns 403 if the number is not assigned.

**DB tables** (migration 010):
- `telephony_providers` — system registry of providers (vobiz, twilio, plivo, exotel). Super admin CRUD. Carries `live_transfer_enabled` (migration 074), the per-carrier **live-transfer (human escalation) governance flag**: seeded ON for vobiz + plivo + twilio (plivo because it already transferred before the flag existed), default OFF for everything else. The enabled set is `live_transfer_enabled AND status='active'` (`telephonyProviderRepository.findLiveTransferEnabledNames()`, read from Postgres on every call and **never cached** — a read-through copy let a read that SELECTed before a disable `SET` the pre-toggle set after the invalidation's `DEL`, re-authorizing the carrier for a TTL; callers are ~1/min per core replica plus rare metadata misses, against a handful of rows), served to core over `GET /internal/telephony-providers/live-transfer` (core intersects it with its code-level `TRANSFER_CAPABLE_PROVIDERS` and fails closed without it) and intersected into `/proxy/metadata`. A write to the flag or to `status` busts the provider cache (repository) **and every `cache:metadata:*` key** (`invalidateAllMetadataCache`, called by the `PUT /super-admin/telephony-providers/:id` route — the repository deliberately has no metadata side effect). Because `status` gates the set, deactivating a carrier whose flag is ON stops its live transfers: that write is logged at warn and its audit entry carries `live_transfer_warning`. Provider cache keys are `cache:telco:v2:*` — versioned so rows cached before the column existed are never served.
- `phone_numbers` — global pool with provider FK, capabilities, max_concurrent_calls, status (active/retired/deleted), and `pool_eligible` (migration 037).
- `tenant_phone_assignments` — which tenants can use which numbers. Partial unique index enforces one default per tenant. Auto-assigned (least-used **within the signup pool**) on tenant creation.
- `phone_account_tags` — tenant admins tag numbers to specific accounts. Untagged = accessible to all accounts.

**Signup pool vs dedicated numbers (`pool_eligible`, migration 037):** Only numbers a super admin has explicitly flagged `pool_eligible = true` may be auto-assigned to brand-new (unverified) tenants at signup — `phoneNumberRepository.findLeastAssigned()` filters to `status='active' AND pool_eligible=true`. Numbers left unflagged (the **default is `false`**) are *dedicated*: they can only ever be assigned manually by a super admin and are never handed to a signup. The flag is set/toggled via the super-admin create/update phone-number routes. Signup auto-assignment is best-effort and non-fatal: an empty pool just provisions the tenant without a default phone (logged + `signup_phone_assignments_total{result="pool_empty"}` metric for ops alerting). Migration 037 backfills only the historically-shared seed number `+918046733449` to `pool_eligible=true`; existing tenant assignments are untouched.

**Lifecycle:** active → retired (reversible, blocked if assignments exist) → deleted (irreversible).

### Inbound DID configuration (`src/services/inbound-config.service.ts`, `src/api/routes/phone-number.routes.ts`)

Which AI (or IVR workflow) answers when someone **dials** a tenant's DID. The rows live in core (`inbound_phone_numbers`); master owns the tenant-facing surface, the RBAC gate and the carrier question, and holds no inbound table of its own.

**`SUPPORTED_INBOUND_PROVIDERS` is a hand mirror of core's `INBOUND_CAPABLE_PROVIDERS`** (`magic-voice-core/src/core/inbound-providers.ts`), currently `{vobiz, plivo, telnyx, twilio}`. Core registers `/api/v1/webhooks/{provider}/incoming` and `/inbound-status` once per entry there, so a carrier missing from that map has no URL for the carrier to POST an arriving call at. It is a mirror rather than a lookup because **core publishes no inbound-capability field**: `GET /api/v1/metadata` carries `telephony.default_provider`, `telephony.providers` and `escalation_transfer.transfer_capable_providers`, none of which answer this — and `telephony.providers` is actively the wrong list, since core states inbound registration is "deliberately NOT derived from `TELEPHONY_ENABLED_PROVIDERS`" (a deployment can dial a carrier it cannot receive on, and vice versa). `test/unit/services/inbound-providers-contract.test.ts` parses core's `SPECS` and asserts set equality, `skipIf` core is not checked out beside master — the same guard shape as the agency S2S contract, and for the same reason: an unenforced hand mirror is how master's agency error-code copy fell behind.

Drift is silent in **both** directions. Too narrow and the carrier is unreachable through the product **and** `GET /:assignmentId/inbound/conflict-check` short-circuits to `{in_use_externally: false}` without asking core — a real cross-tenant conflict on a live DID reads as clear, which is worse than a missing feature. Too wide and a DID is configurable for a carrier whose webhook 404s, so the caller hears nothing. Three enforcement points read the set: the `supports_inbound` flag cusui renders (cusui holds **no** carrier list of its own — that flag is the entire contract), the 409 on `PUT /:assignmentId/inbound`, and that conflict-check short-circuit.

**Carrier keys are normalized (trim + lowercase) on every value sent to core**, which matches them with SQL `=` — a row stored as `"Plivo"` sits active in the table and is invisible to every Plivo webhook. Nothing in master can currently produce a mixed-case name (`telephony_providers.name` is seeded lowercase, `createTelephonyProviderSchema` enforces `/^[a-z0-9_]+$/`, and neither `updatePhoneNumberSchema` nor `updateTelephonyProviderSchema` can change a carrier afterwards), so this is depth, not a live bug. `providerSupportsInbound` is deliberately **total**: every call site reads `provider_name` through an `as any` cast that proves nothing, and the predicate must not turn a missing value into a 500.

**Two deletes with deliberately opposite carrier semantics**, which is the easiest thing here to get backwards:

| Caller | Carrier | Why |
|---|---|---|
| `DELETE /super-admin/phone-numbers/:id/assign/:tenantId` (unassign cascade) | **omitted** ⇒ every carrier | The fact recorded is "this tenant no longer holds this number", true of every carrier it may be registered under. Core's by-phone DELETE reads an absent `?provider=` as exactly that cascade, and this caller is the one that semantic was written for. The delete is tenant-scoped by core, so widening across carriers cannot reach another tenant's rows. |
| `DELETE /phone-numbers/:assignmentId/inbound`, and the untag cascade | n/a — resolves one row | Removes the row behind one assignment. |

**Omitted and blank are not the same thing on that cascade.** Core 400s a present-but-blank `?provider=` precisely so a client serializing "carrier unknown" as `''` cannot silently widen its own irreversible delete; reading blank as absent locally would hide that refusal and perform the widening it guards against, so `removeAllForTenantPhone` throws on a blank rather than letting it travel. Only `undefined` omits the key. (Omitting the key outright, rather than sending an empty value, is also what stops `URLSearchParams` serializing `undefined` as the literal string `"undefined"`.)

**`upsert` refuses a carrier mismatch; `findOne` selects the active row explicitly and sends no `?provider=`.** The two are a pair, because the cross-carrier lookup below is right for deletion and wrong for a write: **core's update schema has no `provider` field**, so a carrier cannot be changed in place. Without the guard, configuring inbound on a Plivo assignment whose number still carries an active VoBiz row PUTs the routing fields onto that VoBiz row, answers 200, and leaves the UI showing inbound enabled — while `/api/v1/webhooks/plivo/incoming` resolves `(phone, 'plivo')`, finds nothing, and hangs up on every caller, with nothing red anywhere. It is **refused** (409 naming both carriers) rather than repaired: deleting the stale row to recreate it destroys its prompt/IVR/escalation config on a hard delete nobody asked for, and creating a second row leaves the number active on two carriers, which core warns about and resolves by deployment default. The disable path refuses too — reporting "disabled" for an assignment whose live row is on another carrier would be false while that row went on answering. The guard fires only on a *known* mismatch: a row returned without a carrier is missing data, not evidence of a different one.

**`findOne` selects the active row explicitly, and sends no `?provider=`.** Core orders the scoped read `is_active DESC, created_at DESC` so `rows[0]` is the live row — but the caller then PUT/DELETEs that id, and migration 034's uniqueness is partial (`WHERE is_active`), so any number of inactive rows can sit beside the live one. Selecting on `is_active` keeps the intent local instead of resting on another repo's `ORDER BY`. A carrier-keyed read would be exact but fails **silently**: if core's row carries a different carrier than master's pool record, it finds nothing, `remove()` returns early, and the route answers 204 having deleted a row that is still answering calls.

**The lead-capture proxy (`/proxy/inbound-intents`) is WITHDRAWN — both routes answer 410 Gone.** It forwarded the marketing site's lead form to core's `POST /internal/inbound-intents`, pre-registering a lead against a DID so an inbound call from that number reached the right tenant (or so core placed an immediate callback). The product no longer needs it. Core's `/internal/inbound-intents` routes are untouched; only master's public proxy in front of them is gone.

**410, not 404, and a stub rather than a deletion.** A 404 is what a typo'd path returns, so a surviving caller cannot tell "I have the URL wrong" from "this was withdrawn". Every hit is logged with connection metadata — never the body, which carried lead PII — so a real integration still pointed at it shows up in Grafana rather than failing into a quiet retry loop. Delete the plugin once those logs are silent for a full retention window.

Removing it regresses nothing observable, because **neither route worked as shipped**:

- `GET /phone-numbers` had returned 400 on every call since core added `authMiddleware` to its `inboundPhoneNumbersRoutes` plugin — it sent an S2S bearer token and no `x-mgkvc-tenant`/`x-mgkvc-account`, which that middleware rejects before any key check. Nothing called it anyway: `www`'s form hardcodes its DID rather than listing them.
- `POST /` was reachable at its real path, but its only intended caller never reached it. `www/src/components/sections/LeadCapture.tsx` posts `/api/inbound-intents`; **this service has no global `/api` prefix** (`src/index.ts`), and neither `nginx.conf` nor `www/vercel.json` rewrites one. Both sides shipped in the same commit (#55) with the mismatch already present, so the form has 404'd since it existed.

The caveat that follows from the second point: the POST *endpoint* did work at its real path, so a direct integration built against `/proxy/inbound-intents` rather than through the form does break here. That is the decision the deprecation records, and those logs are what would surface such a caller. `www`'s lead form is now dead UI — it posts a path that 404s at a backend whose target is gone; removing it is a marketing-site change, not bundled in here.

### BYOC telephony (`src/api/routes/super-admin-telephony.routes.ts`, `src/services/byoc-phone-number.service.ts`)

A tenant may dial on **their own carrier account**. **Core owns the credentials AND the BYOC numbers; master persists neither** — there is no migration, no repository and no cache of either in this repo, and master's `phone_numbers` inventory carries no ownership flag (that was the reverted design, `056ad0a`/`b57e683`). Master does exactly two things.

**1. An audited super-admin passthrough** to core's `/internal/telephony-credentials/*` and `/internal/byoc-phone-numbers/*`, shaped like `super-admin-sip.routes.ts`. `GET/POST /super-admin/tenants/:id/{telephony-credentials,byoc-phone-numbers}`, `PUT/DELETE /super-admin/{telephony-credentials,byoc-phone-numbers}/:id`, `POST /super-admin/telephony-credentials/:id/verify`, `POST /super-admin/byoc-phone-numbers/:id/accounts`. **PUT, not PATCH** — `coreInternalRequest`'s method union has no PATCH and widening it is churn. Three rules are load-bearing rather than stylistic: **master never stores, caches or logs the carrier auth token** (it exists as one field on two in-flight bodies; `safeIssues` scrubs it out of validation feedback because zod's enum message quotes the received value, which is what an operator pastes it into); audit `details` is a **named allow-list**, never a body spread, so a core response that grows a token-shaped field cannot ride along; and audit rows are written **only on `isSuccess(result.status)`** (`super-admin-usage.routes.ts:41-59` explains why at length). Core's revoke 409 carries a per-call-type breakdown and is exempted from `errorMaskHook` per resolved response, shape-checked — a 409 without the breakdown stays masked. Provider is restricted to `BYOC_PROVIDERS = ['vobiz', 'plivo', 'twilio']` in one named const: core's factory throws for an unmapped provider, and a silent fallback to the platform carrier is exactly the caller-ID/account mismatch the feature exists to prevent. `checkProviderAuthId` adds a per-carrier format guard on the auth id — VoBiz's `MA_`/`SA_` prefix, and Twilio's `AC` + 32 hex — because pasting the auth *token* into the auth *id* is the obvious operator slip. It matters more for Twilio: a Twilio auth token is also 32 hex, so the fields look interchangeable, and core resolves a tenant's INBOUND webhook signing key by that `auth_id`, so a wrong one 403s every inbound call on their DID rather than merely failing to dial.

**2. Stopping its own fail-closed caller-ID gate from 403-ing BYOC numbers.** This is the one real integration point: `resolveCallerPhoneNumber` 403s on a `phone_numbers` miss, so **every BYOC call fails until this is handled**. Both branches gained a fallback — the platform lookup runs first and unchanged, and core is asked only on a miss (`POST /internal/byoc-phone-numbers/resolve` for a named `caller_id`; the `is_default` flag from `GET …/caller-ids` when the tenant has no *platform* default at all, which a BYOC-only tenant never does). A double miss throws the same `PhoneNumberNotAssignedError` with the **same message** — a BYOC tenant and a typo must stay indistinguishable. `ResolvedPhoneNumber` gains `isByoc` and `credentialId` (always present; `false`/`null` for platform numbers), cached under the **same** `cache:phone:*` key and 4h TTL so `invalidatePhoneCacheForTenant` already covers them. The pool form keeps `MixedProviderCallerIdsError` and adds `MixedCarrierOwnershipCallerIdsError` (→ 400): a BYOC and a platform number can both be `vobiz`, so the provider check cannot see that they dial on two different carrier accounts.

**Cache invalidation is not optional here.** A 4h stale resolution on a *revoke* means a tenant keeps dialling on a credential the operator believes they switched off. Every write on the super-admin surface busts `cache:phone:<tenant>:*` from core's response `tenant_id`, falling back to the whole family when the response names none (a bodiless 204 revoke). Writes made *inside* core call `POST /internal/phone-numbers/cache-invalidate` (S2S, `{tenant_id?}`) to reach the same bust.

**Tenant-facing surfaces that merge BYOC numbers:** `GET /phone-numbers` appends them with `is_byoc: true` (every field named, never spread — core's rows join the credential table), and `/internal/phone-numbers/caller-ids` + `/validate` accept them so core's own WebRTC dialer picker does not reject a tenant's own numbers. `is_byoc` is on **both** halves of the caller-ids list, `false` included: a flag that only appears when true is indistinguishable from a client that forgot to read it. Both merges **degrade** — an unreachable core yields the platform numbers and a warn, not a 500 — while the resolver treats the same silence as fail-closed. No new governance capability and no new RBAC permission: the super-admin surface is JWT-gated and the tenant-facing surfaces reuse `proxy.phone_numbers.read`.

### Contact Lists (`src/contact-lists/`)

CSV-based bulk contact management. Users upload CSV files with phone numbers and/or email addresses plus arbitrary variable columns. The system parses, validates, stores raw CSV in S3, and caches metadata (columns, row count, first 20 rows) in the DB. Contact lists are type-agnostic — reusable across IVR, static calls, messaging, AI voice calls, and email campaigns.

**Key files:**
- `csv-parser.ts` — Parses CSV buffer; **requires a `phone` OR `email` column (auto-detected, case-insensitive header match)** — voice/IVR/static/WhatsApp key on `phone`, email campaigns key on `email`. Validates the present recipient identifier(s) — E.164 for phone, format check for email — per row (a row is valid if it carries at least one usable identifier, so email-only lists are supported); enforces limits (10K rows, 50 cols). Downstream dispatch selects the field via `recipientField` (`chunked-dispatch.ts`) / `phoneField = isEmail ? 'email' : 'phone'` (messaging routes).
- `template-generator.ts` — Generates context-aware sample CSV templates (fetches workflow/prompt variables from core). `type=email` emits an `email`-keyed template; all other types are `phone`-keyed.
- `contact-list.service.ts` — Orchestrates upload (parse → S3 → DB), delete (DB → S3), and re-parse from S3
- `contact-list.repository.ts` — DB CRUD for `contact_lists` table
- `chunked-dispatch.ts` — Splits contacts into 100-phone batches, reserves credits per chunk, proxies each to core. Returns `dispatched_items` (`{ id, recipient }[]`) purely for internal per-item automation stamping — it is **stripped from client-facing responses** by the routes (destructured out before `reply.send`) to keep the API surface stable.
- `finalize-chunked-dispatch.ts` — Shared `finalizeChunkedDispatchJob(job, result, { bindingKind?, resolvedAutomations?, tenantId, accountId?, notificationEmails? })` helper (ticket 86d3k6eh9): the single choke point that rolls up chunk counters, appends core batch ids, sets the terminal job status, stamps attached automations per dispatched item, and fires the job-completion email (skipped on total failure, matching the routes' 422-before-email behavior). Returns `{ jobStatus, errorDetail }`; the IVR/static/AI-voice contact-list branches keep their own 422-vs-200 control flow. Messaging delegates the counters/status portion here too (no `bindingKind`/emails — messages carry no completion trigger and email is sent via its own `maybeSendJobEmail`). Deliberately a separate module from `chunked-dispatch.ts` because that module is fully mocked in the route unit tests.

**S3 storage** (`src/storage/s3.ts`): Direct AWS SDK v3 integration (separate from core's S3). Bucket provisioned via `serverless.yml`. Config: `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`.

**Batch initiation via contact list:** Existing proxy routes (`proxy-ivr`, `proxy-announcements`, `proxy-messaging`) accept `contact_list_id` as an alternative to `phones[]`. When provided: fetch list → resolve caller_id once → download CSV from S3 → chunk → reserve credits per chunk → proxy each chunk to core. IVR uses `chunkSize=1` when CSV has per-contact variables (columns beyond `phone`).

### Scheduling (`src/scheduling/`)

Schedule-ahead module for all communication types (AI Voice, IVR, Static Calls, WhatsApp). Schedules fire via AWS EventBridge Scheduler + Lambda callback. Per-contact retry with user-defined intervals. Feature-flagged by presence of `scheduler` config block.

**Sent Campaigns visibility + automations (product decision, ticket 86d3k6egy):** a scheduled campaign **is** a campaign, so its execution surfaces in Sent Campaigns and fires attached automations, exactly like a direct/contact-list send (mirrors PR #137). When a schedule fires, `executeSchedule()` creates a `bulk_dispatch_job` (**source `scheduler`**, `schedule_id` linked) and finalizes it from the dispatch outcome through the **shared park-or-finalize gate** (`src/dispatch/resolve-final-status.ts`), like every other dispatch path. It was pure **dispatch-ack** (terminal status reflects what core accepted, not eventual call completion) until the `dispatched`-vs-`completed` fix (ClickUp `86d2hme6q`): now a scheduled campaign whose job snapshotted `completion_tracking_expected` parks in `dispatched` (+ `dispatched_at`, no `completed_at`) and reaches a terminal status from core's `batch.completed` webhook or the reconcile sweeper. The per-contact AI-voice case still finalizes immediately, because core returns no batch id for it and therefore sends no callback — `createSchedulerJob` already records that truthfully. This happens **only on the below-threshold direct path**; the above-threshold path already routes through `bulkDispatchProducer.enqueue` which owns its own job (the scheduler just forwards `attachedAutomations`). One job is created **per execution attempt** (so a retry that re-dispatches a subset gets its own row, consistent with the SQS path); retry-attempt jobs get a ` (retry N)` name suffix so they don't read as duplicate rows. If dispatch throws mid-flight (e.g. a later chunk hits insufficient credits after earlier ones went out), the catch **flushes the already-dispatched batches** and marks the job `partially_failed` rather than a misleading zero-progress `failed`. Batch granularity: AI voice dispatches per-call (batch == call, no core batch id) so its job carries empty `dispatched_batch_ids`; chunked types (IVR/static/WhatsApp) batch at 100 and record each chunk's `batch_id`. Counters are applied in one `addBatchCounters` UPDATE at finalization (not one-per-batch). Automations are attached at **creation** time via `automation_ids` on `POST /proxy/schedules` (and recurring), resolved + version-snapshotted (`resolveAutomationIds`, validated against the schedule type's `DISPATCH_TYPE_COMPATIBLE_TRIGGERS` — an incompatible/disabled/unknown id → 400) and persisted to `schedules.attached_automations` (migration 041). At execution each created call/session is stamped with a `workflow_binding` (`call`/`ivr_session`/`static_call`); `whatsapp_message` has no completion trigger so an automation can never attach to a WhatsApp schedule. Recurring schedules snapshot on the template and copy the snapshot onto each fired instance (`update` re-resolves for future instances only).

**Creating a schedule is ALL-OR-NOTHING via a compensating delete, and the contact set is normalized + de-duplicated before any of it (ClickUp `14ygtkj8u67`).** `createSchedule` makes three writes — the `schedules` row, the `schedule_contacts` rows, the EventBridge one-time fire — and they are not one transaction and **cannot be**, because the third is an external call. A duplicate phone therefore used to raise `23505` on `uq_schedule_contact` (migration 013) at step 2, *after* `pending_count` had committed and *before* any job existed: the UI rendered `Scheduled` forever, nothing dispatched, and only a manual cancel cleared it. Three rules follow, and each was a live defect:

1. **`normalizeScheduleContacts` (`contact-normalizer.ts`) runs before anything is written**, and normalization runs BEFORE de-duplication — `+91 91243 29502` and `+919124329502` are one row to the constraint and two strings to a naive `Set`. First occurrence wins (matching the CSV parser's own "first seen at row N" warning), and the surviving phone's `contact_data` travels with it or the `contactData?.[i]` index zip pairs a phone with another contact's variables. A phone that cannot be coerced is kept **verbatim**, matching `normalizePhonesArray`: it becomes one visible `failed` contact rather than a silently shorter campaign.
2. **Every derived figure reads the SURVIVING set** — `pending_count`, `estimated_credits_mc`, the stored `phone_numbers`, the audit `total_contacts`, and `trackScheduleCreated.contactCount`. Sizing any of them off the raw input leaves `pending_count` above the number of contact rows that exist, so `decrementPendingCount` never reaches 0 and the schedule can never complete — a different bug wearing the first one's clothes.
3. **Steps 2 and 3 are wrapped, and the compensating delete never masks the cause.** `scheduleRepository.deleteById` removes the row (`schedule_contacts` follows via `ON DELETE CASCADE`), the original error is rethrown, and a delete that itself fails is logged at `error` rather than swallowed — the caller needs the constraint violation or the AWS refusal, not whatever the clean-up hit. `createRecurringSchedule`, `executeRecurringInstance` and `RetryManager.handleBatchCompletion` carry the same guard, each with the compensating action its own state allows.

**The de-duplication lives in the scheduling layer, NOT in `csv-parser.ts`**, though the ticket proposed the parser. `uq_schedule_contact` is scheduling-specific, while `parseCsv`/`getContactsFromS3` also feed `proxy-messaging.routes.ts` and `dispatch/run-dispatch.ts`, where two rows for one phone are a legitimate second send and dropping one would silently lose a message. Same call the agency ingest already made for the opposite reason (`agency-csv-ingest.ts` is a separate parser *because* the roster needs dedupe): the consumer that owns the constraint owns the dedupe. Note the consequence — `contact_lists.row_count` counts duplicates and cusui renders it when picking a list, so a schedule's contact count can legitimately come out one lower with nothing explaining the gap.

**Key files:**
- `scheduler.service.ts` — Core orchestrator: create, cancel, execute, handle completion. Resolves telephony provider from caller_id before dispatch. Promise-based concurrency limiter for AI voice calls (10 concurrent). Resolves telephony provider from caller_id before dispatch. Promise-based concurrency limiter for AI voice calls (10 concurrent).
- `eventbridge.client.ts` — Wraps `@aws-sdk/client-scheduler`. Creates/deletes one-time schedules with auto-cleanup (`ActionAfterCompletion: DELETE`), DLQ, retry policy.
- `retry.manager.ts` — Post-batch retry: finds retryable failed contacts, creates new attempt rows, schedules next EventBridge fire. **Arming a retry is all-or-nothing too**, by a different compensating action: three DB writes around one external call on a schedule that is LIVE, so the row cannot be deleted to undo them. Half-applied it was not merely untidy but UNRECOVERABLE — the sweep re-enters here and re-derives the retry from `findRetryable`, which requires `status = 'failed'`, while the arming UPDATE has already moved those rows to `retry_pending`; so the sweep found nothing retryable, finalized the schedule `completed`/`failed`, and the attempt-N+1 rows it had already inserted were left for nothing to dial. A retry the customer configured silently did not happen. `scheduleContactRepository.revertRetryPreparation` restores the exact pre-arming state in one transaction (delete attempt N+1, put attempt N back to `failed`, leaving `failure_retryable` alone — it is what `findRetryable` gates on), so the next sweep re-derives the same decision. A stray EventBridge job from a failure at the last step is deliberately left: it fires against a schedule whose `current_retry` never advanced, `atomicClaim` refuses it, and one-time jobs self-delete. **The revert's two predicates are pinned against a real Postgres** (`test/integration/repositories/schedule-contact.repository.test.ts`), because a mocked pool never parses SQL — the same reason the credit ledger's idempotency is; the round-trip case asserts `findRetryable` sees the reverted rows again, which is the property the whole undo exists for, and is invisible to any assertion on the query text. Its transaction control (one connection, ROLLBACK on failure, the connection released on every path, a failing ROLLBACK not replacing the caller's cause) is the unit half, in `test/unit/db/repositories/schedule-contact.repository.test.ts`. **Arming is also SINGLE-WRITER, by a compare-and-set on `schedules.current_retry`** (`scheduleRepository.compareAndSetCurrentRetry`, `atomicClaim`'s pattern one column over) — and without it the compensation above was the thing doing the damage. This method is entered concurrently as a matter of routine: the recovery sweep runs on every replica against the same `findStuck` set, and core redelivers completion webhooks onto arbitrary replicas. Two workers read the same `findRetryable` rows; the loser's arming UPDATE matched zero rows, it inserted attempt N+1 anyway, hit `uq_schedule_contact`, and its revert then DELETED THE WINNER'S attempt-N+1 rows and put attempt N back to `failed` — while the winner went on to create the EventBridge job and advance the schedule. One retry armed, its contacts deleted by the other worker, a job firing against nothing. The claim runs BEFORE any of the three writes, so the loser writes nothing, reverts nothing, throws nothing and — critically — does NOT finalize (closing the schedule underneath a retry somebody else is arming is the original bug from the other side). It also fences the compensation by construction: only the worker that claimed the attempt can reach the writes that need undoing. `current_retry` is therefore the CLAIM's column and `updateStatus` no longer carries it — a second writer of it is what the election exists to remove — and the failure path RELEASES the claim (compare-and-set in reverse, so it can never clobber a claim since taken legitimately), because `findRetryable` gates on `current_retry` and leaving it advanced hides the very rows the revert just restored. The predicate and its `rowCount` are pinned against a real Postgres in `test/integration/repositories/schedule.repository.test.ts`, including the concurrent-claimants case, for the reason the revert's predicates are: a mocked pool never evaluates a `WHERE`.
- `recovery.ts` — Startup + periodic sweep (`RECOVERY_SWEEP_INTERVAL_MS`, **1 hour**) for stuck schedules in `executing` or `partially_failed` state. **It does not cover `scheduled`**, so a row whose EventBridge job was never created is invisible to every sweep — which is why the create path has to be all-or-nothing rather than recoverable after the fact. Each schedule is swept inside its own try/catch: the outer one wraps the whole loop, and `findStuck` returns the same set every hour, so one reliably-throwing schedule used to abandon every schedule behind it on every tick, indefinitely — including the retry revert above, which depends on this sweep to re-run.
- `timezone.ts` — Converts naive datetime + IANA timezone to UTC using `Intl.DateTimeFormat`.

### Bulk Dispatch Queue (`src/queue/`)

Queue that throttles bulk call/message dispatch to magic-voice-core. When any dispatch path (direct UI, contact list, or scheduler) exceeds a configurable phone threshold (default 5), phones are enqueued as per-batch units instead of dispatching directly.

**Two transports, one set of semantics.** All dispatch behaviour — credit reservation, the core call, partial-failure handling, schedule-contact bookkeeping, automation binding stamps, job counters, finalization, credit abort — lives in `batch-executor.ts` and is shared verbatim by both transports, so they cannot drift:
- **`lane-scheduler.ts`** (current) — per-tenant, per-type fair scheduling off a Postgres ledger. See below.
- **`bulk-dispatch.consumer.ts`** (legacy) — the SQS FIFO consumer, retained so batches already queued when the scheduler is enabled still drain. Do not add features to it.

### Campaign lifecycle: `dispatched` ≠ `completed` (`src/dispatch/resolve-final-status.ts`)

```
queued  →  processing  →  dispatched  →  completed | partially_failed | failed | cancelled
"Waiting"   "Sending"      "Calling"      "Done"
```

`bulk_dispatch_jobs.status` always carried `dispatched` ("every batch is with core, calls are
still in flight"), but only the queued path ever wrote it. The direct and contact-list-chunked
paths wrote `completed` + `completed_at = NOW()` on core's 2xx — and since the queued path only
runs above `sqsBulkDispatch.threshold`, the COMMON case reported a finished campaign with zero
calls connected: wrong `completed_at`, no Stop affordance (`/cancel` takes
`queued|processing|dispatched`), and a "Job Completed" email in the customer's inbox at dispatch
time. ClickUp `86d2hme6q`; the cross-service contract is
`MagickVoice-platform/docs/bulk-campaign-lifecycle-design.md`.

**One gate, four callers.** `resolveFinalJobStatus` is the only place that decides, and
`batch-executor.ts`, `run-dispatch.ts`, `finalize-chunked-dispatch.ts` and
`scheduler.service.ts` all call it. Three copies of this rule is how the drift happened.

```ts
supportsBatchCompletion(dispatch_type)   // static_call | ai_voice_call | ivr_call
  && completion_tracking_expected        // the ROW's snapshot, not live config
  && batches_succeeded > 0               // an all-failed dispatch gets no webhook
```

Each negation is a job that would otherwise hang: **messaging types have no per-call terminal
webhook and must keep finalizing immediately**; a job created without
`BATCH_COMPLETION_WEBHOOK_URL` has nothing to move it out of `dispatched`; an all-rejected
dispatch has no accepted batch to report on. Parking writes `dispatched_at` (migration 071) and
**not** `completed_at`, which reverts to meaning completion.

**Two emails, one of each.** `sendJobDispatchedEmail` (new) fires at the `dispatched`
transition and must never claim completion or carry a `Completed At`; `sendJobCompletionEmail`
moved to the real terminal transition only. A parked job gets both; an immediate-finalize job
(messaging, no webhook config, all batches failed) gets only the completion mail, as before.
Exactly-once holds because a job parks on the one path that dispatched it, and every terminal
transition out of `dispatched` goes through `tryFinalizeDispatched`, which is fenced on
`WHERE status = 'dispatched'` — the loser of the race sends nothing.

**The reconcile sweeper is what makes parking safe** (`src/dispatch/reconcile-dispatched-jobs.ts`,
started unconditionally in `index.ts` beside the DNC sweep). Parking makes the job depend on
core's `batch.completed` webhook, and core's settlement fan-out is documented as non-durable —
so a lost webhook, previously invisible, would now strand a job in a non-terminal state forever,
which is worse than the bug being fixed. Each tick reads jobs parked longer than
`BULK_DISPATCH_RECONCILE_MIN_AGE_MS` (2 min), asks core for the grouped per-batch summary, and
finalizes through the same `determineTerminalStatus` the webhook uses once in-flight calls reach
zero; past `BULK_DISPATCH_RECONCILE_MAX_AGE_MS` (12 h) it finalizes anyway and stamps
`error_message`. **It never finalizes on a failed read** — unreachable core, non-200, or a body
with no `by_batch` envelope all mean *unknown*, and unknown leaves the row alone. Multiple
replicas sweeping the same job is safe by construction (the fence), so nothing is locked or
claimed. The age anchor is `COALESCE(dispatched_at, started_at, created_at)`, because migration
071 deliberately does not backfill and rows parked before it are the ones most likely stuck.

**Stopping a campaign (ClickUp `14ygtkj95yp`).** Every path that tells core to stop goes through `cancelCoreBatches` (`src/dispatch/cancel-core-batches.ts`, which also owns `CANCEL_PATH`): core's **multi-batch** `…/batches/cancel`, 500 ids per request (core's `CANCEL_BATCHES_MAX_IDS`), serial, never throws. The single-batch child is no longer used by master, and it was the defect: a variable-column IVR contact list is one contact per core batch, so `/cancel` looped ~5,000 single-batch POSTs into core's 200/min per-tenant limit, never read the non-2xx answers, and reported a cancelled job while core kept dialling (the single-batch form also dispatches no settlement). `/cancel` and `/stop-remaining` stay 200 — the job IS cancelled here — and add `core_cancel_complete` / `core_cancel_failed_batches` beside `cancelled_in_core`; `false` means some batches were not confirmed stopped (a non-2xx, a throw, or an unresolvable core key), and pressing Stop again is safe because core's cancel is idempotent. Three rules close the windows a cancel used to lose: **`updateStatus` refuses to move a job off `cancelled`** (`AND (status <> 'cancelled' OR $2::text = 'cancelled')`, returns whether it wrote) and every finalizer gates its mail and outcome metric on that boolean, the `tryFinalizeDispatched` pattern; a batch's `error_message` is written by `setErrorMessage`, never by re-writing the status read before dispatch; and **a batch id that reaches the row after the cancel is cancelled in core by whoever appended it** — the executor re-reads the status after `appendBatchId`, and the chunked, direct and scheduler finalizers (which append only at the end, so the cancel route saw no ids) cancel their own batches when the guarded write is refused. The in-request chunked dispatch checks `shouldStop` between chunks, and **so does the scheduler's direct path** (no SQS, or below its threshold): `SchedulerService.jobStopCheck` asks `findStatus` before every chunk after the first in `dispatchInChunks` (IVR, static, WhatsApp and the multi-caller-ID AI bulk path) and before every contact after the first on the per-call AI-voice path, **fails open** on a throw, and latches once it reads `cancelled`. Without it a stopped scheduled campaign sent every remaining chunk — reserving credits and dialling — with only the finalizer's cancel reaching core afterwards. The contacts it never reached are moved `pending` → **`skipped`** (`scheduleContactRepository.skipPendingContacts`, `error_code = 'JOB_CANCELLED'`) and `pending_count` drops by the rows that moved: left `pending` they would hold the counter above zero so the schedule never completes, and `skipped` rather than `failed` keeps them out of `findRetryable`, so a retry cannot dial a contact the operator stopped. **`/cancel` adds `core_cancel_pending_dispatch`**, `true` exactly when the cancel statement found the job in `processing` (`bulkDispatchJobRepository.cancel` returns `previous_status`, read in a `FOR UPDATE` CTE — `RETURNING` only sees the new row, and without the lock the CTE reads its snapshot and a cancel queued behind a completing write overwrites `completed`; both races are pinned against a real Postgres). It qualifies `core_cancel_complete`, which only ever describes the batch ids on the row: the in-request and scheduler paths append theirs when the loop *finishes*, so a mid-send cancel used to answer `complete: true` over an empty list, and a queued-path job may have one batch mid-request — so **`/cancel` answers `core_cancel_complete: false` whenever `core_cancel_pending_dispatch` is `true`**, and the direct `runDispatch` path writes `processing` after its reservation and before its one core call so that window is visible too (a 402 still leaves `queued`). `true` means the stop is still being carried out by that dispatcher (each re-checks and cancels in core what it sent). Deliberately the pre-cancel status alone — a fact the statement read, not an inference; its one false positive (a queued job between batches) only tells a client to wait for a stop that already finished. `/stop-remaining` always answers `false` (terminal jobs only). `cancelCoreBatches` also **drops non-UUID ids before chunking** (one warn with the count; counted neither cancelled nor failed): core's cancel validator takes any string and its column is UUID, so one junk id `22P02`'d the whole 500-id chunk. **A scheduled campaign's contacts are settled by the stop too** (`settleContactsOfCancelledJob`, `src/scheduling/cancelled-job-contacts.ts`, never throws): batch-dispatched contacts carry the BATCH id in `external_ref_id`, so no settlement resolves them and the recovery sweep used to time them out as *retryable* — a stopped campaign with retries on was re-dialled. `/cancel`, `/stop-remaining`, the executor's late-batch cancel and the scheduler's `cancelBatchesOfCancelledJob` move the cancelled batches' still-`dispatched` contacts to `failed` / `BATCH_CANCELLED` / non-retryable; `/cancel` also skips the current attempt's still-`pending` contacts **only while the schedule is `executing`** (the queued path has no loop left to do it; a schedule that has since armed a retry is `partially_failed` and its next attempt is not this job's), and the executor skips the phones of a batch it discards because its job is cancelled. `pending_count` drops by the rows that moved, and the schedule is completed when that reaches 0 (except on the in-process scheduler, whose own `checkSynchronousCompletion` follows). `markDispatched` / `markDispatchedBulk` are now guarded on `status = 'pending'` so a chunk in flight during that skip cannot move a `skipped` contact back to `dispatched` and double-decrement. **Reservation mappings land before any cancel can see a batch**: core's cancel settles the calls as non-billable at once and the settlement finds its hold by resource id, so `ReservationBatch.mappingsPersisted()` is awaited by the direct path before `appendBatchId`, by `dispatchChunkedBatch` before it returns or throws, by the scheduler per chunk, and by the executor before its post-append cancel (which now runs last, after the contacts are marked). One window remains on the queued path: the executor appends the id before `matchAndSettle` (it needs `isNewBatch` to know whether to match or release), so a `/cancel` landing in the few ms between can still beat the mapping. **A chunked dispatch that throws keeps what it sent**: `dispatchChunkedBatch` attaches its partial result to the rethrown error (`contact-lists/partial-dispatch.ts`, a separate module because route suites mock `chunked-dispatch.js` wholesale) and `failChunkedDispatchJob` records those batches on the row before the `failed`/`partially_failed` write, cancelling them in core if a Stop had won. Still not covered: a **per-call AI-voice** call already accepted by core has no batch id, so nothing master sends can cancel it — the stop check only prevents the *next* dial — and cancelling the tracking job does not cancel the **schedule**, so contacts from other batches that fail retryably can still be picked up by the retry pass; cancel the schedule to stop that.

**Legacy rows are NOT backfilled** and cannot be: a job already written `completed` with
`completion_tracking_expected = false` cannot be told apart from one that never had callbacks
configured (migration 049's note). `SETTLING_JOB_SQL` and cusui's "Finishing up" stay as the
legacy-only fallback; new rows never reach that branch. `STOP_REMAINING_ELIGIBLE` also stays
terminal-only — `/cancel` now covers the whole live window, which is the real fix.

### Per-Tenant Lane Scheduler (`src/queue/lane-scheduler.ts`)

The unit of scheduling isolation is a **lane** = `(tenant_id, dispatch_type)`. Pacing and concurrency attach to the lane, so a tenant's WhatsApp backlog cannot delay that tenant's calls, and no tenant's backlog can delay another tenant's anything.

**Why it replaced the SQS consumer.** The consumer received exactly one message per poll (`receiveSqsMessages(1, 5)`) and then slept `batchDelay[dispatch_type]` on a single shared `pollTimer` — a *global* pause, not a per-job one. A 334-batch `whatsapp_message` job at 100s/batch therefore blocked every other job, of every type, for every tenant, for ~9 hours; three static-call campaigns sat at zero batches dispatched and two were cancelled by the user. `SQS_BULK_DISPATCH_MAX_CONCURRENT_JOBS` never helped: `activeJobs` was only an admission gate, never real concurrency. The queue could not be fixed in place — SQS FIFO cannot be asked for "a message from any lane except the cooling ones", and deferring via `ChangeMessageVisibility` burns `ApproximateReceiveCount` toward `maxReceiveCount` (3) and DLQs healthy batches.

**How fairness works.** `bulkDispatchBatchRepository.claimBatches()` is one statement that claims at most one slot per lane, ordered by `dispatch_lanes.last_dispatched_at` **ascending** — the least-recently-served lane wins whenever the global cap binds, so enqueue order no longer decides who gets served. Capacity is applied in two stages, per-lane then per-tenant **over the survivors**; ranking the tenant over all pending rows would let one deep-backlog lane consume the tenant's budget for its other lanes (a bug the integration tests caught).

**Race safety, three layers:** (1) the claim UPDATE re-checks `status='pending'` under the row lock, so two instances cannot both claim a row — the loser updates zero rows; (2) the lane cooldown is reserved **at claim time inside the same transaction**, not after dispatch completes, so an instance polling a millisecond later sees the lane cooling; (3) `locked_until` leases the row and `reclaimExpired()` returns it to `pending` if an instance dies mid-dispatch — this is the visibility timeout. Multi-instance safe by construction.

**Two independent delays:** the per-**lane** cooldown (`dispatch_lanes.next_eligible_at`) paces steady-state throughput; the per-**batch** `available_at` implements exponential retry backoff. A batch in backoff is excluded rather than reordered, so its successors are neither overtaken by it nor blocked behind it.

**Bounded failure, in the claim itself.** `attempts < maxAttempts` is a filter on `claimBatches`, not only a check on the dispatch result. A batch whose dispatch throws (or whose instance is killed) never reaches the result path, so without it the row would loop claim → crash → lease expiry → reclaim forever, holding its lane's only slot — head-of-line blocking recreated *inside* a lane. The sweep's `failExhaustedBatches` then retires such rows and settles their job counters (`settleAbandonedBatch`), so the job can finalize instead of sitting in `processing` forever. Every terminal transition is **fenced on `locked_by`**: a dispatch that overran its lease cannot overwrite the state of whoever re-claimed the row, which would otherwise strand the second attempt's credit reservations as `pending` (invisible to the retention purge).

**Claim cost is O(lanes x capacity), not O(pending).** Measured at 200k pending across 200 lanes: ~7ms. The naive shape (rank every pending row, discard 99%) was ~1008ms with a 16MB disk sort, re-run every second. A loose index scan enumerates lanes without reading their rows, and a `LATERAL` pushes each lane's `LIMIT` into an index scan. `idx_bulk_dispatch_batches_claim`'s column order `(tenant_id, dispatch_type, created_at, batch_index)` must stay in lockstep with that query.

**Security improvement:** the SQS path serialised the *decrypted* `core_api_key` into every message body. The ledger deliberately does not persist it — `lane-scheduler.ts` resolves it per dispatch via `resolveCoreApiKey()` (already 5-min LRU cached), so a plaintext credential never comes to rest in a queryable table.

**Enablement is a transport switch, not a feature flag.** `SQS_BULK_DISPATCH_QUEUE_URL` still gates whether a large send is queued at all (every route's threshold check is unchanged), and the existing `SQS_BULK_DISPATCH_BATCH_DELAY_*` values are still the per-type pacing — they simply throttle one lane now. With `BULK_DISPATCH_LANE_SCHEDULER_ENABLED=true` the producer writes ledger rows; both transports run side by side. The flag gates **only the producer** — the scheduler always consumes the ledger, so flipping the flag back off never strands rows already written (gating both was a rollback trap: those jobs lost their only consumer and sat in `queued` forever). Retire the SQS queue only once it reports empty.

**Cross-transport isolation.** Both transports share one `BatchExecutor` so the `bulk_dispatch_active_jobs` gauge stays truthful, but the SQS consumer's admission gate counts **only SQS-origin jobs** (`activeJobCountFor('sqs')`). Counting the shared total meant five concurrent ledger jobs — an ordinary steady state — permanently closing the consumer's door; it defers without deleting, so `ApproximateReceiveCount` climbs to `maxReceiveCount` and SQS dead-letters the very backlog the dual-transport window exists to drain.

**Per-tenant overrides** live in `dispatch_lanes` (`batch_delay_seconds`, `max_concurrent_batches`, `paused` — each NULL/false meaning "inherit the env default") and are editable at runtime through `/super-admin/dispatch-lanes/*`, so a noisy tenant can be throttled or paused without a deploy. Note `paused` halts a lane **without** cancelling its job or losing queued batches.

**Metrics:** `bulk_dispatch_lane_queue_depth{tenant_id,dispatch_type}` is the "who is waiting behind whom" series that was unanswerable during the incident, plus `bulk_dispatch_lane_claimed_total`, `bulk_dispatch_lane_in_flight`, `bulk_dispatch_lane_reclaimed_total`.

**Capped broadcasts** (`max_concurrency`) are fed just in time — at most K = 2 batches outstanding per job, enforced inside the claim's `lane_picks` LATERAL; see *Per-broadcast "Simultaneous calls" cap* below.

**Key files:**
- `sqs.client.ts` — AWS SQS client initialization (lazy singleton, same pattern as EventBridge client)
- `bulk-dispatch.types.ts` — Shared types: SQS message shape, dispatch type enum, completion mode, core API paths
- `bulk-dispatch.producer.ts` — Creates `bulk_dispatch_jobs` DB record + sends per-batch SQS messages. Called by proxy routes and scheduler when above threshold.
- `bulk-dispatch.consumer.ts` — Reactive in-process consumer. Wakes on: producer signal, batch completion + delay, AI voice webhook. No polling loop — uses `EventEmitter` + `setTimeout` + SQS long polling.

**Queue:** Single SQS FIFO queue (`magick-bulk-dispatch-{stage}.fifo`). `MessageGroupId` = `job_id` ensures per-job ordering while allowing cross-job parallelism. DLQ after 3 failed receives.

**Consumer behaviors:**
- Parallel across jobs (capped by `SQS_BULK_DISPATCH_MAX_CONCURRENT_JOBS`, default 5), sequential within each job
- Batch types (static/IVR/WhatsApp/Telegram): dispatch ack mode — POST phones array to core, wait for HTTP 2xx, then per-type delay. `telegram_message` is a supported dispatch type alongside `whatsapp_message`.
- AI voice calls: webhook wait mode — POST per phone, wait for `call_completed` webhooks (timeout configurable)
- Cancellation: consumer checks job status before each batch; if cancelled, deletes message and skips
- Job finalization: after last batch, sets status to `completed`/`partially_failed`/`failed`

**DB:** Migration `017_bulk_dispatch_jobs.sql` — `bulk_dispatch_jobs` table with batch counters, status tracking, and source/schedule linkage.

**Config:** Optional `sqsBulkDispatch` block, feature-enabled by `SQS_BULK_DISPATCH_QUEUE_URL`. Per-type batch sizes and delays. See env vars section.

**API:**
- `GET /bulk-dispatch-jobs` — paginated list. **`status` is multi-value** (single `?status=failed`, comma-separated `?status=failed,partially_failed`, or repeated params — all normalize to a de-duped array → SQL `status = ANY()`); also filterable by `dispatch_type`, `source`, `name`, date range, `contact_list_id`. **Server-side sorting** via `sort_by` (whitelist: `created_at`, `name`, `total_contacts`, `status`, `started_at`, `completed_at`) + `sort_order` (`asc`/`desc`, default `created_at DESC, id DESC`), injection-safe through the shared `buildOrderByClause` (`src/utils/sort.ts`, mirrors core). Invalid params return 400 (`safeParse`). Every ordering it returns ends in `id` — see *Total ordering* under Key Patterns.

  **Cost shape (P8).** The SELECT enumerates columns instead of `SELECT *`, specifically to leave `dispatch_payload` — the whole-campaign config snapshot, `phone_variables` and all, megabytes on a big campaign — out of a response that never renders it; retry reads it through `findById`. That is a **wire-bytes** win (~12kB → ~4kB per 20-row page synthetic), not a DB-time one: measured, the two page queries differ by ~0.01ms. `BULK_JOB_LIST_COLUMNS` + a type-level exhaustiveness check keep the SELECT and `BulkDispatchJobListRecord` in lockstep.

  The `total` stays a **separate `COUNT`**, deliberately. Folding it in as `COUNT(*) OVER()` looks free and is not: a whole-partition window aggregate must materialise every matching row before `LIMIT` can emit its first, so the page scan stops terminating early — measured at 5k rows/account, `actual rows=20`/24 buffers became `actual rows=5000`/5,128 buffers — and the standalone `COUNT` can take an index-only scan the window form never can. The folded form only wins when a non-index-covered filter (e.g. `status`) is present, which is not the default listing. Don't re-fold these without re-measuring the **unfiltered** default sort.

  **Index coverage vs the sort whitelist (P11).** `idx_bulk_dispatch_jobs_tenant` is `(tenant_id, account_id, created_at DESC)`, so only the *default* sort is index-ordered; the other five whitelist columns each read the account's whole filtered set and top-N heapsort it. Measured on a seeded 200k-row table: `created_at` **0.21ms**, every alternate **12–14ms** at 4k rows/account and **24–27ms** at 50k, and **0.08ms** with a targeted `(tenant_id, account_id, <col>)` index. No index was added, deliberately: three of the five sort columns (`status`, `started_at`, `completed_at`) are **mutated after insert** by `updateStatus`/counter/webhook paths, so indexing them defeats HOT updates and trades list latency for index bloat on a table that takes many UPDATEs per campaign. `name` and `total_contacts` are immutable and would be the cheap ones if a sort ever proves popular. **Revisit trigger:** if the p95 per-account row count passes ~50k, or telemetry shows one alternate sort dominating — `SELECT account_id, count(*) FROM bulk_dispatch_jobs GROUP BY 1 ORDER BY 2 DESC LIMIT 20;` answers the first half.
- `GET /bulk-dispatch-jobs/summary` — account-wide KPI aggregate for the "pulse bar". One SQL pass over `bulk_dispatch_jobs` returns `total_jobs`, `total_contacts`, `live_jobs`, `contacts_in_flight`, `needs_attention`, and a complete per-status `by_status` histogram; honors every list filter **except** `status` (the histogram already breaks results down per status), pagination, and sort. Enriched best-effort with `contacts_in_progress` — the live "on a call now" count summed from core's per-batch status-summary over live jobs (capped at 100 live jobs); `0` when there are no live batches, `null` when core is unreachable (so the UI shows "—" rather than a wrong 0). Truthful over the full filtered account, replacing the page-derived client approximation.
- `GET /bulk-dispatch-jobs/:id` — detail with `progress_pct`, `status_summary`, `status_summary_stopped` and `records_updated_at` (one grouped core read; see below)
- `GET /bulk-dispatch-jobs/:id/analytics` — job-level aggregate analytics; `ai_voice_call` jobs proxy all `dispatched_batch_ids` to core's `POST /calls/batch-analytics` in one call (zeroed shape when nothing dispatched; core leaves deliberately stopped calls out of every figure and reports them as `totals.stopped_before_connect`). `ivr_call` / `static_call` jobs read core's grouped status summary and do the same from its `stopped_by_batch` (`liveCountsExcludingStopped`); if core cannot say they fall back to the cached `call_status_counts` with `stopped_before_connect: null` (unknown, never 0), and a job with nothing dispatched answers `0` without a core call — unless it holds cached counts without batch ids (rows from before `dispatched_batch_ids` was tracked), which answers `null`: calls existed that core cannot be asked about. Message types return the generic subset summed from `call_status_counts` without calling core, with no stopped key (nothing stops a message)

The list's status-summary fan-out is now **one core request per dispatch type per page**, not one per job. Core's status-summary surfaces take an opt-in `group_by=batch_id` (POST body `{ batch_ids, group_by: "batch_id" }` → `{ by_batch: { "<batch_id>": { "<status>": count } } }`) and master partitions locally — see `src/dispatch/core-status-summary.ts`, which is the single place that contract is written down. **A batch id absent from `by_batch` means "no rows yet", never an error**, and a body with no `by_batch` envelope at all (an older core, ignoring `group_by`) is read as *unknown* rather than as zero — the reconcile sweeper depends on that distinction to avoid closing live campaigns. Every one of core's summary surfaces (`/calls`, `/messaging/messages`, `/static-calls`, `/ivr-calls`, grouped and ungrouped) scopes on tenant **and** account — static/IVR were tenant-only until core closed that cross-account leak — so a summary call must carry the account the rows were dispatched under; every caller passes the job's own account, and a mismatch reads as "no rows yet" rather than erroring.

**`status_summary_stopped` (list rows and detail) is the part of `status_summary` that was deliberately stopped before connecting** (Stop, a user cancel, a credit abort, the capped ceiling), per status. Core's grouped call summaries carry it as the sibling `stopped_by_batch`, from the same pass and the same per-table rule super-admin usage excludes, and `stoppedSummaryForBatches` (`src/dispatch/core-status-summary.ts`) folds it per job from the SAME grouped read and cache entry as `status_summary`. It is a SUBSET, not extra rows — a stopped AI call is `failed` + a stop code, so it stays in `status_summary.failed` and appears here too — which is the only way a client can tell it from a real failure; cusui's broadcast page uses it to keep stops out of the connect rate. `{}` is a measured zero; `null` is unknown: no read, an older core, a messaging job (that surface has no stop concept), an entry cached before the field existed, or ANY batch that has rows but no stopped entry (a partial sum would understate the stops and read as a measured figure). A batch with no rows contributes nothing, as in `status_summary`.

**`records_updated_at` (list rows and detail) is the latest core ROW write across the job's batches, and it is the only honest "did anything change?" signal for a finished campaign.** `bulk_dispatch_jobs` has no `updated_at` column, and adding one would not help: the per-call changes a reader of the campaign's records cares about — a recording URL, a transcript, an outcome, post-call analysis, a delivery receipt — are written to core's rows and never touch this table. So the value is derived, not stored: core's grouped status-summary answer carries a sibling `last_updated_by_batch` (core's `docs/architecture/api-routes.md`), and `recordsUpdatedAtForBatches` (`src/dispatch/core-status-summary.ts`) folds it per job from the SAME grouped read that produces `status_summary` — no extra core round trip, and the two are cached together in one entry under the same generation fence and epoch, so they cannot describe different reads. That is why the **detail** now reads the grouped surface too (flattened for `status_summary`, which is exactly what core's ungrouped body is), and why the grouped cache namespace is `-v2` (the cached value's shape changed; the epoch key is deliberately unversioned so a command path on either release invalidates both). A cached stamp is never NEWER than the truth, so what a consumer stamps before pulling cannot claim a change it did not see — but on the COMPARING read it can be OLDER: a refresh served from the cache can match a stamp a write has already moved, and skip that write until the entry expires. Staleness is therefore bounded by `STATUS_SUMMARY_CACHE_TTL_SECONDS` (8 s), not zero. **`null` means unknown and must never be read as unchanged**: the job has no batches, `include_status_summary=false`, the type has no grouped surface, core's read failed or predates the key (an older core — every grouped surface, `/messaging/messages` included, now serves it), any one batch is missing from the map, or core reported a batch `null` (written within its 120 s settle window). A job-level max over only the batches that answered would be a confident claim about a batch nobody looked at. A row deletion (core retention) does not move a max — consumers that care pair the stamp with `status_summary`, whose counts it does move.

`STATUS_SUMMARY_FANOUT_LIMIT = 8` (via `mapWithConcurrency` in `src/utils/concurrency.ts`) survives as a bound on the shape rather than a throttle: it used to bind on the PAGE SIZE (a page holds up to 100 jobs and `include_status_summary` defaults **on**, so the uncapped per-job form put 100 concurrent requests on core per list load, per user, per poll), and now binds on the number of dispatch types (at most six). With the N+1 gone the summary is cheap enough to return on every poll, which is what makes cusui's live/settling display reliable — `include_status_summary` stays for compatibility but no longer needs rationing.

**Per-status summary (`STATUS_SUMMARY_PATH`)** covers `static_call`/`ivr_call`/`ai_voice_call` **and** the three message types (`whatsapp_message`/`telegram_message`/`email_message` → core `POST /messaging/messages/status-summary`). List and detail enrich `status_summary` the same way as call jobs (best-effort: a miss leaves it `null` rather than failing the request). **The pulse-bar live count does not query the messaging path** — `contacts_in_progress` / `contacts_dialing` are call-slot occupancy (`in_progress` / initiating+ringing), and a 404 from an unshipped core aggregate would poison the whole account figure. Message-type retry has its own arm — see *Retrying a message campaign* below.
- `POST /bulk-dispatch-jobs/analytics` — merged aggregate across up to 50 deduped `job_ids` (ai_voice_call only; all batch ids combined into a single core call)
- `POST /bulk-dispatch-jobs/:id/cancel` — cancel queued/processing job
- `POST /bulk-dispatch-jobs/:id/retry` — re-dial a finished voice job's selected non-connected outcomes. It pages core's `…/search` (`limit=100`, `sort_by=created_at&sort_order=asc`) per status, and two guards stand between those pages and a dial, because core orders by `created_at` alone until its `id` tiebreak deploys and tied rows overlap and skip across OFFSET pages: rows are **deduplicated by their own id** (`call_id` on AI, `id` on static/IVR) across pages and statuses — never by phone, since two failed calls to one number exist only because the original list carried it twice, and the retry mirrors it — and each status must yield **at least as many distinct rows as the largest `total`** any of its pages reported (terminal statuses only grow, so the largest is the latest truth). When the page that reaches that total is **full**, one trailing probe page is read before judging: rows are oldest-first, so a call that settled into a retryable status mid-walk sorts into a range already consumed and shows only as a larger `total` on the NEXT page — without the probe a full last page ended the walk and the retry went out one number short with a 200. A probe that reports a larger total over a page start it has not reached is walked like any other page; a probe that began at or past the largest total is the last page read. Termination never rests on `total` alone, since core can report any total it likes: every page that lets the walk continue must add an id that status had not seen, and a page made entirely of re-served rows ends it (the count check then answers `short_list`), so pages are bounded by the distinct rows core actually returns — even against a core that ignores `offset` and grows its total every page. It is still a paged read, not a snapshot, and the check compares counts rather than identities — `collectRetryRows`' docstring states exactly what is and is not guaranteed. A page whose `total` is not a non-negative integer is a refusal too — an absent total used to read as 0, stop paging after page 1 and "pass" an unchecked read. So is any candidate without a non-empty string id (`missing_id` — the id is the dedupe key and what makes "a page of re-served rows" detectable, and every core surface sends one) or without a non-blank string phone (`recipient_phone` on AI, `phone` on static/IVR; `missing_phone`): such a row has an id, so it counts toward the total, but cannot be enqueued — dropping it let two distinct ids, one phone-less, pass `total: 2` and retry one number. A shortfall dispatches nothing and answers a reviewed, unmasked **502** (`RETRY_LIST_INCOMPLETE_MESSAGE`) whose body adds `statusCode`, `requestId` and a closed `reason` (`core_error` | `missing_total` | `empty_page` | `short_list` | `missing_phone` | `missing_id`), with `x-request-id` re-set by the route — `errorMaskHook` returns a reviewed body untouched, so unlike a masked 5xx its body carried no `requestId` to quote. Each refusal writes a warn with `event: 'bulk_dispatch_retry_refused'` + that request id, and counts `bulk_dispatch_retry_refused_total{dispatch_type,reason}` through the `setRetryRefusalObserver` seam (`src/dispatch/retry-refusal.ts`, wired in `index.ts` — suites that load these routes stub metrics with explicit factories). Both label sets are the `as const` tuples `RETRY_REFUSAL_DISPATCH_TYPES`/`RETRY_REFUSAL_REASONS` there, which `trackBulkDispatchRetryRefused` takes its parameter types from via `import type` (erased, so metrics.ts gains no runtime dependency) — one definition, so the counter's labels cannot drift from the route's in either direction. A sustained `short_list`/`empty_page` rate means core's ordering is still not total. Consequence: against a core without the tiebreak, a status with enough tied rows can refuse on every attempt — **deploy core's fix first**.

  **Retrying a message campaign** (ClickUp `86d33391z`). WhatsApp / Telegram / Email jobs take a separate arm, `retryMessageJob`, sharing only the candidate read (`collectRetryRows`, every completeness guard above included) and the retry lineage. It answered `409 "No failed calls to retry"` for every message campaign for as long as it existed — it read core's answer through the call chain (`calls ?? sessions`) while `/messaging/messages/search` answers `messages`, and email rows key the recipient as `to_email` — and was then blocked outright. Each type now names its own surface (`RETRY_LIST_SURFACE`: path, rows key, recipient field) so no surface can read another's shape. Selectable outcomes: `failed` everywhere, plus `undelivered` (WhatsApp) and `bounced` (email); never `complained` (re-sending to someone who marked it spam is exactly wrong) and never `sent` (a provider that returns no receipt leaves a delivered message `sent` forever). The rest differs from voice: permission is `proxy.messaging.send`; `caller_ids` is a 400; the snapshot's connection must still exist (404 → 409) and be `active` — and, because core refuses a send on them even while `active`, an email connection's domain must be `verified` and a WhatsApp Personal instance `authorized` (each a 409 rather than a 200 whose every batch then fails) — and the `messaging` capability **and** the provider's (`PROVIDER_CAPABILITY`, now in the import-free `capability-keys.ts`) must be on — the retry is a new send, so it is gated as one; a campaign that targeted WhatsApp groups is refused, even one that also went to individual numbers (a group is not sliceable — the queued retry would send its message once per batch — and splitting off "the phone part" would re-decide what the operator sent); "still finishing" means a `queued`/`sending` message. An email `bounced` lands asynchronously after `sent`, so a retry started soon after a campaign finished will not include bounces that have not arrived yet; retrying again later picks them up. **Email per-recipient variables come from master, never core**: the map recorded beside the job (`bulk_dispatch_job_recipient_variables`, below; `{}` is a real "none", an unreadable value is "unknown"), else — for a job written before that existed — the slices its ledger rows carry (`findRecipientVariableSlices`), else the retry is **refused (409)** rather than sent with every personalised field blank, which is the silent loss the ticket was about. Older direct-path and SQS-transport email jobs land there. **The map is keyed by address, so a list that names one address twice with DIFFERENT details cannot be retried for that address**: the in-request contact-list path builds each 100-row chunk's variables from that chunk's own rows, so the occurrences may have gone out with different values, and nothing on core's row says which occurrence a failed message was. `conflictingEmailRecipients` records those addresses beside the map (`ambiguous_recipients`), and a retry naming any of them is refused whole (409, "…had the same email address more than once with different details…"), never partially — a retry that skipped some failed addresses would read as complete. Identical duplicates are not ambiguous; addresses compare exactly, as the map keys and core's `to_email` do. Only that path records any: the queued contact-list and direct paths send every occurrence the one map, so a retry from it repeats what was sent. Merging legacy ledger slices applies the same rule (`mergeRecipientVariableSlices`), and an unreadable `ambiguous_recipients` is "unknown", like an unreadable map. Only the retried recipients' entries are handed to the producer, which slices them per batch and records them for the child job, so a retry can itself be retried. Shared `variables`, template, text and media ride on the snapshot unchanged. `bulk_dispatch_retry_refused_total` gained the three message `dispatch_type` values.

### Per-broadcast "Simultaneous calls" cap (`src/dispatch/broadcast-concurrency.ts`, ClickUp 14ygtkj9pgr)

`max_concurrency` (int 1..1000 | null) on `POST /proxy/calls/bulk`, `/proxy/ivr-calls`, `/proxy/static-calls`, in `call_payload` for schedules + recurring schedules, and on `POST /bulk-dispatch-jobs/:id/retry`. Absent/null = no cap = today's behaviour, **with no core call at all** (route suites pin the exact `proxyToCore` sequence). **Core enforces the cap**; master validates, persists and threads it. Design: root `docs/broadcast-concurrency-design.md`.

- **Validation** is an orchestrator-owned `runDispatch` stage (`applyConcurrencyStage`) that runs right AFTER `prepareBranch`, because the ceiling is the allocation for the RESOLVED provider (`GET /api/v1/account-settings/concurrency`: `provider_breakdown` → that provider's row, missing = 0 → refused; `legacy_total` → the total). A `provider_breakdown` account whose broadcast resolved NO carrier is refused (`requireProvider`, the schedule-create rule) rather than checked against the account total, which can be far above the one carrier the calls dial on. The passthrough schemas stay "document, don't reject". Refusals are `400 { error: 'Validation failed', message, details: { max_concurrency } }` — `details` is what makes them survive `errorMaskHook` even after a recorded core 4xx on the same request. Customer-facing copy never names a carrier slug ("…up to 10 for the selected phone numbers"; logs keep the provider). Both core reads pass `recordCoreErrors: false` and are cached 60s per tenant/account; an unreadable flag/allocation is a 503 ("Could not verify the simultaneous calls limit right now. Try again shortly."), never a guess — marked `reviewed` and sent through `sendCapRefusal`, which sets `preserveReviewedUpstreamError` so the mask neither rewrites it to "contact support" nor logs it as a masked internal error (the cause is logged at warn where it happens). `invalidate*` also defeats a read already in flight (a generation counter checked before the cache write, and the in-flight entry dropped), so a super-admin allocation/flag change is never re-cached stale by a read that left before it.
- **Validation order** (`validateMaxConcurrency`): deployment preconditions → value shape (integer 1..1000, refused "from 1 to 1000" with NO core call) → core flag → allocation → the value against the provider's ceiling. Schedule create passes `requireProvider`: on a `provider_breakdown` account a payload whose caller ID does not resolve is refused rather than checked against the account total. It also passes its tenant-key and caller-ID lookups LAZILY (`resolveDeps`, run only after the preconditions, range and flag checks), so `0` or a feature-unavailable account gets its details-shaped 400 without any fallible lookup — never a 5xx. The allocation and flag reads are cached 60 s with a per-key in-flight guard (concurrent cold reads share one core call); master's own super-admin relays bust this replica's copy on a successful write (`PUT …/accounts/:id/concurrency`, `…/retry-sync`, any `broadcast_concurrency` override write) — other replicas converge within the TTL.
- **Feature gate** = core flag `broadcast_concurrency` (read over S2S `GET /internal/feature-flags/resolve`, NOT the client-exposed map) **AND** deployment preconditions (`sqsBulkDispatch` configured AND `bulkDispatchLanes.enabled` AND `BATCH_COMPLETION_WEBHOOK_URL` set — without the webhook nothing releases a capped job's next wave but the 5-minute sweep, and the job would finalize at dispatch ack while core still parks its waves). Either off + a cap sent → 400 "Simultaneous calls isn't available on this account." `GET /proxy/calls/concurrency-limits` (`proxy.calls.create`) serves `{ enabled, mode, account_total, providers }` — read-only, no version (the D10 exception; see `proxy-agency-campaigns.routes.ts`). The gate is resolved FIRST: closed ⇒ `200 { enabled: false, mode: 'legacy_total', account_total: 0, providers: {} }` (`DISABLED_CONCURRENCY_LIMITS`, same shape, neutral values) with NO allocation read and NO tenant core-key lookup (the flag is read over S2S, so a flag-off tenant without a core key still gets `enabled: false`, not a masked 500); an unreadable flag, or an unreadable allocation with the gate open, is a 502.
- **Rollout / rollback rule.** Enable the flag only once every core AND master replica runs this version. Turning the flag OFF stops NEW capped broadcasts (core refuses a new group; master refuses the cap, fails a capped scheduled fire, and 400s an inherited-cap retry) while RUNNING ones finish under their cap — core keeps admitting batches of a group that already exists. **But a capped job accepted while the flag was on whose FIRST batch reaches core after it is turned off has no core group row yet, so core refuses it** (a queued job, or a scheduled fire that already passed master's check): turning the flag off stops new capped broadcasts; ones already feeding finish under their cap; ones accepted but not yet started will fail — stop them, or let them start, before turning it off. Before rolling master back past this version: flag off, drain or stop capped broadcasts, then wait 1500s (a renewed credit hold outlives the old code's lookback — see *Credit holds* below).
- **Persisted** on `bulk_dispatch_jobs.max_concurrency` (migration 075, CHECK 1..1000 added `NOT VALID` — catalog-only, still enforced on every write; every pre-existing row is NULL by construction. Mark it validated out of band, non-blocking, whenever convenient: `ALTER TABLE bulk_dispatch_jobs VALIDATE CONSTRAINT bulk_dispatch_jobs_max_concurrency_range;` — never in a migration of the same deploy, where it would scan under the ACCESS EXCLUSIVE lock, see 065) at every create site, and in the `dispatch_payload` snapshot. **The column is the authority** — the super-admin in-flight change (`PATCH /super-admin/tenants/:tenantId/bulk-dispatch-jobs/:jobId/concurrency`, core PUT first, column second) rewrites only it. It sends core `requested_by: <admin email>` (core's audit actor); the body is built by `concurrencyGroupUpdateBody` and pinned against core's schema by the contract test. If the column write fails after core accepted, the route logs `{ jobId, requested, coreUpdated }`, still audits (`column_updated: false`) and answers an unmasked 500 saying core already enforces the new cap.
- **PATCH runbook (super-admin cap change).** One change per job at a time: the whole read → core PUT → column + re-chunk (one transaction, `applyCapChange`) → re-sync sequence runs under `bulkDispatchJobRepository.withCapChangeLock` (a session `pg_try_advisory_lock(764_211, hashtext(jobId))` on a dedicated connection; never queues), so a concurrent PATCH is `409 "Another change … is in progress. Try again in a moment."` and core and the column always end on the same value. Answers, all reviewed and unmasked for the console: `200 { job, core_updated, concurrency, ledger_rechunked[, core_resync_failed] }`; `400` (range / above the allocation — the feature gate is skipped); `404` (job not in that tenant); `409` (uncapped or terminal job, row changed underneath, or a concurrent change); `502 "Could not update the cap in the voice service, so the cap was not changed."` (core refused/unreachable — nothing changed; retry); `503 "Could not load this tenant's voice service credentials…"` (`resolveCoreApiKey` failed — nothing changed) or the validation 503 (allocation unreadable — retry); `500` with `core_updated` (column write + re-chunk failed, both rolled back — retry to record it; if `core_updated: true` core already runs the new cap). `core_resync_failed: true` on a 200 ⇒ core may still run the old cap: retry the PATCH. `concurrency: null` on a 200 is normal when core had no group yet or could not read Redis occupancy (`in_use: null`).
- **Threaded** as `concurrency_group: { id: <job id>, max_concurrent }` on EVERY core request of a capped job via `withConcurrencyGroup` (which also strips `max_concurrency` — core would drop it silently — and any client-supplied group): `batch-executor.dispatchBatchToCore` (both transports, reads the job ROW), `runDispatch` direct + chunk bodies (injected once, not per spec), and the scheduler's chunk loop. A capped scheduled AI send is forced onto `/calls/bulk` (single `/calls` has no group field).
- **Credit holds** of a capped job's batches use `CAPPED_CREDIT_HOLD_TTL_SECONDS` (= `MAX_CREDIT_HOLD_TTL_SECONDS`, 1500) through the optional TTL on `ReservationBatch` → `reserveCreditsBatch` → `reserveMany`; uncapped paths keep their exact 5-argument calls and the configured default. **And they are RENEWED while their batch is outstanding at core**, because no fixed TTL bounds how long a capped call waits in core's park (IVR's 3600s cap, a queued-dial carrier's pickup window, AI transfers, an account kept busy by its OTHER traffic parks rows on account capacity, a super-admin lowering the cap). The batch executor leases each capped batch's holds (`credit_hold_leases`, migration 078: `reservation_id`, `tenant_id`, `batch_id`, `held_until`, no FKs) right after the reserve; `queue/capped-hold-renewer.ts`, on every lane-scheduler sweep BEFORE the core-facing completion sweep, renews every lease that is due (renewed > 5 min ago, `held_until > now()`, batch `dispatching`/`dispatched` with no `call_completed_at`, younger than the 48h capped ceiling) — **Postgres first** (`held_until = now() + 1500 + CREDIT_HOLD_LEASE_MARGIN_SECONDS`), **then Redis** (`creditExtendHolds` Lua: `PEXPIREAT` only a key that still EXISTS, never an amount, to the ABSOLUTE instant `held_until − margin` that `renewDue` returns — a relative TTL computed before the command would be stretched past the lease by a delayed delivery, since ioredis has no command timeout; a key whose TTL is already beyond that cap is pulled IN to it, because Redis expiry ≤ lease − margin outranks "never shorten"; a cap already past expires the key, reported gone). Pages of 500 run until nothing is due or 5 s (`CAPPED_HOLD_RENEW_BUDGET_MS`) is used. Only Postgres↔Redis clock skew remains, absorbed by the 60 s margin. Why a lease and not just a longer TTL: `sqlOpenRedisHolds` counts a Redis hold only while its reservation row is younger than the 1500s lookback, so a renewed hold would read as spendable to `getBalance`'s fallback, every Postgres write gate and the reconcile — a double spend. The reconstruction now adds a second, disjoint term: reservation rows OLDER than the lookback whose lease is live (probe of `idx_credit_hold_leases_tenant_live`, zero rows for every tenant without a capped broadcast). Invariants: no double charge or double release (only TTLs move; a settled/released hold is never revived and is excluded by the anti-join whatever its lease says); no double spend (Redis expiry always before lease expiry — the conservative direction on every failure, including a Redis error after the Postgres write, counted `redis_unavailable`); bounded (renewal stops when core reports the batch complete, at the 48h ceiling, or when Redis reports the hold gone — its lease is then deleted; lapsed leases are purged after 1h); uncapped holds never get a lease. Why not the ledger path (`reserveBatchWithLedger`, no TTL): it is the Redis-unavailable fallback, debits Postgres without touching the cached spendable balance (every Redis reservation would then spend the same credits again unless all three money paths learned to sync the cache), gates on the non-authoritative ledger reconstruction while Redis is live, and a DB hold whose settlement webhook is lost is stranded FOREVER (a lost Redis hold at least expires and a reconcile recovers it). Residual: a capped batch dispatched with NO core batch id is born call-completed (nothing could ever release it), so its holds are never renewed — they keep the fixed 1500s TTL, as before. The sweep cadence (`BULK_DISPATCH_LANE_SWEEP_INTERVAL_MS`, default 60s) is capped at 5 minutes by the schema (`MAX_BULK_DISPATCH_LANE_SWEEP_INTERVAL_MS`): a lease is due 300 s after its last renewal, so at the slowest sweep it is renewed by minute 10 of its hold's 25, with three sweeps of slack. Metric: `bulk_dispatch_capped_hold_renewals_total{result=renewed|renewed_late|gone|redis_unavailable|error}` — exclusive results; `renewed_late` = renewed with under 10 minutes left on the hold (sweeps missed, or the budget too small for the lease count), the early warning before `gone` on outstanding batches.
- Schedules validate at create and **clamp + log at execute** (`clampStoredMaxConcurrency` — still fewer calls, never more); an inherited retry cap is clamped the same way, an explicit one validated (`requireProvider`, like a fresh broadcast). **A stored cap the feature can no longer honour is REFUSED, never dropped**: with the flag off or the preconditions gone a scheduled/recurring fire FAILS through `failSchedule` (`error_code: CONCURRENCY_LIMIT_UNAVAILABLE`, pending contacts skipped, warn log; a recurring schedule keeps its future fires and each fails the same way until the cap is removed), and a retry that inherits a cap (no `max_concurrency` key) answers `400 { error: 'Validation failed', message, details: { max_concurrency } }` — "The original broadcast was limited to N simultaneous calls, but that setting isn't available on this account right now. Retry without a limit, or contact support." — where an explicit `max_concurrency: null` is the "retry without a limit" that succeeds. (An UNREADABLE flag keeps the stored cap: core still enforces it.) A cap never reaches a message job: a message retry takes its own arm, which ignores `max_concurrency` and strips any from the snapshot, and a non-voice type is ignored and never snapshotted. Job list + detail return `max_concurrency`; detail adds best-effort `concurrency: { max_concurrent, in_use, parked } | null` from core `GET /calls/concurrency-groups/:jobId`.
- **Just-in-time feeding** (migration 076). A capped job **always** goes through the producer + lane ledger, whatever its size (`mustQueueCapped` bypasses `SQS_BULK_DISPATCH_THRESHOLD` in both `runDispatch` branches and `executeSchedule`), so a capped broadcast of 3 answers the same `202 { job_id, status: 'queued', … }` as one of 30,000 and a credit shortfall surfaces at batch time (`abortJobForCredits`), not as a 402; the direct/chunk paths are untouched for uncapped jobs (and their group injection is now defence in depth only). Batches are `cappedBatchSize` = **min(cap, 100)** (core's per-request ceiling) — deliberately NOT min(cap, per-type default): with K batches of the cap at core, a smaller batch would silently lower the cap. The claim lets a capped job have at most **K = 2** batches *outstanding* (`status IN ('dispatching','dispatched') AND call_completed_at IS NULL`; for caps > 100 the count scales to keep ≤ 2 × cap recipients at core — `cappedMaxOutstandingBatches` / `cappedMaxOutstandingSql`, keep in lockstep). The filter sits **inside the `lane_picks` LATERAL `WHERE`** (via the `capped_jobs` / `capped_frontier` CTEs, which also cap how many of one job's rows a single claim may take), so a blocked job never eats a lane's picks; uncapped rows have no frontier entry and claim exactly as before. `hasPendingWork` / `nextEligibleAt` exclude K-blocked jobs so the scheduler idles instead of re-running the claim CTE. **K holds across replicas** because, while any capped job is live (an EXISTS probe of `idx_bulk_dispatch_jobs_capped_live`), every claim transaction first takes ONE global `pg_advisory_xact_lock(CAPPED_CLAIM_LOCK_NAMESPACE, CAPPED_CLAIM_LOCK_KEY)` (the budget is computed from the claim statement's snapshot, so without it two overlapping claims — or a backoff expiring / a lease reclaimed under an uncommitted claim — could each see room and exceed K); `rechunkPendingForCap` takes the same key. One key rather than one per capped job: every claim touches every live capped job anyway, so per-job keys bought no concurrency, cost one lock-table entry per job per claim, and needed an out-of-order second pass that could deadlock. With no capped job live no lock is taken; a job that goes live between the probe and the claim has had nothing claimed, so every claimer computes the same first-K frontier and the UPDATE's `status = 'pending'` re-check hands each row to one claim — still ≤ K. A capped job flips `queued` → `processing` on its first EXECUTED batch whatever its index (`markProcessingIfQueued`, guarded and idempotent — a re-chunk before start supersedes batch 0); uncapped jobs keep the batch-0 rule. A lane whose claimed rows are all capped does **not** reserve the per-type cooldown (`batch_delay_seconds`) — capped waves are paced by K and core's gate — but still records `last_dispatched_at` for fairness. Cost: a blocked job's pending rows are still stepped past by the lane index scan — measured ~0.5 ms per 1,000 of them per claim (20k-batch blocked job ≈ 10 ms), only while other work keeps the scheduler ticking.
- **Releasing the next wave.** `batch.completed` (`webhook-core.routes.ts`) runs its unchanged job bookkeeping first, then `bulkDispatchBatchRepository.markCallCompleted(jobId, coreBatchId, tenantId)` (idempotent, also on the duplicate path) and `wakeLaneScheduler()` (injected from `index.ts` as a route option). `markDispatched` makes a capped batch **born complete** when core returned no batch id (nothing could ever release it) or when the webhook already beat the ledger write (its `call_status_counts` entry exists). An all-rejected batch is `failed`, never outstanding. A webhook that lands before any ledger row (or job) carries its batch id gets ONE delayed retry (2 s, bounded, fire-and-forget); what it still misses is counted `missed` and left to the sweep. **Lost webhooks:** `queue/capped-completion-sweeper.ts`, run at the end of every lane-scheduler sweep, claims outstanding capped batches of `queued`/`processing` jobs overdue by `BULK_DISPATCH_CAPPED_COMPLETION_MIN_AGE_MS` (5 min) — `FOR UPDATE SKIP LOCKED` + a `call_completion_checked_at` stamp, so replicas take disjoint pages — asks core's grouped status summary once per job, and releases batches whose calls are all terminal, or which core has no rows for on TWO consecutive passes (`call_completion_absent_at`, migration 077 — core inserts a batch's rows synchronously in the dispatch request); never on a failed read, and an unanswered batch's stamp is cleared so the next pass asks again; bounded by `…_SWEEP_LIMIT` (50) and `…_TIMEOUT_MS`. All feeding state is in Postgres — a restarted or fresh scheduler resumes exactly; a crashed instance's leases are reclaimed and redelivered under the same `${job_id}-${batch_index}` idempotency key.
- **Reconciler backstop** skips a capped job past `maxAgeMs` while core still reports calls in flight (parked calls are in flight; logged once per job per hour) — up to `BULK_DISPATCH_RECONCILE_CAPPED_MAX_AGE_MS` (48 h), past which it force-finalizes with its own `error_message` and the `finalized_capped_ceiling` outcome label; it still fires when core says nothing usable, and the age anchor (`dispatched_at`) is already the LAST wave. **A second ceiling covers a capped job still FEEDING** (`queued`/`processing` — a batch core keeps reporting live holds the next wave back forever, so it never reaches `dispatched`): past the same 48h from `started_at`, the reconciler (`findCappedFeedingPastCeiling`) retires its pending ledger rows, cancels its core batches, folds core's outcomes and finalizes through `tryFinalizeFeeding` (fenced on the feeding statuses), logged at error, label `finalized_capped_feeding_ceiling`. The retire and the core cancel run BEFORE the fence and stand if it loses (idempotent; whoever won — a cancel, another replica, the last wave going out — wants the same end state). A wave mid-POST during the close is cancelled either by the reconciler (the fenced close RETURNS the row's batch ids, and any appended since the first cancel are cancelled) or by the executor (`cancelIfJobClosed`: its post-append status re-read now cancels its own batch when a CAPPED job is terminal, not only `cancelled`; uncapped jobs keep the cancel-only rule). **At both ceilings core is told to cancel** (`cancelCoreBatches`, `error_code: CAPPED_BROADCAST_CEILING`) BEFORE the job is reported done, and core's summary is re-read so the outcomes include the rows just cancelled — otherwise parked rows keep dialling under a job that reads Done. **Stop** needs nothing new: `/cancel` retires `pending` ledger rows (`cancelPendingForJob`) and the claim refuses terminal jobs, so held-back waves never go out; batches already at core are cancelled as before.
- **Super-admin cap change re-sizes the ledger:** after the core PUT, `bulkDispatchBatchRepository.applyCapChange` writes the column AND re-packs the job's never-claimed (`pending`, `attempts = 0`) batches to `min(newCap, 100)` in ONE transaction under the global capped-claim advisory lock (lock → pending rows `FOR UPDATE` → job row; nothing locked before the claim lock, never held across an HTTP call), BEFORE the post-404 re-sync PUT. Atomic because a claim budgets from the column but takes whatever rows exist: a claim between a separate column write and a separate re-chunk (on the 404 path that gap held the up-to-10 s re-sync) took old-sized rows under the new budget and marked them attempted, so the re-chunk skipped them for good (100 → 10 could park 200 holds). A claim during the core PUT takes old rows under the OLD budget — what the job was already allowed — and they count against the new budget afterwards. Re-pack rules — order kept, no phone twice in a batch, per-recipient data moved with its recipient, replaced rows `cancelled` (indexes stay taken), new rows on FRESH batch indexes (so no `${job_id}-${batch_index}` idempotency key is reused), `total_batches` adjusted. Rows attempted even once keep their size: they may have reached core under their key. Reported as `ledger_rechunked` (always present on a 200; zeros when nothing needed re-sizing).
- **Throughput expectation: K counts BATCHES, not calls.** A batch stops being outstanding only when its LAST call ends, so wave N+2 is not sent until every call of wave N has finished. Within the two outstanding waves core keeps the cap full (a slot freed in wave N is refilled from wave N+1, already parked in core), but a slow tail call in wave N holds the next wave back: expect the live count to dip below the cap at each wave boundary, most for small caps and long-tailed call durations.
- **The super-admin cap change re-syncs core after a 404.** Core keeps the first value it sees for a group, so if a first batch created the group (from the OLD column) between core's 404 and the column write, the old cap would stand forever; the route PUTs core once more after the column write + re-chunk and reports `core_updated` from that answer (`core_resync_failed: true` when it could not be confirmed — retry the PATCH).
- **`progress_pct` of a capped job counts WAVES HANDED TO CORE** (`batches_dispatched / total_batches`), not calls finished: a cap-5 broadcast of 1,000 shows 100 % only once its last wave is at core, and its calls then drain behind the cap (suggest noting this in `docs/bulk-campaign-lifecycle-design.md`).
- **Metrics:** `bulk_dispatch_capped_batch_completions_total{source=webhook|webhook_retry|missed|sweeper|sweeper_absent}` (a rising `sweeper` share = webhooks being lost), `bulk_dispatch_capped_completion_sweep_total{outcome}`, `bulk_dispatch_capped_hold_renewals_total{result}`, gauge `bulk_dispatch_capped_jobs_blocked`; `bulk_dispatch_reconcile_total` gains `finalized_capped_feeding_ceiling`.

### Recurring Schedules (`src/scheduling/recurring-schedule.service.ts`)

Recurring schedules automate calls/messages on a daily, weekly, or monthly cadence. A `recurring_schedules` table stores the recurrence template; each fire creates a child one-time `schedule` row (linked via `recurring_schedule_id` FK) that flows through the existing execution pipeline unchanged.

**Key files:**
- `recurring-schedule.service.ts` — Create, execute instance, cancel, pause, resume, update. On each EventBridge cron fire: re-fetches contacts from S3, **normalizes + de-duplicates** them, creates a one-time schedule instance, delegates to `schedulerService.executeSchedule()`. The re-normalization looks redundant beside the validator and is not: rows stored before `phoneNumberSchema` reached the recurring schemas still hold `+91 91243 29502` and copy it onto every instance, so **this is the repair path for legacy rows, and it repairs DISPATCH only — `recurring_schedules.phone_numbers` itself stays as stored until someone re-saves.** A failed contact insert rolls the instance back and deliberately does **not** advance `total_instances`: nothing fired, so counting it would misreport the schedule's history and burn the `#N` suffix the next real instance should carry. **The compensation boundary extends through `incrementInstanceCount`**, not merely through the contact insert, because an instance is only recoverable once it is EXECUTING: `findStuck` covers `executing`/`partially_failed` and nothing else, so a pool blip on that one parent-counter UPDATE left a fully-populated instance stranded `scheduled` — invisible to every sweep, carrying a `pending_count`, with the cron minting another next tick. One case the compensation cannot make clean, and it is the cheap direction: a counter that COMMITTED and then failed to report leaves it advanced with the instance deleted, so the next fire skips a `#N`. A gap in the numbering is cosmetic; the orphan is not. `update` normalizes + de-duplicates too — the rule held on one of the two write paths, so an edit could restore the duplicates creation had just removed, leaving the template permanently disagreeing with every instance it fires and `phone_numbers.length` (what cusui renders as the campaign's contact count) over-reporting for the life of the schedule.
- `cron-builder.ts` — Converts frequency/time/days into AWS EventBridge cron expressions. Timezone handled natively by EventBridge's `ScheduleExpressionTimezone`.
- `eventbridge.client.ts` — Extended with `createCronSchedule()`, `updateCronSchedule()`, `deleteCronSchedule()` for persistent cron schedules (no `ActionAfterCompletion: DELETE`).
- `recurring-schedule.repository.ts` — CRUD, list, status updates, instance count tracking.
- `recurring-schedule.validator.ts` — Zod schemas for create/update/list. `phone_numbers` shares ONE `phoneNumberSchema` with `schedule.validator.ts` (`src/api/validators/phone-e164.schema.ts`), and the sharing is the fix rather than tidiness: two validators holding one rule is exactly how they drifted — recurring took a bare `z.array(z.string())` while one-time coerced, so an identical number was stored two ways and core rejected one of them (`14ygtkj8u67`). **Consequence worth knowing:** `update` now rejects too, so a legacy row holding a genuinely uncoercible entry cannot be saved from the edit form until that entry is fixed, even for an unrelated change. Deliberate — the alternative is a write path that can still store what dispatch will reject.
- `recurring-schedule.routes.ts` — Full CRUD + pause/resume/cancel + instance listing with analytics drill-down.

**DB:** Migration `016_recurring_schedules.sql` — `recurring_schedules` table with frequency/days_of_week/day_of_month/time_of_day columns, plus `schedules.recurring_schedule_id` and `schedules.instance_number` FK columns.

**Callback:** `scheduler-callback.routes.ts` extended to handle `recurring_schedule_id` in EventBridge payload, routing to `RecurringScheduleService.executeRecurringInstance()`.

**Lifecycle:** active → paused (reversible, deletes EventBridge cron) → cancelled (irreversible). Edit updates future instances only; existing instances keep their own lifecycle.

Hence `lock_timeout`; the `NOT VALID` + `VALIDATE` split does **not** help inside one transaction
- 067: `platform_audit_log.actor_type` (`human`/`api_key`/`system`) + `api_key_id`, plus a partial index on `(tenant_id, api_key_id, created_at DESC) WHERE api_key_id IS NOT NULL` for revocation forensics. Both nullable, and there is deliberately **no backfill** — NULL means "written before this column", and a historical row with a `user_id` may be a person *or* a creator-backed key, which is unknowable now. No CHECK constraint either, and that is not laziness: `AuditBuffer` inserts in batches and drops a batch after three failed retries, so a constraint violation would silently discard the VALID rows buffered alongside it; the value set is enforced by `tsc` instead (`actor_type` is required on `CreateAuditLogInput`). No FK on `api_key_id` — an audit row must outlive the credential, and migration 065 is the standing illustration of what an FK onto an audit-relevant table costs
- 070: `idx_credit_transactions_release_idempotent` — the release half of the credit ledger's idempotency, mirroring `idx_credit_transactions_consumption_idempotent`. Partial on `type = 'release' AND reference_type IS NOT NULL`, so it covers no historical rows (every release row ever written carried `reference_type` NULL) and needs no backfill. Additive rather than a widening of the consumption index, whose DROP + CREATE would land on the credit hot path; `lock_timeout` bounds the wait exactly as 065 and 066 do
- 069: `membership_invites` — the token that binds a Firebase identity to a membership (see *Invitations* below). `token_hash` (sha256 hex) is unique; the raw token is never stored. A partial unique index (`uq_membership_invites_live`, `membership_id WHERE claimed_at IS NULL AND revoked_at IS NULL`) makes "one live token per membership" a schema fact rather than a property of statement order. `email` and `role` are COPIES of what was offered rather than joins, because `GET /invites/:token` renders them to an unauthenticated reader and must describe the invitation AS SENT. Deliberately adds **no unique index on `users.email`** — duplicates already exist in production rows, so the `CREATE UNIQUE INDEX` would fail inside `docker/entrypoint.sh` before the app boots (zero logs, zero metrics); the claim path is written so it never needs one
- 072: `user_notification_preferences` + `notification_deliveries` — the notification engine. Sparse per-user overrides against the frozen catalog in `src/notifications/engine/catalog.ts`, plus the claim-before-send ledger that makes a scheduled digest idempotent. `tenant_id` is IN the delivery unique index deliberately: without it a person who administers two tenants receives the first workspace's digest and has the second silently skipped as a duplicate. The delivery table is the one `PURGE_TARGETS` entry with a floor of its own (30 days, via `GREATEST`) — a dedupe claim's job ends within hours, nothing reconciles against it, and left unpurged it would grow as `audience × periods` forever
- 073: `users.email_unverified` — TRUE when an invite claim ACTIVATED A STUB without proving the row's email address (see *Invitations*; re-binding a row that is already that same identity leaves the column alone, so an unverified or phone-auth second claim cannot revoke a proof the row already carries). Default `false` plus a **backfill**, and the backfill is load-bearing: the first version reasoned that every pre-existing row came either from `/auth/session` (behind `sessionLinkEmail`'s verified-email refusal) or from a `pending_` stub nobody can sign in as — and missed that the CLAIM flow predates this column and already accepted an unverified token while passing `adoptEmail: true`. So a row bound by a historical claim can already key under an address nobody proved, and defaulting it to `false` would have the three authority-granting lookups trust the pre-staged version of the attack from the moment the migration lands. Nothing recorded whether a given claim's token was verified, and an honest claim and the attack are the same shape on disk, so it flags EVERY row bound through a claimed invitation: conservative in the only safe direction, because a missed row is a live takeover while a wrongly flagged row costs its owner one verified sign-in (path 1 clears it). Deliberately no index — every reader that filters it reaches its rows by something already indexed and then rechecks the flag over the handful that can match: the by-address lookups (`resolveByProvenEmail`/`findByProvenEmail`, reached by `POST /users/invite` and both super-admin provisioning routes) by `idx_users_email`, and the two membership race guards (`membershipRepository.create`/`reactivateWithRole` under `requireProvenEmail`) by the primary key. A partial index would earn nothing on a table every authenticated request reads; `findByEmail` only ORDERS by the column. `lock_timeout` as 065/066/070: a constant default makes the ALTER metadata-only from PG 11, but it still takes ACCESS EXCLUSIVE on `users`
- 074: `telephony_providers.live_transfer_enabled` — per-carrier live-transfer governance flag (default false; seeded true for vobiz, plivo and twilio). Replaces core's `ESCALATION_TWILIO_TRANSFER_ENABLED` env gate. The ADD COLUMN and the seed run inside one `DO` block keyed on the column's absence, so re-applying it (ledger repair) never re-enables a carrier a super admin switched off
- 079: `bulk_dispatch_job_recipient_variables` — an email job's whole per-recipient map, beside its row rather than on `dispatch_payload` (see *Retrying a message campaign*). `job_id` is the PK and cascades from `bulk_dispatch_jobs`; the row's presence (`{}` included) is what tells a retry the variables are known. `ambiguous_recipients` (JSONB array, `[]` default) lists the addresses the list named twice with different details, whose retry is refused

### Notifications (`src/notifications/`)

Every customer-facing email this service sends, on Mailjet Send API v3.1. Fire-and-forget — failures are logged, never thrown, and never block the caller.

**The engine is `src/notifications/engine/`; the mailers are the modules beside it.** Before it, each mailer was a module that knew its own audience, rendered its own HTML and called the transport directly — four private answers to the same four questions (who gets this, can they decline it, has it already been sent, what is it called on a settings page), and the fourth had no answer anywhere.

**`catalog.ts` is the enumeration, frozen, in the `governance/catalog.ts` shape**: the default for every event lives in code and the DB holds only sparse per-user overrides, so a user who has never opened the settings page has no rows and changing a default changes behaviour for everyone who never chose and for nobody who did. Four events today — `campaign.dispatched`, `campaign.completed`, `agency.campaign.completed`, `usage.digest`. Adding one is a catalog row plus a renderer; the settings page, the preference validation and the suppression check pick it up with no further edit. Lookups go through a `Map`, never an object index — `EVENTS['constructor']` resolves to a truthy value on an object literal and every "unknown event" guard downstream of a bare index silently passes, the incident `src/autopilot/` records at four sites.

**The invite mailer is deliberately NOT in the catalog.** It carries the token that is somebody's only route into the product; there is no coherent "off" for it, because suppressing it does not spare the recipient a mail, it denies them the account. A credential delivery is not a subscription. Pinned by test, because "add every mailer to the catalog" is the obvious next change somebody makes.

**The primitives are small and composable, not one dispatcher.** `audience.ts` resolves who and whether they still want it; `deliver.ts` claims, sends and records; `campaign-gate.ts` is what the two pre-existing campaign mailers compose. The three mailers that predate this each resolve their audience at a different point and in a different shape — one reads free text off a campaign row, one derives a supervisor roster, the digest groups by account scope — so forcing all three through one `render(recipient)` seam would have meant rewriting a 522-line module with its own discriminated result type to gain nothing it did not already have.

**`notification_deliveries` (migration 072) is claim-before-send, and it is the only thing between an at-least-once trigger and duplicate mail.** The dispatcher INSERTs a row per recipient BEFORE sending with `ON CONFLICT DO NOTHING RETURNING`; a zero-row result means that exact notification already went to that exact inbox. Nothing upstream is exactly-once: EventBridge is at-least-once by contract, the trigger Lambda retries a non-2xx, an operator re-runs the internal route by hand, and a retry after a timeout reaches a DIFFERENT master instance while the first is still working — which is precisely the case an in-process "already running" flag cannot see.

Four rules about that table are load-bearing:

- **The `account_id` lookup is TENANT-SCOPED**, and it is a scalar subquery rather than a direct bind. The subquery came first: `isUuid` is a shape check, so it normalises the `bulk_dispatch_jobs` sentinel `'default'` to NULL but passes a well-formed uuid for an account that no longer exists — and because `notification_deliveries.account_id` has an FK to `accounts(id)` while `bulk_dispatch_jobs.account_id` has none, that raised `23503` and, the whole multi-row INSERT being one statement, the abort withheld the notice from EVERY recipient of that campaign rather than merely mis-scoping it. The tenant predicate (`AND a.tenant_id = $3`) is the second half: `bulk_dispatch_jobs.account_id` has no tenant check either, so a stale or hand-repaired job row can name another tenant's account and a bare existence test resolved it happily, writing tenant A's delivery row with tenant B's `account_id`. The column is read by no authorization path today (written here, aged out by `retention-purge.ts`, served by nothing), so that was latent rather than a live cross-tenant leak — fixed now because the day it becomes a filter is not the day to discover a row was mis-scoped years earlier.
- **`tenant_id` is IN the unique index**, and leaving it out was a real bug rather than a hypothetical. The natural key looks like `(event_key, dedupe_key, recipient)`: a consultant who is `account_admin` in tenants A and B receives A's digest, and B's INSERT — same event, same period, same inbox — then hits the conflict and is silently skipped as "already sent". They would never receive a digest for the second workspace and nothing would report it. The `dedupe_key` additionally names the account scope explicitly (`tenant:<uuid>` / `account:<uuid>`), so two scopes of one tenant cannot collide either — a sentinel that is merely ABSENT for the tenant-wide case collides the first time somebody passes `''`.
- **A failed send keeps its row where the outcome is AMBIGUOUS, and only there.** Deleting on failure to allow a retry reopens the exact double-send the table exists to prevent, because the commonest "failure" is a TIMEOUT, and a timeout after Mailjet already accepted the message is indistinguishable here from one before. So a failed digest is a lost digest; `error` is what tells support why, and the self-service Preview is the recovery. A claim is RELEASED wherever nothing was delivered PROVABLY: no transport configured, a renderer that threw, or a provider that answered and refused (`rejected`). `timeout` AND `error` keep it, because neither proves nothing was delivered — both mean *no answer was read*, and a `fetch` rejecting with `ECONNRESET` can reject after Mailjet accepted the message. Releasing on `error` was the more expensive half of a pair of bugs that hid each other: `mailjet.client.ts` detected the timeout with `err instanceof Error && err.name === 'TimeoutError'`, which misses the abort on both of its real shapes (a `DOMException` that can fail the `instanceof`, and undici burying the reason one level down on `.cause`), so every `MAILJET_TIMEOUT_MS` abort was labelled `error` — and the release rule looked safe precisely because the outcome that should have exercised it was mislabelled. `src/utils/abort-error.ts` is now the shared duck-typed predicate (two private copies in `src/agency/` predate it and should migrate to it). Getting this wrong on the campaign mailers was a silent regression: they called the boolean `sendEmail`, which collapses all four facts into `false`, so one transient 503 burned the job's dedupe key and the next core webhook redelivery — which before the gate existed would have re-sent the mail — found the key taken and sent nothing, forever. They call `sendEmailWithOutcome` now.
- **The transport check happens BEFORE the claim.** Claiming first in an environment with no `mailjet` block would burn every recipient's dedupe key for the period while sending nothing — and because a burned key is never retried, configuring Mailjet afterwards would deliver nothing until the NEXT period. This is why `sendEmailWithOutcome` exists beside the historical boolean `sendEmail`: `unconfigured`, `rejected` and `timeout` are three different facts and the ledger turns on the difference.
- **It is in `PURGE_TARGETS` with a 30-day floor of its own** (`GREATEST($1, NOW() - INTERVAL '30 days')`, so a tighter retention window still wins). **`GREATEST`, not `LEAST`, and this line said `LEAST` while the code was being corrected away from it.** Both operands are past timestamps, so `LEAST` picks the EARLIER one — at the production 85-day window that is the ordinary cutoff, the 30-day floor collapses to a no-op, and the purge runs, reports the table, and deletes almost nothing. Nothing fails; the table just never bounds. Only a run against a real Postgres showed it. Dedupe only has to outlive the retry horizon and nothing reconciles against these rows; left out, the table would grow as `audience × periods` forever and become the second thing in this schema that never self-bounds.

**`user_notification_preferences` is scoped `(user, tenant)`, deliberately not `(user, tenant, account)`.** One person can belong to several tenants and reasonably want a different answer in each. The account is out because a digest's scope is already decided by the recipient's own `memberships.account_id` (tenant-level ⇒ the whole tenant, account-scoped ⇒ that account), so an account column would let somebody store preferences for accounts they cannot see and would multiply the settings page by the account switcher. `event_key` is TEXT rather than an enum or an FK, same reasoning as the governance overrides: a row naming a retired key is INERT — never served, never deleted, because a key removed by mistake and restored next release would have taken every customer's preference with it.

**Two collapse rules, both forced by the schema.** `memberships` permits a user to hold a tenant-level row AND an account-scoped one, so one person can appear twice — they get ONE digest, at the WIDEST scope. And `users.email` carries only a NON-unique index (migration 069 says so in as many words), so two users can share an inbox — the mail is sent if ANY of them wants it, because an inbox cannot be half-subscribed. **The cadence tie-break among them is CADENCE-AWARE**, and was not: "the first enabled user decides the frequency" meant a shared alias where one person chose weekly and another daily resolved to whichever row the roster query happened to return first, so the other's subscription was suppressed by a colleague's unrelated choice — and nothing looked broken, because the alias still received the winner's cadence. An enabled preference MATCHING the requested cadence now wins outright, and first-enabled only breaks ties among equally-good candidates, which is what makes the daily and weekly runs address disjoint sets of people rather than racing for one inbox. Addresses are lower-cased once, in `collapseByInbox`, which is where they stop being a database value and become a dedupe key.

**The explicit-audience rule is the INVERSE of the role-floor one, and the asymmetry is the point.** A `campaign.*` address was typed into a campaign form by a person, and most are not platform users at all — a client's ops inbox, a shared alias. There is no preference for such an address and no user whose choice could speak for it, so it is always sent to; suppressing it would be this service overriding an explicit instruction on behalf of nobody. An address that DOES resolve is suppressed only when EVERY active user behind it has declined.

**Failure directions differ by event, deliberately.** A preference lookup that fails **fails OPEN** on both campaign mail and the agency notice — those addresses were named explicitly, or the recipients were entitled by role before preferences existed, and a database blip must not silently withhold operational news. A claim that fails **fails CLOSED** — without it there is no idempotency, a missed notification is recoverable from the campaign page, and a duplicate cannot be un-sent.

**The usage digest (`src/notifications/digest/`) is built from master's OWN tables**, `credit_transactions` and `bulk_dispatch_jobs`, with no core call. Three reasons, all pointing the same way: the ledger is the BILLED truth and a headline figure must agree with the invoice; it is the one table retention never purges, so a period-over-period comparison cannot lose its baseline; and a scheduled fan-out over every active tenant must not turn a core blip into a whole missed cycle, because there is no redelivery for a cron. Three costs, each repeated to the reader in the mail itself: only billed events appear (a call that never connected settles at zero), rows are stamped at SETTLEMENT time rather than call time, and there is no per-call outcome breakdown.

⚠️ **The two tables DISAGREE about how ids are typed.** `credit_transactions.tenant_id`/`account_id` are `UUID` (migration 002); `bulk_dispatch_jobs`' are `VARCHAR(255)`, with `account_id NOT NULL DEFAULT 'default'` (migration 017). So every predicate against `bulk_dispatch_jobs` compares **text** — `tenant_id = $1::uuid` there raises `operator does not exist: character varying = uuid` and kills the digest — and a `UNION` across the two must cast both sides. The literal `'default'` matches no account-scoped predicate, which is correct rather than a bug: such a row predates jobs carrying a real account and belongs to nobody's account.

**"Active account" is a query, not a policy**, and it is what makes on-by-default defensible: `findActiveTenantIds` returns only tenants with consumption or a campaign in the window, and a scope whose snapshot is empty is skipped entirely. A digest saying "you did nothing this week" is the mail that gets a sender filtered. Top-ups alone do NOT make a period non-empty — that tells the buyer something they already know and carries no usage.

**Window arithmetic is UTC and reports the most recently COMPLETED period, never the one in progress** (`engine/period.ts`). The schedules fire a little way INTO the new period (02:30 UTC daily, 03:00 UTC Monday) and the resolver steps back a whole one, so every hour of every day appears in exactly one digest, once. Two traps are pinned by test: `getUTCDay()` is 0 on Sunday, so the offset is `(day + 6) % 7` — the naive `day - 1` sends Sunday FORWARD past its own Monday and produces a window starting in the future, i.e. a busy week reported as empty; and the window must be a function of the calendar rather than `now − 24h`, or the scheduled fire at 02:30 and a retry at 10:00 compute different `periodStart`s and therefore different dedupe keys, which is a second digest. Month names are written out rather than taken from `toLocaleDateString`, whose ICU data renders September as "Sept" or "Sep" depending on the Node build. Per-user timezones are deliberately deferred; the mail states its UTC window in both parts, because for an IST customer "yesterday" is 05:30 to 05:30.

**The runner is bounded in two independent places.** `TENANT_CONCURRENCY` (4) bounds the DATABASE work against the same 20-connection pool settlement uses; the send semaphore in `deliver.ts` (6) is **process-wide**, not per fan-out, because a per-tenant limiter running over N tenants is a burst of 6×N simultaneous outbound requests at 02:30. One tenant's failure is logged and skipped — the rest have done nothing wrong and a scheduled job has no second chance inside the period.

**`period_start` is the recovery for a missed tick.** Without it the window is a pure function of the clock, so a failed Monday run means last week's digest can never be sent. It is validated by `resolveDigestWindow` (which owns the calendar) rather than by a regex in the validator, and re-running a period that already went out claims nothing and sends nothing.

**It must be a real period boundary AND a period that has FINISHED, and the second half was missing.** `resolvePeriodWindow` positions itself relative to the probe it is given, so a probe inside any period reports that period as "most recently completed" — today's and 2099's alike. An operator re-running what they think of as "today" therefore built a PARTIAL-day digest, mailed it, and claimed that period's dedupe key for every recipient; the scheduled run next morning found the key taken, counted a duplicate, and the real full-day digest was never sent. A typo'd year did the same to a period that had not happened yet. Half-open windows make the check exact: `to` is the first instant NOT in the period, so `to <= now` is precisely "finished".

**The route resolves it BEFORE answering 202, not inside the backgrounded run.** On the non-dry path the runner is invoked with `void` after the reply has gone out, so its refusal landed in a log line while the caller received `202 {"status":"started"}` — on the one path that exists to recover a missed digest, with the trigger Lambda treating 2xx as success. Both paths now answer 422.

**`dry_run` short-circuits BEFORE the dispatcher, not inside it**, and is answered synchronously rather than backgrounded. A dry run that claimed would burn every dedupe key for the period and make the real run a silent no-op — the exact opposite of what somebody running it wants to find out.

**The 409 on `/internal/notifications/digests/run` means the OPPOSITE of the retention purge's, and the trigger Lambda treats it as SUCCESS.** Overlapping purges are dangerous; overlapping digest runs are benign, because the ledger's claim makes the second pass a no-op per recipient — so the in-process flag saves database work rather than preventing harm, and failing the invocation would alarm on a system behaving exactly as designed. Documented on both sides so neither gets "tidied up" to match the other.

⚠️ **That is only true of two runs of the SAME cadence, and the guard is keyed by cadence for exactly that reason.** `buildDedupeKey` puts the frequency in the key precisely so daily and weekly claim different rows, so a cross-cadence overlap suppresses REAL work rather than duplicate work. A single boolean made `isDigestRunning()` answer for the wrong cadence, and the two schedules are thirty minutes apart on Monday morning: the daily fan-out over every active tenant was routinely still running when the weekly one fired, the weekly got a 409, the Lambda treated it as success and did not retry, and the whole week's digest was never sent — silently, with the next tick seven days later computing a different `periodStart`, so the week could not be recovered except by a manual re-run nobody knew to do.

⚠️ **A `dry_run` neither TAKES nor RELEASES that flag** — the same bug in a second form. A dry run claims nothing and sends nothing, so the ledger makes it a no-op against a real run of its own cadence too, and the 409 it could cause is benign in neither direction. Taking the flag let an operator checking audience at 02:29 hold it across the whole tenant fan-out (the dry path is awaited, not 202'd) and 409 the 02:30 scheduled tick. Releasing it would have been worse: a dry run finishing while a real run of the same cadence was still going would `delete` a flag it never took, re-opening the genuine overlap the guard exists to stop. Real-run-only, on both edges; `isDigestRunning()` answers only about work that actually writes.

**Metrics:** `notification_sends_total{event_key,result}` and `notification_digest_runs_total{period,result}`. The `result` values are a CLOSED SET enumerated in `src/utils/metrics.ts`; a value emitted anywhere and missing from that list is a series no dashboard or alert rule was written against, which is how `suppressed` went unlisted while being counted. Deliberately **no `tenant_id` label**, unlike the credit/webhook counters: a digest run touches every active tenant at once, so a tenant label would multiply the series by the customer count on one tick for a breakdown nobody asks this counter for — the per-tenant question is answered from `notification_deliveries`, which holds the row. Three `result` values are NOT failures and must not be alerted at threshold 0: `duplicate` (the idempotency working), `unconfigured` (normal in an environment with no Mailjet), and `suppressed`. The alertable ones are `rejected`, `render_error` and `claim_error`.

**Config:** Optional `mailjet` block — `MAILJET_API_KEY`, `MAILJET_API_SECRET`, `MAILJET_FROM_EMAIL`, `MAILJET_FROM_NAME`. `CUSUI_BASE_URL` provides clickable job detail links in emails. **The engine adds NO new environment variables**: it sends on the same Mailjet block, links with `CUSUI_BASE_URL`, brands with `PLATFORM_BRAND_*` and reports runs to `RETENTION_SLACK_WEBHOOK_URL` when one is set. The scheduled half is the `notificationDigestTrigger` Lambda in `serverless.yml` (two EventBridge schedules, one function — the cadence rides on the event Input, not an env var, so there is one log group and one set of permissions), posting to `/internal/notifications/digests/run` with a token from `S2S_AUTH_TOKENS`.

**Routes:** `GET`/`PUT /notifications/preferences` and `POST /notifications/digests/preview` are authenticated and tenant-scoped. The two PREFERENCE routes carry **no `requirePermission`** — both are about the CALLER and take no subject, so a `viewer` manages their own subscriptions exactly as a `tenant_owner` does and gating on any existing permission would lock somebody out of their own unsubscribe. **`POST /digests/preview` is the exception and carries the `usage.digest` catalog floor**, and it had no gate at all: "only ever themselves" bounds the SUBJECT and says nothing about the PAYLOAD, and this route BUILDS the workspace's billed usage and campaign figures. An `agent` is level 5, below `viewer`, and holds neither `credit.read` (`GET /credits`) nor `proxy.static_calls.read` (`GET /bulk-dispatch-jobs`) — so this was the only route on the platform serving either figure to them, and the catalog's "a viewer can already fetch the balance" disclosure note does not cover it (not even a viewer can get the campaign breakdown). Gated on the catalog floor rather than a literal `account_admin` so widening `usage.digest`'s audience widens the preview with it. Any route added under this prefix that returns workspace data rather than a personal setting needs the same treatment. `denyPlatformApiKey` applies, for `GET /auth/me`'s reason: there is no "me" for a machine credential, and a key minted by a person authenticates carrying that person's `UserRecord`, so without it a leaked key would read and rewrite its creator's personal settings. The preview scope comes from the caller's own membership, never `X-Account-Id` — that header is unauthenticated and optional, so preferring it would let an account-scoped member preview a sibling account's spend by omitting it.

**The invite mailer (`invite-mailer.ts`) SENDS, on Mailjet — and the `platformEmail` block it was once specced against is now a reserved, unused seam.** An earlier revision of this file said the mailer "is a SEAM and sends nothing yet" and that "routing invites through Mailjet would mean the platform's own product cannot send the platform's own mail". Both are out of date: Mailjet is exactly what shipped. The dogfooded path is still the intended end state, but it needs a `messaging_connections` row in CORE with a verified sending domain, an S2S contract for a platform-scoped (rather than tenant-scoped) send, and a decision about whose message ledger it lands in — none of which exists, and none of which an invited agent's only route into the product should have waited on. `mailjet.client.ts` already carries job-completion and agency-campaign-completion mail, is bounded in time, and reports rather than throws. `invite-mailer.ts`'s module header carries the full argument and the consolidation plan: swap the transport inside `sendInviteEmail`, below the config guard, and nothing else on that path changes.

So today: `mailjet` sends the invite; the optional `platformEmail` block — `PLATFORM_EMAIL_CONNECTION_ID` (required, gates the block), `PLATFORM_EMAIL_FROM_EMAIL`, `PLATFORM_EMAIL_FROM_NAME` — remains in the schema, is **read by nothing**, and setting it changes no behaviour. It is kept rather than deleted because the connection id is the one fact master cannot derive when the consolidation happens. `sendInviteEmail` returns a discriminated `{ sent: true, messageId } | { sent: false, reason: 'not_configured' | 'not_implemented' | 'failed' }`. The negative reasons are distinct on purpose: `not_configured` is an operator's problem (no Mailjet block), `not_implemented` is ours — and it is now scoped to ROLE rather than to the feature. Only `agent` gets a real mail, because only an `agent` has a destination to be sent to (`/agency/join/:token`); there is no equivalent workspace-onboarding page for a `viewer` or an `account_admin`, and mailing them a link into a sign-in page they have no credential for would be the same dead end one role over. Same env-gating convention as every optional block, so **a behaviour that silently does nothing in a running service is usually an unset env var rather than a bug**. The invite response gained `invite_email` and `sign_in_url` — **additive; `membership` and `user` are untouched** — and `invite_email.sent` is what the customer UI needs before it can stop instructing supervisors to send the link themselves. The call is made after the membership is written and is wrapped, so the invite cannot fail on it. `inviteSignInUrl` serves an `agent` the Agency Dialer's own sign-in page, `/agency/login`, and every other role the plain `/login`. It used to be `/login?next=%2Fdialer`; the `next` is gone because the agency door defaults to `/agency`, which resolves the persona from the RBAC role, so the landing rule lives in one place in cusui rather than being copied into a link this server cannot see change. The two pages are **not** two spellings of one thing — `/login` carries a Sign Up tab, and `POST /auth/session` provisions a brand-new tenant for an address it does not recognise, so an invited agent who signs up instead of signing in lands in a private empty tenant while the membership this route just wrote goes unclaimed. Only an `agent`: a supervisor is `account_admin`+ and legitimately administers in `/app`, and most tenants hold no dialer at all. That rule is **duplicated** in cusui's `TeamPage.tsx`, which computes it from `window.location.origin` in the browser while this copy needs the server-side `CUSUI_BASE_URL` — one rule, two inputs, neither repo able to import the other. Accepted while the rule is two paths; if it grows per-role branches, cusui should render the served `sign_in_url` instead. **Drift now costs an onboarding, not a click** — a master still serving `/login` to agents after cusui has moved reopens the stray-tenant hole silently. **No test catches that drift**, and it is worth knowing rather than assuming: each repo's suite asserts its own hand-written literal against its own source, so moving this path and updating one suite leaves both green while the wrong URL ships. What bounds it instead is that cusui prefers the served `sign_in_url` and only falls back to its own derivation when `CUSUI_BASE_URL` is unset — so **change master first**, and in a configured deployment master is the only side that decides. A real contract test would follow `src/agency/agency-s2s-contract.fixture.json`; none exists for this seam yet.

### Audit (`src/audit/`)

**The campaign activity trail is a MERGE, not a query** (`src/agency/agency-activity.ts` + `.service.ts`, MAG-158). The two audit stores are separate databases with different schemas — core's `audit_logs` has `event_type`/`event_category`/`severity`/`event_data`/`actor`/`timestamp`, master's `platform_audit_log` has `action`/`resource_type`/`resource_id`/`details`/`user_id`/`actor_type`/`api_key_id`/`created_at` — so `GET /proxy/agency/campaigns/:id/activity` fetches core's page over S2S (`GET /internal/audit-logs`) and interleaves it in application code. There is no join to write and no shortcut.

Four things about it are load-bearing:

- **The filter is `campaign_id` on both sides, never `resource_id`.** On master's campaign rows `resource_id` *is* the campaign, but on a disposition row it is the **attempt** id and on a DNC row the entry id — so a `resource_id = :campaignId` filter silently drops every disposition and every DNC mark, i.e. most of what a compliance reviewer came for, while looking like a working feature. MAG-157 denormalised `campaign_id` onto those rows at write time (migration `061`) precisely so this filter can be one column.
- **Both stores write some of the same action names, and both rows belong in the trail.** `agency_campaign.paused` appears from master (a supervisor pressed Pause) and from core (the campaign transitioned). `source` is what tells them apart, which is why it is a first-class field. The rows only core has are the auto-pause with its measured abandonment rate; the rows only master has are dispositions, DNC marks and staffing changes. **A test asserting "200 with rows" passes against a route returning master's half** — the assertion that distinguishes a working merge is one core-only and one master-only row in the same payload.
- **The ownership probe degrades too.** It is a `proxyToCore` call, which *rethrows* on a transport failure — so an unguarded probe turned the headline case (core is down) into a masked 500 with no trail, no banner and no reason. A transport failure now yields `partial` with master's rows scoped by the caller's **membership account**, which is what stands in for the ownership check core would have done; a core *refusal* is still forwarded verbatim. An inverted `from`/`to` is master's own **400**, not a forwarded core 422 — the latter surfaces as `partial: core_error`, i.e. a user input error dressed as a dependency outage.
- **Core's half is best-effort and says so.** A degraded core returns master's rows plus `partial: true` and a reason, never a 500 and never a silently short list; `total` goes `null` rather than counting one half. Both keys are always present — a `partial` that only appeared when something was wrong is indistinguishable from a client that forgot to read it. The **CSV export is the exception and refuses (424)**: a screen can carry a banner, a file that leaves the building cannot. 424 rather than 503 because `errorMaskHook` masks every 5xx unconditionally, which would replace the remedy with a support-ticket message.
- **A core row that cannot be read drops that ROW, not the page.** `parseCoreBody` parses the timestamp rather than only type-checking it: `new Date('nope').toISOString()` throws, and that throw was swallowed by `readCore`'s catch — so one bad row discarded core's entire half and reported `core_unreachable`, which is false when core answered 200 (and became a 424 refusal of the whole CSV export). Any skipped row still sets `partial`, because a dropped row is a short list.
- **The action vocabulary is SERVED, not mirrored.** `GET …/activity` carries `available_actions` (`{value,label,group}[]`, `src/agency/agency-activity-actions.ts`) — master's campaign-scoped catalog actions plus core's agency event types, which is a set only master knows in one place. CusUI used to hand-maintain the same list and nothing could check it: master is not a dependency of that repo, and a set-equality test would have been wrong in both directions anyway (11 `schedule.*` actions belong to neither campaign nor client, and 5 of the offered actions — including the auto-pause — are core's and are not in master's catalog at all). Master's half is exhaustive against `PLATFORM_AUDIT_ACTIONS` at compile time AND in `test/unit/agency/agency-activity-actions.test.ts` (vitest does not type-check, so the test is what fails in `npm test`); core's half is a transcription that names the core file and line each value is written at, because that is the strongest thing a repository which cannot import core can do. **Not on `…/activity.csv`** — a file has no filter to draw, and its ten columns are a fixed contract (86d45t7rm's two actor columns are APPENDED for exactly that reason: inserting one would have shifted `target_type`/`target_id`/`detail` under every positional consumer). The client renders the filter from it and hides the control entirely when it is absent (an older master), rather than falling back to a copy, which would be the mirror again.
- **The actor axis IS stored, and that is the opposite call from the product axis — deliberately** (86d45t7rm, migration 067). `actor_type` (`human` / `api_key` / `system`) plus `api_key_id` are columns, because unlike `product` they are **not** derivable from anything on the row: `user_id` alone cannot distinguish "Alice clicked stop" from "someone used a key Alice minted two years ago", and that was exactly the state — `sessionMiddleware`'s key branch loads `platform_api_keys.created_by` into `request.user`, so every audited write stamped the creator as though they had acted. Master's own trail therefore contradicted core's `last_transition_by`, which had already been corrected for the same defect: one said "Alice started it", the other said nobody did. The repair had to be platform-wide — the narrow version (drop `user_id` on the four agency lifecycle routes) was declined in review, because it would have isolated four of the audited sites *and* traded a misleading principal for no principal at all. `actor_type` is a **required** field of `CreateAuditLogInput`, so `npm run lint` enumerates all 29 call sites rather than leaving the field to be remembered; `requestAuditActor` (`src/audit/audit-actor.ts`) is the single discriminator and keys on `apiKeyTenantId`, never on `!request.user`, because a creator-backed key has both. A key row names the **credential**, not its creator — who remains one join away in `platform_api_keys.created_by`, non-nullable-by-deletion since migration 065 for exactly this. `system` is a third value rather than a null so a scheduler tick and a key call stay distinguishable, which is the ambiguity the ticket names in core's `last_transition_by` and is deliberately not recreated here. **NULL means "predates the column"**, with no backfill, and `normalizeMasterRow` bridges it to the inference the activity trail made before — so historical rows render exactly as they always did while `ActivityActor.type` still reports `'unknown'` for them. The activity trail's `system` flag is now read from `type` rather than from `user_id === null`: after this change a key row also has a null `user_id`, and the old inference would have reported "nothing human was involved" about an action somebody's credential performed. **On a pre-067 row the two deliberately disagree** — `type` is `'unknown'` (nothing was recorded) while `system` keeps the legacy `user_id === null` reading, so historical rows render exactly as they always did. A client migrating from `actor.system` to `actor.type === 'system'` would therefore flip every historical background row to an unhandled `'unknown'`; read `system` for rendering, `type` for whether the distinction was actually captured.
- **The product axis is DERIVED, never stored.** `AuditProduct = 'ai' | 'agency'` (`src/audit/vocabulary.ts`) is a total function of the action key, so `?product=` on `GET /audit-log` expands into the existing `actions` predicate and `available_products` is served alongside `available_actions`. Nothing is persisted and no `auditLogger.log` call site changed: a stored copy of a derived value can disagree with the derivation on historical rows, and `details` JSONB would have accepted it silently. The compiler still enumerates the decision — `product` is REQUIRED on `AuditActionOption`, and the pre-existing bidirectional `Exclude` checks make the vocabulary total over `catalog.ts`, so a new catalog action cannot ship without someone choosing a product for it. `?product=` is a closed Zod enum, so a typo is a 400 rather than an empty log — and so is a pair that cannot both hold (`?product=agency&action=schedule.failed`), which is provably empty from the catalog before a row is read. Both are refused on the same reasoning: an empty audit log is read as a statement about the tenant. `dnc_entry.*` is classified `agency` per Q2, which is why the map is per-action rather than an `agency_`-prefix rule — the prefix rule would be wrong today, not hypothetically. The union is deliberately two values; where a `'platform'` value would go is documented at the type.
- **Pagination is keyset, because two OFFSET-paginated sources cannot be merged coherently.** Both repositories order by a TOTAL key (`(created_at, id)` / `(timestamp, id)`) and take a `before` position; the cursor is one such position per source, base64url-encoded and opaque. The tie-break is not decoration: both audit loggers batch, one flush is one transaction, and `now()` is fixed per transaction, so a whole flush shares a timestamp to the microsecond. Both stores compare and order on a **millisecond-truncated** key, because the cursor is millisecond-precision while the columns are microsecond — comparing against the raw column silently skips rows (see core's *Audit* section). Cursor ids are validated as UUIDs so a hand-edited cursor is a 400 rather than a Postgres `22P02` surfacing as a 500. Every page size obeys one invariant — **`<page size> + 1` must fit inside core's `/internal/audit-logs` cap**, because the merge asks each source for `limit + 1` and an over-large request 400s core on every full-size page, degrading it to `partial` (and on the CSV route to a 424 refusal). `ACTIVITY_MAX_LIMIT` is **99** for that reason historically, when core's cap was 100; core's cap is now **1000** and 99 remains simply because it is a screen's page size. The export uses `ACTIVITY_EXPORT_PAGE_SIZE` = **500** instead: it is draining the trail rather than rendering it, and each page costs one master SELECT + one S2S round trip + two identity lookups (users and API keys, concurrent with each other) in series, so a 5000-row export went from ~51 of those to ~10. Master's own `auditRepository.find` ceiling was raised 100 → **1000** in lockstep, and that is not cosmetic — a clamp BELOW the requested size makes `mergeActivityPage` read "fewer rows than I asked for" as "stream exhausted", so the export would have stopped at 100 rows and handed over a file that looked complete. `test/unit/agency/agency-activity.test.ts`'s `describe('the page ceiling')` mirrors core's cap and pins both page sizes against it.

RBAC is `audit.read`, settled on MAG-157 (option 2): its floor dropped to `account_admin`, the same floor as `agency.supervise`, so the supervisor who controls a campaign can read its trail — no new permission and no governance-catalog key. Ownership is verified by proxying `GET /agency-campaigns/:id` **before either read**, because `requirePermission` proves the caller's role and never looks at the target row; core's 404 is forwarded verbatim so a cross-tenant id and a nonexistent one stay indistinguishable.

Batched writes (flush every 500ms or 100 events). Platform audit log partitioned by month. Migration `034_audit_partitions_extend.sql` extends `platform_audit_log` partitions (3 months back through 18 ahead of migration time) and adds a DEFAULT partition — migration 005 only created 4 months of partitions with nothing creating more, so inserts would hard-fail once the window passed (same bug core fixed in its migration 038).

### Data Retention (`src/maintenance/retention-purge.ts`)

Daily purge of transactional records older than a retention window (production policy: 85 days, mirroring magic-voice-core). An EventBridge-scheduled Lambda (`lambda/retention-trigger/index.ts`, wired in `serverless.yml`, 22:00 UTC = 03:30 IST — 30 min after core's purge) holds the policy (`RETENTION_DAYS`) and calls `POST /internal/maintenance/retention-purge` (S2S bearer auth via `config.s2sAuth.tokens`) with `{ retention_days, dry_run?, requested_by? }`; the route responds 202 and runs the purge in-process in the background (409 if already running, 422 if `retention_days < RETENTION_MIN_DAYS`, default 30).

**What it deletes** (batched 5000-row `DELETE`s, FK-safe order): `workflow_runs` (terminal: `sent`/`failed`/`skipped`) → `bulk_dispatch_jobs` (terminal statuses only) → `schedule_contacts` → `schedules` (not `scheduled`/`executing`, and only when no surviving bulk job references them) → `contact_messages` → `credit_reservations` (`settled`/`released` only — `pending` is kept) → `notification_deliveries` (the notification engine's dedupe claims, at their OWN 30-day floor rather than the retention window — see *Notifications*), all by `created_at < cutoff`. `platform_audit_log` monthly partitions entirely older than the cutoff are `DROP`ped and the DEFAULT partition is row-deleted. **Never purged:** `credit_transactions` (billing ledger), `super_admin_audit_log`, and all config/master data (tenants, accounts, users, contact lists, workflows, bindings, recurring_schedules, phone numbers, rate cards).

**Reporting:** posts a per-table count summary (or failure message) to a Slack incoming webhook when `RETENTION_SLACK_WEBHOOK_URL` is set. Config: `RETENTION_SLACK_WEBHOOK_URL` (optional), `RETENTION_MIN_DAYS` (default 30).

### Auto-provisioning (POST /auth/session)

New Firebase user → DB transaction: create user + tenant + default account + tenant_owner membership + 100,000mc signup bonus → external call to core's POST /internal/api-keys → encrypt + store core API key → **auto-assign a default phone number from the signup pool** (`findLeastAssigned()`, restricted to `pool_eligible=true` numbers — see Phone Number Management). The phone-assignment step runs outside the transaction and is best-effort: an empty pool or assignment error never fails the signup (the tenant is just left without a default phone for manual assignment later). Outcome is tracked via the `signup_phone_assignments_total{result}` metric.

**Email-based link and signup require a verified Firebase email.** Path 1 (user already found by `firebase_uid`) does not consult `email_verified`. On a UID miss, `sessionLinkEmail` (`src/auth/session-email.ts`) treats `email_verified !== true` as `403 email_unverified` and does **not** fall through to path 4: an unverified email/password token can be minted for any address without inbox control, and both super-admin tenant create and `POST /users/invite` write `pending_*` stubs keyed on that column. Binding on it is account takeover of every not-yet-activated owner and invitee; planting the address on a new row makes a later verified owner's `findByEmail` a coin-flip (`users.email` is not unique). Phone-auth tokens (no email) still provision. The invite-claim route is the deliberate exception — possession of a token delivered to the invited inbox is the proof there.

### Invitations — the token-bound claim flow (`src/invites/`, `src/api/routes/invites.routes.ts`, migration 069)

**The token replaces an EMAIL MATCH as the thing that binds an invitee to a membership, and that substitution is the whole feature.** `POST /users/invite` writes a membership plus, for an unknown address, a stub user whose `firebase_uid` is `pending_<uuid>`; the only thing that used to adopt that stub was `POST /auth/session` path 2 matching `decoded.email` against `users.email`. An invitee who signed up with a different address than the one that was typed fell through to **path 4** instead — a brand-new private tenant, a default account, a signup credit bonus and a fresh core API key — while the membership somebody deliberately created sat unclaimed and nothing told anybody. `users.email` also carries only a NON-UNIQUE index (`001_initial_schema.sql:60`), so the match was not even a unique lookup. Now `issueInvite` mints a 256-bit `randomBytes` token per agent invite, stores `sha256(token)` in `membership_invites`, mails the raw value, and the claim resolves the user through `invite.membership_id → memberships.user_id`. **Nothing on the claim path can provision anything** — no tenant, no account, no membership, no credit row, no core API key — and `invites.routes.ts`'s suite asserts that as a property over the module rather than case by case, because the failure mode is a branch somebody ADDS later.

**Two of the three routes are PUBLIC, and they have to be.** `GET /invites/:token` (what is this invitation?) and `POST /invites/:token/claim` (bind this Firebase identity) run with no `sessionMiddleware`, no `tenantContextMiddleware` and no RBAC: the caller has no account, no session and no tenant — that is the state an invitation exists to end. So every lookup derives its tenant from the INVITE ROW, never from a header, and the token's authority is bounded by exactly the membership it names. `POST /invites/resend` is the exception and carries the full chain as per-route `preHandler`s (`sessionMiddleware` → `tenantContextMiddleware` → `denyPlatformApiKey` → `requirePermission('user.invite')` → `canManageRole` on the target membership's role), because it is the same act as `POST /users/invite`: it mints a credential that binds an identity. It lives in the same file anyway so the revoke/mint rule sits beside the claim rule it has to agree with.

**The raw token is a bearer credential, so it may not reach a log line or a span.** It travels in the URL PATH, and master logs `url: request.url` at `info` on every request while `PinoInstrumentation` bridges pino into OTel Logs and `instrumentation-http` writes the same string onto every server span — so the unredacted version published a live, single-use, seven-day credential into Grafana Cloud on every request. `src/utils/redact-url.ts` rewrites the token segment to `:token` at all four sinks (both request-log hooks in `index.ts`, both error middlewares, and the HTTP instrumentation's `startIncomingSpanHook`, whose attributes are merged LAST over the instrumentation's own — verified against the installed package, not assumed). It is deliberately **import-free** so `instrumentation.ts` can reach it before the application graph loads, and it knows `resend` is a route literal rather than a token, because flattening an authenticated admin write into `/invites/:token` would be silently wrong rather than merely less detailed.

**`InviteStatus` has four values because the remedies differ**, and collapsing any two of them is the recurring bug here: sign in (`claimed`), ask for a new one (`expired`), check your inbox for a newer mail (`revoked`), check you copied the whole link (`not_found`). Precedence on a row that is several at once is REVOKED → CLAIMED → EXPIRED, shared by the GET and the claim so the page a person is reading and the request its button makes cannot disagree. The same distinction has to survive the RACE: a resend that revokes the token between the route's read and the claim's conditional UPDATE makes `WHERE claimed_at IS NULL AND revoked_at IS NULL` match nothing, and reporting that as one boolean answered "this invitation has already been used, sign in to continue" to somebody with no account and a working link already in their inbox. `markClaimed` therefore re-reads the row on the 0-row path and reports WHICH predicate failed.

**Two axes the shared `inviteStatus` function cannot see, and both had to be closed at BOTH routes.** It is a pure read of the invite row, so "same function, therefore no disagreement" was only ever true of `claimed_at`/`revoked_at`/`expires_at`. (1) **The membership.** Offboarding sets `memberships.status = 'revoked'` and touches nothing in `membership_invites`, so the GET answered `200 { status: 'pending', invite: {…} }` and the claim then answered 409 "a newer one may have been sent" — the wrong remedy for the wrong reason, since nobody resent anything and they were removed. Both routes now make the same tenant-scoped `findByIdInTenant` read off the INVITE's own `tenant_id` and answer `revoked` on a miss, which also stops an unauthenticated holder of a leftover token reading the tenant and inviter copy for a workspace they are out of. (2) **The clock, at write time.** The route's expiry check sits above `verifyIdToken` (an outbound call) and the membership read, so a TTL lapsing inside that window still bound; `expires_at > NOW()` is now a conjunct of the conditional UPDATE and the 0-row re-read classifies `expired` as well as `revoked`/`already_claimed`. Membership validity is deliberately NOT folded into that statement — it would put an `EXISTS` against another table inside the election that picks the single winner, for a race whose outcome is benign (a bind onto a revoked membership grants nothing: every session and RBAC lookup is status-filtered).

**Claim and bind commit TOGETHER, and the order inside the transaction is load-bearing.** Claim first: its row lock is taken before anything touches `users`, so the loser of a concurrent double-claim refuses before it can write an identity. Bind-then-claim would let two claims carrying DIFFERENT Firebase identities — exactly what a leaked token produces — both bind, with the loser's write landing last. Claim-then-bind as two separate statements leaves the invite spent with nobody bound. The bind itself is `adoptFirebaseIdentity(..., { onlyUnclaimedStub: true, adoptEmail: true })`: **without the first predicate this is a remote account takeover**, because `POST /users/invite` aims a membership at an EXISTING user row whenever the address is already known, and the claim binds an identity with no relation to the invited address. Six refusal REASONS come back as 409s rather than a masked 500 (five distinct bodies — `cross_tenant_identity` deliberately shares `identity_already_bound`'s, see below) — `already_claimed`, `revoked`, `expired`, `identity_already_bound` (the target row is already somebody ELSE's), `identity_in_use` (the incoming Firebase uid belongs to another row here), `cross_tenant_identity` (the stub is also another workspace's pending member — see below) — and the three identity arms roll the claim back so the invitation stays OUTSTANDING: on the honest reading nothing needs spending, and on the hostile one burning the link would let an attacker deny a real invitee their invitation.

**`onlyUnclaimedStub` is "not somebody else's", NOT "a stub", and the narrow first version refused the rightful owner.** The predicate is `stub OR firebase_uid = <the incoming uid>`. `POST /users/invite` reuses the existing `users` row for an address master already knows, writes a new membership against it, and still mails a join link — so the ordinary "add an agent who already has a MagickVoice login" invite arrives at a row whose `firebase_uid` is real, and a stub-only test rolled the claim back and answered `409 identity_already_bound`, the sentence written for the hostile reading, to the person holding the mail. The own-uid arm binds idempotently (nothing changes hands), a different uid is still refused, and the distinction stays in the `WHERE` rather than becoming a route-level "treat `identity_already_bound` as success", which would be a read and a write that can disagree.

**A MISMATCHED address still binds, and the audit row is the compensating control.** The token was delivered to the invited inbox, so possession of it is the authority; refusing an agent whose only Google account is personal would recreate the original defect one layer up. An UNVERIFIED Firebase email is accepted too — but it no longer writes itself onto the row, and the row is marked as carrying an address nobody proved (see the next paragraph): the token's authority is over the MEMBERSHIP, and it is evidence about the inbox only while the inviter is somebody else. What that costs is that `memberships` afterwards holds no trace of the discrepancy, so `user.invite_claimed` records `email_matched` plus BOTH addresses: "the addresses differed" without saying which one arrived is unanswerable in the dispute the row exists for.

**An unverified claim may not leave the row keyed under the address it did not prove, because `users.email` is how three write paths decide WHO somebody is.** Accepting an unverified Firebase email rests on "the token was delivered to the invited inbox" — and that is not evidence when the inviter and the claimant are the same person, because `POST /users/invite` returns the raw join link in its own 201 body. So: an attacker registers a Firebase email/password account for `victim@corp.test` (Firebase mints a token for any address; it is simply `email_verified: false`), invites that address into their OWN tenant as an `agent`, reads the link out of their own 201, and claims it. Neither claim-path guard has anything to refuse — the row is a fresh stub in one tenant, so `onlyUnclaimedStub` and `confineStubToTenantId` both pass honestly — and `adoptEmail` then wrote `victim@corp.test` onto a row the attacker signs in as. The payoff lands later, at the three lookups that resolve a typed-in address and then attach authority to it: `POST /users/invite`, super-admin tenant-create (`owner_email` → `tenant_owner`) and super-admin add-user. The next person to name that address hands the attacker the membership.

The fix is one column and one split lookup. **`adoptEmail` writes the address only when Firebase reports it VERIFIED**; otherwise `users.email_unverified` is set (migration 073) and the invited address stays where it was. **`userRepository.findByProvenEmail` is what all three reuse paths call** — `POST /users/invite` and both super-admin provisioning routes, the latter two passing their transaction's client, because a hand-copied statement is a second definition of the rule and mutation testing proved both copies could be reverted with zero tests failing anywhere. It refuses a flagged row — and a MISS is two answers, not one, which the first version got wrong. `resolveByProvenEmail` reports `none` (nothing keys under the address) or `unproven_conflict` (rows exist and every one is flagged). `none` writes a fresh stub, which is right: two principals sharing a string, on a column that has never been unique, and the other person's claim carries a different uid so it binds cleanly. `unproven_conflict` is a **refusal** (`409 unverified_address_holder`), because a flagged row is always BOUND — only `adoptFirebaseIdentity` sets the flag and it binds — so the fresh stub would be a second row for an identity that already has one, and `firebase_uid` is `UNIQUE`: when that same person claims the new invitation the bind raises `23505`, they are told `identity_in_use`, and the membership sits on a row nothing can ever activate with nobody watching. Refusing names a remedy the recipient can perform. `findByEmail` keeps its old semantics for `/auth/session` path 2/3 alone, because that caller has PROVEN the address (`sessionLinkEmail` refused anything else) and is therefore entitled to the row — and its adopt **clears** the flag. That lookup also gained a deterministic `ORDER BY email_unverified ASC, created_at ASC`: a flagged row beside a clean stub is exactly what the refusal creates, and "whichever row Postgres hands back first" must not be the thing that picks between a trap and the intended row.

**The flag has to be CLEARABLE, and the first version of this was not — which broke multi-workspace onboarding for the majority of claimants.** The repair was documented as `/auth/session` path 2's adopt clearing the column, "the rightful owner signing in repairs the row on the way in". That branch is unreachable for the population that gets flagged: the claim writes THAT PERSON'S OWN `firebase_uid` onto the row, so every later sign-in of theirs resolves at **path 1** (`findByFirebaseUid`), which returns the session payload and never adopts. Verifying the address in Firebase changed nothing, and the flag was permanent. Because `firebase_uid` is `TEXT NOT NULL UNIQUE`, a second workspace inviting that address then missed on `findByProvenEmail` and wrote a DUPLICATE stub which could never be bound at all — an `agent` claim died on `23505` → `identity_in_use`, and every other role activates through path 2, which a uid-bearing row can no longer reach. Silent, irreversible, and on the common path. `userRepository.clearEmailUnverifiedIfProven` is the missing half: path 1 clears the flag when the bound identity presents a `email_verified === true` token for the address ALREADY on the row, in one statement whose address predicate is a conjunct of the write. So there are **two** repairs because there are two ways to arrive holding proof — path 2's adopt for a row the person has not yet bound, path 1's clear for one they have.

Three further consequences worth knowing. **The ordinary unverified claim costs nothing**, because the common shape is an email/password account created on the join page with the INVITED address — adopting and not adopting write the same string. **What it does cost** is that such a claimant is not reusable by address until they verify — in either workspace, for any role — which is the whole of what the repair above restores. **A phone-auth claim is flagged too and can NEVER be repaired**: it binds an identity that can sign in as a row keyed under an address it never proved (the same trap by a different door, so flagging is right), but it carries no address to prove, so such a row stays out of the by-address reuse paths permanently and the remedy is a support-side merge rather than a weaker predicate. **`email_verified` is named explicitly in `claimWithIdentity`'s `Pick`**, because it is optional on `DecodedFirebaseToken` — a `Pick` that omitted it still type-checked and silently meant "unverified", which is the direction that flags every row. Pinned in `test/integration/repositories/user-email-proof.test.ts` against real Postgres (dropping either half of the fix fails it) and composed with path 2 in `invite-claim-session-composition.test.ts`.

**`onlyUnclaimedStub` asks whether the row is already SOMEBODY's; `confineStubToTenantId` asks whether it is already SEVERAL WORKSPACES'. Both are needed, and the second was missing.** A stub is a shared object — `POST /users/invite` reuses an existing `users` row whenever the address is already known, and super-admin tenant-create and add-user do the same — so one `pending_` row can carry a `tenant_owner` membership a super admin provisioned for tenant A **and** an `agent` membership an attacker wrote in their own tenant B. The stub test passes honestly there (nobody has signed in as the row), and an `agent` invite mints a token and hands the raw join link back to the **inviter** — so anyone who can sign up, which is everyone (`auth.routes.ts` path 4 makes every signup a `tenant_owner`), held a live credential for a row they did not own. Claiming it bound their uid, and `buildSessionPayload`'s `findAllByUserId` has no tenant filter, so the session came back holding tenant A's ownership, usable immediately with `X-Tenant-Id`. The invariant restored is that **a claim confers only what its token names**: the bind refuses to ACTIVATE a stub carrying `status = 'active'` memberships outside the invite's tenant, exempting only a row that is already the incoming identity (their own memberships, in every workspace they hold one). `status = 'active'` rather than any row, because `findAllByUserId` and `listByUserId` are both status-filtered and a revoked membership elsewhere confers nothing.

Four things about it are worth knowing before changing either side. **It could not live at invite time**, which is where the finding pointed: the two memberships can be written in EITHER order, so an attacker whose stub is provisioned onto afterwards passes an invite-time check that had nothing to see. **Minting a second `users` row instead was considered and is wrong** — `users.email` is non-unique, so the insert would succeed and silently split the address, and `POST /auth/session` path 2 (`findByEmail`, which picks ONE row) would then activate one and leave the other tenant's invitation permanently unclaimable; for every non-`agent` role that path IS the activation mechanism, since no token is minted (`roleGetsTokenInvite`). **The honest reading has a working remedy and the 409's copy points at it**: two workspaces can legitimately invite one address before anybody signs in, and `POST /auth/session` — which requires a VERIFIED Firebase email — is proof of the inbox rather than of one invitation, so it activates the shared stub across every tenant waiting on it. A resend does not help, because it mints another token against the same row. **`buildSessionPayload` is deliberately NOT filtered**: the fix is at the bind, so by the time it runs the row is either confined to the invite's tenant or was already the claimant's own, and a tenant filter there would hide a person's other workspaces from them on the one screen that lists them. Pinned against a real Postgres in `test/integration/repositories/membership-invite-claim-confinement.test.ts` (removing the option fails exactly the two attack cases), and composed with path 2 in `invite-claim-session-composition.test.ts`, because what makes the refusal correct is that the victim can still activate their own stub afterwards.

**`cross_tenant_identity` is a METRIC LABEL and a log field, never a wire status — and the first version of it was an enumeration primitive.** The arm fires exactly when the invited row holds an active membership in a tenant that is not this invitation's, so answering it distinctly turns the public claim route into a membership oracle: anyone can sign up (path 4 makes every signup a `tenant_owner`), invite an arbitrary address into their OWN tenant, claim their own link, and read the discriminator — a distinct status means "that address is a member somewhere else", a success means it is not. This work exists to close a takeover, not to trade it for a platform-wide customer-enumeration primitive, so the response is byte-identical to `identity_already_bound`'s (`BOUND_ADDRESS_CONFLICT`, one shared constant so the two cannot drift) while the `warn` log and `invite_claims_total` keep the distinction where it cannot be probed. `identity_already_bound` already answered the neighbouring question, so collapsing into it adds no signal that was not there. `identity_in_use` is deliberately NOT folded in: it is about the CALLER's own Firebase account, which the caller can see for themselves, and says nothing about the invited address. The test asserts the two arms return the SAME body by driving both through the route and comparing, rather than against a copied literal — a literal is the second copy that keeps passing after one arm is reworded.

**A `WHERE` clause is not a predicate lock, and closing the confinement race took a lock on BOTH sides.** `confineStubToTenantId`'s `NOT EXISTS` is a snapshot read under READ COMMITTED (nothing in this service sets an isolation level), so a concurrent `POST /users/invite` resolving the same address can INSERT exactly the membership it looked for, after the subquery is evaluated and before the claim commits — and the bind then lands on a row that now grants the foreign membership. The same race runs the other way: the invite resolves a clean stub, a claim binds and flags it, and the invite attaches authority to a row that is now somebody else's trap. Both halves are the original takeover reached through an interleaving rather than a missing check. The claim now takes `SELECT id FROM users WHERE id = $1 FOR UPDATE` as **its own statement** before the bind, so the UPDATE is planned under a snapshot that already includes anything an invite committed first — deliberately not relying on the UPDATE's own row lock, which would leave the re-check to EvalPlanQual re-evaluating a subquery against a new row version. The invite side passes `requireProvenEmail` to `membershipRepository.create`/`reactivateWithRole`, which lock the user row in the SAME statement as the write (`WITH proven AS (SELECT ... FOR UPDATE)`) and write nothing when the row has changed hands in the meantime — `FOR UPDATE` blocks while the bind is in flight and, on unblocking, Postgres re-evaluates the qual against the new row version, so a row the claim just rewrote simply no longer matches. (The super-admin provisioning routes need no such option: both hold `FOR UPDATE` on their own transaction's client from the `resolveByProvenEmail` lookup through the membership INSERT, so a concurrent bind is blocked for the whole window.)

**What that option carries is the ADDRESS, and the first version — a boolean that rechecked `email_unverified` alone — closed only half of it.** The flag is set by the UNVERIFIED claim; the claim path deliberately also accepts a VERIFIED address that differs from the invited one, and that arm takes `adoptEmail`'s proven branch, which REWRITES `users.email` to the claimant's own address and sets the flag to **`false`**. So the row an invite resolved as `victim@corp.test` could become the claimant's, keyed under the claimant's address, with the flag clear — and a flag-only CTE saw a perfectly clean row and attached the membership to it. The same takeover, through the one arm the flag was never going to cover, and the follow-up re-read never ran because the INSERT had succeeded. The guard's predicate is now `email = <the address this caller resolved by> AND email_unverified = false`, an equality rather than `lower(btrim(...))` deliberately: it must be the SAME comparison `resolveByProvenEmail` used to pick the row, or the guard can pass on a row that lookup would never have returned. A zero-row result is therefore "somebody bound this address while we were deciding", and the route's re-read tells the three cases apart because their remedies differ — `unverified_address_holder` (the address resolves to somebody who has not proven it; they verify), `address_rebound_during_invite` (a verified claim took the address, nobody is waiting on a verification, so send it again), and the ordinary #280 membership conflict. Pinned in `test/integration/repositories/user-email-proof.test.ts`: reverting the predicate to the flag alone fails exactly the two attack cases and nothing else.

**The flag is set only while ACTIVATING A STUB, and setting it unconditionally was a way to REVOKE an established proof.** `adoptFirebaseIdentity`'s stub predicate admits two shapes and they mean opposite things for this column: activating a `pending_` stub keys a row under an address the identity has not proven, while re-binding a row whose `firebase_uid` is ALREADY this identity changes nothing and hands nothing over — that is the ordinary second-workspace claim by somebody who already has an account here, and their address may have been proven long ago. Flagging that arm too meant one unverified claim could strip a proven address out of `POST /users/invite` and both super-admin provisioning routes. The **phone-auth** form was unrecoverable: it carries no address, so `clearEmailUnverifiedIfProven` can never run and the proof was gone for good. `true` is therefore a REQUEST to flag, honoured by a `CASE` in the statement itself (`WHEN starts_with(firebase_uid, $7) THEN true` — the right-hand side of `SET` reads the OLD row, so it asks what the row was BEFORE the bind); a read beforehand would be the fetch-then-check this file closes everywhere else.

**A mismatched claim also REWRITES `users.email` to the bound identity's address (`adoptEmail`), and without that the pair is an identity swap.** The bind used to write `firebase_uid` alone, leaving the row keyed under the INVITED address while naming the CLAIMANT — and `POST /auth/session` path 2 finds a user BY that column and adopts unconditionally, with no `onlyUnclaimedStub`. (`sessionLinkEmail` now refuses unverified tokens before that lookup, which closes the email/password-without-inbox race; this is the remaining *verified*-token case.) So anyone who could present a verified Firebase token for the invited address took the claimed membership over and locked the agent out, silently. The old justification — "Firebase's one-account-per-email rule stands behind path 2" — does not cover it: that rule keys on the Firebase account's email, not on a `users.email` column this bind deliberately left stale. Consequences, all deliberate: `membership_invites.email` keeps the address AS INVITED (that is the audit record); and since `users.email` has only a non-unique index this can never raise a constraint error but CAN leave two rows sharing an address, which is why nothing on the claim path resolves an identity from one. **Read the rest of this paragraph as scoped to a VERIFIED claim**, which is the only kind that rewrites the column since migration 073 — there, a later sign-in with the invited address finds no row and falls to **path 4**, provisioning a fresh tenant for what is genuinely a different person. On an UNVERIFIED claim — the common shape — the invited address STAYS on the row and the flag is set instead, so path 2 still finds it and adopting is still correct: whoever arrives with a verified token has proven the inbox, which is exactly the claim the flagged row could not make. Composed in `test/unit/auth/invite-claim-session-composition.test.ts`, because each half is defensible alone and neither suite could see the pair.

**One live token per membership is enforced by the SCHEMA, not by the order of two statements.** `POST /invites/resend` used to revoke and then issue as separate autocommit operations, so two concurrent resends could both revoke before either inserted and leave two working links — the one thing a resend exists to prevent. The revoke now rides inside the insert's transaction (`membershipInviteRepository.createSupersedingOutstanding`, reached through `issueInvite`, so every issuing path gets it including the first invite, where it is a no-op), and because a transaction alone cannot fix it — under READ COMMITTED the loser's revoke re-evaluates and does not see the winner's new row — migration 069 carries a **partial unique index** `uq_membership_invites_live` on `membership_id WHERE claimed_at IS NULL AND revoked_at IS NULL`. The loser's `23505` becomes `LiveInviteConflictError` and then a 409 naming what happened, never a masked 500; a `token_hash` collision from the same statement is deliberately NOT matched by that predicate and stays a genuine error.

**Rate limits are the only abuse control on the two public routes** — a dedicated 20/minute IP bucket (`PUBLIC_INVITE_RATE_LIMIT`), applied through `@fastify/rate-limit`'s route `config` the way `POST /contact` and `POST /super-admin/login` are. Its realistic job is not enumeration (256 bits from a CSPRNG is not walkable) but the mundane one: the claim route calls Firebase token verification on every request, so an uncapped POST turns an unauthenticated endpoint into an outbound amplifier against a third party we are rate-limited by. **`RATE_LIMIT_ENABLED=false` makes it inert**, silently — `registerRateLimit` returns before registering the plugin, so every per-route bucket goes with the global one. The flag keeps its semantics (an incident lever needs to be one switch with no exceptions); the consequence is documented on the flag itself and in `.env.example`.

Config: `INVITE_TOKEN_TTL_DAYS` (default 7, bounded 1–90 — a TTL of 0 mints links already expired when the mail is sent, and a year-long one still works after the person has left) and the `brand` block (`PLATFORM_BRAND_NAME`/`ACCENT`/`LOGO_URL`) the email renders with. The accent is regex-validated as `#RRGGBB` because it goes straight into an inline `style` attribute in mail sent outside the tenant.

The two gates are independent: enabling either alone reaches nothing, which is the most likely "I turned it on and nothing happened" ticket.

*The capability is asserted on four paths, and the count is the point* — the catalog declares `api` enforcement, and that declaration is only true if none is missed. `/proxy/messaging/messages` and the discovery passthroughs, `POST /threads/follow-up`, automation create/update/dry-run, **and the automation queue consumer**. The consumer is the one that matters most and is the easiest to miss: it fires *stored* actions with no request to 403, so without a check there an action saved while the capability was on keeps posting after it is turned off — the off switch would not govern the surface it exists for. It fails the run with `group_capability_disabled` and makes no send. Parent-gating substitutes nowhere, because `messaging.whatsapp_personal` must be **on** for the tenant to hold a personal connection at all. The key lives in `governance/capability-keys.ts` — a deliberately import-free module, **not** `require-capability.ts`, because 25 test files mock the latter with explicit `vi.mock` factories and Vitest fails a mocked module the moment production code reads an export the factory does not list (the same hazard core's CLAUDE.md records for its telephony `factory.ts`).

*Groups are refused on every fan-out path rather than chunked.* `group_ids` is a recipient list that cannot be sliced: it is the same 1..10 targets for the whole request, so any path that rebuilds a body per chunk sends each group message once per chunk. `checkGroupTargeting` 400s the combination of `group_ids` with a `contact_list_id`, with a recipient list above `SQS_BULK_DISPATCH_THRESHOLD` (default 5), or with `recipient_variables` (a group has no single contact, so `{{contact_name}}` would ship as a visible placeholder); `withoutGroupIds` strips the key from every snapshot as the structural backstop. "Send the groups on the first chunk only" was considered and rejected: `buildChunkBody` receives no chunk index, the queued path spreads the snapshot in shared `batch-executor` code, and SQS redelivers — so it is neither reliably once nor reliably at-least-once, while refusing is exactly-once by construction. **The practical consequence worth knowing: sending to a contact list *and* posting in a group is two requests.**

*Scheduling refuses them too, at three write paths and once at fire time.* `checkStoredGroupPayload` (`scheduling/group-payload-guard.ts`) is shared by `POST /proxy/schedules` and **both** recurring write paths — `executeRecurringInstance` copies a recurring `call_payload` onto every child schedule, so one stored value would fire forever. It rejects any *present non-empty* value, not just a non-empty array: a bare string sailed through an `Array.isArray` check, got stored, and then depended on the fire-time strip running on whichever path it took. `call_payload` is an open `z.record(z.unknown())` on all three routes, so none of this can be a schema rule. The fire-time strip lives at the **top of `executeSchedule`, before the SQS-vs-chunked fork** — inside `dispatchChunked` it covered one branch of two, leaving every schedule above the SQS threshold producing exactly the duplicate blast the guard exists to prevent.

*Billing counts a group as one recipient.* One group message is one `greenapi_messages` row and one `whatsapp_message` credit regardless of member count, so `countMessagingRecipients` sums `phones + group_ids`. That helper exists specifically so `/threads/follow-up` bills like a bulk send; it read only `phones`/`recipients`, so a group-only follow-up hit the absent-array fallback and reserved **1 credit for up to 10 sends**. The `|| 1` floor applies to the empty case only, never to the sum.

*Automations carry `to_type?: 'phone' | 'group'`*, deliberately optional so stored automations need no migration (**absent means `phone`**). One action is one recipient, so an automation never emits both keys. Because a trigger supplies exactly one context, `{{callee.name}}` in the body still resolves for a group send — that is the primary use case, not a caveat. The dispatched value is **trimmed**: `validateRenderedTo` trims before matching, so a template emitting trailing whitespace passed validation and then 400'd at core's anchored `@g.us` schema.

Every route requires the `knowledge_bases` capability plus RBAC (`proxy.knowledge_bases.read` for GET, `proxy.knowledge_bases.write` for mutations). JSON CRUD via `proxyToCore`; file uploads stream through an isolated `@fastify/multipart` sub-plugin (re-adds session/tenant/capability hooks).   **Record filters** (all four routes): `status` (comma-separated, per-offering allow-list), `direction` (`ai_calls` only), `spoken_seconds_min`/`spoken_seconds_max` (call offerings only). **Master mirrors only the shape** — the allow-list and every cross-field rule (direction on the wrong offering, spoken-seconds on `messages`, min > max) belong to core, which 400s. Three things master must nonetheless do itself, because it sits upstream and core's own guards never see the raw input: a **blank/whitespace-only value is dropped, not coerced** (`z.coerce.number()` turns `''` and `'  '` into `0`, so a forwarded `"0"` becomes a real `spoken_seconds <= 0` bound and the CSV comes back holding only unconnected rows); the numeric bounds are capped at **int4 max** (a typo'd extra digit otherwise reaches Postgres and returns as a masked 500); and the query schemas are **`.strict()`**, so an unknown param is a 400 rather than a silently stripped filter — a stripped filter is whole-period totals rendered under a "Filtered view" heading. That last guard is partial by construction: it cannot help when an *older* master (pre-`.strict()`) receives newer params, and the filter-echo handshake that would close it was deliberately not built.

  **Error surfacing is not uniform, and the split is the mask's `details` rule** (`errorMaskHook`): core's filter/shape 400 is `{ error: 'Validation Error', details: [...] }`, so it reaches the operator intact — offending value and valid-value list included. Core's semantic period 422 is `{ error: 'Invalid Period', message }` with **no** `details` and no allow-listed label, so only the **422 status** survives; the wording is masked into the generic support message and logged. Master's own 502 is likewise masked (5xx always is).

  **Audit:** `usage.viewed` / `usage.exported`, written **only on a 2xx from core** — a rejected query exported nothing, and a row written before the status was examined is indistinguishable from a successful export in the one log that is supposed to be authoritative about it (it is also how a caller-supplied 500-char `status` reached `super_admin_audit_log.details` after failing validation). Failed attempts remain visible via the masked-error warn log (with request id) and `proxy_requests_total`. `details` carries `tenant_id`, `account_id`, `offering`, `from`, `to` plus the four filter keys `status` / `direction` / `spoken_seconds_min` / `spoken_seconds_max` (each `null` when absent) — which slice left the building matters as much as which period. The write stays fire-and-forget (`.catch(() => {})`): the audit must never fail the request.

Service Configuration saves that include `default_pipeline` (super-admin tenant settings, `PUT /tenants/:id`, account create/update) are mirrored into core's `account_settings.default_ai_pipeline` via `src/services/core-account-settings-sync.service.ts` (read-modify-write to preserve `max_concurrent_calls`), so inbound calls — which bypass magick-master — honor the workspace default.

### Agency Dialer — the agent read surface (authenticated + RBAC + `agency` capability)

**The floor is the whole design here.** `agent` is hierarchy level 5, *below* `viewer`, so it holds exactly the four `agency.*` permissions and nothing that predates the feature. Every agent-facing route therefore floors at **`agency.station.connect`**, and gating one on a `viewer`-floored permission — `proxy.contact_lists.read` is the tempting wrong answer, because the neighbouring campaign reads use it — 403s the exact role the route exists for. The supervisory twins floor at **`agency.supervise`** (`account_admin`), which an `agent` cannot reach; without that split, reading a colleague's dispositions and talk time would be open to every agent.

`proxy-agency-performance.routes.ts` (thin proxies to core's per-agent endpoints):
- `GET /proxy/agency/my-stats` — the caller's own scorecard, verbatim from core (`totals` with connect/success rates, AHT, occupancy by state; `buckets[]`; `by_campaign[]`). Query `from`/`to`/`bucket`/`campaign_id`
- `GET /proxy/agency/my-attempts` — the caller's own attempt page (`{ rows, next_cursor, limit }`). Query `outcome`/`state`/`disposition_code`/`campaign_id`/`from`/`to`/`cursor`/`limit`
- `GET /proxy/agency/agents/:userId/stats`, `GET /proxy/agency/agents/:userId/attempts` — the supervisory twins. `agent_name` is added by master (core has no user table, D3) and degrades to `null` rather than 500ing; the subject is proved against `memberships` in this tenant first, answering **404, not 403**, for a foreign or unknown id — core treats `agent_user_id` as an opaque string and cannot refuse a foreign one on master's behalf. That proof uses **`membershipRepository.findAnyByUserAndTenant`, which does NOT filter `status`**: offboarding sets `revoked`, so the active-only lookup answered "not a member of this workspace" for exactly the departed agent a dispute is about. Same deliberate choice, same reasoning, as `userRepository.findDisplayNamesInTenant` — which already names revoked members on these payloads. The tenant predicate is untouched, so a user who was never in the tenant is still refused
- `GET /proxy/agency/agents/stats` — **the ROSTER read** (phase 01 of the supervisor console): one row per agent who dialled in the window, plus the cohort `benchmark` (pooled rates *and* p25/median/p75, computed by core) that makes a single row readable. `agency.supervise`. Query `from`/`to`/`campaign_id`/`sort`/`order`/`limit` forwarded to core — the ranking is core's, because sorting in master would sort what `limit` had already discarded — plus `include_inactive`, which is **master-only and never forwarded** (declared `consumedByRoute` on `forwardAllowedQuery`, so it is neither refused nor silently dropped). `agent_user_id` is not accepted: the subject is the whole roster, and the compare surface is phase 02.
  **`request.accountId` is REQUIRED** — a missing `X-Account-Id` is 400 `account_scope_required`, not a tenant-wide read; a tenant-wide roster is a deliberate future mode and must not be reachable by leaving a header off. **This is defence in depth, not the only thing in the way — the read would NOT “silently widen to every account in the tenant” without it,** which an earlier version of this entry (and of the route's docstring) claimed. `proxyToCore` does omit the account header when master has none, but core's `authMiddleware` requires it on every authenticated route and answers 400 `Missing required header: x-mgkvc-account` before any core handler runs. What master's own check buys is the message and the cost: a named `account_scope_required` the console can act on rather than core's header complaint, which `errorMaskHook` rewrites into “contact support” (a core-forwarded 4xx with neither `details` nor an allow-listed `code`); and no per-tenant key decryption and no S2S round trip spent on a request that cannot succeed. (It used to claim a third merit — “and it holds on the platform-API-key branch too” — which the actor guard below has since made unreachable: every platform key is refused one line earlier, so no credential-authenticated request gets as far as this predicate on these two routes.) (The `:userId` twins above are narrowed to one tenant-checked person and carry no check of their own — core's header requirement answers an unscoped one there.)
  **EVERY platform API key is refused here — 400 `missing_actor` — on the same `isPlatformApiKeyCaller` predicate the `my-*` routes use.** `rbac.middleware.ts` opens with `if (request.apiKeyTenantId && !request.user) return;`, so a key with no `created_by` user is waved past *before* `agency.supervise` is ever evaluated: the floor is correct and never consulted, and one GET with a tenant-scoped system key would return the whole floor's ranked scorecard with no role, no user and no audit subject. A credential that names nobody cannot hold a permission whose purpose is authorising action on somebody else's work, so the roster closes the door at its own call site (the platform-wide fix in `rbac.middleware.ts` is a separate, much larger change). **The condition was at first deliberately narrower — userless keys only — and that was wrong.** The argument for admitting a creator-backed key is that `sessionMiddleware` loads `platform_api_keys.created_by` into `request.user`, so `requirePermission` makes a real `account_admin` decision about a real person: all true, and about the wrong person. `created_by` is provenance of the credential, not the identity of whoever holds it now (the same correction `resolveMyAgentId` and `resolveAgencyActor` already carry), so a key pasted into CI or leaked from a laptop read **the whole floor as its creator**, with the audit trail naming somebody who did not make the request. An integration that wants this read presents a session. Knock-on: no key-authenticated request now reaches the account predicate on these two routes at all, so R5's “and it holds on the platform-API-key branch” is unreachable rather than untrue — strictly stronger, and the tests say so out loud.
  **The core call carries a wall clock**, `ROSTER_CORE_TIME_BUDGET_MS` (30s, exported from the route module) — the same reader-facing number and the same argument as `ACTIVITY_EXPORT_TIME_BUDGET_MS`: the roster runs an attempt aggregate plus an occupancy read over every agent state transition in the window, two long statements in series, and core has **no `statement_timeout`**, so with no `timeoutMs` the call inherits undici's 300s header timeout. Expiry is not caught: it reaches Fastify's `errorHandler` as a `statusCode`-less `TimeoutError` and the client gets a 500 that `errorMaskHook` has already replaced with the generic support body, so nothing internal leaks. Master has no 504 convention anywhere and this route does not invent one.
  **Departed agents are master's decision.** Core returns every agent who dialled — `agent_user_id` is opaque to it (D3) — so master drops rows whose membership here is `revoked`/`inactive`, keeps them under `?include_inactive=true`, and reports `inactive_omitted` either way so a short list is never silently short. **“Still here” is answered against the ACCOUNT the read is scoped to, not the tenant**: an agent revoked from this account is a departure from this page even while active on an account the supervisor cannot see, and a tenant-level membership (`account_id IS NULL`) reaches every account and counts. Ids are compared case-insensitively on both sides — `memberships.user_id` is a Postgres `uuid` and comes back lower case, while core's `agent_user_id` is an opaque string, and an upper-case id matched in SQL (`= ANY($1::uuid[])`) and then missed a case-sensitive `Set`, dropping a working colleague as `unattributed_omitted`. **The filter is gated on `Array.isArray(body.rows)` (`pageRows`), never on `asSpinePage`**: that is the CURSOR-page narrowing and it refuses a body whose `limit` is not a number — `limit` is a query param, so a core echoing `?limit=50` back as `'50'` made a real page skip the filter entirely and report `inactive_omitted: 0` on a page that had hidden people. Serve unfiltered only when there is genuinely no row array. One membership read for the whole page (`membershipRepository.findAnyByUsersAndTenant`, the set form of `findAnyByUserAndTenant`, status RETURNED rather than filtered), never one per row. Three states, not two: no membership row of any status is *not* a departure, is dropped under either flag, and is reported as its own top-level `unattributed_omitted` as well as logged. Never folded into `inactive_omitted` (reporting a stranger as a departed colleague is a different lie from hiding one) and never withheld either — a row that vanishes with no counter behind it makes the console's reconciliation arithmetic wrong with nothing on the wire to say so. It is reachable, not theoretical: core keeps attempt history forever while a `memberships` row goes away with the user. Unlike the name lookup, this read is **not** degraded: serving departed agents with `inactive_omitted: 0` is a payload that states, falsely, that nothing was hidden.
  **The `benchmark` is never recomputed or touched.** Its cohort is the floor as it actually was that week, revoked members included; `include_inactive` controls which ROWS come back, not what they are measured against, and a number that moved when a row filter was toggled would be two numbers under one name. `total_agents` likewise stays core's pre-`limit`, post-scope count. Master adds exactly three things to the frozen phase-01 payload, all of them ADDITIONS (the one kind of change the freeze permits): `agent_name` per row (through the same `enrichAttemptAgentNames` the campaign spine uses — one query per page, degrading to `null` with a warn), and top-level `inactive_omitted` and `unattributed_omitted`.

- `GET /proxy/agency/agents/grouped-stats` — **the GROUPED read** (phase 02a): one general aggregate over agency dial attempts, grouped by 1 or 2 caller-chosen dimensions (`agent`, `campaign`, `disposition`, `day`, `day_of_week`, `hour_of_day`), so the console answers "who drove this campaign", "which hours connect" and "how does this agent's week trend" without a route per question. A SIBLING of the roster rather than a `group_by` on it: `AgencyRosterAgentRow` is keyed on `agent_user_id` and the roster's payload is frozen, so a campaign- or hour-grouped row would make a frozen `rows` polymorphic. Rows are `{ key, attempts, connected, successes, talk_seconds, wrapup_seconds, connect_rate_pct, success_rate_pct, aht_seconds }`; `key` carries a member **iff** its dimension is grouped. Same gate as the roster (`agency.supervise`, `account_admin`, capability `agency`), same required `X-Account-Id` (400 `account_scope_required` before `resolveCoreApiKey`), same platform-key refusal (400 `missing_actor` for EVERY key, `isPlatformApiKeyCaller`), and the same `ROSTER_CORE_TIME_BUDGET_MS` — shared, not a second constant with one value; core has no `statement_timeout` and this read's row count is the PRODUCT of the grouped cardinalities where the roster's is bounded by headcount. Query `from`/`to`/`campaign_id`/`group_by`/`sort`/`order`/`limit` forwarded, `include_inactive` master-only (`consumedByRoute`), `agent_user_id` refused.
  **`group_by` is forwarded UNPARSED.** The vocabulary, the 1-or-2-dimension cap (`too_many_dimensions`), the canonicalisation of the order, the `[from, to)` 92-day window and the rule that a time dimension across campaigns in different zones is **400 `timezone_ambiguous`** (buckets are cut in the CAMPAIGN's own zone, so "the 18:00 column" is not one thing across zones — and there is deliberately no `tz` param and no implicit UTC fallback) are all core's, because core is where the rows are grouped. A second parser in master is a second definition of the same enum and the copy that drifts is the one no query exercises.
  **The membership filter is CONDITIONAL, and master reads the condition off the ROWS.** Departed agents are dropped only when `agent` is grouped, because that is the only case in which a row is *about* a person; `inactive_omitted` and `unattributed_omitted` are both emitted on every path, including the not-grouped one (`0`/`0`, truthfully) and the no-row-array degrade path — the second one is what makes the reconciliation gap below quantifiable rather than merely narrated, since on an `agent,campaign` page one unaccountable id drops one row per campaign. Whether `agent` was grouped is decided by `groupedRowHasAgentKey` — `Object.hasOwn(key, 'agent_user_id')`, i.e. the key's SHAPE — not by re-parsing the caller's `group_by` (a fork of core's canonicalisation) and not by trusting core's echoed `group_by` (a field no row is keyed to). **Shape, not the id's usability, and the two are different tests**: while the branch was chosen by `groupedRowAgentId(row) !== null`, a page whose only agent keys were empty strings, nulls or numbers looked *not* agent-grouped and was served unfiltered with both counters at 0. `groupedRowAgentId` stays the per-ROW value extractor, and a present-but-unusable id is R4's third state (dropped, counted in `unattributed_omitted`). An EMPTY page still takes the pass-through branch, which is the right answer and spends no database read.
  ⚠️ **The reconciliation asymmetry, which is not a bug and which a console must not present silently.** A campaign-grouped total INCLUDES a departed agent's attempts — the row is an aggregate over everyone who dialled and there is nothing to drop — while an agent-grouped view of the same campaign EXCLUDES them by default. The two do not add up, and the difference is exactly the departed agents' work. `include_inactive` is meaningful only when `agent` is grouped. Pinned on one fixture with both groupings in `test/unit/agency/proxy-agency-grouped-stats.routes.test.ts`, because it is counter-intuitive enough that a future reader will "fix" one number to make the other agree.

**The agent id on a `my-*` route is `request.user.id`, taken server-side, and the query whitelist is the mechanism rather than a convention.** `forwardAllowedQuery` copies only the named params, so an `?agent_user_id=` never reaches core even as an ignored extra — a route that honoured one would be a full read of any colleague's history while passing every floor assertion. A platform API key proves a TENANT and names no caller, and RBAC waves it past, so `my-*` routes answer 400 `missing_actor` (the shared `resolveMyAgentId` → `replyMissingActor`) rather than answering for an arbitrary agent. **The refusal keys on `request.apiKeyTenantId`, never on a missing `request.user`** — "a key carries a tenant and no user" was written all over this feature and is false: `sessionMiddleware`'s API-key branch loads `platform_api_keys.created_by` into `request.user`, so a key minted by a person authenticated carrying that person and every `if (!request.user?.id)` guard answered with the KEY CREATOR's own scorecard, attempts and staffing history. Only a NULL-`created_by` system key was ever refused, which is the one shape the tests modelled. `created_by` is provenance of the credential, not the identity of whoever holds it now. The same correction applies to `resolveAgencyActor` (`src/agency/agency-actor.ts`), where a creator-backed key dispositioned a customer in the creator's name — with `on_behalf: true` when they hold `agency.supervise`.

`proxy-agency-staffing.routes.ts` also serves `GET /proxy/agency/my-campaigns` — the agent's full staffing HISTORY from `agency_campaign_agents`, **closed rows included** (`{ campaign_id, campaign_name, campaign_status, assigned_at, unassigned_at, active }`, newest first). Migration 060 closes rows rather than deleting them precisely so "who was staffed here in March" stays answerable, and until this route every reader carried `unassigned_at IS NULL` — the history was stored and unreadable. It reads a separate repository method (`listAllForUser`), never a flag on `listActiveForUser`, whose callers all want active-only: the landing-page picker must not offer a campaign the agent was taken off. **Bounded in three places**, because closed rows only accumulate (`closeAllForUser` manufactures one per campaign, nothing ever deletes) and the route is reachable by an `agent`: a hard `LIMIT` (`HISTORY_LIMIT_MAX`) no query param can raise, an optional `from`/`to` window on `assigned_at` so the rows past the ceiling stay reachable by period (the shape the repository docstring nominated — a period, not a cursor, is what this question is always about), and a cap on the DISTINCT campaigns whose names are resolved (`SUMMARY_LOOKUP_MAX`; rows are newest-first, and beyond it `campaign_name` is `null`, which is this route's documented normal path anyway). Each summary lookup carries `SUMMARY_TIMEOUT_MS` — without a `timeoutMs` a proxy call inherits the process-wide dispatcher's **300s** default. Truncation is reported as `X-Staffing-Truncated: true`, a header rather than a body key, because the customer UI reads `assignments` and a previous defect here rendered every agent's history empty.

**Offboarding closes staffing (`user.routes.ts`).** `DELETE /users/:id/membership` and a `PUT /users/:id/role` that moves someone *away from* `agent` both call `agencyCampaignAgentRepository.closeAllForUser`, writing one `agency_campaign_agent.unassigned` audit row per closed assignment with `details.reason`. **Each row is stamped with the ASSIGNMENT's `account_id`, never the actor's** — the close spans every account in the tenant while `GET /audit-log` is account-scoped (`auditAccountScope`), so a single actor-supplied account filed the whole batch under whichever account the offboarding admin had selected and the `account_admin` whose roster changed saw nothing; and this route floors at `tenant_admin`, for whom omitting `X-Account-Id` is legal, which made every row account-less. A NULL on the assignment stays NULL (a tenant-level member writes NULL into that column) rather than being back-filled from the actor. Before this, nothing in master called any bulk unassign and a departed agent stayed on every supervisor's staffing list forever. Three rules: **staffing is not authorization** (a closed row revokes nothing — migration 060's header), so this runs LAST, after the authoritative write and the cache invalidation, and its failure is logged and swallowed rather than failing the membership change; the role predicate is `from === 'agent' && to !== 'agent'` and must stay that narrow, because supervisors can legitimately be staffed and an unrelated promotion must not unstaff them; and a demotion is skipped while another `agent` membership survives in the tenant, since this route changes one membership of possibly several.

## OpenTelemetry (`src/instrumentation.ts`, `src/utils/tracing.ts`)

Distributed tracing matching the voice-core setup. Conditional on `OTEL_ENABLED=true` + `OTEL_EXPORTER_OTLP_ENDPOINT`, and off under the standard `OTEL_SDK_DISABLED=true` (`resolveOtelExportMode` in `metrics-pipeline.ts` decides once, for traces, logs AND metrics — NodeSDK honours the variable on its own, but the OTLP metrics reader is the pipeline's, so without that gate the kill switch would have left metrics exporting). `OTEL_ENVIRONMENT` must be set per deployment: it is `deployment_environment`, which every alert groups by, and its `NODE_ENV` fallback is `production` on staging too. `OTEL_NODE_RESOURCE_DETECTORS` is ignored by design (see `service.instance.id` below).

- `src/instrumentation.ts` — Loaded first by `src/bootstrap.ts` (the entry point for `npm start`, `npm run dev` and the Docker image), which then imports the app dynamically. Creates the metrics pipeline (below) in both modes, and when OTel is enabled bootstraps NodeSDK with auto-instrumentation (HTTP, pg, ioredis, undici, openai, Pino — **traces and the log bridge only**, see below) and OTLP exporters (http/protobuf for Grafana Cloud). The instrumentation set is built by `src/utils/otel-instrumentations.ts` (so a test can construct exactly what production runs); `instrumentation.ts` is a side-effecting boot script and cannot be imported.
- `src/utils/tracing.ts` — Manual span helpers: `withSpan()`, `startSpan()`, `getActiveSpan()`. Same API as voice-core.
- **Cross-service propagation**: `proxyToCore()` injects W3C `traceparent` headers via `propagation.inject()`, so traces span magick-master → voice-core.
- **Log correlation**: Pino instrumentation auto-injects `trace_id` and `span_id` into all log records.
- **Metrics — one pipeline, one instrument per metric** (`src/utils/metrics-pipeline.ts`, `src/utils/metric-instruments.ts`, `src/utils/metrics.ts`). Every counter and histogram is a single OpenTelemetry instrument on a MeterProvider the pipeline module owns, and every gauge a single snapshot the pipeline appends to each collection, both read by two readers: a Prometheus reader rendered on demand for the local `:9091/metrics` scrape (`config.metrics.port`; served whether or not OTel is enabled, never shipped anywhere), and — only when `OTEL_ENABLED=true` + an endpoint — an OTLP `PeriodicExportingMetricReader` that is Grafana Cloud's only feed. There is no prom-client and no `otel*` twin: record once. Five things are load-bearing:
  - **Instruments come from the pipeline's provider, never `metrics.getMeter()`.** The API has no proxy provider, so a meter taken before the global is registered is a silent no-op forever; the pipeline is created on first use, and it is deliberately **not** registered as the API global (see the next point). What ordering still decides is only whether the OTLP reader is attached — sdk-metrics 2.x takes readers at construction — so `instrumentation.ts` calls `initMetricsPipeline` before the app graph loads, and a pipeline that already existed is reported at `console.error` ("OTLP METRICS EXPORT IS OFF") rather than silently local-only. Pinned by `test/unit/utils/metrics-pipeline.wiring.test.ts`.
  - **Every histogram declares its buckets** (`advice.explicitBucketBoundaries`); without it the SDK default is 0..10000, which for values in seconds put every sub-5s request in one bucket (Grafana p50≈2.5s for everything). API/proxy latency: `[0.01,0.025,0.05,0.1,0.25,0.5,1,2.5,5,10]`.
  - **Application gauges are last-value snapshots that each reader reads on its OWN collection, not SDK instruments** (`withSnapshotGauges` in `metrics-pipeline.ts`: it wraps each reader's public `collect()` and appends the snapshots to the `magick-master` scope). That is what makes `reset()` drop a label set on both readers. As SDK observable gauges it did not, in either of two ways: under cumulative temporality sdk-metrics re-reports every attribute set it has ever observed; and even under DELTA it runs an observable's callback on each reader's collection but records the result into EVERY reader's storage, so a set dropped by `reset()` lingered in whichever reader had not collected since — measured: set a,b → OTLP export → `reset()` → set a, and `/metrics` still rendered b; the reverse put one stale point into the next OTLP export. Draining by collecting the local reader was rejected for the runtime-collector reason below. Consequences: the `collect` refresh hook runs on every collection of every reader (and on `Gauge.get()`); the reader's temporality/cardinality selectors do not reach these gauges, so the pipeline caps each at `METRIC_CARDINALITY_LIMITS.gaugeSnapshot` on its CURRENT snapshot (a `reset()` frees slots); and `withSnapshotGaugeTemporality` (DELTA for SDK observable gauges) now only concerns the three runtime gauges. Pinned by `test/unit/utils/metrics-pipeline.gauges.test.ts` with both readers attached. A gauge whose value is an external measurement (`dnc_publish_lag_*`, `bulk_dispatch_capped_jobs_blocked`, `provider_concurrency_unsynced_accounts`) is ABSENT until first set, never a placeholder 0 — and the DNC lag gauges go back to absent when a refresh fails (`clearDncPublishLag`), because a snapshot is re-exported with a fresh timestamp on every collection and a kept value would read as current; `mm-dnc-lag-unmeasured` pages on that absence per environment.
  - **What reaches the readers is an ALLOW-LIST, and the provider has NO views — both because a view leaks.** Exactly two things record on the pipeline: the application instruments (meter `magick-master`) and `instrumentation-runtime-node`, which is handed `pipeline.runtimeMeterProvider` (`allowlistedMeterProvider`: real instruments for `KEPT_RUNTIME_INSTRUMENTS` — `nodejs.eventloop.delay.p99`, `nodejs.eventloop.utilization`, `v8js.memory.heap.used` — and API no-ops for the other ~14). Every auto-instrumentation is handed `TRACES_ONLY_METER_PROVIDER` (a no-op), and `instrumentation.ts` re-pins it **after** `sdk.start()`, because `start()` runs `registerInstrumentations`, which resets every instrumentation to the API global meter provider. Views are ruled out for two measured reasons, and it is worth being exact about which one was ever live: **(1) with two readers a view is an unbounded heap leak** — sdk-metrics gives a view-matched instrument ONE storage shared by every reader (`MeterSharedState._registerMetricStorage`), and `TemporalMetricProcessor._stashAccumulations` queues each collection's accumulation for every OTHER reader until that reader collects; the local Prometheus reader collects only when `/metrics` is rendered, which production never does (and `METRICS_ENABLED=false` makes impossible), so every DROP-matched http/undici/pg/runtime instrument and every kept runtime gauge leaked one map per OTLP export — 117–140 MB/day of heap on realistic http+pg traffic (140.5 MB over 1,440 one-minute cycles in the probe), 0.5 MB and flat after. That leak was introduced by this overhaul's own first cut (`c322e8e`: pipeline = global + keep/DROP views on two readers) and fixed before merge — **main never had it**: main's DROP views sat on NodeSDK's single OTLP reader beside a separate prom-client registry, and a lone reader has no other reader's stash to grow. **(2) a drop-list ships what it does not name** — that one WAS live on main: its DROP list (`http.*`, `db.client.*`, `rpc.*`, `nodejs.*`, …) never named openai's `gen_ai.client.operation.duration` / `gen_ai.client.token.usage`, which reached Grafana. Without a view every instrument gets one storage PER reader, so an unscraped reader costs bounded memory (its delta map holds at most the cardinality limit of sets) and nothing grows with time. **Do not add a view to this provider, register it as the global, or hand it to a third-party instrumentation** — filter at the source instead. `test/unit/utils/metrics-pipeline.isolation.test.ts` pins all of it against the real instrumentation set and both readers (collect one reader 40×, assert the other's stash never grows; only app metrics + the three runtime gauges render; a real global plus `registerInstrumentations` is undone by the re-pin). prom-client's `collectDefaultMetrics` series (`process_*`, `nodejs_heap_*`, `nodejs_eventloop_lag_*`) no longer exist.
- **Metric export interval** defaults to **60s** (`OTEL_METRICS_EXPORT_INTERVAL_MS`); Grafana Cloud bills per data point per minute, so 30s cost ~2x. Every `rate()`/`increase()` must therefore use `$__rate_interval` (or ≥ 2m), never `[1m]`.
- **Stable `service.instance.id`** (Grafana's `instance` label), first non-blank of: `OTEL_SERVICE_INSTANCE_ID`, `service.instance.id` in the standard `OTEL_RESOURCE_ATTRIBUTES`, `os.hostname()` (`resolveServiceInstanceId`). **This label is NEW with the metrics overhaul**: before it NodeSDK ran its default detectors — `[env, process, host]` in sdk-node 0.213 — so series carried no `instance` at all and there was no restart churn; the first deploy of this code therefore rotates every series ONCE (a break in any panel spanning the deploy), not on every restart. The id must stay stable (every distinct value is a new set of series) and unique per running copy (two copies with one id write one set of cumulative series and corrupt every `rate()`). NodeSDK merges detected resources OVER the configured one, so `instrumentation.ts` passes the pipeline's resource with `autoDetectResources: false`: with `OTEL_NODE_RESOURCE_DETECTORS=all` (or one naming `serviceinstance`) the SDK's `serviceInstanceIdDetector` would otherwise stamp a per-process UUID over it and THAT would churn every series on every restart. `docker/docker-compose.yml` sets `hostname: ${OTEL_SERVICE_INSTANCE_ID:-magick-platform}` because a container's default host name is its id, new on every recreate; the fallback suits exactly one copy of the stack per `deployment_environment`, so a second host needs its own `OTEL_SERVICE_INSTANCE_ID`.
- **Final telemetry flush is the LAST step of `index.ts`'s graceful shutdown** (`src/utils/telemetry-shutdown.ts`): `instrumentation.ts` only registers `sdk.shutdown()` + the OTLP reader's shutdown, and `shutdown()` awaits `shutdownTelemetry()` after the drain and `closePool()`, right before `process.exit(0)`, bounded by 5s (`TELEMETRY_SHUTDOWN_TIMEOUT_MS`) and never throwing. `instrumentation.ts` used to start that export from its own SIGTERM handler, in parallel with the drain, so metrics recorded while draining were never exported and the export raced the exit. Do not add a signal handler there.
- **Manual spans**: `proxyToCore()` (SpanKind.CLIENT), `credit.reserve`, `credit.settle`, `settlement.call`.

## Product Analytics (`src/analytics/posthog.ts`)

PostHog product/business analytics — a thin, fail-safe layer over `posthog-node`. Disabled by default; gated on `POSTHOG_ENABLED`. When off, the client is never constructed and every emitter is a no-op. `initAnalytics()` runs at startup in `src/index.ts`; `shutdownAnalytics()` flushes during graceful shutdown. Designed for **PostHog Cloud**, sharing the **same project** as voice-core for a unified cross-service view.

**Identity (richer than voice-core, which only knew account_id):** `distinct_id = userId ?? accountId ?? tenantId` (real user for authenticated actions; falls back for S2S/webhook events). Every event is attached to **two groups** — `tenant` and `account` (account omitted when absent) — whose keys match voice-core exactly, so both services roll up under the same tenant. Every event also carries an `environment` property (`POSTHOG_ENVIRONMENT`, falling back to `NODE_ENV`).

**Group names for filtering:** `identifyGroups()` sets the tenant/account **display name** as a PostHog *group property* (`name`) so insights can be filtered/broken-down by name, not just opaque id. Group properties are global per group key, so a single identify covers every event already attached to that group — the name is never put on individual events. It's driven from `tenant-name-resolver.ts` (the same choke point that feeds the `x-mgkvc-*-name` core headers — HTTP requests via tenant-context middleware, plus background dispatch), de-duped per `{group, name}` for ~1h. The org display name is the one deliberate exception to the "no names on events" rule (it's a group property, and an org name — not contact/end-user PII).

**Scope = business framing only** (call-level events are owned by voice-core to avoid double-counting). All events are PII-free — only IDs, enums, counts, amounts, durations, booleans (never email/name/phone/ip/contact data). Emitters live in `src/analytics/posthog.ts` and are best-effort fire-and-forget:
- **Credits/billing** (emitted from `credit.service.ts`, covering both API and webhook-settlement paths): `credit_reserved`, `credit_settled`, `credit_released`, `credit_topup`, `credit_deducted`, `credits_allocated`, `credits_deallocated`. Amounts in millicredits plus a derived `credits` field.
- **Dispatch/campaigns**: `bulk_dispatch_job_created` (producer), `bulk_dispatch_job_completed` (repository — the single finalization choke point, covers webhook-driven completion too), `contact_list_uploaded`, `schedule_created` (one_time + recurring).
- **Automations**: `automation_created`/`automation_updated` (routes), `automation_execution_triggered` (`webhook-core.routes.ts`, per evaluated binding with `matched`), `automation_action_completed` (`workflow-action.consumer.ts`, terminal send/fail).

**Config:** `POSTHOG_ENABLED` (default false), `POSTHOG_API_KEY` (required when enabled), `POSTHOG_HOST` (default `https://us.i.posthog.com`), `POSTHOG_ENVIRONMENT` (default = `NODE_ENV`), `POSTHOG_FLUSH_AT` (20), `POSTHOG_FLUSH_INTERVAL_MS` (10000), `POSTHOG_REQUEST_TIMEOUT_MS` (10000).

**Test note:** importing the analytics module loads the real config (which `process.exit`s on validation failure in a bare env), so any unit test that transitively imports a hooked service must `vi.mock('.../analytics/posthog.js', ...)`. A *partial* posthog mock must include every export the code path touches — note `tenant-name-resolver.ts` now calls `identifyGroups`, so services that resolve tenant/account names (tenant-context middleware, scheduler, recurring schedules, bulk-dispatch consumer) need `identifyGroups: vi.fn()` in their mock (or to mock the resolver itself).

### AutoPilot (`src/autopilot/`)

A streaming, tool-using assistant over one editable thing at a time. Three surfaces today — the **call script** (core's prompt templates), an **automation** (master's own workflows) and an **IVR workflow** (core's) — each with its own endpoint pair under its own prefix. Gated on the shared `llm` config block plus `AUTOPILOT_ENABLED`; no per-surface flag.

**Nothing here writes.** The write tool's invocation is *terminal* and produces a `ValidatedProposal` the browser renders for the author to accept — the engine executes nothing on its behalf, on any surface. A save still goes through the ordinary CRUD route the author's own edits go through.

**The seam is `AutopilotSurface` (`types.ts`), not a registry.** The engine (`engine.ts`) owns the bounded agentic loop and knows nothing about prompts, automations or steps: stream a completion, relay prose deltas, reassemble tool-call deltas, run the surface's read tools, go round again — until the write tool is called, the model answers in prose, the turn budget is spent, or the caller aborts. A surface owns its system prompt, its tool set, how a read tool is answered, and how write-tool arguments become a proposal. Adding a fourth means one file under `surfaces/` and one route.

**Shared machinery, extracted when there was a second caller and not before:**
- `proposal.fields.ts` — the two-audience `DroppedField` (`reason` is the model's copy and the log's; `note` is the author's, and its absence is normal), the field-by-field loop, and the log-safe Zod issue formatter. **Field-level, never payload-level:** one bad member must not discard a good rewrite in the same payload, so each field carries its own schema and its own verdict, and an all-dropped proposal is still returned with the reasons.
- `api/routes/helpers/autopilot-routes.ts` — the SSE transport. Everything that can fail with a JSON body is checked **before** `reply.hijack()`; the abort listener is on the **response**, not the request (`IncomingMessage`'s `close` has already fired by the time the handler runs); and every emitted event goes through one `emitOrAbort` helper, so a turn that opens with a tool call cannot keep billing for a dead socket. Triplicating this would have meant three copies of those subtleties. `proxy-prompts-autopilot.abort.test.ts` asserts that wiring at the source level, because a behavioural test cannot tell which of the two mechanisms aborted.

**Grounding is the part schemas cannot do, and it fails CLOSED.** An id the model invented reads to the author as a resource they forgot they had, so the tenant's real inventory is fetched by the surface and an id that does not resolve is a dropped change with a reason. Inventory reads are Redis-cached for 60s — a **failed** read for 3s, because caching one transient core blip for the full minute poisoned grounding for every run in that tenant long after core was healthy.

**`buildProposal` and `runReadTool` must not throw, and the two ways they did are both closed.** The contract is in `types.ts` and `engine.ts` calls `buildProposal` unguarded, so a throw escapes `runAutopilot` as a generic `upstream_error` — costing the author the whole turn, including the rename in the same payload that needed none of the machinery that failed. (1) **Every inventory load is wrapped**, and reports `loadFailed`, which drops exactly the fields grounding would have checked and leaves the rest: a Postgres blip on the automation read, a Redis timeout in a capability lookup, a rejected core fetch. (2) **A value nested past `MAX_VALUE_DEPTH` (24) is refused before Zod sees it**, by an *iterative* check in `proposal.fields.ts`. `predicateSchema` is `z.lazy` around a union containing itself with no bound of its own, and the 64 KB tool-argument cap leaves room for ~1,300 levels of `{"op":"not","clause":{…}}` — that parse overflows the stack, and a `RangeError` is thrown rather than returned. 24 is generous: the deepest legitimate value on any surface is an automation's `actions` at 13.

**Every reason a field was refused is reported, not the first.** The grounding checks used to run in sequence, each `delete`-ing the field on failure, so every check after the first was skipped — a proposal whose steps named a dead connection AND an unapproved template reported only the connection, and the model heard about the template on the *next* turn, out of a budget of six. Each field's checks are collected now (`actionFailures`/`conditionFailures`, and `groundSteps`' `reject`) and the field is dropped once with all of them. Two things stay true and are load-bearing: `dropped` may carry several entries for one field, and the field is still dropped exactly **once** — `actions`/`steps` carry one complete replacement value, so a partial application is never an option. Only two cases still stop early, and both are cases where nothing below is *knowable* rather than merely unchecked: the inventory failing to load, and the saved row being unreadable.

**On the create flow, conditions are grounded against the PROPOSED trigger.** "Set this up for when analysis is ready" is a trigger and a condition in one payload, and grounding the condition against whatever the empty builder happened to be showing meant the author got the trigger and lost the conditions. This is not the "grounding against its own invention" the general rule guards: `trigger_type` is a closed enum on the write tool's schema, already parsed, and it is refused outright on a saved automation before this runs.

**A proposal the author is offered must be a proposal that saves.** That is the whole reason bounds are duplicated, and it decides two per-surface trades:
- **Automation** — nothing is mirrored. `src/automations/schemas.ts` IS the authority (master's own feature), so `automation.validator.ts` imports `actionSchema` / `predicateSchema` / `triggerTypeSchema` and a bound tightened on the save path tightens here in the same commit. What it adds is grounding: `connection_id` against **active** connections whose `provider` equals the step's `channel` (core calls it `provider`; the builder's own picker filters on exactly that), `template_id` against approved WhatsApp templates, predicate `{{path}}`s against what the trigger actually publishes, plus predicate depth (`predicateSchema` alone does not check it — the save path's `superRefine` does), the immutable `trigger_type`, the `messaging.whatsapp_personal_groups` capability, and the credential rules below. One more that is easy to miss: a **WhatsApp template marked `needs_parameters`** is refused outright. `ACTION_SCHEMA` has no `template_components`, so a template needing a media header or `{{1}}`-style body values produces a step cusui's own `whatsappActionBlockReason` then refuses to save — the author accepts a card and has to delete it, which is precisely the failure the whole rule exists to prevent.
- **IVR** — `ivr-workflow.validator.ts` is the platform's **only** master-side IVR step schema, and it is deliberate. The passthrough stays byte-transparent (see `/proxy/ivr-workflows` above); this applies to proposals, where the alternative is the model's most confident output becoming a 400 at the moment the author clicks Apply. `CORE_IVR_VALIDATOR_SOURCES` names every file it mirrors and the smart-TTS trio is pinned by test, because those are the fields a mirror lost once before. `steps` gets **one verdict** rather than a per-field one: half a graph is a broken workflow, not a smaller one. Graph integrity mirrors core's `validateWorkflow`; `prompt_template_id` and `audio_file_id` are grounded; webhook `headers` follow the credential rules below.

**No credential ever leaves master for the model, and the first version of this depended on one doing so.** Both new surfaces' prompts told the author that a webhook's authentication is theirs to set and "you will never see it", while `get_automation_state` returned `row.actions` verbatim — signing `secret` and `headers` map included — and the IVR header rule was a `JSON.stringify` comparison against the stored value, which is *only implementable if the model can see it*. The snapshot made it worse than a single leak: it is re-sent as prefill on every turn, so one unredacted secret is `max_turns` copies at the provider. Three rules now, and the call script had all three from the start (`TOOL_ROW_FIELDS` allow-lists a `has_headers` **boolean**):

1. **Redact on the way out, on every path.** `redactActionCredentials` / `redactStepCredentials` replace `secret`/`headers` with `has_secret`/`has_headers` in the read tool AND in `pickAutomationSnapshot`/`pickWorkflowSnapshot` — the snapshot is a request body, so server-side is the only place the promise can be kept. The booleans are not decoration: they are what lets the model *anticipate* rule 3 instead of hitting it blind and re-proposing.
2. **Any credential key arriving in a proposal is invented, and is refused.** Not stripped — a webhook whose auth the model made up is a webhook whose auth is wrong, and dropping the key would offer it as if it were right.
3. **A proposal that would DESTROY a stored credential is refused.** `actions`/`steps` replace wholesale, so a stored credential survives only if the replacement still contains that step — for an automation keyed on `url` (its actions have no ids; the save path is a positional array), for IVR on `id` **and** `url`. Drop it or re-point it and accepting the card silently deletes a credential the author set, with nothing in the proposal mentioning it and no way back once saved. The same rule the call script applies to a header-bearing tool it may not delete, and the same remedy: the author does it in the builder. What replaces the old echo-it-back mechanism is the **browser** carrying the stored map forward — by `url` / by step `id` — so the value never has to leave the author's own tab.

`test/unit/autopilot/surfaces/credentials.test.ts` is one table over all three surfaces, asserting on the **serialized** form throughout: a tool result is JSON-encoded into the conversation, so "the secret is not in this object" has to mean "nowhere in the bytes", not "the top-level key I thought of is absent".

**`variables` and `max_duration_seconds` are readable but not proposable on IVR**, and the reason is the same rule: cusui's builder derives the first from its gather steps on every save and carries the second off the stored row, so either would be a card the author accepts and does not get. They stay in `IVR_SNAPSHOT_FIELDS` (the model must still describe the workflow accurately) and are absent from the write tool, so no turn is spent on them.

**The editor's snapshot is untrusted data.** It arrives client-supplied, is narrowed by the surface to the fields it owns (so a client cannot inflate the prompt or smuggle keys into it), size-capped, and fenced in the system prompt by a long delimiter rather than backticks — the content is arbitrary author text that routinely contains markdown fences of its own. Every surface's prompt says in as many words that imperative language inside the fence is material to edit, never an instruction.

**Every model-output lookup uses `Object.hasOwn`, never `in` or a bare index.** A plain object literal inherits from `Object.prototype`, so `READ_TOOLS['constructor']` resolves to `Object` — truthy, so an unknown-tool guard after a bare lookup never fires and `handler(ctx)` evaluates `Object(ctx)`, returning `ctx` ITSELF with the tenant's decrypted core API key in it, into a tool result and on to the model provider. The same guard appears at all four such lookups; the incident is written up at each.

**Routes:** `/proxy/prompts/autopilot/*`, `/proxy/automations/autopilot/*`, `/proxy/ivr-workflows/autopilot/*` — each two static segments, which is what lets them share a prefix with a sibling plugin owning `/:id` (Fastify prefers a static branch). Each requires its surface's **write** permission (AutoPilot exists to change the thing; a viewer cannot apply a proposal) and has its **own** rate-limit bucket, so a tenant hammering one editor cannot lock the author out of another.

## Key Patterns

- **Zod everywhere**: config validation (`src/config/schema.ts`), API request schemas (`src/api/validators/`)
- **Repository pattern**: singleton classes with `getPool().query()` in `src/db/repositories/`
- **Total ordering on every OFFSET-paginated list**: an `ORDER BY` that pages with `LIMIT/OFFSET` must end in the row's unique `id` (through `buildOrderByClause`/`stableOrderBy` in `src/utils/sort.ts`, or a literal `, id <dir>`). Rows of one multi-row INSERT or batched flush share `created_at` to the microsecond, and Postgres' top-N sort breaks ties differently per OFFSET with no writes at all — measured on the real schema, 7 of 11 master lists overlapped and skipped across pages before the tiebreak (`test/integration/repositories/paginated-list-order.test.ts`). **Enforced** by `test/unit/db/paginated-order-total.test.ts`, a TypeScript-parser source audit of every `.ts` under `src/` (ported from core's): any SQL literal whose `ORDER BY` governs an `OFFSET` — across lines, across concatenated or interpolated literals, inside a subquery — must end in `id`/`<alias>.id`, or be an interpolation built by `buildOrderByClause`/`stableOrderBy` (an `${orderBy}` from anything else fails); SQL comments are stripped quote-aware, so `-- , id` cannot pass. It has a site-count floor plus a list of known files so it cannot pass vacuously, and exactly one allow-list entry — `claimBatches`' capped frontier, an OFFSET that picks one row of one job and is total via `UNIQUE (job_id, batch_index)`; the entry holds only while `p.job_id = cj.job_id` is a top-level AND-conjunct of the WHERE of the same SELECT that carries the ORDER BY — not merely present in its text: inside a nested subquery or under an `OR` (`a AND b OR c` is `(a AND b) OR c`) it no longer pins the rows being ordered, and the audit fails closed on any WHERE it cannot read as a plain conjunction. What it does NOT check: `LIMIT n` with no OFFSET (single-shot claims, sweeps and keyset/cursor pages are not OFFSET-paginated), and SQL the parser cannot follow — a value imported from another module or returned by a function is opaque. An opaque ORDER BY *fails*; an opaque OFFSET (a `${pageClause}` from a helper) is *invisible*, so keep `LIMIT … OFFSET` in the same file's literals. `test/unit/db/repositories/paginated-list-order.test.ts` additionally pins the runtime ORDER BY of the 11 lists that existed when the rule landed.
- **No per-item loops over I/O**: anything that operates on a *set* — recipients in a batch, contacts in a chunk, workflows behind a set of bindings — gets a set-shaped repository/service method (`= ANY($1)`, multi-row `INSERT`, one Lua call), not an awaited loop. The batch methods that exist today: `reserveCreditsBatch`, `creditReservationRepository.bulkCreate`, `creditTransactionRepository.bulkCreate`, `redisCreditCache.reserveMany`, `scheduleContactRepository.{markDispatchedBulk,failPendingContacts,findPendingByPhones}`, `scheduleRepository.decrementPendingCount(id, n)`, `workflowRepository.{findByIds,findByIdsUnsafe}`. Prefer extending these over reintroducing a loop. Two consequences worth knowing before converting a loop: a multi-row `INSERT` is **atomic per chunk**, so it cannot half-succeed the way N independent writes could (usually the point — see the reservation ledger); and it has **no per-row failure isolation**, so where the old loop caught per-item errors, the set-shaped version fails the whole set and the handling has to move up a level (`batch-executor.ts`'s all-recipients-rejected path logs at error and leaves the contacts to the recovery sweep). The **unwind** paths are still per-item loops (`releaseCredits` + `markSettled` per hold at six call sites) — the remaining known gap.
- **Structured logging**: Pino with child loggers bound to `{component}`, OTel trace_id/span_id injection. The root logger's `base` stamps `service` and `version` (`APP_VERSION` from `src/utils/version.ts`) on every line, so all logs are tied to the running app version for tracing. `APP_VERSION` is the single source of truth, also used as the OTel `service.version`. Fastify's built-in request logging is **disabled unconditionally** (`disableRequestLogging: true`) — the `onRequest`/`onResponse` hooks in `src/index.ts` emit the same two events with strictly more detail (duration + the request metrics recording) and exempt `/health`, `/ready`, `/metrics`. Leaving it on outside dev, as the old `env === 'development'` check did, produced four log lines per request in production, two of them redundant.
- **One metrics pipeline**: each metric is one OpenTelemetry instrument (a gauge: one snapshot the pipeline reads), served locally on port 9091 (Prometheus text) and exported via OTLP when enabled — see *OpenTelemetry* above. Never record the same event on two instruments
- **Bounded metric labels**: a cumulative OpenTelemetry instrument keeps every label combination it has ever seen for the life of the process — and every one is a billable Grafana Cloud series — so **anything that reaches a label must have bounded cardinality** — enums, statuses, route templates. Never a resource id, an interpolated path, a URL, or free text. Interpolated proxy paths are templated by `src/utils/metric-path.ts` (see Proxy Layer); if you add a metric whose label values you cannot enumerate up front, bound it explicitly. Note the deliberate exception: `tenant_id` labels on the credit/schedule/webhook/contact-list/release counters, which are bounded by the tenant count rather than by an enum. **`account_id` is deliberately NOT a label anywhere** — it was dropped from `webhook_requests_total`, `credit_reservations_total`, `credit_settlements_total`, `schedule_executions_total`, `recurring_schedule_fires_total` and `contact_list_uploads_total`, because tenant × account multiplied every one of those by the account count for a breakdown no panel or alert read. A per-account question is answered from Postgres, which already holds it: `credit_transactions.account_id` (reservations, settlements, releases), `bulk_dispatch_jobs.account_id`, `schedules.account_id`, `contact_lists.account_id`. Do not add it back to a metric. Likewise a histogram carries no `status` (`api_request_duration_seconds{method,path}`; the status source is `api_requests_total{method,path,status}`) — each histogram label set costs one series per bucket.
- **Cardinality limits are explicit and differ by instrument kind** (`METRIC_CARDINALITY_LIMITS` in `src/utils/metrics-pipeline.ts`, applied to both readers by `withCardinalityLimits`; the pipeline has no views, so every SDK instrument — the kept runtime gauges included — takes the reader's selector, and the application gauges, which are not SDK instruments, are capped by `withSnapshotGauges`). Past the limit the SDK folds new attribute sets into one `otel.metric.overflow=true` series (`otel_metric_overflow="true"` in Grafana — alert `plat-metric-cardinality-overflow` in the superproject's `grafana/terraform/alert-rules-platform.tf`, whose `mm-metric-cardinality-overflow` here is the file-provisioned reference copy; dashboard panel 192); those points lose their labels, so label-filtered panels and alerts on that metric under-report. What the limit counts was **measured against sdk-metrics 2.6, and it is not what "per-instrument limit" suggests**: for a **counter or histogram** it is the NEW attribute sets recorded within **one collection cycle** (60s for OTLP) — the cap sits on the per-cycle delta map and the cumulative merge after it has none — so `perCollection` (5000) is a *burst* guard, and a label leaking an id at a steady rate below it grows the series count forever **without ever overflowing** (watch series counts for that, not the overflow alert). For an **SDK observable gauge** (only the three runtime gauges now) it is the distinct sets observed over the **process lifetime** — `batchCumulate`'s memo is never pruned — so once `lifetime` (20000) is spent every new set is exported as overflow until restart; harmless for fixed runtime sets, and one reason application gauges are not SDK observables. An **application `Gauge`** is capped by the pipeline itself at `gaugeSnapshot` (20000) sets per collection, counting its CURRENT snapshot (so a `reset()` frees slots), sized for the tenant-keyed gauges (`credit_balance_current` never drops a tenant); past it, the rest fold into one `otel.metric.overflow=true` point carrying the value of the last excess set in the snapshot's insertion order (one arbitrary set's value, not a total — only its presence means anything), and that point stops being exported once the snapshot shrinks back under the cap. Neither reader's constructor forwards a `cardinalitySelector`, so it is set on the instance. The two readers' windows differ for counters/histograms — the local reader's "cycle" is since the last `/metrics` render, i.e. the whole process lifetime when unscraped — so the local endpoint can show overflow Grafana does not; collecting it on a timer to align them was rejected because every collection runs every observable callback and the runtime collectors reset their state there (a second collector would shorten the p99/utilisation window Grafana receives). Pinned in `test/unit/utils/metrics-pipeline.test.ts` ("cardinality limits"). An overflow is answered by bounding the label, not by raising the limit.
- **Graceful shutdown**: flush audit buffer, drain the lane scheduler, close DB/Redis connections, then — last, bounded, never throwing — flush OTel spans, logs and metrics (`shutdownTelemetry`, see *OpenTelemetry*)
- **ESM bootstrap**: `src/bootstrap.ts` is the true entry point — it imports `instrumentation.ts` (OTel SDK) first, then dynamically `import('./index.js')` so auto-instrumentation hooks register before any library loads. Do not add static imports to `bootstrap.ts`.
- **.js extensions**: all imports use `.js` extension (Node16 ESM resolution)
- **vi.hoisted()**: required for vitest mocking with ESM
- **Retry with backoff**: `src/utils/retry.ts` provides exponential backoff for external calls
- **AES-256-GCM encryption**: `src/utils/crypto.ts` for core API key storage/retrieval

- Strict mode with `noUncheckedIndexedAccess`

- **The unit suite must not need a `.env`.** `src/config/index.ts` validates with Zod at module load and `process.exit(1)`s on failure, and it is imported *transitively* by a lot of source — so a test file that never mentions config still boots it. `vitest.config.ts` therefore loads `test/setup/unit-config-env.ts`, which supplies obviously-fake placeholders for every required setting that has no schema default (`DATABASE_URL`, `REDIS_URL`, `FIREBASE_PROJECT_ID`, `CORE_SERVICE_URL`, `CORE_S2S_TOKEN`, `ENCRYPTION_KEY`, `CORE_WEBHOOK_SECRET`). Keep that list minimal; add to it only when a *required* setting has no default, never to paper over a config bug. Any test that cares about a specific config value mocks `src/config/index.js`.

**The integration suite needs the same thing, and went without it.** `vitest.config.integration.ts` had no `setupFiles` at all, so `test/setup/integration-config-env.ts` is its counterpart — same required set, but `DATABASE_URL`/`REDIS_URL` point at the real 5434/6381 stack, because here a connection is the *point* rather than something to make fail fast. The lesson it was found through is narrower and worse than "add a setup file": **a test can mock every config-touching import it can SEE and still boot the real config.** `test/integration/api/user.routes.test.ts` mocks `db/connection`, both middlewares, RBAC, `redis-cache` and the logger — and both `POST /invite` creation cases still 500'd on `main`, because `invite-mailer.ts` reads config through a lazy `import('../config/index.js')` **inside a function**, which is invisible to the `vi.mock` list at the top of a test file. The diagnostic was a bare `expected 500 to be 201` with the real cause only in stderr. When a new required setting lands it needs a line in **both** shims; there is deliberately no shared base, because the db/redis values are meant to differ and a base taking overrides would hide exactly that.

Note what the shim must not be allowed to hide: `POST /users/invite` also had a genuine bug on that path — `inviteSignInUrl` sat outside the `try` that exists so the mail work can never fail the invite, so a config failure turned a **written membership** into a 500. The supervisor is told the invite failed, retries, and gets a 409 from the row the "failed" attempt created. Production has no shim and `CUSUI_BASE_URL` is genuinely optional, so that guarantee is asserted directly in `test/unit/api/routes/user-invite-mailer-isolation.test.ts` by making the call reject.

## Versioning & Releases

Versioning is automated with [semantic-release](https://github.com/semantic-release/semantic-release). The `.github/workflows/release.yml` workflow runs on every push to `main` (i.e. each PR merge) and derives the next version from the Conventional Commit messages merged since the last release tag.

**Bump rules** (`.releaserc.json`, Conventional Commits preset):
- `feat:` → **minor** (0.1.0 → 0.2.0)
- `fix:`, `perf:`, `refactor:`, `revert:` → **patch** (0.1.0 → 0.1.1)
- `feat!:` / `fix!:` / a `BREAKING CHANGE:` footer → **major** (0.1.0 → 1.0.0)
- `docs:`, `style:`, `test:`, `build:`, `ci:`, `chore:` → **no release**

Because PRs are **squash-merged**, the PR title becomes the commit on `main` and is the signal semantic-release reads — so PR titles must follow Conventional Commits (they already do, e.g. `feat(automations): ...`).

**On each qualifying merge**, semantic-release:
1. Bumps `version` in `package.json` (no npm publish — package is `private`)
2. Updates `CHANGELOG.md` (grouped by Features / Bug Fixes / etc.)
3. Commits both with `chore(release): <version> [skip ci]` and creates an annotated `v<version>` git tag
4. Publishes a GitHub Release with auto-generated notes

The release commit is skipped by the release workflow itself (the `if:` guard) and the `ci.yml` workflow only triggers on `pull_request`, so there is no loop. The runtime reads its version from `npm_package_version` (`src/instrumentation.ts`).

**Caveat:** the version-bump commit is pushed back to `main` by `@semantic-release/git` using the default `GITHUB_TOKEN`. If `main` has branch protection that blocks direct pushes, either allow the GitHub Actions bot to bypass it or drop `@semantic-release/git` from `.releaserc.json` (the tag + GitHub Release will still be created; only the in-repo `package.json`/`CHANGELOG.md` commit is skipped).

To preview what would be released without publishing: `GITHUB_TOKEN=<token> npx semantic-release --dry-run`.
